# 第45章 分布式一致性与共识协议

第44章把 Agent 交给运维，本章回到分布式系统最深的底层："多个节点如何对一个值达成唯一决定"。朴素主备切换在网络分区下必然脑裂，过半投票是唯一的解药；Raft 把共识拆成选主、日志复制、安全三个可理解的问题，ZK 与 etcd 把它做成了生产服务；CAP 与一致性谱系告诉我们"哪些接口值得付强一致的代价"；租约与 fencing token 守住分布式锁的最后一道防线。本章按「为什么需要共识 → CAP 与一致性谱系 → Raft 选举 → 日志复制与安全 → ZooKeeper → etcd → 分布式时钟 → 租约与 fencing → Quorum 仲裁 → 共识的工程代价 → 配置中心案例」的顺序讲。所有示例仍是纯 JDK：朴素主备的脑裂现场真实推演，Raft 选举投票约束真跑，日志冲突修复与 MVCC 版本回放真实执行，fencing token 真实拦截过期写入，不需要 ZooKeeper 或 etcd 集群。

### 45-01 为什么需要共识

**知识点**
- **复制的根本分歧问题是"谁说了算"**：三副本集群收到写请求时，如果两个副本各自认为自己是主，同一个键就会被写两次不同的值。**共识（consensus）就是让多个节点对"一个值"达成唯一决定**——它是复制、选主、分布式锁、配置中心的共同底座。
- **故障模型决定协议难度**：崩溃故障（节点停了就不再回来作恶）与拜占庭故障（节点可能撒谎）是两个世界。**数据中心内部只需要处理崩溃故障**——Raft/Paxos 的适用域；区块链处理拜占庭。选协议先问"我要防什么样的坏节点"。
- **分布式系统的敌人是异步网络**：消息可以丢失、延迟、乱序，节点时钟不可信，你无法区分"节点挂了"和"网络很慢"。**共识协议的全部复杂性都来自这个不确定性**——单机程序没有这个问题。
- **安全性与活性的取舍**：安全性（决不返回两个不同的值）是底线，任何网络分区下都不能违反；活性（最终能做出决定）在分区时可能暂停。**Raft 选择"分区时少数派停服，多数派继续"**——宁可不服务，不给错误答案。
- **共识在 Java 系统里的身影**：ZooKeeper/etcd（配置与协调）、Redis Cluster/ES master 选举（41/38 章的选主）、Kafka Controller、K8s 的 etcd 底座——**你已经天天在用共识，只是被封装了**。本章把它拆开看。
- **不要自己实现共识**："看起来简单的协议"（两阶段提交+超时切换）在分区下几乎必然产生脑裂。**正确姿势是用经过验证的库**（etcd/raft 库、ZooKeeper），自己写只存在于学习场景。
- 易错点：把"过半数确认"理解成"过半机器在线就行"（是过半的**投票**，不是机器活着）；在少数派分区里继续写（脑裂）；用共享存储当共识（存储挂了就没有共识）；以为 Raft 保证"所有请求都成功"（少数派请求会失败，客户端要重试到新主）。

### 45-02 CAP 与一致性谱系

**知识点**
- **CAP 的准确读法**：网络分区（P）发生时，**一致性（C）与可用性（A）只能二选一**——这不是"三选二"的选择题，而是"分区时你选哪边"的承诺。无分区时 C 和 A 可以兼得。**CAP 是分区预案的设计约束，不是架构选型的口号**。
- **一致性是一个谱系而非开关**：**线性一致**（读到的值与所有进程的操作顺序一致，像单机）> **顺序一致**（同客户端有序，跨客户端可乱）> **因果一致**（有因果关系的操作有序）> **最终一致**（停止写入后收敛）。**不同接口可以承诺不同级别**——同一系统里"配置读取"线性一致、"计数"最终一致很常见。
- **线性一致的代价**：每次读都要与多数派交互（或读主），延迟 = 一次 RTT 往上，吞吐受限。**只对真正需要的接口承诺线性一致**（选主、锁、配置变更确认），其余用本地读。
- **最终一致的业务后果要先想清楚**：余额查询最终一致 = 用户刚充 100 元查不到（客诉）；库存扣减最终一致 = 超卖。**"读自己的写"（read-your-writes）是最常见的最低要求**：用户提交后必须看到自己刚写的数据（39-04 sticky routing 的理论根基）。
- **BASE 与 ACID 的适用边界**：跨服务的业务流程用 BASE（最终一致 + 补偿，39-09 的本地消息表），单库事务仍用 ACID。**"放弃强一致"不是放弃正确性**，而是把正确性从"数据库保证"变成"架构保证"（幂等、对账、补偿）。
- **PACELC 补充了无分区时的取舍**：分区时选 C 或 A；**无分区时选延迟（L）或一致性（C）**——线性一致每次多一次 RTT，这就是"为什么默认读本地副本"的理论解释。
- 易错点：把 CAP 当"三选二"选型表（P 是必选项不是选项）；以为最终一致 = 数据可以随便错（收敛性与收敛时间是有契约的）；所有接口都上线性一致（延迟与吞吐双输）；把"读写主库"当成唯一解（读自己的写只需要会话粘性）。

### 45-03 Raft 领导者选举

**知识点**
- **Raft 把共识拆成三个可理解的问题**：**选主**（谁当 leader）、**日志复制**（leader 怎么让全员对操作顺序达成一致）、**安全**（新 leader 不能丢已提交的数据）。每个问题独立可测——这是 Raft 相比 Paxos 的最大工程价值。
- **三种角色与任期（term）**：Follower / Candidate / Leader。逻辑时钟是**任期号**（单调递增），一轮选举 = 一个任期。**任期的单调性是全局顺序的基石**：旧任期的消息一律拒绝——它替代了不可信的物理时钟（45-07 的伏笔）。
- **选举流程**：Follower 超时没听到 Leader 心跳 -> 自增任期、转 Candidate、给自己投票、向所有节点拉票 -> **获过半选票**则当选，立刻广播心跳确立权威 -> 未过半则等待随机超时后新一轮。**随机化选举超时**（150~300ms 抖动）避免两个节点同时发起导致选票分裂。
- **投票的安全约束**：每个节点**一个任期只投一票**（先到先得）；**只投给日志不落后于自己的候选者**（比较最后一条日志的 term+index）——这两条保证"当选者拥有全部已提交日志"。
- **脑裂不可能产生两个主**：过半票只有一个（3 节点需 2 票），两个 Candidate 都拿不到 2 票时谁也不当选，等下一轮。**45-01 的朴素方案缺的正是这个全局约束**。
- **选举风暴与心跳**：Leader 每隔心跳间隔（如 100ms）广播心跳抑制选举；网络抖动导致的频繁换届要监控（换届率是集群健康信号，42 章方法论）。
- 易错点：选举超时不随机（两节点同刻拉票死循环）；任期号用了物理时间（时钟回拨毁掉顺序，39-07/45-07 同款问题）；少数派分区里不断重试选举刷任期号（应静默等待恢复）；投完票还接受旧 term 的消息（安全漏洞）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Random;

public class RaftElection {
    enum Role {
        FOLLOWER, CANDIDATE, LEADER
    }

    /** 单节点状态：任期、投票、角色 */
    static class RaftNode {
        final String name;
        Role role = Role.FOLLOWER;
        int term = 0;
        Integer votedFor = null;       // 本任期投给谁（null 未投）
        int logLastTerm = 0;           // 本地最后一条日志的任期（安全比较用）

        RaftNode(String name, int logLastTerm) {
            this.name = name;
            this.logLastTerm = logLastTerm;
        }

        boolean canVoteFor(int candidateLogTerm) {
            // 只投给“日志不落后于我”的候选者（简化：只比 term）
            return votedFor == null && candidateLogTerm >= logLastTerm;
        }
    }

    static void electionRound() {
        System.out.println("【一轮选举：3 节点，n2 先超时】");
        List<RaftNode> cluster = List.of(
                new RaftNode("n1", 3), new RaftNode("n2", 4), new RaftNode("n3", 4));
        RaftNode n2 = cluster.get(1);
        n2.role = Role.CANDIDATE;
        n2.term = 5;
        n2.votedFor = 2;                       // 自己投自己（节点编号示意）
        Map<Integer, Integer> votes = new LinkedHashMap<>();
        votes.put(2, 1);
        System.out.println("  n2 超时 -> term=5 转 Candidate，投自己");
        for (RaftNode n : cluster) {
            if (n != n2) {
                boolean grant = n.canVoteFor(n2.logLastTerm);
                if (grant) {
                    n.term = 5;
                    n.votedFor = 2;
                }
                votes.put(cluster.indexOf(n), grant ? 1 : 0);
                System.out.printf("  n2 -> %s 拉票(term=5, logTerm=%d) -> %s%n",
                        n.name, n2.logLastTerm, grant ? "同意（votedFor=2）" : "拒绝（日志落后/已投）");
            }
        }
        int total = votes.values().stream().mapToInt(Integer::intValue).sum();
        boolean won = total >= 2;
        System.out.printf("  得票 %d/2 -> %s%n", total, won ? "n2 当选 LEADER（term=5），广播心跳" : "选举失败，随机超时后重选");
        System.out.println();
    }

    static void splitVote() {
        System.out.println("【选票分裂与随机超时的化解】");
        System.out.println("  n1、n3 同刻发起选举（term=6），各拿 1 票（自己 + 互投失败）");
        System.out.println("  双方都未过半 -> 各自等待随机超时（150~300ms 抖动）");
        int n1Delay = 180, n3Delay = 260;
        System.out.printf("  n1 先超时（%dms）-> term=7 重新拉票 -> 获得 2 票当选%n", n1Delay);
        System.out.printf("  n3 晚 %dms 收到 n1 心跳 -> 退回 Follower%n", n3Delay - n1Delay);
        System.out.println("  随机化让“同时发起”大概率自然化解——分布式去重的经典手法");
        System.out.println();
    }

    static void partitionBehavior() {
        System.out.println("【分区行为：旧主与新主】");
        System.out.println("  集群 {n1(旧leader,term=4), n2, n3}，n1 与 n2/n3 分区");
        List<String> lines = List.of(
                "n2/n3 侧：选举出新 leader（term=5），继续接收写入",
```

### 45-04 Raft 日志复制与安全

**知识点**
- **一切操作都先变成日志**：客户端请求到达 Leader -> 追加为日志条目（term+index）-> 并行复制给 Follower -> **过半节点落盘** -> Leader 提交并应用 -> 通知客户端成功 -> Follower 跟随提交。**日志就是全集群的唯一操作顺序**，状态机按序回放日志得到一致状态。
- **提交规则是安全的核心**：只有**当前任期**的条目被过半复制才能直接提交；提交当前条目会**间接提交**之前所有已复制条目（Raft 安全性论文的经典补丁——旧任期条目不能靠计数直接提交，否则已提交数据可能被覆盖）。
- **日志匹配性质**：两节点日志在相同 index 上 term 相同，则该位置之前的所有日志完全相同（归纳保证）。AppendEntries 自带一致性检查：Follower 缺失/冲突时 Leader 回退 nextIndex 重发，**冲突的 Follower 条目被 Leader 覆盖**。
- **新 Leader 的安全保证**：当选者日志不落后于任何过半节点（45-03 投票约束）=> **已提交的条目必然在新 Leader 日志里**——这就是"提交过的数据永不丢"的推导链。
- **读请求的处理**：写走日志，读也要保证线性一致时不能只读本地——**ReadIndex**（leader 确认自己在当前 term 内仍是 leader：与多数派交换一次心跳）或 **Lease Read**（租约期内信任本地，45-08）。**"读不走日志所以没有一致性问题"是常见误解**。
- **性能工程**：日志条目合并（batch）、流水线化（不等上一条确认就发下一条）、follower 读（ReadIndex 下放）、快照压缩日志（快照点之前的日志可丢弃）。**etcd 的实践：写 QPS 上千就很可观**——共识不便宜，能不用就不用（缓存、无状态计算不进共识）。
- 易错点：commit 后才回复客户端（应过半落盘即可回复，apply 异步）；忽略"旧任期提交规则补丁"（自己实现时最易犯的安全 bug）；Follower 冲突日志直接追加不回退（日志分叉）；把大 value 塞进日志（建议日志只存命令引用，数据走外部存储）。

### 45-05 ZooKeeper 与 ZAB

**知识点**
- **ZooKeeper 的定位是"协调服务"而不是"数据库"**：它提供分层命名空间（znode 树）、 watches（变更通知）、临时节点（会话绑定的存活性信号）、顺序节点（全局递增编号）——**用这四样积木拼出选主、分布式锁、配置订阅、队列**。存数据是次要能力（单 znode 默认 1MB 上限）。
- **ZAB 协议 = Raft 的近亲**：同样是过半投票选主 + 日志复制（ZAB 叫"崩溃恢复与消息广播"两阶段）。理解了 Raft（45-03/04）就理解了 ZK 的可用性边界：**3~5 节点、写走 leader、过半确认**。
- **临时节点是"存活性"的原语**：客户端 session 断开（心跳超时）时其临时节点自动删除——**选主的经典实现**：所有候选者创建 `/master` 临时节点，创建成功者为主，其余 watch 该节点，节点消失即触发重新竞选。**它比心跳探测可靠**：session 失效由 ZK 集群裁决（共识），不是客户端自己的观察（45-01 脑裂的反例）。
- **顺序节点是"公平锁与队列"的原语**：`/lock/lock-0000012` 全局递增，拿最小编号者持锁、其余 watch 前一个编号——避免惊群，保证公平。**这是分布式锁的标准姿势**（45-08 的 Redis 方案对比）。
- **Watch 是一次性触发**：收到通知后要重新注册（或用 Curator 缓存封装），**watch 通知不保证送达内容**，只保证"有变化"——读取最新值必须重查。
- **ZK 的运维红线**：写吞吐低（全集群过半确认，每秒几千写已是极限）；session 超时调太短（GC 停顿就掉 session -> 临时节点消失 -> 选主抖动，29 章 Nacos 为什么最终不用 ZK 做注册中心的原因之一）；**不要把 ZK 当消息队列或大数据存储用**。
- 易错点：用非临时节点做选主（进程挂了节点还在，双主）；watch 只注册一次（丢后续变更）；把大数据量塞 znode（写放大拖垮集群）；session 超时与业务 GC 停顿不匹配（频繁重连风暴）。

### 45-06 etcd 与线性一致读

**知识点**
- **etcd 是 K8s 的元数据底座，也是 Raft 的参考实现**：与 ZK 定位相似（协调服务），但协议更现代（Raft）、支持 MVCC 多版本与事务（mini-transactions：if-then-else）、**gRPC 端到端**。K8s 的一切对象都存 etcd——它挂了 K8s 只读不写。
- **MVCC 是 etcd 的重要设计**：每次写产生全局递增 revision，键值对保留历史版本——**watch 按 revision 流式消费不漏事件**（对比 ZK watch 的一次性触发），**compact 修剪旧版本**（不压缩历史会无限膨胀）。
- **串行读 vs 线性一致读**：串行读（默认）只读本地状态——**便宜但可能读到旧主数据**（分区中旧 leader 的内存状态）；线性一致读走 ReadIndex：leader 向多数派确认自己权威再读（45-04）。**K8s 用 quorum 读保关键路径，监控用串行读省代价**——分级一致性的实践样本（45-02）。
- **lease 是 etcd 的活性原语**：客户端申请带 TTL 的 lease，key attach 到 lease，续约失败过期则 key 自动删除——**与 ZK 临时节点同构的选主/存活性方案**。
- **事务（txn）让"检查并写入"原子化**：`if value(k)==A then put(k,B) else put(k,C)`——**分布式锁、防并发写、leader 切换保护的实现基座**。没有 txn 时这些要靠外部锁。
- **运维视角**：etcd 对磁盘延迟极敏感（fsync 是写路径关键段，磁盘 >10ms 延迟会导致心跳超时换届）——**专用 SSD + 隔离部署**是 K8s 生产铁律；compact 与 defrag 要排期。
- 易错点：把 etcd 当通用数据库存业务数据（K8s 元数据专用定位）；不配 compact（revision 无限增长拖垮查询）；串行读用于选主结果判断（读到旧主）；lease TTL 太短（抖动即 key 删除，业务雪崩）。

### 45-07 分布式时钟与顺序

**知识点**
- **分布式系统的顺序不能靠物理时钟**：两台机器的时钟各有漂移（ppm 级），NTP 校准有毫秒级误差且可能回拨——**用时间戳排序事件 = 依赖一个不可靠的全局参照**（43-02 事件时间的教训在元数据层的同款）。
- **时钟回拨的破坏力**：39-07 雪花 ID 拒绝回拨保 ID 唯一；45-03 任期号绝不用时钟保顺序；43-02 服务端打点但容忍乱序——**共识系统直接放弃物理时钟做顺序**。
- **逻辑时钟（Lamport Clock）**：每个事件带 (counter, nodeId)，事件发生 counter++，收到消息 counter=max(local, remote)+1——**保证因果序**：a -> b 则 a 的时钟 < b 的时钟。但它不能区分"并发"与"先后"（时钟相等无法判定谁是因）。
- **向量时钟（Vector Clock）**：每个节点维护全量计数向量，比较向量可判定**因果先后或并发**——Dynamo 类系统用它检测冲突（两个并发写 -> 冲突交给业务合并）。代价：向量长度 = 节点数，扩展性受限。
- **混合时钟（HLC/Hybrid Logical Clock）**：物理时间戳 + 逻辑计数组合——保因果序又接近物理时间（对分桶/限流友好）。CockroachDB/Yugabyte 的选择，也是 43 章窗口聚合与共识世界的桥。
- **外部一致性的真解是原子钟/TrueTime**：Spanner 用 GPS+原子钟给出有界误差的时间（±几 ms），等待误差过去再提交——**用硬件砸出全局顺序**，普通公司不复制，但知道天花板在哪。
- 易错点：用 `System.currentTimeMillis` 排序分布式事件（漂移+回拨双重坑）；把 NTP 精度想成毫秒级（公网 NTP 可能几十 ms 且依赖网络）；逻辑时钟当物理时间用（不能做分桶/限流）；冲突检测缺失直接 last-write-wins（丢数据）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class DistributedClocks {
    /** Lamport 逻辑时钟：counter + nodeId */
    static class Lamport {
        long counter = 0;
        final String node;

        Lamport(String node) {
            this.node = node;
        }

        long localEvent() {
            return ++counter;
        }

        long onReceive(long remote) {
            counter = Math.max(counter, remote) + 1;
            return counter;
        }

        String stamp() {
            return "(" + counter + "," + node + ")";
        }
    }

    static void lamportDemo() {
        System.out.println("【Lamport 时钟：跨节点保持因果序】");
        Lamport a = new Lamport("A"), b = new Lamport("B");
        long e1 = a.localEvent();                       // A 本地事件
        long e2 = a.localEvent();
        long sent = e2;                                  // A 发消息
        long e3 = b.onReceive(sent);                     // B 收到消息
        long e4 = b.localEvent();
        System.out.printf("  A: 本地事件 %s -> %s%n", e1, e2);
        System.out.printf("  A 发送消息(携带 %d) -> B 收到 -> %s -> 本地 %s%n", sent, e3, e4);
        System.out.println("  因果链 A.e2 -> B.e3：时钟 2 < 4，因果可判");
        System.out.println("  局限：A.e1(1) 与 B.e3(3) 无因果但时钟可比 —— 并发无法识别");
        System.out.println();
    }

    static void vectorClock() {
        System.out.println("【向量时钟：判别并发写冲突】");
        record VC(Map<String, Long> v) {
            boolean before(VC o) {
                boolean allLE = true, someLT = false;
                for (Map.Entry<String, Long> e : v.entrySet()) {
                    long other = o.v().getOrDefault(e.getKey(), 0L);
                    if (e.getValue() > other) {
                        allLE = false;
                    }
                    if (e.getValue() < other) {
                        someLT = true;
                    }
                }
                return allLE && someLT;
            }

            boolean concurrent(VC o) {
                return !before(o) && !o.before(this);
            }
        }
        Map<String, Long> a1 = new LinkedHashMap<>();
        a1.put("A", 2L);
        a1.put("B", 1L);
        Map<String, Long> b1 = new LinkedHashMap<>();
        b1.put("A", 1L);
        b1.put("B", 2L);
        VC va = new VC(a1), vb = new VC(b1);
        System.out.println("  客户端A 写入版本 " + a1);
        System.out.println("  客户端B 写入版本 " + b1 + "（基于同一旧版本，未见过 A 的写）");
        System.out.printf("  判定：%s%n", va.concurrent(vb) ? "并发 -> 冲突！需合并或业务裁决" : "有因果 -> 取较新者");
        System.out.println("  对照 last-write-wins：按墙钟比较会静默丢掉一方写入");
        System.out.println();
    }

    static void hybridClock() {
        System.out.println("【混合时钟：物理 + 逻辑的折衷】");
        long wallMs = 1763350000000L;
        long logical = 3;
        System.out.printf("  HLC = 物理部分 %d + 逻辑部分 %d%n", wallMs, logical);
        List<String> benefits = List.of(
                "保留物理时间语义：可做时间窗口分桶（43-03 兼容）",
                "同毫秒内用逻辑位排序：解决毫秒内并发",
                "时钟漂移被物理位吸收，回拨只影响逻辑位");
        for (String b : benefits) {
            System.out.println("  - " + b);
        }
        System.out.println("  CockroachDB/Yugabyte 的选择：对外像物理时间，内部保证因果");
    }

    public static void main(String[] args) {
        lamportDemo();
        vectorClock();
        hybridClock();
    }
}
```

### 45-08 租约与分布式锁

**知识点**
- **锁的本质问题是在不可靠网络上的互斥**：持锁者崩溃但锁还在它名下（其他人永远拿不到）——**租约（lease）解法：锁带 TTL，到期自动失效**。TTL 之内持锁者可用，之外系统自动回收。
- **租约的时钟依赖**：TTL 的计时在服务端（共识系统裁决，可靠）；**客户端基于"剩余租约时间"做的乐观假设依赖本地时钟有界偏移**（Lease Read 的理论基础）。时钟漂移大时要么缩短租约要么放弃乐观。
- **Fencing Token 是防脑裂的最后防线**：锁服务每次发放锁都带**单调递增编号**；下游存储只接受编号更大的请求——即使旧持锁者（GC 停顿后醒来）还以为自己在持锁，它的旧编号请求会被拒绝。**没有 fencing 的分布式锁在高 GC 场景必然出事**。
- **GC 停顿的经典事故链**：A 拿锁 -> A 进入 GC 停顿 10s -> 租约过期锁转给 B -> B 修改数据 -> A 醒来以为自己持锁继续写 -> 覆盖 B。**每一步都"合理"，结局是数据错乱**——fencing 编号让 A 的写入被拒。
- **ZK 锁 vs Redis 锁的取舍**：ZK（45-05）自带公平性、存活性、 fencing 语义（顺序节点编号）——但每次加锁走共识，延迟与吞吐受限；Redis 锁（SETNX+TTL）快但**单实例锁在主从切换时会丢**（RedLock 的争议），需要 fencing 兜底。**结论：性能敏感 + 能容忍偶发失效 -> Redis 锁 + fencing；正确性敏感 -> ZK/etcd 锁**。
- **能不用分布式锁就不用**：很多"用锁"的场景其实是"防重复执行"——幂等键（39-09）、数据库唯一约束、乐观版本号往往更简单可靠。**锁是协调成本最高的同步原语，最后才考虑**。
- 易错点：锁不设 TTL（持锁者崩溃死锁）；锁续约失败还继续执行（应先检查租约有效性）；无 fencing（旧持锁者污染新持锁者的数据）；把锁当业务互斥的万能药（幂等能解决的不用锁）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class LeaseFencing {
    /** 锁授权：租约到期时间 + 单调递增 fencing 编号 */
    record LockGrant(String owner, long expiresAt, int fencingToken) {
    }

    /** 锁服务：租约 + fencing token */
    static class LockService {
        static int tokenSeq = 0;
        final Map<String, LockGrant> held = new LinkedHashMap<>();

        LockGrant acquire(String key, String owner, long ttlMs, long now) {
            LockGrant cur = held.get(key);
            if (cur != null && cur.expiresAt() > now) {
                return null;                     // 仍被持有
            }
            LockGrant g = new LockGrant(owner, now + ttlMs, ++tokenSeq);
            held.put(key, g);
            System.out.printf("  %s 获得锁 %s，fencing=%d，TTL=%dms%n",
                    owner, key, g.fencingToken(), ttlMs);
            return g;
        }
    }

    /** 下游存储：只接受更大 fencing 编号 */
    static class FencedStore {
        int maxToken = 0;

        boolean write(int token, String value) {
            if (token <= maxToken) {
                System.out.printf("  拒绝写入 fencing=%d（当前最大 %d）—— 旧持锁者的过期写入%n",
                        token, maxToken);
                return false;
            }
            maxToken = token;
            System.out.printf("  接受写入 fencing=%d value=%s%n", token, value);
            return true;
        }
    }

    static void gcIncident() {
        System.out.println("【GC 停顿事故链：无 fencing 的悲剧】");
        LockService svc = new LockService();
        FencedStore store = new FencedStore();
        long now = 0;
        LockGrant a = svc.acquire("order-lock", "A", 5000, now);
        System.out.println("  A 拿锁进入业务 -> GC 停顿 8 秒...");
        now = 8000;
        LockGrant b = svc.acquire("order-lock", "B", 5000, now);   // A 租约已过期
        store.write(b.fencingToken(), "B 修改: 库存=18");
        System.out.println("  A 醒来，以为自己还持锁：");
        store.write(a.fencingToken(), "A 修改: 库存=25");
        System.out.println("  无 fencing：A 覆盖了 B —— 数据错乱");
        System.out.println("  有 fencing：A 的旧编号写入被拒绝（上面已演示拒绝路径）");
        System.out.println();
    }

    static void fencingDemo() {
        System.out.println("【fencing 生效现场】");
        FencedStore store = new FencedStore();
        store.write(5, "B 的写入");
        store.write(3, "旧持锁者 A 的迟到写入");
        store.write(6, "C 的合法写入");
        System.out.println("  编号单调 + 下游拒绝旧编号 = 过期者无法破坏现状");
        System.out.println();
    }

    static void alternatives() {
        System.out.println("【先问能不能不用锁】");
        String[][] rows = {
                {"防重复执行", "幂等键 + 唯一约束（39-09）", "无锁，天然可靠"},
                {"防并发覆盖", "乐观版本号 CAS（32 章）", "无锁，冲突重试"},
                {"资源配额互斥", "数据库原子 UPDATE ... WHERE 剩余>0", "无锁，行锁内部化"},
                {"真全局互斥（极少数）", "ZK/etcd 锁 + fencing", "有锁，走共识"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-12s %-32s %s%n", r[0], r[1], r[2]);
        }
        System.out.println("  口诀：幂等 > 版本号 > 数据库约束 > 分布式锁");
    }

    public static void main(String[] args) {
        gcIncident();
        fencingDemo();
        alternatives();
    }
}
```

### 45-09 Quorum 读写与仲裁

**知识点**
- **Quorum（仲裁）是不走共识协议时保证一致性的简化机制**：N 副本，写入需 W 个确认，读取需 R 个确认，**W + R > N 保证读写集合必有交集**——读到至少一个最新副本。Dynamo/Cassandra 族的核心参数。
- **参数的物理含义**：N=3, W=2, R=2（标准配置）——容忍 1 副本故障仍可读写，读写各付一次多数派代价；W=1, R=3（写快读慢，有脏读窗口）；W=3, R=1（读快写慢）。**调节 W/R = 调节延迟与一致性曲线**（45-02 PACELC 的直接应用）。
- **Quorum 不等于线性一致**：W+R>N 只保证"读到至少一份最新数据"，**如果读到的恰好是旧副本**（交集里有最新也有旧），仍可能返回旧值——Dynamo 用向量时钟（45-07）+ 读修复解决：全部副本读回、比较版本、取最新并写回落后副本。
- **读修复与反熵**：读时发现副本版本不一致 -> 立即修复（read repair）；后台周期性同步（anti-entropy/merkle tree）。**最终一致的收敛机制**——"会收敛"不是靠等待，是靠这两个主动机制。
- ** sloppy quorum 与降级**：指定副本不可达时允许"附近的"副本代替（Dynamo 的 sloppy quorum）——提高分区时可用性，代价是一致性窗口扩大。**是否开启是业务决策**。
- **与共识的关系**：共识（Raft）= quorum + leader + 日志顺序 + 安全约束，是"管理型的过半"；纯 quorum 系统无 leader、允许并发冲突（交给向量时钟）。**需要严格顺序选共识，容忍冲突合并选 quorum**。
- 易错点：把 R+W>N 当线性一致（还要版本比较与修复）；只调大 N 不调 W/R（副本多但读写都是 1，一致性没变）；读修复缺失（最终一致永不收敛）；Sloppy quorum 默认开（一致性窗口悄悄变大）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class QuorumReplication {
    /** 副本：key -> 带版本号的值 */
    record Versioned(String value, long version) {
    }

    static Map<String, Versioned> r1 = new LinkedHashMap<>();
    static Map<String, Versioned> r2 = new LinkedHashMap<>();
    static Map<String, Versioned> r3 = new LinkedHashMap<>();
    static List<Map<String, Versioned>> replicas = List.of(r1, r2, r3);

    static void writeW(int w, String key, String value, long ver) {
        int acked = 0;
        for (Map<String, Versioned> r : replicas) {
            if (acked < w) {
                r.put(key, new Versioned(value, ver));
                acked++;
            }
        }
        System.out.printf("  写 %s=%s(v%d) W=%d -> %d 副本确认%n", key, value, ver, w, acked);
    }

    static void readWithRepair(int r) {
        System.out.printf("  读 %s（R=%d）-> 全量读 %d 个副本比较版本：%n", "x", r, replicas.size());
        Versioned newest = null;
        List<Integer> stale = new ArrayList<>();
        for (int i = 0; i < replicas.size(); i++) {
            Versioned v = replicas.get(i).get("x");
            if (v == null) {
                stale.add(i);
                continue;
            }
            if (newest == null || v.version() > newest.version()) {
                newest = v;
            }
        }
        System.out.printf("    最新值：%s(v%d)%n", newest.value(), newest.version());
        for (int i : stale) {
            replicas.get(i).put("x", newest);
            System.out.printf("    读修复：副本%d 版本落后 -> 回填 %s(v%d)%n", i, newest.value(), newest.version());
        }
        System.out.println("    返回给客户端：" + newest.value());
        System.out.println();
    }

    static void paramWalkthrough() {
        System.out.println("【W/R 参数的组合语义（N=3）】");
        String[][] rows = {
                {"W=2, R=2", "标准：容 1 故障，读写各付多数派代价", "大多数业务"},
                {"W=1, R=3", "写延迟最低，读全量对比", "写密集 + 可读修复"},
                {"W=3, R=1", "写最慢，读最快（可能脏读）", "读密集且容忍旧值"},
                {"W=1, R=1", "最快，故障时丢数据", "缓存类，非真实数据"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-10s %-32s %s%n", r[0], r[1], r[2]);
        }
        System.out.println("  铁律：W+R>N 且 W>N/2（写集合自己也过半，防止两个并发写都成功）");
        System.out.println();
    }

    static void notLinearizable() {
        System.out.println("【为什么 W+R>N 仍可能读到旧值】");
        System.out.println("  写 v2 到 {r1,r2}（W=2）成功，r3 还是 v1");
        System.out.println("  读时 R=2 读到 {r1(v2), r3(v1)}：交集成立但客户端拿到 r3 的 v1");
        System.out.println("  两个必要补充：");
        System.out.println("    1) 版本比较：全部副本读回取最高版本（本课 readWithRepair 的实现）");
        System.out.println("    2) 读修复：把落后副本回填，让收敛真实发生");
        System.out.println("  结论：quorum 是必要条件，一致性靠“比较+修复”补完");
    }

    public static void main(String[] args) {
        writeW(2, "x", "v2-value", 2);
        // 模拟 r3 未同步（W=2 只写前两个副本）
        r3.remove("x");
        r3.put("x", new Versioned("v1-value", 1));
        readWithRepair(2);
        paramWalkthrough();
        notLinearizable();
    }
}
```

### 45-10 共识的工程代价

**知识点**
- **共识不便宜，先算代价再上**：每次写至少一次多数派 RTT（同机房 1~2ms，跨机房 30ms+）+ 多数派 fsync（磁盘毫秒级）。**etcd 单集群写 QPS 上千是健康极限**——共识集群是"协调者"不是"数据主库"。
- **集群规模的收益递减**：3 节点容忍 1 故障，5 节点容忍 2——每加一台，写路径都要联系更多人，**延迟与故障概率同步上升**。生产 3 或 5 台是甜蜜点，7 台以上要有特殊理由。
- **跨机房部署的取舍**：三个机房各一台（任一机房挂仍有过半）但写延迟 = 最慢机房 RTT；同机房三台（快）但机房故障全挂。**PC-EC 判断：机房级容灾 > 毫秒级延迟时才跨机房**，或用"两层架构"（本地快集群 + 异步跨机房镜像）。
- **共识成员变更的危险性**：在线改集群成员（3->5）本身需要共识保证——配置错误瞬间可能没有过半（新旧配置各 3 台互不相认）。**joint consensus 两阶段变更**是安全做法；运维上更常用"停写 + 一次性替换"。
- **日志增长与快照**：日志无限增长 -> 快照压缩（状态机快照 + 截断日志）-> 恢复可以走快照 + 追日志。**快照频率与大小**影响恢复时长，也是 43-05 checkpoint 思想的一致。
- **监控与告警**（42 章方法论）：commit 耗时 P99、fsync 慢日志、换届频率、成员健康、磁盘水位——**共识集群挂了会拖垮依赖它的所有系统（K8s/配置/锁），必须最高优先级监控**。
- 易错点：把业务数据写进共识集群（容量与吞吐双爆炸）；跨机房配置了共识却不接受写延迟（用户感知到"慢"）；在线成员变更无两阶段（分区分裂风险）；无快照（重启恢复要重放亿级日志）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class ConsensusCost {
    static void latencyMath() {
        System.out.println("【写延迟的物理构成】");
        double rttSameRack = 0.3, rttCrossAz = 1.8, fsync = 1.2;
        double sameRoom = 2 * rttSameRack + fsync;      // leader->2 follower 并行 + 落盘
        double crossAz = 2 * rttCrossAz + fsync;
        System.out.printf("  同机房 3 节点：2×%.1fms(RTT) + %.1fms(fsync) ≈ %.1fms%n",
                rttSameRack, fsync, sameRoom);
        System.out.printf("  跨可用区：2×%.1fms + %.1fms ≈ %.1fms（慢 %.1f 倍）%n",
                rttCrossAz, fsync, crossAz, crossAz / sameRoom);
        System.out.println("  结论：共识集群放同机房，跨机房用异步镜像（45-11 案例）");
        System.out.println();
    }

    static void clusterSize() {
        System.out.println("【集群规模：容忍度与代价】");
        String[][] rows = {
                {"1", "0 故障", "无共识可言（单点）"},
                {"3", "1 故障", "最小生产配置，写联系 2 台"},
                {"5", "2 故障", "滚动维护更从容，写联系 3 台"},
                {"7", "3 故障", "写延迟与故障概率上升，需特殊理由"},
        };
        for (String[] r : rows) {
            System.out.printf("  %s 台：容忍 %s 故障，%s%n", r[0], r[1], r[2]);
        }
        System.out.println("  甜蜜点：3 或 5。规模不是越多越可靠——写路径人数是代价");
        System.out.println();
    }

    static void membershipChange() {
        System.out.println("【成员变更：危险的在线操作】");
        List<String> steps = List.of(
                "危险做法：直接把配置从 {n1,n2,n3} 改成 {n1,n4,n5}",
                "  -> 旧配置 3 台与新配置 3 台同时存在，任一侧都可能“过半”",
                "  -> 两个 leader 并存的窗口（脑裂）",
                "安全做法一：joint consensus 两阶段（先联合配置 C_old,new，再切 C_new）",
                "安全做法二（运维常用）：停写 -> 一次性替换成员 -> 验证 -> 恢复");
        for (String s : steps) {
            System.out.println("  " + s);
        }
        System.out.println("  K8s etcd 扩容的“官方姿势”就是保守路线：能停就停，不能停走 joint");
        System.out.println();
    }

    static void usageDiscipline() {
        System.out.println("【使用纪律：什么该进共识，什么不该】");
        List<String> dos = List.of(
                "该进：选主结果、锁/租约、配置元数据、集群成员表、调度决策",
                "不该进：业务订单数据（走主库+复制）、高频计数（走 Redis+对账）、");
        System.out.println("  " + dos.get(0));
        System.out.println("  " + dos.get(1));
        System.out.println("  大 value 处理：日志只存引用（对象存 OSS，元数据进共识）");
        System.out.println("  判断式：这个数据需要“全局唯一顺序”吗？不需要就不进共识");
    }

    public static void main(String[] args) {
        latencyMath();
        clusterSize();
        membershipChange();
        usageDiscipline();
    }
}
```

### 45-11 综合案例：配置中心的高可用设计

**知识点**
- **把本章共识知识收束成一个生产组件**：配置中心（29 章已用过 Nacos 视角）的底座设计——**Raft 集群存配置元数据（45-03/04）+ MVCC 与 watch 推送（45-06）+ 分级读（45-02）+ 变更审计（41 章思想）+ 客户端本地快照兜底**。
- **写路径**：控制台变更 -> 写请求 -> Raft 过半提交 -> 版本递增 -> 长轮询/gRPC 流推送变更到客户端 -> 客户端落地本地快照。**推送失败靠客户端定期全量拉齐兜底**（推拉结合）。
- **读路径分级**：业务进程启动时全量拉取（线性一致读一次）；运行中读本地缓存（微秒级，最终一致）；配置变更后热更新（watch 推送 + 版本号确认）。**业务热路径零共识开销**——共识只发生在配置变更瞬间。
- **容灾设计**：Raft 集群挂 -> 客户端用**本地快照继续跑**（配置不常变，旧配置可用性高于准确性——PACELC 的业务化选择）；恢复后按版本对齐。**"客户端自持快照"是配置中心与传统数据库的最大区别**。
- **脑裂防护**：客户端只接受**版本号单调递增**的配置（fencing 思想，45-08）——分区期旧实例的推送（旧版本）被拒；同版本冲突靠 hash 校验。
- **灰度与回滚**：配置变更按实例灰度（41-07 金丝雀思想）+ 一键回滚到任意历史版本（MVCC 天然支持）+ 变更审计（谁改的、改了什么、谁审批的）。
- 易错点：客户端本地快照缺失（配置中心挂 = 全公司进程起不来）；推送依赖长轮询无超时兜底（推送丢失后配置永久不更新）；热更新不校验 schema（一个 typo 全线崩）；配置变更无灰度直接全量（错误的连接串推到全部实例）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ConfigCenterCase {
    /** 服务端：Raft 底座上的配置表 + 版本 */
    static class ConfigServer {
        final Map<String, String> data = new LinkedHashMap<>();
        long version = 0;
        final List<String> audit = new ArrayList<>();

        void put(String key, String value, String operator) {
            // 简化：假设已过半提交
            data.put(key, value);
            version++;
            audit.add(String.format("v%d %s 改 %s=%s", version, operator, key, value));
            System.out.printf("  [服务端] v%d 提交：%s=%s（操作人 %s）%n", version, key, value, operator);
        }

        String readLinear() {
            return "v" + version;
        }
    }

    /** 客户端：本地快照 + 版本单调 + 推拉结合 */
    static class ConfigClient {
        final Map<String, String> local = new LinkedHashMap<>();
        long localVersion = 0;

        void bootstrap(ConfigServer server) {
            local.putAll(server.data);
            localVersion = server.version;
            System.out.printf("  [客户端] 启动全量拉取：%s（线性一致读 %s）%n",
                    local, server.readLinear());
        }

        void onPush(String key, String value, long version) {
            if (version <= localVersion) {
                System.out.printf("  [客户端] 拒绝 v%d（本地已是 v%d）—— fencing 防旧实例推送%n",
                        version, localVersion);
                return;
            }
            local.put(key, value);
            localVersion = version;
            System.out.printf("  [客户端] 热更新 v%d：%s=%s + 落地本地快照%n", version, key, value);
        }

        void pullFallback(ConfigServer server) {
            if (server.version > localVersion) {
                onPush(null, null, server.version);
            }
        }
    }

    static void fullFlow() {
        System.out.println("【一次配置变更的完整链路】");
        ConfigServer server = new ConfigServer();
        server.put("db.url", "jdbc:mysql://db-a:3306/order", "ops-wang");
        ConfigClient client = new ConfigClient();
        client.bootstrap(server);
        System.out.println("  —— 10 分钟后修改连接串 ——");
        server.put("db.url", "jdbc:mysql://db-b:3306/order", "ops-wang");
        client.onPush("db.url", server.data.get("db.url"), server.version);
        System.out.println("  业务热路径全程未碰共识集群（本地缓存读取）");
        System.out.println();
    }

    static void disasterRecovery() {
        System.out.println("【容灾：Raft 集群挂了业务怎么办】");
        List<String> timeline = List.of(
                "T0 Raft 集群 3 台全挂（机房故障）",
                "T1 客户端推送失败 -> 静默重试，继续用本地快照服务",
                "T2 业务进程照常启动（新实例读本地快照文件）",
                "T3 恢复后按版本对齐：本地 v42 < 服务端 v43 -> 全量拉取",
                "T4 审计复盘：确认快照落盘策略（每版本落盘 + 保留 5 份）");
        for (String t : timeline) {
            System.out.println("  " + t);
        }
        System.out.println("  设计哲学：配置的可用性（旧配置能跑）优先于绝对最新——业务化 PACELC");
        System.out.println();
    }

    static void checklist() {
        System.out.println("【配置中心上线检查单】");
        List<String> items = List.of(
                "Raft 3~5 台专用部署，SSD，监控 commit P99 与换届",
                "客户端启动全量 + 运行热更新 + 定期兜底拉齐",
                "本地快照落盘（版本单调/fencing），防旧实例推送",
                "变更审计 + 按历史版本一键回滚（MVCC）",
                "schema 校验：变更先过格式与连接性检查再提交",
                "灰度：按实例比例生效，观察指标再全量",
                "演练：杀掉全部服务端节点，验证业务自持快照存活");
        for (String i : items) {
            System.out.println("  [ ] " + i);
        }
    }

    public static void main(String[] args) {
        fullFlow();
        disasterRecovery();
        checklist();
    }
}
```
