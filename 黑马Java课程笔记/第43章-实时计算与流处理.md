# 第43章 实时计算与流处理

第42章解决了"怎么看系统"，本章解决"数据来得太快怎么办"。批处理是"数据先齐再算"，流处理是"数据边来边算"——分界的本质不是速度，是有无数据终结点。一旦进入流的世界，时间要显式处理（事件时间与处理时间）、数据会乱序（水位线赌乱序有界）、状态要可恢复（checkpoint）、重复要可消除（幂等与 Exactly-Once）。本章按「流与批 → 时间语义 → 三种窗口 → 水位线 → 状态与容错 → Exactly-Once → 流式 Join → 反压调优 → CDC 与实时数仓 → Flink 与 Spark 对比 → 实时大屏案例」的顺序讲。所有示例仍是纯 JDK：三种窗口真实切分统计，水位线与乱序旁路真实推演，checkpoint 恢复与幂等重放真跑闭环，倾斜加盐与异步批量真实对比，不需要 Flink 或 Kafka 集群。

### 43-01 流与批的分界

**知识点**
- **批处理是"数据先齐再算"，流处理是"数据边来边算"**：日报/月报跑批（Hive/Spark SQL）等 24 点切分区；实时大屏/实时风控（Flink）每秒处理增量。**分界的本质不是速度，是有无"数据终结点"**。
- **Lambda 架构的历史包袱**：早期实时框架不保证正确性，于是"批出准数 + 流出快数"两套代码双跑再对账——同样的逻辑写两遍是维护地狱。**现代流处理（Flink 的 Exactly-Once + 事件时间）让"流批一体"成为可能**：一套代码，流跑实时、批跑历史回放。
- **什么时候必须流处理**：延迟要求秒级以内（风控拦截要在支付前）、持续聚合（大盘每秒刷新）、CDC 增量同步（binlog 不能等天级）。**能跑批的就别上流**——流系统的运维复杂度（状态、水位线、反压）远高于批。
- **流处理的心智模型转变**：数据无界（没有"跑完"）、计算常驻（7×24 进程）、故障要自恢复（状态可重建）、时间要显式处理（事件时间 vs 处理时间，43-02）。**把批思维带进流系统，第一个坑就是"为什么数据对不上"**。
- **流的三个可靠性等级**：At-most-once（可能丢）、At-least-once（可能重）、Exactly-once（不丢不重）。等级越高成本越高，**按业务选等级而不是默认最高**（43-06 细讲）。
- **Java 工程师的位置**：实时计算的主力框架 Flink 是 JVM 生态，Java 是一等公民。业务侧更多是"把逻辑交付给流系统"（UDF、规则引擎、特征计算）与"消费流的结果"。
- 易错点：把实时当"跑得快的批"（忽略无界与常驻）；两套代码双跑不对账（Lambda 架构的隐性成本）；所有场景都上流处理（运维复杂度爆炸）；忽略流系统的常驻成本（7×24 集群哪怕没有数据也在烧钱）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class StreamVsBatch {
    record Order(long id, long ts, double amount) {
    }

    static void batchMindset() {
        System.out.println("【批处理：数据先齐再算】");
        List<Order> dayOrders = List.of(
                new Order(1, dayStart() + 100, 69.0),
                new Order(2, dayStart() + 200, 199.0),
                new Order(3, dayStart() + 300, 29.0));
        double total = dayOrders.stream().mapToDouble(Order::amount).sum();
        System.out.printf("  23:59:59 后跑批：当日 %d 单，GMV %.1f 元 —— 输入完整，结果确定%n",
                dayOrders.size(), total);
        System.out.println("  特点：输入有界、可重跑、延迟天级、运维简单");
        System.out.println();
    }

    static long dayStart() {
        return 1763347200000L;
    }

    static void streamMindset() {
        System.out.println("【流处理：数据边来边算】");
        List<Order> arriving = List.of(
                new Order(4, dayStart() + 400, 59.0),
                new Order(5, dayStart() + 500, 129.0));
        double running = 297.0;   // 之前累计
        for (Order o : arriving) {
            running += o.amount();
            System.out.printf("  t+%dms 到达订单 %d -> 实时 GMV 刷新为 %.1f 元%n",
                    o.ts() - dayStart(), o.id(), running);
        }
        System.out.println("  特点：输入无界、计算常驻 7×24、秒级输出、要管状态与容错");
        System.out.println("  关键问题：这条“实时 GMV”到 24 点会和批跑的一致吗？（43-02/06 回答）");
        System.out.println();
    }

    static void whenToStream() {
        System.out.println("【决策：必须流 vs 应该批】");
        String[][] rows = {
                {"支付前拦截风险", "流（秒级）", "批等不到这笔交易发生"},
                {"实时大屏/监控", "流", "展示要求秒级刷新"},
                {"binlog 增量同步", "流（CDC）", "天级批无法满足一致性窗口"},
                {"日报/月报/对账", "批", "延迟可接受，批更简单可靠"},
                {"历史特征回填", "批", "输入是有界的历史数据"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-14s %-12s %s%n", r[0], r[1], r[2]);
        }
        System.out.println();
    }

    static void lambdaCost() {
        System.out.println("【Lambda 架构的双份成本】");
        Map<String, String> dup = new LinkedHashMap<>();
        dup.put("业务逻辑", "批 SQL 一份 + 流代码一份（同逻辑两实现）");
        dup.put("对账", "每日批跑完与流结果 diff，差异排障");
        dup.put("修复", "逻辑变更要改两处，先后上线节奏不一致就出差异");
        for (Map.Entry<String, String> e : dup.entrySet()) {
            System.out.printf("  %-6s %s%n", e.getKey(), e.getValue());
        }
        System.out.println("  现代解法：流批一体（同一套 API）+ 事件时间 + Exactly-Once");
        System.out.println("  流结果可信后，批只负责历史回填与审计");
    }

    public static void main(String[] args) {
        batchMindset();
        streamMindset();
        whenToStream();
        lambdaCost();
    }
}
```

### 43-02 时间语义：事件时间与处理时间

**知识点**
- **同一笔订单有三个时间**：**事件时间**（业务发生时刻，订单里的 create_time）、**处理时间**（流系统收到它的机器时钟）、**摄入时间**（进入框架的时刻）。**用哪个时间分桶，决定了统计口径**。
- **处理时间的陷阱在乱序与延迟**：网络抖动让订单 B（11:59:58 生成）比订单 A（11:59:59 生成）晚到——按处理时间分桶，B 掉进了第二天，GMV 在 24 点边界处永远对不上批结果。**事件时间按业务发生时刻分桶，乱序不改变归属**。
- **事件时间的前提是数据带可信时间戳**：源头的钟不准（客户端时间可改）、时钟回拨（39-07 的雪花时钟回拨同一问题）、字段缺失——**时间戳治理是流处理的隐形工程**：服务端打点为主、客户端时间为参考、格式统一 UTC 毫秒。
- **两种语义的适用场景**：处理时间适合"现在系统怎么样"（监控类，低延迟优先）；事件时间适合"业务到底发生了什么"（计费/对账/报表，正确性优先）。**钱相关的统计必须事件时间**。
- **迟到数据的两种命运**：事件时间窗口已关闭后到达的数据——丢弃（丢 GMV）或允许迟到（更新窗口结果，需要窗口能重算，43-04 水位线控制）。**"允许迟到多久"是业务决策**：电商订单通常允许 5~15 分钟。
- **回溯（backfill）的正确性**：事件时间让"重放昨天流量"得到与当时一致的窗口结果——这是流批一体的根基；处理时间重放会得到完全不同的分桶。
- 易错点：用处理时间算 GMV（跨天边界永远对不上）；信任客户端时间戳（可伪造可漂移）；窗口关闭=数据丢失（没设计迟到策略）；时间字段混用秒/毫秒（差三个数量级的分桶）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class TimeSemantics {
    record Order(long id, long eventTs, long processTs, double amount) {
        String eventDay() {
            return eventTs >= DAY2 ? "11-18" : "11-17";
        }

        String processDay() {
            return processTs >= DAY2 ? "11-18" : "11-17";
        }
    }

    static final long DAY2 = 1763433600000L;   // 11-18 00:00

    static void disorderDemo() {
        System.out.println("【跨天边界的两笔订单：两种语义的不同归属】");
        List<Order> orders = List.of(
                new Order(101, DAY2 - 1000, DAY2 + 800, 199.0),    // 23:59:59 生成，晚到 0.8s
                new Order(102, DAY2 + 500, DAY2 + 900, 69.0));     // 00:00:00.5 生成
        for (Order o : orders) {
            System.out.printf("  订单%d 事件时间=%s 处理时间=%s%n",
                    o.id(), o.eventDay(), o.processDay());
        }
        System.out.println("  订单 101 事件时间属 11-17，处理时间却落到 11-18");
        System.out.println("  处理时间 GMV：11-17 少 199 元 —— 与批结果永远差这一笔");
        System.out.println("  事件时间 GMV：与批完全一致（按业务发生时刻归属）");
        System.out.println();
    }

    static void timestampGovernance() {
        System.out.println("【时间戳治理：事件时间的前提】");
        String[][] rows = {
                {"客户端打点", "钟不准/可伪造", "仅作参考，服务端打点为准"},
                {"服务端打点", "统一 NTP，相对可信", "主来源（网关入口打点）"},
                {"时钟回拨", "短暂倒退", "单调化处理（39-07 同款方案）"},
                {"单位混乱", "秒 vs 毫秒", "统一 UTC 毫秒，schema 声明"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-10s %-16s %s%n", r[0], r[1], r[2]);
        }
        System.out.println();
    }

    static void latePolicy() {
        System.out.println("【迟到数据的两种命运：业务决策】");
        record LateOrder(long id, int lateSec, String decision, String reason) {
        }
        List<LateOrder> lates = List.of(
                new LateOrder(201, 30, "允许迟到：更新窗口", "GMV 精确性优先"),
                new LateOrder(202, 300, "允许迟到（上限 5 分钟）", "支付回调链路可能慢"),
                new LateOrder(203, 3600, "丢弃 -> 进旁路统计", "一小时前的订单不该影响实时大屏"));
        for (LateOrder l : lates) {
            System.out.printf("  订单%d 迟到 %ds -> %s（%s）%n",
                    l.id(), l.lateSec(), l.decision(), l.reason());
        }
        System.out.println("  “允许迟到多久”写进需求文档，不是技术拍脑袋");
        System.out.println();
    }

    static void replayValue() {
        System.out.println("【事件时间的回放价值：重放=复现】");
        System.out.println("  把昨天的原始事件流按事件时间重放：");
        System.out.println("  事件时间窗口 -> 得到与昨天完全一致的统计（可用于修复错误统计）");
        System.out.println("  处理时间窗口 -> 得到“按今天重放时刻”的统计（毫无用处）");
        System.out.println("  结论：事件时间是流批一体与可修复性的根基");
    }

    public static void main(String[] args) {
        disorderDemo();
        timestampGovernance();
        latePolicy();
        replayValue();
    }
}
```

### 43-03 窗口：滚动、滑动与会话

**知识点**
- **窗口是把无界流切成可聚合片段的机制**，三种基础形态：**滚动窗口**（tumbling，固定长度不重叠：每分钟 GMV）、**滑动窗口**（sliding，固定长度带步长重叠：近 5 分钟 QPS 每 10 秒刷新一次）、**会话窗口**（session，按活动间隔动态划分：用户一次浏览会话）。
- **窗口的关键参数语义**：滚动窗口只有 size；滑动窗口有 size（统计范围）与 slide（刷新频率），slide < size 时同一事件归属多个窗口（被多次统计）；会话窗口的参数是**间隔 gap**（gap 内无活动则窗口关闭）。
- **窗口归属由事件时间决定**（43-02 的直接应用）：事件落在 `[窗口起点, 终点)`。**窗口是"开区间闭区间"的口径问题**，与批 SQL 的 `GROUP BY date_trunc` 完全对齐——对不上批就是口径错了。
- **迟到与窗口生命周期**：窗口在其事件时间终点 + 水位线（43-04）到达后触发计算；允许迟到期间窗口保持"可更新"状态。**窗口状态的存在时间 = size + 迟到容忍**，直接影响状态存储量。
- **会话窗口的实现成本**：每个 key 维护"当前会话"状态，gap 内合并、gap 外新开——状态按活跃用户数计。大促日活跃千万级时会话窗口的状态量要提前估算。
- **窗口与下游的契约**：窗口结果带（窗口起点、终点、水位线）元数据输出——下游要知道"这个 11:59 的数字是几点几分最终确定的"。**不带窗口元数据的输出无法被信任**。
- 易错点：滑动窗口理解成"每 slide 秒重新统计全部"（事件重复计入多个窗口是设计而非 bug，但下游消费要明确）；会话 gap 设得太小（会话被切碎）；窗口边界口径与批 SQL 不一致（对不上账）；窗口结果没有"最终/临时"标记（下游把临时值当最终值）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

public class WindowsDemo {
    record Event(long ts, double amount) {
    }

    /** 事件流（相对秒） */
    static final List<Event> EVENTS = List.of(
            new Event(5, 60), new Event(35, 80), new Event(65, 40),
            new Event(95, 100), new Event(125, 70), new Event(155, 30));

    static void tumbling() {
        System.out.println("【滚动窗口：size=60s，每分钟 GMV】");
        TreeMap<Long, Double> windows = new TreeMap<>();
        for (Event e : EVENTS) {
            long win = e.ts() / 60;          // 归属哪一分钟
            windows.merge(win, e.amount(), Double::sum);
        }
        for (Map.Entry<Long, Double> w : windows.entrySet()) {
            System.out.printf("  [min%d, min%d)  GMV=%.0f 元%n", w.getKey(), w.getKey() + 1, w.getValue());
        }
        System.out.println("  特点：不重叠、每个事件只属一个窗口；等价于批的 GROUP BY 分钟");
        System.out.println();
    }

    static void sliding() {
        System.out.println("【滑动窗口：size=120s，slide=60s（近2分钟GMV每分钟刷新）】");
        for (long slide = 0; slide <= 2; slide++) {
            long start = slide * 60, end = start + 120;
            double sum = EVENTS.stream()
                    .filter(e -> e.ts() >= start && e.ts() < end)
                    .mapToDouble(Event::amount).sum();
            System.out.printf("  窗口[%3d, %3d) 当前累计 %.0f 元（刷新于 slide=%d）%n",
                    start, end, sum, slide);
        }
        System.out.println("  事件 ts=65 同时落在窗口[0,120) 与 [60,180)：被统计两次是设计使然");
        System.out.println("  下游消费契约：滑动结果用于“当前水平”，不用于累加求和");
        System.out.println();
    }

    static void sessionWindow() {
        System.out.println("【会话窗口：gap=20s，按用户活动划分】");
        record Click(long userId, long ts) {
        }
        List<Click> clicks = List.of(
                new Click(1, 0), new Click(1, 10), new Click(1, 28),   // 10<20 合并；28-10=18<20 合并
                new Click(1, 60),                                       // 60-28=32>20 新会话
                new Click(2, 5), new Click(2, 90));                     // gap 85 -> 各自成会话
        Map<Long, List<Long>> sessions = new LinkedHashMap<>();
        for (Click c : clicks) {
            List<Long> list = sessions.computeIfAbsent(c.userId(), k -> new ArrayList<>());
            if (!list.isEmpty() && c.ts() - list.get(list.size() - 1) > 20) {
                list = new ArrayList<>();
                sessions.put(c.userId(), list);
            }
            list.add(c.ts());
        }
        for (Map.Entry<Long, List<Long>> e : sessions.entrySet()) {
            System.out.printf("  用户%d 会话数=%d：%s%n", e.getKey(),
                    e.getValue().size(), e.getValue());
        }
        System.out.println("  参数是间隔而非长度：会话边界由数据自己决定");
        System.out.println();
    }

    static void lifecycle() {
        System.out.println("【窗口生命周期：状态存在多久】");
        long sizeSec = 60, allowedLateness = 300;
        System.out.printf("  size=%ds + 允许迟到=%ds -> 每个窗口状态存活 %d 秒%n",
                sizeSec, allowedLateness, sizeSec + allowedLateness);
        System.out.println("  状态量估算：活跃窗口数 = 360s 内的事件 key 数（大促需提前算）");
        System.out.println("  输出契约：结果带 (窗口起止, 是否最终) 元数据，下游据此消费");
    }

    public static void main(String[] args) {
        tumbling();
        sliding();
        sessionWindow();
        lifecycle();
    }
}
```

### 43-04 水位线与乱序处理

**知识点**
- **水位线（watermark）回答"什么时候窗口可以关"**：事件时间窗口不能等全部数据（数据无界），需要一个时间进度信号——"水位线 = T 表示：T 之前的事件应该都到了（除非超过容忍度）"。**水位线是流系统对"数据完备性"的乐观声明**。
- **水位线的生成**：通常 = 当前最大事件时间 - 有界乱序容忍度（如 5 秒）。事件到达会推进水位线；**某个分区/源停滞会拖住全局水位线**（所有上游的最小值）——这是"水位线卡住"故障的根源（空闲分区要发 idle 标记）。
- **水位线触发窗口**：水位线越过窗口终点（终点 + 允许迟到）时触发计算并关闭窗口。**容忍度是"正确性与延迟"的交换**：容忍 5s -> 结果最多晚 5s+窗口长，但 5s 内的乱序都能正确归属；容忍 0 -> 最快但乱序全部迟到丢弃。
- **迟到数据的旁路（side output）**：超过允许迟到的数据不进窗口，写入旁路流单独统计（"迟到丢弃数"本身是监控指标——突然升高说明上游时钟或网络出问题）。
- **水位线的正确性边界**：它不是"保证不会有更早的数据"，而是"声明不会有"。事件时间 < 当前水位线的数据就是迟到数据。**水位线本质是赌"乱序有界"**，赌输的部分走旁路。
- **幂等更新替代完美水位线**：下游支持重算（窗口结果带版本）时，水位线可以激进、迟到数据重发更新结果——**"可以修正的输出"比"完美的水位线"更工程化**（与 42 章窗口"是否最终"标记衔接）。
- 易错点：水位线容忍度拍脑袋（不测真实乱序分布）；空闲分区拖住全局水位线（窗口迟迟不触发，表现为"实时大屏卡住"）；把水位线当精确时钟（它是启发式）；迟到数据静默丢弃（旁路统计缺失，丢数没人知道）。

### 43-05 状态管理与容错

**知识点**
- **流处理是"常驻的有状态计算"**：窗口累计值、去重集合、join 缓存都是**状态**——它们必须活在进程里（快）又能被持久化（挂了可恢复）。**状态管理是流系统与"无状态微服务"的本质区别**。
- **状态的两类存储**：**算子本地状态**（RocksDB/堆内，读写快，计算用）+ **周期性快照**（checkpoint，写到分布式存储 HDFS/S3，恢复用）。**本地状态是主副本，checkpoint 是保险**。
- **Checkpoint 机制（Chandy-Lamport 快照）**：Source 插入屏障（barrier）随数据流流动，barrier 到达某算子时该算子把当前状态快照到远端存储；barrier 对齐保证"快照时点前后数据不混"。**恢复 = 所有算子回到最近一次 checkpoint 的状态，从 Source 重放之后的数据**。
- **恢复依赖"可重放源"**：Kafka 的 offset 就是重放指针——checkpoint 里存了"当时消费到 offset X"，故障后从 X 重读。**不可重放的源（实时 HTTP 推送）配 checkpoint 毫无意义**——这也是"流处理要对接可重放消息系统"的架构原因。
- **状态治理是运维主战场**：TTL（key 1 天不活动就清理，防止状态无限膨胀）、状态大小监控（RocksDB 落盘量、checkpoint 大小与耗时）、大状态拆分（按 key 哈希分散）。**状态失控 = checkpoint 超时 = 一直恢复失败 = 作业死亡循环**。
- **checkpoint 与可用性的平衡**：间隔太密（1s）→ 开销大；太疏（10min）→ 恢复要重放 10 分钟数据。典型 30s~2min，大状态作业放宽并加增量 checkpoint（只传变化部分）。
- 易错点：状态无 TTL（运行三月 RocksDB 500GB）；checkpoint 一直失败没人看（恢复时才发现作业早就"假活"）；把业务数据只存本地内存（挂了全丢）；恢复期间重复消费未做幂等（43-06）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class StateCheckpoint {
    /** 算子状态：窗口累计 + 最近 offset */
    static class OperatorState {
        final Map<String, Double> windowTotals = new LinkedHashMap<>();
        long kafkaOffset = 0;
        int version = 0;

        void process(String key, double amount, long offset) {
            windowTotals.merge(key, amount, Double::sum);
            kafkaOffset = offset;
        }

        Map<String, Object> snapshot() {
            Map<String, Object> snap = new LinkedHashMap<>(windowTotals);
            snap.put("__offset", kafkaOffset);
            return snap;
        }

        void restore(Map<String, Object> snap) {
            windowTotals.clear();
            for (Map.Entry<String, Object> e : snap.entrySet()) {
                if (!e.getKey().equals("__offset")) {
                    windowTotals.put(e.getKey(), (Double) e.getValue());
                } else {
                    kafkaOffset = (long) e.getValue();
                }
            }
        }
    }

    static void checkpointCycle() {
        System.out.println("【一个 checkpoint 周期与故障恢复】");
        OperatorState state = new OperatorState();
        state.process("11-17", 69.0, 100);
        state.process("11-17", 199.0, 101);
        Map<String, Object> snap = state.snapshot();
        System.out.println("  T0 checkpoint#1：" + snap + " -> 持久化到 S3");
        state.process("11-17", 29.0, 102);          // 这条之后发生故障
        System.out.println("  T1 继续处理 offset=102（GMV=297）后作业崩溃");
        OperatorState recovered = new OperatorState();
        recovered.restore(snap);
        System.out.println("  恢复：状态回到 checkpoint#1（GMV=268, offset=101）");
        System.out.println("  重放：从 Kafka offset=101 重读 -> 重新处理 102 -> GMV=297");
        System.out.println("  重复消费了 offset=102！下游必须幂等（43-06）");
        System.out.println();
    }

    static void ttlDiscipline() {
        System.out.println("【状态 TTL：防止状态无限膨胀】");
        record StateItem(String key, String ttl, String effect) {
        }
        List<StateItem> items = List.of(
                new StateItem("去重集合（订单ID）", "24h", "一天前的订单不会再来，清理"),
                new StateItem("窗口累计", "size+允许迟到", "窗口关闭即删"),
                new StateItem("join 左流缓存", "10min", "按 join 语义定"),
                new StateItem("无 TTL 的 user 状态", "——", "三个月 500GB，checkpoint 超时"));
        for (StateItem i : items) {
            System.out.printf("  %-18s TTL=%-14s %s%n", i.key(), i.ttl(), i.effect());
        }
        System.out.println("  规则：每个状态都要回答“什么时候可以删”");
        System.out.println();
    }

    static void healthSignals() {
        System.out.println("【流作业的存活判据：checkpoint 是心跳】");
        List<String> signals = List.of(
                "checkpoint 成功率 100%（失败 1 次即告警，连续失败=作业病危）",
                "checkpoint 耗时 < 间隔的 50%（否则永远在 checkpoint）",
                "Source 消费延迟（lag）持续增长 = 处理不过来",
                "RocksDB 落盘量增速稳定（突然暴涨=状态泄漏）");
        for (String s : signals) {
            System.out.println("  - " + s);
        }
        System.out.println("  对照：进程活着但 checkpoint 失败一周 —— “假活”，恢复时才发现状态早没了");
    }

    public static void main(String[] args) {
        checkpointCycle();
        ttlDiscipline();
        healthSignals();
    }
}
```

### 43-06 Exactly-Once 语义

**知识点**
- **三条可靠性等级**：At-most-once（最多一次：可能丢，简单最快）；At-least-once（至少一次：不丢但可能重，最常用默认）；Exactly-once（精确一次：不丢不重，成本最高）。**选择依据是业务对"丢"与"重"的容忍度**：监控大屏丢了可容忍（at-most-once 也行），支付计费重了就是事故（exactly-once 或幂等兜底）。
- **Exactly-once 的两个层面**：**端到端** = 框架内部状态精确一次（checkpoint 保证）+ **外部副作用精确一次**（写 Kafka/DB/MQ 的结果不重不漏）。框架内部容易，外部难——**外部系统必须参与两阶段提交或提供幂等**。
- **实现手段一：幂等写入**（最常用）：下游按主键 upsert（`INSERT ... ON DUPLICATE KEY UPDATE`）、Kafka 按键写可覆盖。**重放覆盖旧结果，天然收敛**。窗口结果带主键（窗口起点）就是为幂等服务。
- **实现手段二：两阶段提交（2PC）**：Flink 的 TwoPhaseCommitSink——预提交（写事务暂存）+ checkpoint 成功后正式提交。要求下游支持事务（Kafka 事务 API），代价是延迟（数据要等 commit 才可见）。
- **实现手段三：事务性写入下游**（DB 侧）：把"状态更新 + 输出写入"放进下游事务，靠下游原子性兜底。流框架只保证 at-least-once，精确性交给下游约束。
- **"幂等 + at-least-once" ≈ exactly-once**：这是工程上最实用的等价——不追求框架级精确，而是**让每个写操作幂等**，重复执行结果不变。第 28 章消费幂等、第 39 章本地消息表，同一思想贯穿。
- 易错点：以为开启 checkpoint 就端到端 exactly-once（只保了内部状态）；下游写非幂等（insert 重复数据）；2PC 下游不支持事务还硬用（事务泄漏）；把"窗口结果对不上"归罪于框架（多数是幂等缺失或时间语义错）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ExactlyOnce {
    record WindowResult(String windowKey, double gmv, int version) {
    }

    /** 幂等 sink：窗口结果按主键覆盖 */
    static class IdempotentSink {
        final Map<String, WindowResult> table = new LinkedHashMap<>();

        void write(WindowResult r) {
            WindowResult existing = table.get(r.windowKey());
            if (existing == null || r.version() >= existing.version()) {
                table.put(r.windowKey(), r);
                System.out.printf("  写入 %s gmv=%.1f v%d（覆盖式）%n",
                        r.windowKey(), r.gmv(), r.version());
            } else {
                System.out.printf("  忽略 %s v%d（已有 v%d，旧版本）%n",
                        r.windowKey(), r.version(), existing.version());
            }
        }
    }

    static void idempotentReplay() {
        System.out.println("【重放场景：同一窗口结果被写两次】");
        IdempotentSink sink = new IdempotentSink();
        sink.write(new WindowResult("11-17", 268.0, 1));
        // 故障恢复后重放，窗口重算出相同结果（版本相同）或更新结果（版本更高）
        sink.write(new WindowResult("11-17", 268.0, 1));
        sink.write(new WindowResult("11-17", 297.0, 2));
        System.out.println("  最终表：" + table(sink));
        System.out.println("  无论重放多少次，结果收敛 —— 这就是幂等的价值");
        System.out.println();
    }

    static Map<String, WindowResult> table(IdempotentSink sink) {
        return sink.table;
    }

    static void levelChoice() {
        System.out.println("【按业务选等级，不默认最高】");
        String[][] rows = {
                {"监控指标曲线", "at-least-once + 幂等（按窗口键覆盖）", "偶尔重复被覆盖，无损"},
                {"实时大屏 GMV", "幂等 upsert（窗口键主键）", "修正可见，最终一致"},
                {"计费/佣金入账", "事务写入 + 去重表", "钱的事，宁可复杂不可错"},
                {"风控事件流", "at-least-once + 下游幂等消费", "与 28 章消费幂等同款"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-12s %-34s %s%n", r[0], r[1], r[2]);
        }
        System.out.println();
    }

    static void twoPhase() {
        System.out.println("【2PC sink：预提交与正式提交】");
        List<String> steps = List.of(
                "1) sink 收到数据 -> 写入下游事务（未提交，预提交态）",
                "2) checkpoint barrier 到达 -> 状态快照（含事务句柄）",
                "3) checkpoint 成功 -> 正式 commit 事务（数据对外可见）",
                "4) 失败 -> 事务 abort，恢复后从 checkpoint 重放");
        for (String s : steps) {
            System.out.println("  " + s);
        }
        System.out.println("  代价：数据可见延迟 = checkpoint 间隔；要求下游支持事务");
        System.out.println("  实用主义：多数场景「幂等 + at-least-once」已等价于业务上的精确一次");
    }

    public static void main(String[] args) {
        idempotentReplay();
        levelChoice();
        twoPhase();
    }
}
```

### 43-07 流式 Join 与维度关联

**知识点**
- **流上的 Join 难在"两边都在动"**：批处理 join 时两张表都静止；流上订单流与支付流都在到达，**必须各自缓存等待配对**——缓存多大、等多久，是流 join 的核心参数。
- **窗口 join**：两边各按窗口截取，窗口内互相配对（如 10 分钟内订单与支付匹配）。实现简单，代价是**边界订单丢失**（订单 11:59:58、支付 00:00:01 跨窗口）。适合"相关性窗口明确"的场景。
- **区间 join（interval join）**：按业务时间区间配对——`支付时间 BETWEEN 下单时间 AND 下单时间+30min`。语义精确（每个订单在自己区间内找支付），是订单-支付类 join 的标准解。实现上要缓存左流直到区间终点（水位线推进才清理）。
- **维表关联（stream-table join）**：订单流关联商品维表——维表是"慢变的静态数据"。三种实现：**同步查库**（简单但 QPS 高时打爆 DB）、**本地缓存 + 定期刷新**（热路径首选，代价是短暂不一致）、**维表变更流广播**（CDC 推送变更，一致性最好）。
- **迟到与配对失败的处理**：等了 30 分钟没有支付的订单——进"未配对旁路"（对账用），不能静默丢弃。**join 的输出要覆盖三种情况：配对成功、左等待、右等待**。
- **状态量估算**：join 缓存 = 左流速率 × 区间长度。订单 1000 QPS × 30 分钟 = 180 万条在缓存——**区间长度与状态量的乘积关系**决定 join 设计。
- 易错点：join 缓存无清理（状态爆炸，43-05）；用处理时间做区间（乱序下配对错乱）；维表本地缓存无刷新（商品改价后订单一直用旧价）；配对失败的订单静默丢失（财务对不上）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class StreamJoin {
    record Order(long id, long eventTs, double amount) {
    }

    record Payment(long orderId, long eventTs) {
    }

    /** 区间 join：支付需落在订单后 30 分钟内（秒） */
    static final long INTERVAL_SEC = 1800;

    static void intervalJoin() {
        System.out.println("【区间 join：订单流 × 支付流】");
        List<Order> orders = List.of(
                new Order(1, 100, 199.0),
                new Order(2, 200, 69.0),
                new Order(3, 300, 129.0));
        List<Payment> payments = List.of(
                new Payment(1, 150),          // 50s 后支付：命中
                new Payment(2, 2400),         // 2200s 后支付：超区间
                new Payment(3, 320));         // 20s：命中
        for (Order o : orders) {
            Payment hit = payments.stream()
                    .filter(p -> p.orderId() == o.id())
                    .filter(p -> p.eventTs() >= o.eventTs()
                            && p.eventTs() <= o.eventTs() + INTERVAL_SEC)
                    .findFirst().orElse(null);
            if (hit != null) {
                System.out.printf("  配对成功：订单%d（%.0f元）<-> 支付（延迟 %ds）%n",
                        o.id(), o.amount(), hit.eventTs() - o.eventTs());
            } else {
                System.out.printf("  未配对：订单%d -> 进入未配对旁路（对账）%n", o.id());
            }
        }
        System.out.println("  左流缓存存活 = 区间长度；水位线推进过区间终点才清理");
        System.out.println();
    }
```

### 43-08 反压与性能调优

**知识点**
- **反压（backpressure）是流系统的"堵车"**：下游算子处理不过来，压力沿数据流向上游传导，最终表现为 **Source 消费延迟（lag）持续增长**。它是流作业最常见的病，症状是"lag 涨"，根因却五花八门。
- **定位反压的标准路径**：先看 lag（确认堵了）→ 看 Flink WebUI 的反压状态（哪个算子繁忙背压高）→ 看该算子的火焰图（42-09）→ 找热点。**热点通常四类：数据倾斜、外部调用慢、状态过大、序列化开销**。
- **数据倾斜是流处理的第一性能杀手**：某个 key（大卖家、爆款商品、某个用户）占 50% 流量，单并行子任务累死其他空闲。对策：**加盐打散**（key 加随机后缀聚合两次）、**局部预聚合**（先本地聚合再全局）、热点 key 单独通道。
- **外部调用是第二杀手**：算子里同步调 HTTP/DB，单条 50ms × 1000 QPS = 并发不够直接堵。对策：**批量调用**（攒 100 条一次查）、**异步 IO**（AsyncFunction 并发多路）、**本地缓存**（维表 43-07）。
- **状态过大拖慢一切**：RocksDB 读写放大、checkpoint 越来越久。对策：TTL（43-05）、状态键设计（少存大对象）、增量 checkpoint。
- **扩容的边界**：并行度提高受三面墙限制——Source 分区数（Kafka 分区 12 个，并行度 24 也是白搭）、keyBy 后的 key 数（倾斜 key 无法再分）、下游系统容量（DB 扛不住更高并发写）。**扩容前先确认瓶颈不是代码**。
- 易错点：lag 一涨就加机器（倾斜时加多少都堵在同一个子任务）；反压只看 CPU（CPU 空闲也会反压——在等外部 IO）；批量大小拍脑袋（太大 checkpoint 变重）；忽略序列化（对象太大，网络传输成瓶颈）。

### 43-09 CDC 与实时数仓

**知识点**
- **CDC（Change Data Capture）把数据库的每次变更变成事件流**：基于 binlog（Canal/Debezium/Flink CDC）伪装成从库订阅变更，业务零侵入。第 38 章的"ES 数据同步"、第 39 章的"异构数仓"，落地的技术底座就是 CDC。
- **实时数仓的分层**：ODS（binlog 原始层，对应每张表）-> DWD（明细层：清洗、拆列、维表关联）-> DWS（汇总层：实时聚合窗口）-> ADS（应用层：大屏/接口）。**与离线数仓同名分层，实时化替代 T+1**。
- **CDC 的语义细节**：binlog 是 ROW 格式才带完整前后镜像；一条 UPDATE 在 CDC 里是"before + after"两个影像，下游要做对比；**DELETE 也要传播**（下游删数据，漏了就是幻影行）。
- **全量 + 增量的衔接（snapshot reading）**：新表接入先全量快照再接 binlog 增量，衔接点用"快照时的高水位 offset"保证不重不漏——这是 Flink CDC 的核心卖点，省去手工衔接脚本。
- **schema 变更的传播**：源表加列，CDC 下游怎么办——主流方案：下游手动兼容（新字段容忍缺失）或框架自动同步（Flink CDC 3.x schema evolution）。**schema 变更是 CDC 管道的运营常态**，要有演练。
- **实时数仓与离线的口径治理**：同一指标（GMV）实时与离线各算一份，**口径必须同一份定义**（哪些订单算、退款怎么扣），否则"大屏 5000 万、报表 4900 万"的解释成本巨大（43-01 Lambda 架构的遗留问题）。
- 易错点：binlog 还是 ROW 格式之外的（STATEMENT）下游无法解析；DELETE 事件被忽略（下游幻影数据）；全量增量手工衔接出错（重复或漏段）；实时与离线口径独立演化（数字打架）。

**示例代码**

```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class CdcWarehouse {
    record Row(String id, String status, double amount) {
    }

    /** 一条 CDC 事件：表 + 操作 + before/after */
    record CdcEvent(String table, String op, Row before, Row after, long binlogOffset) {
        String describe() {
            return switch (op) {
                case "INSERT" -> "新增 id=" + after.id();
                case "UPDATE" -> "更新 id=" + after.id() + " " + before.status() + "->" + after.status();
                case "DELETE" -> "删除 id=" + before.id();
                default -> "未知";
            };
        }
    }

    static void eventSemantics() {
        System.out.println("【CDC 事件语义：INSERT/UPDATE/DELETE 都要传播】");
        List<CdcEvent> events = List.of(
                new CdcEvent("orders", "INSERT", null, new Row("9001", "PAID", 199.0), 101),
                new CdcEvent("orders", "UPDATE",
                        new Row("9001", "PAID", 199.0), new Row("9001", "REFUNDED", 199.0), 108),
                new CdcEvent("orders", "DELETE", new Row("9002", "CREATED", 59.0), null, 112));
        for (CdcEvent e : events) {
            System.out.printf("  offset=%d %s%n", e.binlogOffset(), e.describe());
        }
        System.out.println("  下游数仓按 offset 应用：INSERT 插、UPDATE 改、DELETE 删");
        System.out.println("  忽略 DELETE -> 下游出现 id=9002 的幻影订单 —— 对账永远差一笔");
        System.out.println();
    }

    static void snapshotHandoff() {
        System.out.println("【全量快照与增量的无缝衔接】");
        List<String> steps = List.of(
                "1) 记录当前 binlog 位点（高水位 offset=500）",
                "2) 全量快照 SELECT 一致性读（相当于 offset=500 时刻的数据）",
                "3) 快照写入下游",
                "4) 从 offset=500 开始消费增量 —— 与快照正好衔接，不重不漏",
                "5) 校验：行数 + checksum 抽查");
        for (String s : steps) {
            System.out.println("  " + s);
        }
        System.out.println("  手工衔接的坑：快照与位点的时间差 -> 重段或漏段");
        System.out.println();
    }

    static void layered() {
        System.out.println("【实时数仓分层与口径治理】");
        Map<String, String> layers = new LinkedHashMap<>();
        layers.put("ODS", "binlog 原样入库（每表一 topic）");
        layers.put("DWD", "清洗 + 维表关联（订单明细实时化）");
        layers.put("DWS", "实时聚合（每分钟 GMV，43-03 窗口）");
        layers.put("ADS", "大屏/接口直接消费");
        for (Map.Entry<String, String> e : layers.entrySet()) {
            System.out.printf("  %-4s %s%n", e.getKey(), e.getValue());
        }
        System.out.println("  口径治理：GMV 定义（含退款？含取消？）实时与离线共用一份定义文档");
        System.out.println("  差异监控：实时值 vs 离线值每日 diff，> 0.5% 告警");
    }

    public static void main(String[] args) {
        eventSemantics();
        snapshotHandoff();
        layered();
    }
}
```

### 43-10 Flink 与 Spark Streaming 概念对比

**知识点**
- **两家框架的根本差异在时间模型**：Spark Streaming（微批 micro-batch）把流当"一小段一小段的批"（DStream/Structured Streaming 的触发间隔），天然批思维；Flink 是真正的逐事件流引擎（DataFlow 模型），事件时间/水位线/状态是一等公民。**"流批一体"的深度 Flink 更彻底**。
- **微批的代价与收益**：代价是延迟下限=批间隔（100ms~秒级）与窗口语义的近似；收益是吞吐高效、模型简单、复用批优化器。**秒级延迟够用的报表类，微批完全胜任**——不必迷信"真流"。
- **Flink 的核心优势场景**：亚秒延迟（风控/告警）、复杂事件时间语义（精确窗口 + 迟到处理）、大状态（RocksDB）、精确一次 sink（2PC）。Spark 优势：SQL 生态统一、批资源复用、团队已有 Spark 基建。
- **API 演进趋势趋同**：Flink SQL 与 Spark Structured Streaming 的 SQL 接口都支持窗口/水位线/(join)——**声明式 SQL 是实时计算的终局形态**，代码 API 是兜底。选型看团队技能栈与运维能力，而不是 API 花哨程度。
- **运维复杂度对比**：Flink 作业是常驻有状态进程（checkpoint、恢复、升级要 savepoint）；Spark 批任务跑完即退（Spark Streaming 的 trigger AvailableNow 其实是"带流外观的批"）。**把批任务迁移上 Flink 要接受"7×24 服务"的运维等级**。
- **选型决策树**：延迟要求 <1s 或强事件时间 -> Flink；T+1 或分钟级且已有 Spark 体系 -> Spark；两者都不熟且是纯 SQL 报表 -> 云厂商托管（省运维）。**没有银弹，只有场景匹配**。
- 易错点：用微批做亚秒级风控（延迟下限不允许）；把 Flink 作业当批任务（没有 savepoint 就升级 = 状态全丢）；迷信框架基准测试（自己的数据倾斜一次就推翻所有 benchmark）。

### 43-11 综合案例：实时大屏（订单成交监控）

**知识点**
- **把本章串成一条实时链路**：MySQL 订单（binlog）-> CDC 采集（43-09）-> Kafka -> Flink 清洗关联维表（43-07）-> 事件时间窗口聚合（43-02/03）-> 水位线控制关闭（43-04）-> 幂等写入 Redis（43-06）-> 大屏接口读 Redis。**每个环节都对应前面一课的设计决策**。
- **大屏的需求即参数**：GMV 每分钟刷新（滚动窗口 60s + 总累计）、成交笔数、实时趋势线（滑动窗口近 10 分钟）、TOP 商品榜（窗口聚合 + 排序）。**每个指标都能追溯到窗口参数与口径定义**——口径文档（含退款是否扣除）是需求评审的一部分。
- **正确性保障**：事件时间语义（跨天准确）、幂等 upsert（重放无损）、未配对旁路（对账兜底）、与离线口径每日 diff。**大屏数字敢被 CEO 盯，靠的是这条链路**。
- **运维保障**：checkpoint 心跳、lag 监控、反压定位预案（43-08）、水位线空闲源标记、窗口结果"是否最终"标记（前端闪烁提示临时值）。
- **容量与降级**：大促峰值 QPS 提前压测（重点测倾斜 key——爆款商品）、Redis 写入批量合并、降级预案（CDC 断流时大屏显示"数据延迟"而不是停更数字）。
- 易错点：大屏只做"显示"不管口径（数字被质疑时无人能解释）；实时与离线两套口径独立演化（数字打架）；不做峰值倾斜压测（大促当天爆款 key 堵死）；降级预案缺失（CDC 断流大屏冻结没人发现）。

```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

public class RealtimeDashboard {
    /** 指标层：Redis 模拟（幂等 upsert） */
    static Map<String, Double> redis = new LinkedHashMap<>();

    record OrderEvent(long id, long eventTs, String shopId, double amount, boolean refunded) {
    }

    static List<OrderEvent> genEvents() {
        List<OrderEvent> events = new ArrayList<>();
        long base = 1763347200000L;
        for (int i = 0; i < 8; i++) {
            events.add(new OrderEvent(9000 + i, base + i * 7000,
                    i % 3 == 0 ? "shop-001(爆款)" : "shop-00" + (i % 3 + 1),
                    69 + i * 10, false));
        }
        return events;
    }

    static void pipeline() {
        System.out.println("【链路总览：CDC -> Kafka -> Flink -> Redis -> 大屏】");
        List<String> steps = List.of(
                "1) MySQL binlog -> CDC（Debezium/Flink CDC）-> topic ods_orders",
                "2) Flink 清洗：过滤测试单 + 维表关联（商品类目，本地缓存）",
                "3) 事件时间滚动窗口 60s：GMV/笔数（keyBy shopId，倾斜加盐）",
                "4) 滑动窗口 10min/1min：趋势线",
                "5) 幂等写 Redis（窗口键主键 upsert）",
                "6) 大屏接口轮询 Redis，展示「是否最终」标记");
        for (String s : steps) {
            System.out.println("  " + s);
        }
        System.out.println();
    }

    static void aggregate() {
        System.out.println("【一分钟滚动窗口聚合（含倾斜加盐）】");
        List<OrderEvent> events = genEvents();
        TreeMap<Long, Double> plain = new TreeMap<>();
        for (OrderEvent e : events) {
            plain.merge(e.eventTs() / 60000, e.amount(), Double::sum);
        }
        for (Map.Entry<Long, Double> w : plain.entrySet()) {
            System.out.printf("  窗口 min%d GMV=%.1f 元（含爆款 shop-001）%n", w.getKey(), w.getValue());
        }
        System.out.println("  倾斜处理：shop-001 加盐 shop-001#0~2 局部聚合，全局合并结果一致");
        System.out.println();
    }

    static void idempotentWrite() {
        System.out.println("【幂等写入与最终标记】");
        // 窗口 [w, w+60s) 首次触发
        redis.put("gmv:11-17:min0", 69.0);
        System.out.println("  T+61s 首次触发：gmv:min0=69.0 (临时)");
        redis.put("gmv:11-17:min0", 139.0);   // 迟到订单更新
        System.out.println("  T+64s 迟到更新：gmv:min0=139.0 (临时)");
        redis.put("gmv:11-17:min0", 139.0);
        System.out.println("  T+364s 水位线越过窗口+5min -> 最终态：gmv:min0=139.0 (final)");
        System.out.println("  大屏契约：临时值带闪烁提示，最终值定格 —— 下游不再误读");
        System.out.println();
    }

    static void ops() {
        System.out.println("【上线保障清单】");
        List<String> items = List.of(
                "口径文档：GMV 是否含退款/取消，与离线对账共用定义",
                "对账：实时 vs 离线每日 diff > 0.5% 告警",
                "压测：大促峰值 + 爆款倾斜 key 专项",
                "监控：checkpoint 心跳 / lag / 反压 / 水位线卡住",
                "降级：CDC 断流 -> 大屏显示“数据延迟 N 分钟”而非冻结数字",
                "回放：原始事件流在 Kafka 保留 24h，统计错误可重放修复");
        for (String i : items) {
            System.out.println("  [ ] " + i);
        }
    }

    public static void main(String[] args) {
        pipeline();
        aggregate();
        idempotentWrite();
        ops();
    }
}
```
