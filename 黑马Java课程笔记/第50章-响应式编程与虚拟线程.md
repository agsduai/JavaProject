# 第50章 响应式编程与虚拟线程

第32章的线程池是并发模型的地基，本章回答"高并发 IO 该用什么模型"。平台线程昂贵而等待免费——响应式用非阻塞换取吞吐（代价是回调心智），JDK 21 的虚拟线程让**同步代码获得异步吞吐**：阻塞时自动卸载载体线程，现有 JDBC 阻塞代码直接受益。本章按「三种并发模型 → Reactor 核心与背压 → WebFlux 分层与陷阱 → 虚拟线程原理 → 实战编排 → pinning 与池化误区 → 响应式 vs 虚拟线程选型 → CompletableFuture 整合 → 实测对比 → 迁移路线 → 聚合网关案例」的顺序讲。所有示例仍是纯 JDK：虚拟线程全部真实运行（JDK 21 原生），10 万并发挂起真跑，Flow API 背压真实推演，pinning 与连接池瓶颈真实对比，不需要 Reactor 依赖。

### 50-01 阻塞与非阻塞的并发模型

**知识点**
- **高并发 IO 的本质矛盾：线程昂贵，等待免费**——平台线程（传统 Thread）1:1 映射内核线程，默认 1MB 栈，万级并发就耗尽内存与调度；但大部分时间线程在“等 IO”（DB/HTTP 响应），CPU 闲着。**并发模型的一切设计都是在解决“怎么用少量线程扛大量等待”**。
- **三种并发模型**：① **阻塞 + 线程池**（简单，线程数=并发上限，池满了排队）；② **非阻塞回调/响应式**（少量事件循环线程 + 异步回调，吞吐高但代码变“回调地狱/响应式链”）；③ **虚拟线程**（阻塞语义 + 海量线程，代码同步写、运行异步化——JDK 21 的答案）。**三者解决同一个问题，体验截然不同**。
- **响应式的代价在心智**：整条调用链必须全异步（一个阻塞调用卡死事件循环）、栈不可读（异常堆栈跨回调）、调试困难。**虚拟线程的承诺是“同步代码获得异步吞吐”**——这是 Java 官方对响应式复杂性的回应。
- **选型的第一问：IO 密集还是 CPU 密集**——IO 密集（等 DB/HTTP）虚拟线程收益巨大；CPU 密集虚拟线程无收益（核数决定），线程池依旧正确。
- **配套生态**：响应式要全套非阻塞驱动（R2DBC/非阻塞 HTTP 客户端）；虚拟线程**现有 JDBC 阻塞驱动直接可用**（这正是它省心的根源）。40-04 SSE 与 48-07 流式服务的连接并发也在此框架下重审。
- 易错点：CPU 密集任务用虚拟线程（只增加调度开销）；响应式链里混入阻塞调用（事件循环被卡，全服务卡顿）；把线程池大小调大当作高并发方案（上下文切换与内存双重反噬）；以为异步 = 更快单请求（异步提升吞吐，单请求延迟可能反而略增）。

**示例代码**
```java
import java.time.Duration;
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class BlockingVsNonBlocking {
    /** 模拟一次下游 IO：等 100ms 返回 */
    static String callDownstream(String req) {
        try {
            Thread.sleep(100);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return "resp:" + req;
    }

    static void model1() throws Exception {
        System.out.println("【模型①：阻塞 + 固定线程池】");
        try (ExecutorService pool = Executors.newFixedThreadPool(10)) {
            long start = System.currentTimeMillis();
            List<String> results = new ArrayList<>();
            List<java.util.concurrent.Future<String>> futures = new ArrayList<>();
            for (int i = 0; i < 20; i++) {
                final String req = "req-" + i;
                futures.add(pool.submit(() -> callDownstream(req)));
            }
            for (java.util.concurrent.Future<String> f : futures) {
                results.add(f.get());
            }
            long cost = System.currentTimeMillis() - start;
            System.out.printf("  10 线程处理 20 个请求（每个等 100ms）-> %dms%n", cost);
            System.out.println("  特点：代码直观；并发上限=线程数（第 11 个请求排队）");
        }
        System.out.println();
    }

    static void model2() throws Exception {
        System.out.println("【模型②：虚拟线程（阻塞语义 + 海量线程）】");
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            long start = System.currentTimeMillis();
            List<java.util.concurrent.Future<String>> futures = new ArrayList<>();
            for (int i = 0; i < 1000; i++) {
                final String req = "req-" + i;
                futures.add(pool.submit(() -> callDownstream(req)));
            }
            for (java.util.concurrent.Future<String> f : futures) {
                f.get();
            }
            long cost = System.currentTimeMillis() - start;
            System.out.printf("  1000 个虚拟线程（阻塞写法）-> %dms（1000 个平台线程不可想象）%n", cost);
        }
        System.out.println("  特点：同步代码 + 万级并发 —— 模型①的心智 + 更高吞吐");
        System.out.println();
    }

    static void model3() {
        System.out.println("【模型③：非阻塞/响应式（少量事件循环）】");
        System.out.println("  事件循环线程数 ≈ CPU 核数，等待期间线程处理别的请求");
        List<String> traits = List.of(
                "吞吐：极高（少量线程扛大量连接，Netty/Reactor 生态）",
                "代码：Mono/Flux 链式（不可阻塞、异常跨回调、栈难读）",
                "生态约束：全链路非阻塞（驱动/客户端都要非阻塞版本）",
                "适用：网关/推送/高扇出聚合（50-11 案例）");
        for (String t : traits) {
            System.out.println("  " + t);
        }
        System.out.println();
    }

    static void decision() {
        System.out.println("【第一决策：负载类型】");
        String[][] rows = {
                {"IO 密集（等 DB/HTTP）", "虚拟线程首选，响应式次之", "等待占比高才值得换模型"},
                {"CPU 密集（计算/压缩）", "固定大小线程池 = 核数", "虚拟线程无收益，只加调度开销"},
                {"超高并发连接（>10k）", "响应式/Netty", "百万连接场景虚拟线程也吃紧"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-16s %-22s %s%n", r[0], r[1], r[2]);
        }
    }

    public static void main(String[] args) throws Exception {
        model1();
        model2();
        model3();
        decision();
    }
}
```

### 50-02 Reactor 核心：Mono/Flux 与背压

**知识点**
- **响应式的数据结构只有两个**：`Mono<T>`（0~1 个元素的异步序列）与 `Flux<T>`（0~N 个）。**它们是“未来的流”**：声明处理管道，订阅时才执行（惰性）。理解“声明 vs 执行”的分离是 Reactor 的入门关。
- **操作符即管道**：map/filter/flatMap/concatMap/zip/merge——**flatMap 决定并发度**（flatMapSequential 保序，flatMap 并发乱序完成）；错误传播沿管道（onErrorResume/onErrorMap），相当于同步代码的 try-catch 在管道里流动。
- **背压（backpressure）**：消费者控制生产者速度（request(n) 拉取）——43-08 反压在应用层的对应机制；无界流（无限 Flux）+ 慢消费者必须背压策略（buffer/drop/latest），否则内存爆炸。
- **订阅才执行**：`flux.map(...)` 只是搭管道；`subscribe()` 才启动——**忘了订阅是响应式第一 bug**（代码写了没效果）；WebFlux 框架帮你订阅，但测试与后台任务要自己 subscribe。
- **阻塞是响应式的毒药**：管道中任何一步调用阻塞 API（JDBC/Thread.sleep/同步锁）会卡死事件循环线程——**检测手段**：BlockHound 类工具在测试中拦截阻塞调用。
- **上下文传递**：MDC/trace_id 在响应式里不能用 ThreadLocal 直传（线程切换）——用 Reactor Context 或改造日志方案（42-02 在响应式的对应改造）。
- 易错点：Mono 里做阻塞 IO（卡死 worker 线程）；subscribe 泄漏（无限流不取消）；flatMap 无界并发（下游被打爆，要 concurrency 参数）；异常没接住（onError 缺失 -> 管道静默终止）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.Flow;
import java.util.concurrent.SubmissionPublisher;
import java.util.concurrent.TimeUnit;

public class ReactorCore {
    /** JDK 自带的 Reactive Streams API（java.util.concurrent.Flow）演示背压 */
    static class TickSubscriber implements Flow.Subscriber<Integer> {
        private Flow.Subscription subscription;
        private final String name;
        private int received = 0;

        TickSubscriber(String name) {
            this.name = name;
        }

        public void onSubscribe(Flow.Subscription s) {
            this.subscription = s;
            s.request(3);                       // 背压：只拉 3 个（消费者控制速度）
            System.out.printf("  [%s] 订阅成功，request(3)%n", name);
        }

        public void onNext(Integer item) {
            received++;
            System.out.printf("  [%s] 收到 %d（共 %d）%n", name, item, received);
            if (received % 3 == 0) {
                subscription.request(3);        // 处理完再拉下一批
            }
        }

        public void onError(Throwable t) {
            System.out.printf("  [%s] 错误：%s%n", name, t.getMessage());
        }

        public void onComplete() {
            System.out.printf("  [%s] 完成%n", name);
        }
    }

    static void backpressureDemo() throws Exception {
        System.out.println("【背压：消费者 request(n) 控制生产速度】");
        try (SubmissionPublisher<Integer> publisher = new SubmissionPublisher<>()) {
            publisher.subscribe(new TickSubscriber("slow-consumer"));
            for (int i = 1; i <= 10; i++) {
                int lag = publisher.estimateMaximumLag();
                publisher.submit(i);
                TimeUnit.MILLISECONDS.sleep(50);
                if (i == 5) {
                    System.out.printf("  [生产者] 已提交 5 个，未消费积压（lag 估计）≈ %d%n", lag);
                }
            }
            publisher.close();
            TimeUnit.MILLISECONDS.sleep(300);
        }
        System.out.println("  生产 > 消费时：积压可观测、消费者限流拉取 —— 43-08 反压的应用层原语");
        System.out.println();
    }

    static void lazyVsEager() {
        System.out.println("【声明 vs 订阅：管道搭好不执行，订阅才跑】");
        List<String> executed = new ArrayList<>();
        Runnable pipeline = () -> {           // 模拟“声明好的管道”
            executed.add("map(加工)");
            executed.add("filter(过滤)");
        };
        System.out.println("  管道已声明：" + executed.isEmpty() + "（尚未执行任何步骤）");
        System.out.println("  订阅（subscribe）触发执行：");
        pipeline.run();
        System.out.println("  执行轨迹：" + executed);
        System.out.println("  响应式第一 bug：搭好管道忘了订阅 —— 代码写了没效果");
        System.out.println();
    }

    static void blockingPoison() {
        System.out.println("【阻塞是响应式的毒药】");
        List<String> consequences = List.of(
                "Mono 里调 JDBC 阻塞 50ms -> 事件循环线程被占 50ms",
                "事件循环线程 = CPU 核数（如 8）-> 并发上限骤降为 160 QPS",
                "对照：全部非阻塞时同 8 线程可扛数千并发",
                "检测：BlockHound 类工具在测试期拦截阻塞调用",
                "铁律：响应式链路里禁止 Thread.sleep / JDBC / 同步锁 IO");
        for (String c : consequences) {
            System.out.println("  " + c);
        }
        System.out.println();
    }

    public static void main(String[] args) throws Exception {
        backpressureDemo();
        lazyVsEager();
        blockingPoison();
    }
}
```

### 50-03 WebFlux 的分层与陷阱

**知识点**
- **WebFlux 与 MVC 的并存**：Spring 5+ 两种栈——Servlet 栈（Tomcat，阻塞友好）与 Reactive 栈（Netty，WebFlux）。**选 WebFlux 的前提是整条链路非阻塞**：R2DBC（数据库）、WebClient（HTTP）、无阻塞锁。混栈是最常见的翻车起点。
- **Controller 返回 Mono/Flux 即接入异步**：框架负责订阅——**返回值类型就是契约**（返回 Mono 的接口天然支持流式/背压，40-04 SSE 在 WebFlux 下就是 Flux 返回值）。
- **陷阱清单**：① Mono 里 .block()（直接阻塞事件循环，测试环境看似正常、生产高并发雪崩）；② 在 controller 里手工 subscribe（自己订阅后框架拿不到结果，返回空）；③ 链路中同步锁/ThreadLocal（线程切换失效）；④ 日志 MDC 丢 trace（50-02 的上下文问题）；⑤ R2DBC 没上（DB 还是 JDBC 阻塞——整个改造白做）。
- **什么场景值得 WebFlux**：聚合网关、长连接推送、高扇出并行调用（下游多个 + 各自延迟）；**普通 CRUD 服务用 MVC + 虚拟线程更省心**（50-07 选型）。
- **与虚拟线程的关系**：JDK 21 后"为吞吐而 WebFlux"的必要性下降——**同步代码 + 虚拟线程达到相近吞吐**；WebFlux 的剩余价值在流式/背压语义（SSE、实时推送）与生态（Gateway/R2DBC 已是事实标准）。
- 易错点：为"显得先进"上 WebFlux（团队不熟 Reactor，隐蔽 bug 群）；block() 出现在生产代码（压测才暴露）；webflux + JDBC 混搭（假异步真阻塞）；错误处理缺失（onErrorReturn 全局兜底漏配）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class WebFluxPatterns {
    /** 用“小事件循环”模拟：2 个 worker 线程扛全部请求 */
    static final ExecutorService EVENT_LOOP = Executors.newFixedThreadPool(2);
    static final List<String> CALLS = new ArrayList<>();

    static String blockingDbCall() {
        try {
            Thread.sleep(50);                   // 模拟 JDBC 阻塞
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return "row";
    }

    static void eventLoopStarvation() throws Exception {
        System.out.println("【事件循环饥饿：一个阻塞调用拖垮全部并发】");
        for (int i = 0; i < 10; i++) {
            EVENT_LOOP.submit(() -> {
                CALLS.add(blockingDbCall());    // 毒药：worker 线程上阻塞 50ms
                return null;
            });
        }
        EVENT_LOOP.shutdown();
        EVENT_LOOP.awaitTermination(5, TimeUnit.SECONDS);
        System.out.printf("  10 个请求 × 50ms 阻塞 ÷ 2 个 worker = 至少 %.0fms 才能清空%n", 10 * 50 / 2.0);
        System.out.println("  期间这 2 个线程无法处理任何其他请求 —— 并发上限被阻塞锁死");
        System.out.println("  WebFlux 等价场景：Mono.fromCallable(::blockingDbCall) 未切弹性调度器");
        System.out.println();
    }

    static void subscribeTrap() {
        System.out.println("【手工 subscribe 陷阱：返回值拿不到】");
        List<String> wrong = List.of(
                "错误写法：pipeline.subscribe() 之后 return null",
                "    -> 框架拿到的是空响应（你自己订阅，框架没东西可消费）",
                "正确写法：return pipeline（把管道交给框架订阅）",
                "后台任务例外：无人消费的管道才需要自己 subscribe 并管理生命周期");
        for (String w : wrong) {
            System.out.println("  " + w);
        }
        System.out.println();
    }

    static void checklist() {
        System.out.println("【WebFlux 上线检查单】");
        List<String> items = List.of(
                "全链路非阻塞：R2DBC/WebClient，禁 JDBC/RestTemplate 阻塞客户端",
                "无 .block()：CI 静态扫描 + BlockHound 测试拦截",
                "无手工 subscribe 泄漏：返回管道交给框架",
                "trace_id 方案改造（Context 或 MDC 桥），禁裸 ThreadLocal",
                "错误兜底：全局 onError 处理 + 每条管道 onErrorReturn",
                "团队培训：Reactor 调试与排障技能确认");
        for (String i : items) {
            System.out.println("  [ ] " + i);
        }
        System.out.println("  任何一项不达标 -> 选 MVC + 虚拟线程（50-07）");
    }

    public static void main(String[] args) throws Exception {
        eventLoopStarvation();
        subscribeTrap();
        checklist();
    }
}
```

### 50-04 虚拟线程原理：载体线程与挂载

**知识点**
- **虚拟线程 = JVM 管理的轻量线程**：不映射内核线程，栈存在堆上（初始几百字节，按需增长）——**百万级虚拟线程可行**。JDK 21 正式发布（Project Loom 的第一块成果）。
- **载体线程（carrier thread）机制**：虚拟线程运行时"挂载"到一个载体线程（ForkJoinPool，默认 = CPU 核数）；**阻塞时（IO/sleep/锁等待）虚拟线程从载体上"卸载"，载体去跑别的虚拟线程**——阻塞不再占用 OS 线程。恢复时重新挂载（可能在另一个载体上）。
- **卸载的条件**：阻塞在可感知的操作（网络 IO、sleep、Object.wait、ReentrantLock）——**JDK 把这些阻塞点改造成了"让出载体"的挂起点**。兼容性奇迹：现有阻塞代码不改就能享受。
- **不卸载的场景（pinning）**：**synchronized 块内阻塞**、native 方法（JNI）内阻塞——载体被钉住，其他虚拟线程无法复用。**JDK 21 的最大坑**（50-06 细讲，JDK 24 已修复 synchronized）。
- **应该怎么用**：**每任务一线程（thread-per-request）回归**——虚拟线程廉价，不再需要池化；`Executors.newVirtualThreadPerTaskExecutor()` 是标准姿势；**不要池化虚拟线程、不要给虚拟线程设上限池**（要限并发用 Semaphore）。
- **可观测**：`Thread.isVirtual()` 判断；JFR 事件（pinning/提交/卸载）；**线程名要设置**（海量虚拟线程的 dump 是茫茫多，命名规范 42-02 同源）。
- 易错点：池化虚拟线程（newFixedThreadPool 包虚拟线程工厂——失去意义还限制并发）；在虚拟线程里跑 CPU 重活（占用载体，影响全部）；用虚拟线程数当并发限流手段（改用 Semaphore 显式限流）；忽略 pinning（synchronized 里调阻塞 IO）。

### 50-05 虚拟线程实战与并发编排

**知识点**
- **虚拟线程的编排原语**：`newVirtualThreadPerTaskExecutor()`（每任务一线程）+ Future/CompletionStage 编排；**结构化并发**（StructuredTaskScope，JDK 21 预览 API——任务生命周期嵌套在作用域内、取消自动传播）理念重要，本课用 Executor + Future 模拟其语义（避免 preview 编译门槛），生产待其转正。
- **扇出聚合模式**（50-11 案例原型）：并行调 N 个下游（各自虚拟线程）-> 全部成功合并 / 任一失败快速失败或降级——**timeout 与取消要显式管理**：`Future.get(timeout)` + 取消其余任务，避免“快的等慢的”。
- **与 Semaphore 的限流配合**：虚拟线程廉价但**下游不便宜**——并发保护下游用 `Semaphore.acquire()`（阻塞在信号量上会卸载，不占载体）——**线程数无限、下游并发有限**的正确表达。
- **与现有设施的关系**：ThreadLocal 可用（每虚拟线程独立副本，但百万副本要算内存账 50-06）；连接池不变——DB 连接仍是稀缺资源，虚拟线程排队等连接，**瓶颈平移到池，吞吐上限由池决定**（池大小重新评估）；Spring Boot 3.2+ 一行开启 `spring.threads.virtual.enabled=true`。
- **错误处理语义**：单任务异常不影响其他任务（各自 Future）；批量场景收集异常而不是快速失败（报告型任务）；关键路径快速失败 + 取消其余（成本控制）。
- 易错点：虚拟线程内再套自定义线程池（资源叠加失控）；Future.get 无超时（一个慢下游拖死整批）；取消不传播（幽灵任务继续跑 43 章概念）；把虚拟线程当异步框架（它是并发原语，生态在追赶 50-07）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.Semaphore;
import java.util.concurrent.TimeUnit;

public class VirtualThreadPractice {
    static String call(String name, long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return name + "-ok";
    }

    static void fanoutAggregation() throws Exception {
        System.out.println("【扇出聚合：并行 3 下游 + 总超时】");
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            long start = System.currentTimeMillis();
            Future<String> f1 = pool.submit(() -> call("stock", 120));
            Future<String> f2 = pool.submit(() -> call("price", 80));
            Future<String> f3 = pool.submit(() -> call("promo", 200));
            String r1 = f1.get(500, TimeUnit.MILLISECONDS);
            String r2 = f2.get(500, TimeUnit.MILLISECONDS);
            String r3 = f3.get(500, TimeUnit.MILLISECONDS);
            System.out.printf("  合并：%s / %s / %s -> 耗时 %dms（≈最慢者而非之和）%n",
                    r1, r2, r3, System.currentTimeMillis() - start);
        }
        System.out.println("  对照串行 400ms；并行收益 = max(下游) —— IO 密集的核心红利");
        System.out.println();
    }

    static void semaphoreGuard() throws Exception {
        System.out.println("【Semaphore：线程无限，下游并发有限】");
        Semaphore permit = new Semaphore(10);       // 下游只承受 10 并发
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            List<Future<String>> futures = new ArrayList<>();
            for (int i = 0; i < 100; i++) {
                futures.add(pool.submit(() -> {
                    permit.acquire();               // 阻塞在信号量：卸载，不占载体
                    try {
                        return call("db-call", 50);
                    } finally {
                        permit.release();
                    }
                }));
            }
            for (Future<String> f : futures) {
                f.get();
            }
        }
        System.out.println("  100 个虚拟线程完成；同一时刻下游最多 10 并发");
        System.out.println("  关键：限流点从“线程池大小”变成“显式 Semaphore”（50-06 池化误区）");
        System.out.println();
    }

    static void timeoutWithCancel() throws Exception {
        System.out.println("【超时与取消：慢下游不拖垮整批】");
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            Future<String> fast = pool.submit(() -> call("fast", 50));
            Future<String> slow = pool.submit(() -> call("slow", 2000));
            String r = fast.get(200, TimeUnit.MILLISECONDS);
            slow.cancel(true);
            System.out.printf("  fast=%s；slow 已取消（释放资源，不拖尾）%n", r);
        }
        System.out.println("  结构化并发（preview API）将把这类模式标准化：作用域内自动取消传播");
        System.out.println("  生产注意：cancel(true) 中断要被任务体响应（sleep/阻塞点感知中断）");
    }

    public static void main(String[] args) throws Exception {
        fanoutAggregation();
        semaphoreGuard();
        timeoutWithCancel();
    }
}
```

### 50-06 虚拟线程的坑

**知识点**
- **Pinning（钉住）：synchronized 内阻塞不卸载**——虚拟线程阻塞在 `synchronized` 块内时**无法从载体卸载**，载体线程被占死；高并发下“核数个载体”全部被钉住 -> 服务假死。**JDK 21 生产第一坑**（JDK 24 已修复 synchronized 的 pinning，21 必须代码层规避）。
- **pinning 的检测与修复**：JFR 事件 `jdk.VirtualThreadPinned` 记录钉住时长与栈——筛 >10ms 事件按栈聚合 Top 方法；命中 synchronized -> **热点改 ReentrantLock**（可卸载），不必全局替换（先测后改）。
- **池化误区**：`newFixedThreadPool(200, virtualFactory)` 是反模式——池化为了复用昂贵资源，虚拟线程廉价无需复用；池引入排队与上限**反而废掉虚拟线程的价值**。限并发用 Semaphore（显式语义），不用池大小。
- **ThreadLocal 的内存账**：百万虚拟线程 × 每个 ThreadLocal 副本（如大对象缓存）= 内存放大——**审计**每个 ThreadLocal 存储的对象；方案：显式传参 / ScopedValue（preview）/ 限制规模。trace 方案在虚拟线程下 ThreadLocal 可用但要算账（42-02 的 MDC 在虚拟线程的对应改造）。
- **CPU 任务的干扰**：虚拟线程跑长计算霸占载体（无法卸载）——**CPU 活留给固定平台线程池**，虚拟线程只做 IO 编排；混合负载用隔离执行器（47-08 弹性的线程维度）。
- **兼容性排查**：JDBC 阻塞驱动天然兼容（阻塞即卸载）✓；老版本连接池/驱动内部 synchronized+IO 组合要排查；升级 JDK 24 可大幅缓解 synchronized 问题（升级评估项进 41 章 ADR）。
- 易错点：synchronized 包住 HTTP 调用做“防重复”（pinning 灾难）；全局替换 synchronized（应热点优先）；ThreadLocal 缓存大对象（百万副本放大）；开启开关就宣布完成（pinning 与连接池两关都要过）。

### 50-07 响应式 vs 虚拟线程选型

**知识点**
- **两者解决同一问题的两条路**：响应式（2017~）：编程模型换非阻塞，吞吐换复杂度；虚拟线程（2023~）：运行时换载体调度，**保留同步编程模型**。**JDK 21 之后，默认答案从响应式移向虚拟线程**——同步代码 + 海量并发的承诺兑现。
- **决策矩阵六项**：负载类型（IO/CPU 密集，50-01）、并发规模（<10k 虚拟线程够用；极端长连接规模 Netty 生态仍占优）、流式/背压刚需（Flux 语义不可替代）、团队熟练度（Reactor 熟练的沉默成本）、存量栈（WebFlux 不重写）、JDK 版本（虚拟线程需 21+）。**六项打分，不是直觉站队**。
- **推荐形态**：新 CRUD/业务服务 -> MVC + 虚拟线程（默认答案）；实时推送/SSE -> WebFlux（背压语义剩余价值区）；聚合网关 -> 两者皆可按团队栈定；存量 WebFlux -> 保持 + 新代码虚拟线程试点（渐进不重写，49-10 成本框架）。
- **代码与调试体验对比**：同一聚合任务——WebFlux 链式 15 行（栈跨回调、断点难）vs 虚拟线程同步 12 行（栈可读、可单步调试）；**可维护性在功能等价时占优**。
- **生态现状**：R2DBC/WebClient 成熟；虚拟线程生态在追赶——**“兼容现有阻塞客户端”是最大优势**（JDBC/Redis 客户端无需替代品，改造成本近零）。
- 易错点：选型当站队（全站一刀切）；用跑分定选型（自己的 IO 形态才是真实依据）；忽略存量成本（WebFlux 推倒重写是负收益）；忘记响应式的背压/流式语义在特定场景不可替代（40-04 SSE、43 章反压）。

### 50-08 CompletableFuture 与两者整合

**知识点**
- **CompletableFuture 是“回调与组合”的中坚**：JDK 8 引入，_supplyAsync/thenApply/thenCombine/allOf 提供组合能力——**它是响应式思想在 JDK 内的最早形态**，也是虚拟线程前“并发编排”的事实标准（32 章 JUC 的编排层）。
- **CF 的位置在三者地图上**：CF（回调组合，JDK 内置）< Reactor（完整响应式流 + 背压）< 虚拟线程（同步语义）——**CF 依然是默认可用项**：不引框架、不用新 JDK 特性、语义够用的编排场景用它。
- **CF 与虚拟线程的配合**：CF 的默认执行器在 JDK 21 之后是虚拟线程执行器（`CompletableFuture` 静态方法的 async 变体走虚拟线程）——**回调写法 + 虚拟线程执行**融合；`orTimeout` 提供超时（48-07 预算思想的 JDK 原生）。
- **CF 的坑**：默认池是 ForkJoinPool.commonPool（CPU 密集导向，IO 任务会饿死其他并行流）——**IO 任务显式传 executor**；异常处理链遗漏（exceptionally/handle 缺失 -> 异常静默吞掉）；thenApply 与 thenApplyAsync 的线程语义混淆。
- **迁移视角**：存量 CF 代码无需重写——虚拟线程时代 CF 仍是有效编排工具；**新代码的简单场景用虚拟线程同步写，复杂组合（扇入/竞速）用 CF**——按表达式复杂度选。
- 易错点：commonPool 跑阻塞 IO（全局并行流与 CF 一起挨饿）；allOf 后不 collect 结果（只等完成不取值）；超时缺失（orTimeout 不用，请求悬挂）；异常链断裂（上一阶段异常未处理，下一阶段不执行也无提示）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class CfIntegration {
    static final ExecutorService VIRTUAL = Executors.newVirtualThreadPerTaskExecutor();

    static CompletableFuture<String> call(String name, long ms) {
        return CompletableFuture.supplyAsync(() -> {
            try {
                Thread.sleep(ms);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            return name + "-ok";
        }, VIRTUAL);
    }

    static void combination() throws Exception {
        System.out.println("【CF 组合：扇入合并 + 竞速】");
        long start = System.currentTimeMillis();
        CompletableFuture<String> all = call("stock", 120)
                .thenCombine(call("price", 80), (s, p) -> s + "+" + p);
        System.out.println("  thenCombine 合并：" + all.get(1, TimeUnit.SECONDS)
                + "（耗时 " + (System.currentTimeMillis() - start) + "ms）");
        CompletableFuture<String> race = call("fast-source", 50)
                .applyToEither(call("slow-source", 300), s -> s);
        System.out.println("  applyToEither 竞速：" + race.get(1, TimeUnit.SECONDS));
        System.out.println();
    }

    static void timeoutAndError() throws Exception {
        System.out.println("【orTimeout 超时与异常链】");
        CompletableFuture<String> hung = call("hung", 2000)
                .orTimeout(200, TimeUnit.MILLISECONDS)
                .exceptionally(ex -> "timeout-fallback");
        System.out.println("  超时兜底结果：" + hung.get(1, TimeUnit.SECONDS));
        CompletableFuture<String> failed = CompletableFuture.<String>failedFuture(
                new IllegalStateException("downstream error"))
                .handle((v, ex) -> ex == null ? v : "degraded:" + ex.getMessage());
        System.out.println("  handle 转译异常：" + failed.get(1, TimeUnit.SECONDS));
        System.out.println("  规则：每个 CF 链必有超时（orTimeout）与异常终态（handle）");
        System.out.println();
    }

    static void allOfCollect() throws Exception {
        System.out.println("【allOf 的正确姿势：等完成 + 收集结果】");
        List<CompletableFuture<String>> futures = List.of(
                call("a", 50), call("b", 80), call("c", 60));
        CompletableFuture<Void> all = CompletableFuture.allOf(
                futures.toArray(new CompletableFuture[0]));
        all.get(1, TimeUnit.SECONDS);
        List<String> results = new ArrayList<>();
        for (CompletableFuture<String> f : futures) {
            results.add(f.join());
        }
        System.out.println("  收集结果：" + results);
        System.out.println("  坑对照：只 allOf().get() 不 join() —— 异常与结果都拿不到");
    }

    public static void main(String[] args) throws Exception {
        combination();
        timeoutAndError();
        allOfCollect();
    }
}
```

### 50-09 高并发 IO 实测对比

**知识点**
- **本课用一组可复现实验回答“虚拟线程到底带来多少”**：三个实验——吞吐对比（固定池 vs 虚拟线程）、并发规模对比（千级 vs 万级任务的内存与调度）、瓶颈平移验证（线程不再是瓶颈后，连接池/下游成为新瓶颈）。**自己测出来的数字才是团队的数字**（46-09 验收思想）。
- **实验设计的控制变量**：任务形态统一（sleep 模拟 IO 100ms）、压测客户端统一、JVM 参数统一（堆大小一致）；**每个实验记录**：完成时间、P99、线程数、内存峰值（42 章实验纪律的并发版）。
- **结果的解读框架**：吞吐提升的来源是“阻塞不占线程”（等待复用）；**提升倍数 ≈ 等待占比**（IO 占 95% 的负载可放大近 20 倍，IO 占 20% 只放大 1.25 倍）——**先测你的等待占比，再预期收益**。
- **内存账**：平台线程 1MB 栈 × 1000 = 1GB；虚拟线程堆上栈 × 10000 ≈ 数百 MB——**在相同 -Xmx 下可承载的并发数差两个数量级**（44-05 显存账的线程版）。
- **CPU 密集对照实验**：同样任务换成 CPU 计算（无 sleep）——虚拟线程与固定池吞吐几乎相同（核数决定）——**验证“虚拟线程只救 IO”**，避免盲目全量替换。
- 易错点：实验不含真实 IO 形态（纯 sleep 低估调度开销、纯 CPU 高估收益）；单次跑分下结论（取多次中位数 42-04 分位数思想）；忽略 JVM 预热（JIT 未热，前几轮数据失真）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

public class IoBenchmark {
    /** IO 任务：等 100ms（模拟下游） */
    static String ioTask() {
        try {
            Thread.sleep(100);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return "ok";
    }

    /** CPU 任务：无等待，纯计算 */
    static String cpuTask() {
        long x = 0;
        for (int i = 0; i < 2_000_000L; i++) {
            x += i * 31;
        }
        return x == -1 ? "impossible" : "ok";
    }

    static long run(String label, ExecutorService pool, int tasks,
                    java.util.function.Supplier<String> task) throws Exception {
        long start = System.currentTimeMillis();
        List<Future<String>> futures = new ArrayList<>();
        for (int i = 0; i < tasks; i++) {
            futures.add(pool.submit(task::get));
        }
        for (Future<String> f : futures) {
            f.get(60, TimeUnit.SECONDS);
        }
        long cost = System.currentTimeMillis() - start;
        System.out.printf("  %-22s %4d 任务 -> %5dms%n", label, tasks, cost);
        return cost;
    }

    static void throughputExperiment() throws Exception {
        System.out.println("【实验一：IO 任务吞吐（200 任务 × 100ms 等待）】");
        long fixed;
        try (ExecutorService fixedPool = Executors.newFixedThreadPool(20)) {
            fixed = run("固定池(20线程)", fixedPool, 200, IoBenchmark::ioTask);
        }
        long virtual;
        try (ExecutorService vtPool = Executors.newVirtualThreadPerTaskExecutor()) {
            virtual = run("虚拟线程", vtPool, 200, IoBenchmark::ioTask);
        }
        System.out.printf("  提速 %.1f 倍；理论等待占比 95%% -> 上限约 %.0f 倍（排队与调度损耗）%n%n",
                (double) fixed / virtual, 100.0 / 5);
    }

    static void scaleExperiment() throws Exception {
        System.out.println("【实验二：并发规模（2000 任务，同 -Xmx）】");
        try (ExecutorService smallPool = Executors.newFixedThreadPool(200)) {
            run("固定池(200线程) 上限", smallPool, 2000, IoBenchmark::ioTask);
        }
        try (ExecutorService vtPool = Executors.newVirtualThreadPerTaskExecutor()) {
            run("虚拟线程(2000并发)", vtPool, 2000, IoBenchmark::ioTask);
        }
        System.out.println("  固定池要扛 2000 并发需 2000 平台线程 ≈ 2GB 栈；虚拟线程 MB 级");
        System.out.println();
    }

    static void cpuControl() throws Exception {
        System.out.println("【实验三：CPU 任务对照（虚拟线程无收益验证）】");
        try (ExecutorService fixedPool = Executors.newFixedThreadPool(
                Runtime.getRuntime().availableProcessors())) {
            run("固定池(核数) CPU 任务", fixedPool, 40, IoBenchmark::cpuTask);
        }
        try (ExecutorService vtPool = Executors.newVirtualThreadPerTaskExecutor()) {
            run("虚拟线程 CPU 任务", vtPool, 40, IoBenchmark::cpuTask);
        }
        System.out.println("  结论：CPU 密集两者相当（核数决定）—— 虚拟线程只救 IO，全量替换是误用");
    }

    public static void main(String[] args) throws Exception {
        throughputExperiment();
        scaleExperiment();
        cpuControl();
    }
}
```

### 50-10 迁移路线：从线程池到虚拟线程

**知识点**
- **迁移是渐进工程，不是开关项目**：路线——① JDK 升级到 21（前置项，41 章 ADR）；② 开启 `spring.threads.virtual.enabled=true`（Tomcat 请求线程虚拟化）；③ JFR 扫 pinning 热点修复（50-06）；④ 连接池重评估（虚拟线程抬高了“需要的连接数”，池跟不上则瓶颈平移）；⑤ 自建线程池逐个评估（IO 型改虚拟、CPU 型保留）；⑥ 压测对比与灰度（41-07）。
- **改动的优先级**：先“零代码收益”（容器请求线程虚拟化）→ 再“热点收益”（自定义 IO 线程池换虚拟）→ 最后“边缘清理”（调度器/异步任务）。**每一步独立可回退**（49-10 演进纪律）。
- **升级的连带检查**：依赖库的 JDK 21 兼容性（老框架的字节码增强）、-XX 参数变化（GC 默认差异小但需回归）、`synchronized` 热点清单、监控线程数指标语义变化（虚拟线程数远超平台线程数，42 章面板要更新）。
- **连接池重评估公式**：虚拟线程时代池大小 ≈ 目标并发 × 下游耗时占比（等待在 DB 上的并发数）——**池从“限流器”变成“真实资源上限”**，池小则吞吐被封顶（50-05 实验）。
- **回退预案**：开关回退（enabled=false 一行）；灰度按服务/命名空间；回退后 pinning 风险自然消失。
- 易错点：升级 JDK 21 直接全量开虚拟线程（未扫 pinning）；连接池没调（虚拟线程全部堵在 10 个连接上，吞吐不升反降）；监控告警阈值没更新（线程数告警误报海量）；自定义池全部替换（CPU 型任务也换，无收益还有调度开销）。

### 50-11 综合案例：聚合网关

**知识点**
- **把本章串成一个经典场景**：BFF/聚合网关——一个用户请求需要并行调 4~6 个下游（商品/价格/库存/营销/评论/推荐），合并后返回。**IO 密集 + 高扇出 + 严格超时**——并发模型的试金石（50-01 的决策原点）。
- **虚拟线程版实现**：每下游一个虚拟线程 + Semaphore 限每个下游并发 + 总超时取消 + 部分失败降级（超时下游返回占位数据而不是整体失败）——**“部分可用优于全失败”的聚合语义**（44-08 降级阶梯的网关版）。
- **超时预算分配**：网关总预算 800ms -> 各下游按重要性分配（商品 400ms/评论 200ms 可失败/推荐 150ms 可失败）——44-08 预算链的网关落地；先完成的先返回（流式聚合可选）。
- **可观测**：每下游耗时打点 + 失败率分下游 + 队列深度（42 章：聚合网关的 SLI 天然按下游维度展开）；取消传播（用户断开 -> 全部下游取消，48-07 同款）。
- **压测验收**：对比三种实现的吞吐/P99——串行（基线）、平台线程池（池大小受限）、虚拟线程（接近理想）——**在真实下游延迟分布下跑**（50-09 实验纪律）。
- 易错点：聚合失败语义一刀切（一个下游挂全页面挂）；超时预算不分级（全部 800ms，慢下游拖死）；无并发保护（大促下游被打爆）；缓存缺失（热点聚合结果缓存，46-10 数据 API 同款）。

**示例代码**
```java
import java.time.Duration;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.Semaphore;
import java.util.concurrent.TimeUnit;

public class AggregationGatewayCase {
    record Downstream(String name, int costMs, boolean critical, int maxConcurrency) {
    }

    static final List<Downstream> DOWNSTREAMS = List.of(
            new Downstream("product", 150, true, 20),
            new Downstream("price", 100, true, 20),
            new Downstream("stock", 120, true, 15),
            new Downstream("reviews", 200, false, 10),
            new Downstream("recommend", 250, false, 10));

    static String call(String name, int costMs) {
        try {
            Thread.sleep(costMs);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        return name + "-data";
    }

    static void aggregate(String requestId) throws Exception {
        System.out.println("---- 请求 " + requestId + " ----");
        long start = System.currentTimeMillis();
        Map<String, String> merged = new LinkedHashMap<>();
        List<String> degraded = new ArrayList<>();
        try (ExecutorService pool = Executors.newVirtualThreadPerTaskExecutor()) {
            List<Future<?>> futures = new ArrayList<>();
            for (Downstream d : DOWNSTREAMS) {
                Semaphore permit = new Semaphore(d.maxConcurrency());
                int budget = d.critical() ? 400 : 200;
                futures.add(pool.submit(() -> {
                    try {
                        permit.acquire();
                        try {
                            String data = call(d.name(), d.costMs());
                            merged.put(d.name(), data);
                        } finally {
                            permit.release();
                        }
                    } catch (Exception e) {
                        if (d.critical()) {
                            merged.put(d.name(), "error");
                        } else {
                            merged.put(d.name(), "placeholder");
                            degraded.add(d.name());
                        }
                    }
                    return null;
                }));
            }
            for (Future<?> f : futures) {
                f.get(450, TimeUnit.MILLISECONDS);
            }
        }
        long cost = System.currentTimeMillis() - start;
```
