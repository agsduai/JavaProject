# 第42章 可观测性平台

第41章让发布变成了日常，下一个问题是"出了事你怎么知道"。监控回答"有没有问题"，可观测性回答"为什么"：指标给你趋势与告警，日志给你细节与时间线，链路给你跨服务的完整旅程——三者靠 trace_id 串成一条证据链。本章按「可观测性总览 → 结构化日志 → 日志存储查询 → 指标模型 → 黄金指标与 SLO → 告警降噪 → 链路追踪 → 采样与成本 → 持续剖析 → 仪表盘与事故响应 → 事故复盘案例」的顺序讲。所有示例仍是纯 JDK：结构化日志真实输出，Histogram 分桶真实算分位数，Span 树真实构建并做慢链路归因，告警聚合抑制与事故时间线全部推演，不需要 Prometheus、ELK 或 SkyWalking。

### 42-01 为什么需要可观测性

**知识点**
- **监控回答"系统有没有问题"，可观测性回答"为什么有问题"**：监控是预设问题（CPU 高吗？错误率超了吗？），可观测性是任意问题的探索能力——出了事先看什么、能不能看出东西。**不预设问题也能排查，才是可观测**。
- **三支柱各管一层**：**指标（Metrics）**聚合数字，回答"系统整体健康吗"，便宜、快、适合告警；**日志（Logs）**离散事件明细，回答"当时发生了什么"，量大、可检索；**链路（Traces）**请求的跨服务路径，回答"慢在哪一跳、错在哪一步"。三者通过关联字段（trace_id）互相跳转。
- **白盒监控优于黑盒监控**：黑盒（从外部探测：接口 200 吗）只能告诉你"坏了"；白盒（内部暴露指标：队列堆积、缓存命中率）在用户感知前就告警。**好的监控体系黑白结合，以白盒为主**。
- **可观测性是设计出来的不是加出来的**：代码里埋点（关键路径打指标、异常带上下文日志、请求传递 trace_id）、中间件暴露指标、统一日志格式——**上线后再补可观测性，等于在运行的火车上装仪表盘**。
- **告警与排障的分层**：告警要少而准（对接值班），排障信息要多而全（对接排查）。**把告警当排障信息源用，值班人员会被淹死**——这是 42-06 的主题。
- **成本意识**：日志与链路是存储大户，采样与保留策略（42-08）从第一天就要设计。可观测性平台的成本随业务线性增长，不治理就是隐形的第二套核心系统。
- 易错点：只装了监控组件（Prometheus/ELK）没在代码里埋点（白盒能力为零）；三支柱数据无法关联（日志没带 trace_id，只能靠时间猜）；把"有 Grafana 面板"当成有可观测性（没人看的面板等于没有）；线上排障靠登录机器 grep（无结构化日志时唯一手段，说明平台缺位）。

```java
        }
```

### 42-02 结构化日志与采集管道

**知识点**
- **非结构化日志是可观测性的第一杀手**：`log.info("用户" + userId + "下单成功")` 人类能读，机器无法可靠解析——字段名漂移、格式随心情变。**结构化日志（JSON 每行一条）让日志变成可查询的数据**：字段固定、类型明确、可索引。
- **一条合格日志的字段骨架**：`timestamp`（毫秒级）、`level`（DEBUG/INFO/WARN/ERROR）、`service`、`trace_id`/`span_id`、`message`（人类可读的一句话）、业务上下文（userId/orderId）、异常堆栈（error 级）。**骨架全团队统一**，业务字段按需扩展。
- **级别的语义纪律**：ERROR 表示"需要人处理的异常"（打多了=狼来了）；WARN 表示"偏离预期但自动恢复"（重试成功、降级触发）；INFO 是关键业务事件（下单、支付、状态迁移）。**DEBUG 生产默认关闭，需要时动态开**（开关按请求灰度）。
- **采集管道的三段**：应用输出 stdout/文件 -> 采集器（Filebeat/Fluent Bit）转发 -> 中心化存储（ES/日志平台）。**应用不直接写中心**（网络抖动不应影响业务进程），本地缓冲 + 重试由采集器负责。
- **日志的上下文传播**：MDC（Mapped Diagnostic Context）把 trace_id/userId 放进线程上下文，日志框架每次输出自动带上——**避免每条日志手工拼**。跨线程（异步任务）要显式传递，漏传是 trace 断裂的常见原因。
- **敏感信息治理**：日志出现密码/token/身份证 = 合规事故。规范：脱敏注解统一处理、日志扫描工具进 CI（36 章的敏感信息检查在这里落地）。
- 易错点：循环里打 INFO（日志洪水）；异常被 catch 后只打 message 不打堆栈（排障断线索）；多行堆栈被采集器按行拆散（要配置多行合并）；日志级别全靠 System.out（无级别无格式不可采集）。

**示例代码**
```java
import java.time.Instant;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.UUID;

public class StructuredLogging {
    /** 极简结构化日志器：演示字段骨架与 MDC 思想 */
    static class Logger {
        final String service;

        Logger(String service) {
            this.service = service;
        }

        String format(String level, String message, Map<String, Object> ctx) {
            StringBuilder sb = new StringBuilder("{");
            sb.append("\"ts\":\"").append(Instant.now()).append("\",");
            sb.append("\"level\":\"").append(level).append("\",");
            sb.append("\"service\":\"").append(service).append("\",");
            sb.append("\"trace_id\":\"").append(MDC.get("trace_id")).append("\",");
            sb.append("\"message\":\"").append(message).append("\"");
            for (Map.Entry<String, Object> e : ctx.entrySet()) {
                sb.append(",\"").append(e.getKey()).append("\":\"").append(e.getValue()).append("\"");
            }
            return sb.append("}").toString();
        }

        void info(String message, Map<String, Object> ctx) {
            emit("INFO", message, ctx);
        }

        void error(String message, Exception e, Map<String, Object> ctx) {
            ctx.put("exception", e.getClass().getSimpleName());
            emit("ERROR", message, ctx);
        }

        private void emit(String level, String message, Map<String, Object> ctx) {
            System.out.println(format(level, message, ctx));
        }
    }

    /** 线程上下文（MDC 的思想）：trace_id 自动进每条日志 */
    static class MDC {
        static final ThreadLocal<String> CTX = new ThreadLocal<>();

        static void put(String key, String value) {
            if ("trace_id".equals(key)) {
                CTX.set(value);
            }
        }

        static String get(String key) {
            return "trace_id".equals(key) ? CTX.get() : null;
        }
    }

    static void goodVsBad() {
        System.out.println("【同一次下单：拼字符串 vs 结构化】");
        Logger log = new Logger("order-service");
        MDC.put("trace_id", UUID.randomUUID().toString().substring(0, 8));
        System.out.println("  反例：log.info(\"用户1001下单成功，订单号" + 9001 + "金额69.0\")");
        System.out.println("    -> 机器无法稳定提取 userId/orderId，换个人写法就变");
        Map<String, Object> ctx = new LinkedHashMap<>();
        ctx.put("userId", "1001");
        ctx.put("orderId", "9001");
        ctx.put("amount", "69.0");
        log.info("下单成功", ctx);
        System.out.println("  正例如上：字段固定，可按 userId/orderId 精确检索");
        System.out.println();
    }

    static void levelDiscipline() {
        System.out.println("【级别的语义：ERROR 是给值班看的】");
        record Event(String event, String level, String why) {
        }
        List<Event> events = List.of(
                new Event("支付回调验签失败", "ERROR", "资金相关，需要人工介入"),
                new Event("调用库存服务超时后重试成功", "WARN", "偏离预期但自愈"),
                new Event("订单创建", "INFO", "关键业务事件"),
                new Event("循环里的每条记录处理", "DEBUG", "生产默认关"));
        for (Event e : events) {
            System.out.printf("  %-16s %-5s %s%n", e.event(), e.level(), e.why());
        }
        System.out.println("  ERROR 频率应接近 0：日志告警群里 ERROR 刷屏 = 无人再看");
        System.out.println();
    }

    static void pipeline() {
        System.out.println("【采集管道：应用不直连中心】");
        List<String> path = List.of(
                "应用 -> stdout（容器环境）或滚动文件",
                "采集器（Filebeat/Fluent Bit）tail + 多行合并（堆栈成一条）",
                "本地缓冲队列：中心不可达时先落盘，恢复后重试",
                "中心存储（ES）按天索引，冷数据转归档");
        for (String s : path) {
            System.out.println("  " + s);
        }
        System.out.println("  应用进程只管快速写出（异步 appender），采集的可靠性归采集器");
    }

    public static void main(String[] args) {
        goodVsBad();
        levelDiscipline();
        pipeline();
    }
}
```

### 42-03 日志存储与查询

**知识点**
- **日志存储的核心矛盾是"量大与可查"**：一个中型服务一天几十亿条日志，全量存 ES 成本爆炸。**分层存储是标准解**：热数据（7~14 天，ES 可检索）、温数据（30~90 天，压缩归档可回捞）、冷数据（合规期，对象存储）。**保留期按排障真实需求定，不按"以防万一"定**。
- **索引按天滚动与查询路由**：`log-2026.11.17` 每天一个索引，查询带时间范围就只碰相关索引——**不带时间范围的日志查询是平台事故**（全索引扫描）。日志平台默认强制时间窗（如最多 7 天）。
- **日志查询的正确姿势**：先缩小范围（服务 + 时间窗 + level）再搜关键词；避免前置通配符（`*error`）；高频查询场景靠字段过滤而不是全文匹配。**让排障的人第一次查询就能命中，靠的是规范的字段而非搜索技巧**。
- **日志量的治理**：采样（DEBUG 按比例打）、聚合（循环日志合并成一条汇总）、分级开关（生产只 INFO+）。**日志量治理是成本工程**：一条日志的成本 = 写入 + 存储 + 索引 + 查询。
- **从日志到证据链**：排障时日志的价值在于"时间线重建"——同一 trace_id 的日志按时间排序就是一次请求的完整生命史；同一 orderId 跨天检索就是业务对象的变更史。**日志平台的导出与分享功能（永久链接）是协作的基础**。
- 易错点：日志量随业务增长没人管（成本失控）；堆栈多行被拆散导致检索出来的错误日志不可读；把日志平台当调试终端（DEBUG 全量开）；敏感字段明文入库（合规风险 + 泄露面扩大）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class LogStoreQuery {
    record LogEntry(String ts, String level, String service, String traceId,
                    String message, String hot) {
    }

    /** 模拟按天索引：查询只碰时间窗内的索引 */
    static List<String> dailyIndices(String from, String to) {
        List<String> all = List.of("log-2026.11.10", "log-2026.11.11", "log-2026.11.12",
                "log-2026.11.13", "log-2026.11.14", "log-2026.11.15", "log-2026.11.16",
                "log-2026.11.17");
        return all.stream().filter(idx -> {
            String day = idx.substring(4);
            return day.compareTo(from) >= 0 && day.compareTo(to) <= 0;
        }).toList();
    }

    static void tieredStorage() {
        System.out.println("【分层存储：热/温/冷的成本阶梯】");
        String[][] tiers = {
                {"热", "7~14 天", "ES 全文可检索", "最贵：副本+索引"},
                {"温", "30~90 天", "压缩归档，回捞分钟级", "中：对象存储"},
                {"冷", "合规期（如 1 年）", "不可检索，仅审计取证", "最便宜"},
        };
        for (String[] t : tiers) {
            System.out.printf("  %-3s 保留%-10s %-20s 成本=%s%n", t[0], t[1], t[2], t[3]);
        }
        System.out.println("  保留期依据：线上事故 90% 在 7 天内完成复盘 -> 热数据 14 天够用");
        System.out.println();
    }

    static void queryDiscipline() {
        System.out.println("【查询纪律：先收窄再搜索】");
        List<String> indices = dailyIndices("2026.11.15", "2026.11.17");
        System.out.printf("  时间窗 11.15~11.17 -> 只碰 %d 个索引（%s）%n",
                indices.size(), indices);
        String[][] queries = {
                {"service=order AND level=ERROR AND 关键词", "PASS：字段过滤先行"},
                {"*退款失败*", "FAIL：前置通配符全索引扫"},
                {"无时间范围 + 关键词", "FAIL：平台级事故，默认拒绝"},
        };
        for (String[] q : queries) {
            System.out.printf("  查询 %-32s %s%n", q[0], q[1]);
        }
        System.out.println();
    }

    static void timelineRebuild() {
        System.out.println("【时间线重建：trace_id 是排障的骨架】");
        List<LogEntry> logs = List.of(
                new LogEntry("10:00:00.101", "INFO", "gateway", "a1b2", "收到请求 POST /order", "热"),
                new LogEntry("10:00:00.105", "INFO", "order", "a1b2", "校验通过，扣库存", "热"),
                new LogEntry("10:00:00.900", "WARN", "stock", "a1b2", "库存服务超时，重试1", "热"),
                new LogEntry("10:00:01.100", "INFO", "stock", "a1b2", "重试成功", "热"),
                new LogEntry("10:00:01.120", "INFO", "order", "a1b2", "下单成功 9001", "热"));
        logs.stream().sorted(Comparator.comparing(LogEntry::ts))
                .forEach(l -> System.out.printf("  %s [%-5s] %-8s %s%n",
                        l.ts(), l.level(), l.service(), l.message()));
        System.out.println("  结论：stock 服务重试耗时 200ms，整体链路 1.019s —— 一目了然");
        System.out.println("  同一 trace_id 的日志 = 一次请求的完整生命史");
    }

    public static void main(String[] args) {
        tieredStorage();
        queryDiscipline();
        timelineRebuild();
    }
}
```

### 42-04 指标模型与时间序列

**知识点**
- **指标 = 时间序列 + 维度标签**：`http_server_requests_seconds{service="order",route="/order",version="2.4.1"}`。**维度（label）决定可切片性**：带 version 才能做金丝雀对比（41-07），带 route 才能定位慢接口。**维度基数是设计红线**：userId 做 label 会产生百万级序列，直接打爆存储（基数爆炸是监控平台的第一事故）。
- **四种指标类型**：Counter（只增计数：请求总数）、Gauge（瞬时值：连接池大小）、Histogram（分桶：延迟分布，算 P99）、Summary（客户端分位数，难聚合，少用）。**延迟必须用 Histogram**：跨实例聚合需要原始分桶。
- **P99 的正确理解**：99% 的请求比这快。它比平均值敏感（平均值掩盖长尾）、比 Max 稳定（Max 被单次 GC 抖动污染）。**观测长尾用 P99，抓极端异常看 P99.9 或 Max**。
- **采集模型：Pull vs Push**：Prometheus 拉模型（服务暴露 /metrics，Prometheus 定期抓，发现服务挂了=抓不到=up=0）；Push（StatsD/推网关，任务型短进程用）。**Pull 天然带健康检查语义**。
- **时间序列的降采样与聚合**：原始精度 15s 保留 30 天，5m 粒度保留 1 年（ Thanos/VictoriaMetrics 的分层）。查询时的 rate/increase 函数处理 Counter 的单调性（重启清零要用 clamp 处理）。
- **指标的命名纪律**：`<namespace>_<subsystem>_<name>_<unit>`（如 `http_request_duration_seconds`），单位进名字，复数不加。命名混乱的指标库半年后没人敢用。
- 易错点：userId/orderId 当 label（基数爆炸）；用平均值当 SLO（掩盖长尾）；Counter 直接画图忘记 rate（曲线只升不降没有信息量）；指标不带 service/version 标签（跨服务对比无从谈起）。

```java
    static double[] BUCKETS = {0.01, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10};

    static int bucketOf(double seconds) {
        for (int i = 0; i < BUCKETS.length; i++) {
            if (seconds <= BUCKETS[i]) {
                return i;
            }
        }
        return BUCKETS.length;   // +Inf

        double p99 = Double.NaN;
        for (int i = 0; i < counts.length; i++) {

        System.out.println("  分桶粒度决定分位数精度：桶太粗 P99 只能落在桶边界上");
        System.out.println("  聚合语义：先合并各实例的桶计数再算分位数（Summary 做不到）");
        System.out.println();
    }

    static void cardinalityDanger() {

        }
        System.out.println("  rate(2m) 曲线（每分钟增量≈120~180 QPS）才有波动信息");
```

### 42-05 黄金指标与 SLO

**知识点**
- **Google SRE 四大黄金信号**：**延迟**（多快，分成功/失败请求看）、**流量**（多少请求）、**错误**（多少失败）、**饱和度**（资源多满：CPU/内存/连接池/队列）。任何服务先补齐这四类指标再谈别的——**四信号覆盖 80% 的事故发现**。
- **SLI/SLO/SLA 的层级**：SLI 是指标（P99 延迟、成功率），SLO 是目标（P99 < 200ms 占 99.9%），SLA 是对外违约条款（SLO + 赔付）。**工程团队对 SLO 负责，商务对 SLA 负责**。
- **错误预算（error budget）是 SLO 的工程化表达**：SLO 99.9% = 每月 43 分钟不可用预算。预算花完 -> 冻结功能发布只修可靠性；预算充足 -> 可以激进发布。**错误预算把"稳定 vs 快速迭代"的争吵变成数字决策**。
- **SLO 要按用户体验定义而不是按机器定义**：用户关心"下单成功率"而不是"CPU<80%"。基础设施指标是原因，SLO 是结果——**告警挂在结果上，排障看原因**。
- **依赖服务的 SLO 传导**：你的服务依赖库存服务，它的 P99 800ms 会吃掉你的延迟预算。**依赖方的 SLO 是你 SLO 的输入**，跨团队 SLO 协议（谁对谁承诺什么）是微服务治理的一部分。
- **饱和度信号最有预见性**：连接池 85%、磁盘 80%、队列持续增长——这些信号在事故前就亮。**延迟/错误是事故本身，饱和度是事故的前兆**。
- 易错点：SLO 定 100%（不可能达成，告警必然误报）；SLO 只看平均值（掩盖长尾）；错误预算花完还继续冲需求（SLO 形同虚设）；每个指标都设告警（告警通胀，42-06 处理）。

### 42-06 告警设计与降噪

**知识点**
- **告警的第一原则：每一条告警都必须需要一个"人"采取行动**。发到群里没人处理的告警是噪音，噪音的累积效应是**告警疲劳**——真警报也被无视。宁可漏掉"可自愈的小事"，不可淹没"需要人的大事"。
- **告警的三级分类**：P1（用户受损，电话/短信，5 分钟响应）、P2（风险积累，IM 通知，30 分钟响应）、P3（提示观察，日报汇总）。**分级依据是用户影响面，不是技术惊悚程度**。
- **告警规则的正确形状**：`症状 + 持续时间 + 影响范围`。"P99 > 500ms" 不是告警，"P99 > 500ms 持续 5 分钟且影响下单主链路"才是。**瞬时抖动（GC、网络毛刺）用持续时间过滤**，机器周期性任务用时间窗屏蔽。
- **降噪三板斧**：**聚合**（同一事故的 30 条同源告警合并成 1 条事件，按根因分组）、**抑制**（DB 挂了 -> 抑制它下游全部服务的连接错误告警，只发根因）、**静默**（已知维护窗口、已知变更期间，人工静默并记录）。告警平台要支持抑制链与静默窗口，这是工具能力不是纪律问题。
- **自愈优于告警**：能自动恢复的（进程挂了拉起、主从切换、限流兜底）先自愈再告警"已自愈"（P3）。**值班名单里出现"重启一下就好"的告警，就是自动化欠账**。
- **告警闭环度量**：每条告警记录"是否有效"（真实故障/误报/已知问题），月度统计误报率与响应时长。**误报率 > 30% 的规则要么修要么删**。
- 易错点：一条规则告所有实例（实例越多告警越雪崩，应聚合到服务级）；把曲线抖动设成告警（没有持续时间条件）；告警直接发到没有响应责任的群（无 owner）；删掉烦人的告警而不是修好它（问题还在，只是没人看见了）。

### 42-07 分布式链路追踪

**知识点**
- **微服务排障的根本困难是"一个请求的真相散落在 N 个服务的日志里"**：链路追踪把一次请求经过的所有服务记录成一棵 **Span 树**——根 Span 是用户请求，子 Span 是各下游调用，每个 Span 带服务名、耗时、状态、标签。**Trace = 请求的完整旅程，Span = 旅程中的一段**。
- **上下文传播是追踪的地基**：入口生成 `trace_id` + `span_id`，每次下游调用把（trace_id, parent_span_id）放进 HTTP 头（W3C 标准头 `traceparent`）或 MQ 消息属性；服务端解析后继续生成子 span。**任何一环丢失传播（异步线程池、手写 HTTP 调用）就是链路断裂**，排查时只能靠时间猜。
- **Span 的关键标签**：`peer`（调了谁）、`status`（ok/error）、错误详情、以及业务标签（orderId）。**耗时 + 状态 + 关系**三要素让"慢在哪一跳、错在哪一步"变成一次查询。
- **追踪的价值场景**：慢请求定位（根 span 展开，最深的子 span 就是嫌疑人）、跨服务错误归属（哪层先抛的错）、容量分析（每个下游的扇出与扇入）、依赖地图（自动生成服务拓扑）。
- **埋点的三个层次**：自动探针（agent 字节码增强，零代码侵入，覆盖 JDBC/HTTP/Redis 客户端）、SDK 显式埋点（框架 hook，需要少量代码）、手工埋点（业务关键段）。**生产以自动探针为主 + 关键业务手工补充**。
- **追踪与日志/指标的联动**：Span 带上 trace_id 后，日志与指标都能按 trace 维度关联（42-01 的"通用钥匙"）。OpenTelemetry 正在统一三支柱的 API 与数据模型——**学概念比学具体组件重要，组件三年一换**。
- 易错点：只在 HTTP 层埋点，JDBC/Redis/MQ 这类"真正慢的地方"没覆盖；异步线程池丢上下文（trace 断裂）；Span 里塞大对象（一个 span 几 MB，存储爆炸）；每跳都建 span 但不打耗时标签（有结构没信息）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class TraceSpans {
    /** Span：一次请求中的一段工作 */
    record Span(String spanId, String parentSpanId, String service, String op,
                long startMs, long endMs, String status, String peer) {

        long costMs() {
            return endMs - startMs;
        }

        int depth() {
            int d = 0;
            String p = parentSpanId;
            // 本演示用简单缩进层级代替真实 parent 查找
            return d;
        }
    }

    static void buildTrace() {
        System.out.println("【一次下单请求的 Span 树】");
        List<Span> spans = List.of(
                new Span("s1", null, "gateway", "POST /order", 0, 1020, "ok", "-"),
                new Span("s2", "s1", "order", "createOrder", 5, 1010, "ok", "-"),
                new Span("s3", "s2", "order", "auth.check", 6, 12, "ok", "auth"),
                new Span("s4", "s2", "order", "db.insert", 13, 45, "ok", "mysql"),
                new Span("s5", "s2", "stock", "deduct", 46, 1000, "ok", "stock-rpc"),
                new Span("s6", "s5", "stock", "db.update", 50, 980, "ok", "mysql"));
        printTree(spans, null, 0);
        Span root = spans.get(0);
        System.out.printf("%n  总耗时 %dms，最深的子链：s5(stock.deduct %dms) -> s6(db.update %dms)%n",
                root.costMs(), spans.get(4).costMs(), spans.get(5).costMs());
        System.out.println("  结论：90% 的时间耗在库存服务的 DB 更新 —— 下一步优化方向明确");
        System.out.println();
    }

    private static void printTree(List<Span> spans, String parent, int indent) {
        for (Span s : spans) {
            if ((parent == null) == (s.parentSpanId() == null) && (parent == null || parent.equals(s.parentSpanId()))) {
                String tree = "  ".repeat(indent) + (indent > 0 ? "└─ " : "");
                System.out.printf("  %s%-10s %-16s %-12s %4dms [%s] peer=%s%n",
                        tree, s.service(), s.op(), s.spanId(), s.costMs(), s.status(), s.peer());
                printTree(spans, s.spanId(), indent + 1);
            }
        }
    }

    static void propagation() {
        System.out.println("【上下文传播：traceparent 头与断裂点】");
        String header = "traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01";
        System.out.println("  W3C 格式：" + header);
        System.out.println("  解析：version=00 trace_id=4bf9...4736 parent_span=00f0...02b7 flags=01");
        List<String> breakPoints = List.of(
                "异步线程池：Runnable 里直接执行 -> 上下文没拷贝 -> 断裂（用装饰器修复）",
                "手写 HttpClient：没把头复制进新请求 -> 断裂",
                "MQ 消费：生产者没写消息属性 -> 断裂",
                "定时任务入口：没有 trace -> 应新建根 span");
        for (String b : breakPoints) {
            System.out.println("  断裂点：" + b);
        }
        System.out.println();
    }

    static void whatTraceSolves() {
        System.out.println("【追踪解决的四个排障问题】");
        List<String> items = List.of(
                "慢请求：展开 span 树，最深子链即嫌疑人（本章示例：库存 DB）",
                "错误归属：从根到叶找第一个 error 状态的 span",
                "扇出分析：根 span 的直接子 span 数 = 每请求下游调用量",
                "依赖地图：按 (caller, callee) 聚合 span 自动生成拓扑");
        for (String s : items) {
            System.out.println("  - " + s);
        }
    }

    public static void main(String[] args) {
        buildTrace();
        propagation();
        whatTraceSolves();
    }
}
```

### 42-08 采样与链路成本

**知识点**
- **全量追踪的成本不可承受**：每个请求几十个 span、每天几十亿请求——全量存储的硬件成本超过业务本身。**采样是链路追踪的必备设计**，采样策略直接决定"你想抓的问题能不能抓到"。
- **头部采样（head sampling）**：入口处按概率决定整条链路是否记录（如 1%），实现简单、成本确定；缺点是**低频异常靠撞运气**——每秒 5 次的错误在 1% 采样下平均 20 秒才有一条。
- **尾部采样（tail sampling）**：请求结束后再决定是否保留，可以**按结果采样**——所有 error 100% 保留、慢请求（P99 以上）100% 保留、正常请求采样 1%。这是问题驱动的理想方案，代价是采集器要**缓存整条链路等它结束**（内存与延迟成本）。
- **两种策略组合是生产标准**：头部 10% 打底 + 尾部"error/慢请求全保"。**漏斗要和 SLO 对齐**：你承诺 P99<300ms，那 >300ms 的请求就该全保留。
- **采样的代价意识**：span 的存储量 = QPS × span 数 × 采样率 × 平均大小。降本的杠杆按大到小：降采样率 > 减 span 数（合并客户端 span）> 压缩。**保留期一般 7~14 天**（与日志同步）。
- **采样影响统计正确性**：1% 采样的 P99 统计不可信（样本太少）。原则：**指标从全量数据算（Prometheus 抓取不分采样），采样只影响"链路明细"的保留**。两者混用是常见误用。
- 易错点：全量追踪直接上生产（成本爆炸）；只配了头部采样导致排查"偶发 500"无链路可看；尾部采样缓存队列被打爆（高流量时 OOM）；把采样率当 SLO 统计口径（统计失真）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;
import java.util.Random;

public class TraceSampling {
    record Request(String id, int costMs, boolean error, boolean keep) {
    }

    static void headVsTail() {
        System.out.println("【头部 10% vs 尾部按结果：同样 20 个请求的保留差异】");
        List<Request> reqs = new ArrayList<>();
        Random r = new Random(42);
        for (int i = 0; i < 20; i++) {
            int cost = i == 7 ? 850 : 80 + r.nextInt(150);
            boolean err = i == 11;
            reqs.add(new Request("r" + i, cost, err, false));
        }
        int headKept = 0;
        for (Request req : reqs) {
            boolean keep = r.nextInt(100) < 10;
            if (keep) {
                headKept++;
            }
        }
        int tailKept = 0;
        for (Request req : reqs) {
            boolean keep = req.error() || req.costMs() > 300;
            if (keep) {
                tailKept++;
            }
            reqs.set(reqs.indexOf(req), new Request(req.id(), req.costMs(), req.error(), keep));
        }
        System.out.printf("  头部采样 10%%：保留 %d 条（随机，错误 r11 大概率丢失）%n", headKept);
        System.out.println("  尾部采样（error 全保 + >300ms 全保）：");
        for (Request req : reqs) {
            if (req.keep()) {
                System.out.printf("    保留 %s cost=%dms error=%s%n",
                        req.id(), req.costMs(), req.error());
            }
        }
        System.out.println("  你要抓的问题（偶发错误、慢请求）100% 在保留集合里");
        System.out.println();
    }

    static void costModel() {
        System.out.println("【成本模型：QPS × span数 × 采样率 × 大小】");
        long qps = 2000, spansPerReq = 30;
        double sampleRate = 0.01;
        long dailySpans = Math.round(qps * 86400 * spansPerReq * sampleRate);
        long dailyGb = dailySpans * 512 / 1024 / 1024 / 1024;
        System.out.printf("  QPS=%d, span/请求=%d, 采样 1%%%n", qps, spansPerReq);
        System.out.printf("  每日 span 数 ≈ %d 亿条级 -> 存储约 %d GB/天（按 512B/span）%n",
                dailySpans / 100_000_000, dailyGb);
        System.out.println("  降本杠杆：采样 1%->0.5% 减半；合并客户端 span 减 span 数；保留期 14d->7d 减半");
        System.out.println();
    }

    static void statsIntegrity() {
        System.out.println("【采样与统计的正确边界】");
        List<String> rules = List.of(
                "指标（QPS/P99/错误率）：从全量请求算，不经过采样",
                "链路明细：按策略采样，用于个案排查",
                "错误率告警如果基于采样数据 -> 统计失真，绝对禁止",
                "尾部采样的缓存队列要有上限与降级（超限退回头部采样）");
        for (String s : rules) {
            System.out.println("  - " + s);
        }
    }

    public static void main(String[] args) {
        headVsTail();
        costModel();
        statsIntegrity();
    }
}
```

### 42-09 持续剖析与资源画像

**知识点**
- **指标告诉你 CPU 高了，Profile 告诉你 CPU 在干什么**：持续剖析（continuous profiling）周期性采集进程的调用栈样本（CPU、内存分配、锁等待、IO），聚合成火焰图。**它是"指标 -> 代码行"的最后一跳**，与第 30 章 JVM 工具（jstack 一次性快照）的区别在于持续与聚合。
- **火焰图的读法**：横轴是 CPU 时间占比（越宽越热），纵轴是调用栈深度（上层的由下层调用）。**找宽的平顶**——又宽又不能继续展开的帧就是热点。采样型 profiler 开销 1~2%，可常驻生产。
- **四类剖析各有用途**：CPU profile（热点函数、正则灾难、JSON 序列化）、alloc profile（内存分配大户，GC 压力来源）、block/lock profile（锁竞争）、off-CPU（等待 IO）。**"CPU 不高但慢"的谜题通常在 off-CPU profile 里解开**。
- **持续剖析的服务形态**：agent 常驻采集（每 10~60s 一轮）-> 上报到剖析平台 -> 按服务/时间/版本聚合对比。**版本对比（diff 火焰图）是发布验证利器**：2.4.0 vs 2.4.1 的 CPU 热点变化一眼可见。
- **与指标的联动**：CPU 饱和度告警触发 -> 平台自动拉取该时段 CPU profile -> 热点函数直出。**告警到根因的自动化路径**是可观测性平台的进阶形态。
- **Go/Java 的生态差异**：Go 的 pprof 是标杆（低成本常驻）；Java 主流是 async-profiler（event-based，低开销）+ JFR（JDK 自带，持续记录）。JFR 是 Java 团队的默认起点——**JDK 21 的 JFR 已经能覆盖 CPU/alloc/lock 全场景**。
- 易错点：只在出事时 attach 工具（错过现场，CPU 尖峰是瞬时的）；采样 profiler 与侵入式 tracer 混淆（前者低开销可常驻）；只看 CPU profile 忽略 alloc（很多"GC 频繁"的真凶是某个函数狂分配）；火焰图存档不保留（没法做版本对比）。

**示例代码**

### 42-10 仪表盘与事故响应

**知识点**
- **仪表盘是"为回答具体问题"而生的**：一张图回答一个问题——"服务整体健康吗"（服务总览）、"下单链路哪一环慢"（链路视图）、"这次发布效果如何"（版本对比）。**没有问题的仪表盘是装饰**，团队仪表盘数量应少于团队人数。
- **服务总览页的标准结构**：顶部 SLO 状态灯（绿/黄/红）+ 错误预算剩余 -> 中部黄金四信号（延迟/流量/错误/饱和度）-> 底部依赖健康。**30 秒内让人判断"要不要介入"**。
- **告警 -> 仪表盘 -> 排障的动线**：告警卡片带跳转链接（直达相关仪表盘与日志查询）——事故响应的每一步都不应手工找入口。**响应速度是动线设计的函数**。
- **事故响应的角色分工**：指挥（IC）统筹决策、通信（CL）对外同步、操作（OML）执行处置。**小团队可以一人分饰，但角色不能缺**——没有指挥的事故响应就是一群人各自为战。
- **响应的时间纪律**：确认（ack）< 5 分钟、初步定级 < 10 分钟、对外同步每 15 分钟一次（哪怕"仍在排查"）。**沉默的值班比故障本身更伤信任**。
- **复盘（postmortem）是无责文化下的改进引擎**：时间线（告警->响应->恢复）、根因链（为什么告警晚了/恢复慢了）、改进项（带负责人与期限）。**改进行动落在系统上而非"下次注意"上**——与第 41 章的发布演练、本章的告警闭环衔接。
- 易错点：仪表盘堆满 30 张图（没人看得过来）；告警不带跳转链接（响应从"找入口"开始）；事故期间全员围观不改代码却没人对外同步；复盘变成追责会（下次没人敢上报问题）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class DashboardIncident {
    record Panel(String question, String charts, String source) {
    }

    static void dashboardDesign() {
        System.out.println("【order 服务的三张仪表盘】");
        List<Panel> panels = List.of(
                new Panel("服务整体健康吗？",
                        "SLO 状态灯 + 预算余额 + 四信号 + 依赖健康", "服务总览（值班首屏）"),
                new Panel("下单链路哪一环慢？",
                        "链路各跳 P99 柱状对比 + 慢请求 trace 抽样", "链路视图"),
                new Panel("这次发布效果如何？",
```

### 42-11 综合案例：一次线上事故的可观测复盘

**知识点**
- **用三支柱 + 剖析完整复盘一次真实形态的事故**：大促期间下单 P99 从 180ms 涨到 2.1s、错误率 0.3%->4%。按"告警 -> 指标定位 -> 日志收窄 -> 链路锁定 -> 剖析定根因 -> 修复 -> 复盘改进"的完整路径走一遍，**本章之前每一课的工具都在这条路径上各就各位**。
- **指标层的判断**：错误率与延迟同时劣化但 CPU 正常 -> 排除容量问题；按 route 维度切片 -> 只有 /order 劣化；按 version 维度 -> 新旧版本都慢 -> **排除新版本引入**（版本维度指标在 41-07 埋下的价值）。方向收敛到"共享下游"。
- **日志层的收窄**：按 trace_id 抽慢请求 -> 顶部模式是 stock 服务 db.update 慢；按 orderId 聚合 -> 慢请求集中在"秒杀商品"。**日志的分组统计（而非逐条阅读）给出模式**。
- **链路层的锁定**：慢 trace 的 span 树显示 stock.deduct 内 db.update 占 92%；对比正常 trace -> SQL 形态差异（`SELECT ... FOR UPDATE` 的行锁竞争）。
- **剖析层的根因**：JFR/锁剖析显示热点在单行 update；结合 DB 侧 `SHOW PROCESSLIST` -> **热点行锁**：秒杀商品的库存行被全部请求串行竞争。第 32 章（CAS 预扣）与第 39 章（分片）的方案在此会师。
- **复盘产出**：改进项落在系统——库存扣减改 Redis 预扣（第 32 章方案）、慢 SQL 进 CI 检查、连接池饱和度告警提前、大促预案增加热点商品压测。**一次事故让整个可观测与架构体系进化一档**。
- 易错点：复盘只写"库存服务慢了"没有根因链（下次复发）；修复只改现象（加超时）不改结构（行锁竞争仍在）；事故期间先优化后恢复（正确顺序：先恢复业务——切流/降级，再优化）。
