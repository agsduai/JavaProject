# 第78章 事件驱动架构与事务消息

当系统从"调用"转向"通知"，解耦与削峰的红利背后是一整套一致性工程：消息不能丢、不能重、不能乱、失败能补偿。本章按「RPC到事件驱动 → 事务消息与本地消息表 → 幂等消费 → 顺序与分区键 → 事件溯源与CQRS → Saga与补偿 → Schema演进 → 死信与积压 → 可观测性 → 事件治理 → 订单履约案例」的顺序讲。所有示例仍是纯 JDK：同步/异步链路对比、Outbox崩溃恢复、去重表四场景、分区有序与队头阻塞、乐观并发与投影重放、反序补偿、跨版本事件兼容、指数退避与DLQ、trace跨生产消费、事件目录校验、履约状态机全部真实运行。

### 78-01 从 RPC 到事件驱动

**知识点**
- **同步 RPC 的耦合**：**调用方必须知道被调方地址、接口、超时**，**被调方故障会直接拖垮调用方**，**链式调用放大延迟与失败率**——**这就是"下单要等积分、短信、推荐全部成功"的痛点**。
- **事件驱动的本质：把"调用"换成"事实通知"**——**生产者只发布"发生了什么"（OrderCreated）**，**消费者各自订阅、各自处理**，**生产者不关心谁消费、消费多久**。
- **三个收益**：**解耦**（新增消费者不改生产者）、**削峰**（事件排队，消费者按能力处理 43 章）、**最终一致**（先落库再异步推进）——**代价是"一致性延迟"与"链路可观测性变难"**（78-09）。
- **什么时候不该用**：**需要强一致/即时返回**（支付扣款结果）、**调用链很短**（多一层 MQ 反而增加复杂度）、**团队没有事件治理能力**（事件散落、无人负责 78-10）。
- 与 28 章的关系：28 章讲"消息队列的确认/重试/死信"，**本章讲"把消息队列用成架构模式"**——**从工具到设计**。
- 易错点：所有调用都改事件（简单查询也异步）；事件里塞全量数据（变成"大对象传输"）；没有事件契约（78-07）；以为"发了事件就一定被消费"（至少一次 + 幂等 78-03）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class EventDrivenOverview {
    record Step(String service, String action, long latencyMs, boolean required) {
    }

    record Event(String type, String payload, long producedAt) {
    }

    static void syncChain() {
        System.out.println("【同步 RPC：下单链路】");
        List<Step> chain = List.of(
                new Step("订单服务", "创建订单", 30, true),
                new Step("库存服务", "扣减库存", 40, true),
                new Step("积分服务", "增加积分", 20, false),
                new Step("短信服务", "发送通知", 80, false),
                new Step("推荐服务", "更新画像", 60, false));
        long total = 0;
        double success = 1.0;
        for (Step s : chain) {
            total += s.latencyMs();
            success *= 0.995;
            System.out.printf("  -> %-8s %-10s %3dms%s%n", s.service(), s.action(),
                    s.latencyMs(), s.required() ? "（强依赖）" : "（弱依赖）");
        }
        System.out.printf("  总延迟=%dms，链路成功率≈%.1f%%%n", total, success * 100);
        System.out.println("  任一弱依赖变慢/失败，都会拖累下单");
        System.out.println();
    }

    static void eventChain() {
        System.out.println("【事件驱动：下单只做两件事】");
        List<Event> events = new ArrayList<>();
        long now = System.currentTimeMillis();
        events.add(new Event("OrderCreated", "order-1001", now));
        System.out.println("  订单服务：本地事务写订单 + outbox（78-02）");
        System.out.printf("  发布事件：%s%n", events.get(0));

        Map<String, Long> consumerLatency = new LinkedHashMap<>();
        consumerLatency.put("库存服务", 40L);
        consumerLatency.put("积分服务", 20L);
        consumerLatency.put("短信服务", 80L);
        consumerLatency.put("推荐服务", 60L);
        long max = 0;
        for (Map.Entry<String, Long> e : consumerLatency.entrySet()) {
            max = Math.max(max, e.getValue());
            System.out.printf("  <- %-8s 异步消费 %-10s %3dms%n",
                    e.getKey(), "OrderCreated", e.getValue());
        }
        System.out.printf("  下单接口只等本地事务（约 30ms），最慢消费者 %dms 不影响返回%n", max);
        System.out.println();
    }

    static void comparison() {
        System.out.println("【对比】");
        String[][] rows = {
                {"耦合", "调用方依赖被调方接口", "只依赖事件契约"},
                {"失败影响", "弱依赖失败拖垮主链路", "消费者失败不影响生产者"},
                {"延迟", "链式累加", "主链路只等本地事务"},
                {"一致性", "强一致（同事务）", "最终一致（延迟）"},
                {"可观测", "调用链清晰", "需 trace 串联（78-09）"},
                {"复杂度", "低", "高（幂等/顺序/治理）"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-10s RPC=%-24s 事件=%s%n", r[0], r[1], r[2]);
        }
        System.out.println();
    }

    public static void main(String[] args) {
        syncChain();
        eventChain();
        comparison();
        System.out.println("【结论】核心交易走同步，周边动作走事件；事件不是免费的解耦");
    }
}
```

### 78-02 事务消息与本地消息表

**知识点**
- **"先写库再发消息"的经典 bug**：**写库成功、发消息失败** -> 下游永远不知道；**先发消息再写库** -> 消息发了但库回滚 -> 下游处理了不存在的数据——**两个操作不在一个事务里，必然有窗口**。
- **本地消息表（Outbox）**：**业务数据和消息记录在同一个本地事务里落库**，**再由后台 relay 轮询未发送消息投递 MQ**——**原子性由本地事务保证，投递由 relay 保证（至少一次）**。
- **事务消息（RocketMQ 风格）**：**先发 half message（对消费者不可见）-> 执行本地事务 -> commit/rollback**；**若 commit 丢失，Broker 回查生产者**——**本质也是"两阶段 + 回查"**。
- **relay 的三个要点**：**按 id 顺序发送**（同聚合保序 78-04）、**发送成功才标记**（至少一次）、**失败重试 + 死信**（78-08）——**消费者必须幂等**（78-03）。
- 与 45 章的关系：45 章的"分布式共识"解决"多副本一致"，**Outbox 解决"本地事务与消息的一致"**——**一个对内，一个对外**。
- 易错点：业务与消息分两个事务（窗口）；relay 先标记后发送（丢消息）；不清理已发送记录（表膨胀）；消费者不幂等（重复投递出问题）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class TransactionalOutbox {
    record Order(long id, String status) {
    }

    static class OutboxEvent {
        final long id;
        final long orderId;
        final String type;
        final String payload;
        boolean sent;

        OutboxEvent(long id, long orderId, String type, String payload) {
            this.id = id;
            this.orderId = orderId;
            this.type = type;
            this.payload = payload;
        }

        @Override
        public String toString() {
            return "OutboxEvent{id=" + id + ", order=" + orderId + ", type=" + type
                    + ", sent=" + sent + "}";
        }
    }

    static final Map<Long, Order> orders = new LinkedHashMap<>();
    static final List<OutboxEvent> outbox = new ArrayList<>();
    static long nextEventId = 1;

    /** 本地事务：订单 + outbox 一起提交（要么都成功，要么都回滚） */
    static void createOrder(long orderId) {
        orders.put(orderId, new Order(orderId, "CREATED"));
        outbox.add(new OutboxEvent(nextEventId++, orderId, "OrderCreated",
                "{\"orderId\":" + orderId + "}"));
        System.out.printf("  本地事务提交：order=%d + outbox=%d%n", orderId,
                outbox.get(outbox.size() - 1).id);
    }

    /** relay：扫描未发送事件，投递并标记（至少一次） */
    static int relay(String phase) {
        int sent = 0;
        for (OutboxEvent e : outbox) {
            if (!e.sent) {
                // 模拟投递 MQ
                System.out.printf("  [%s] 投递事件 #%d %s -> MQ%n", phase, e.id, e.type);
                e.sent = true;
                sent++;
            }
        }
        System.out.printf("  [%s] 本轮投递 %d 条%n", phase, sent);
        return sent;
    }

    public static void main(String[] args) {
        System.out.println("【正常路径】");
        createOrder(1001);
        relay("relay-1");

        System.out.println();
        System.out.println("【故障：本地事务提交后、relay 之前进程崩溃】");
        createOrder(1002);
        System.out.println("  *** 崩溃，outbox #2 未发送 ***");
        System.out.println("  outbox 现状：" + outbox);

        System.out.println();
        System.out.println("【重启：relay 从数据库恢复未发送事件】");
        relay("relay-restart");

        System.out.println();
        System.out.println("【重复投递（至少一次语义）】");
        outbox.get(1).sent = false;                 // 模拟标记丢失
        relay("relay-retry");
        System.out.println("  消费者会收到重复事件 -> 必须幂等（78-03）");

        System.out.println();
        System.out.println("【最终状态】");
        orders.forEach((id, o) -> System.out.println("  " + o));
        outbox.forEach(e -> System.out.println("  " + e));

        System.out.println();
        System.out.println("【要点】同库同事务写 outbox；relay 至少一次；消费者幂等；定期清理已发送");
    }
}
```

### 78-03 幂等消费与去重

**知识点**
- **至少一次投递 = 必然重复**：**网络超时、ack 丢失、relay 重试**都会导致同一条消息被消费多次——**幂等不是可选项，是事件驱动的前提**。
- **幂等的三种实现**：**去重表**（msgId 唯一索引，处理前插入）、**状态机**（只允许合法状态迁移，重复事件自然被忽略）、**业务唯一键**（订单号 + 操作类型做唯一约束）——**按场景选，最稳的是"去重表 + 状态机"双保险**。
- **并发重复**：两个消费者同时收到同一 msgId，**去重表要能"抢占"**（唯一索引插入成功者处理，失败者等待/跳过）——**先插入再处理，而不是先处理后插入**。
- **处理失败与去重记录**：**处理失败要删去重记录或标记失败**（否则重试被误判为重复）——**"处理中"状态要有超时兜底**。
- 与 39 章的关系：39 章的"接口幂等"用幂等键，**消息幂等用 msgId/业务键**——**同一种思想，不同的入口**。
- 易错点：先处理再记去重（并发重复）；失败也留在去重表（重试被吞）；只靠内存 Set（重启丢失）；去重表不清理（无限增长）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class IdempotentConsumer {
    enum State { PROCESSING, DONE, FAILED }

    record Message(String msgId, String orderId, double amount) {
    }

    static final Map<String, State> dedup = new LinkedHashMap<>();
    static final Map<String, String> results = new LinkedHashMap<>();
    static int processed;

    /** 消费：先占位（插入去重记录），再处理 */
    static String consume(Message msg) {
        State existing = dedup.get(msg.msgId());
        if (existing == State.DONE) {
            System.out.printf("  重复消息 %s -> 直接返回缓存结果%n", msg.msgId());
            return results.get(msg.msgId());
        }
        if (existing == State.PROCESSING) {
            System.out.printf("  并发重复 %s -> 拒绝（另一个消费者处理中）%n", msg.msgId());
            return "SKIP";
        }
        if (existing == State.FAILED) {
            System.out.printf("  上次失败 %s -> 允许重试%n", msg.msgId());
        }

        dedup.put(msg.msgId(), State.PROCESSING);
        try {
            String result = doProcess(msg);
            dedup.put(msg.msgId(), State.DONE);
            results.put(msg.msgId(), result);
            processed++;
            return result;
        } catch (RuntimeException e) {
            dedup.put(msg.msgId(), State.FAILED);
            System.out.println("  处理失败：" + e.getMessage());
            return "FAILED";
        }
    }

    static String doProcess(Message msg) {
        if (msg.amount() < 0) {
            throw new IllegalArgumentException("金额非法");
        }
        System.out.printf("  处理消息 %s：订单 %s 增加积分 %.1f%n",
                msg.msgId(), msg.orderId(), msg.amount());
        return "POINTS+" + msg.amount();
    }

    public static void main(String[] args) {
        Message m1 = new Message("msg-1", "order-1001", 10.0);

        System.out.println("【首次消费】");
        System.out.println("  结果：" + consume(m1));

        System.out.println();
        System.out.println("【重复投递（ack 丢失）】");
        System.out.println("  结果：" + consume(m1));
        System.out.println("  实际业务处理次数：" + processed);

        System.out.println();
        System.out.println("【并发重复：第二个消费者先看到 PROCESSING】");
        dedup.put("msg-2", State.PROCESSING);
        System.out.println("  结果：" + consume(new Message("msg-2", "order-1002", 5.0)));

        System.out.println();
        System.out.println("【处理失败后重试】");
        Message bad = new Message("msg-3", "order-1003", -1);
        System.out.println("  第一次：" + consume(bad));
        System.out.println("  修复后重试：" + consume(new Message("msg-3", "order-1003", 8.0)));

        System.out.println();
        System.out.println("【去重表】");
        dedup.forEach((k, v) -> System.out.printf("  %-8s %s%n", k, v));
        System.out.println("  生产：msgId 唯一索引 + 状态超时回收 + 定期归档");

        System.out.println();
        System.out.println("【三种幂等方式】去重表 / 状态机 / 业务唯一键；并发场景要「先占位」");
    }
}
```

### 78-04 顺序消息与分区键

**知识点**
- **顺序的两种语义**：**全局有序**（所有消息一个队列，吞吐受限）与**分区有序**（同一 key 进同一分区，分区内 FIFO）——**绝大多数业务只需要"同一订单/同一用户有序"**。
- **分区键的选择**：**用业务聚合根 ID**（orderId/userId）做 key，**保证同一聚合的事件进同一分区**；**不要用随机 key**（顺序丢失）、**不要用热点 key**（分区倾斜）。
- **顺序与重试的冲突**：**分区内某条消息失败，后面的消息必须等待**（否则乱序）——**这就是队头阻塞（head-of-line blocking）**；**对策：失败快速转死信/暂停分区**（78-08）。
- **顺序与并发的权衡**：**同一 key 串行、不同 key 并行**——**分区数决定最大并行度**，**key 的基数决定倾斜程度**。
- 与 62 章的关系：62 章讲 Kafka"按 key 分区保序"的存储原理，**本章讲"业务上怎么选 key、怎么处理失败"**。
- 易错点：用随机/时间做 key（同一订单分散）；失败无限重试（阻塞整个分区）；分区数太少（并行度不足）；分区数太多（顺序保障变弱、管理成本高）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

public class OrderedMessaging {
    static final int PARTITIONS = 3;
    static final Map<Integer, List<String>> queues = new LinkedHashMap<>();
    static final Map<Integer, Integer> offsets = new LinkedHashMap<>();
    static final Set<String> failing = new LinkedHashSet<>();
    static final Map<String, Integer> attempts = new LinkedHashMap<>();

    static {
        for (int p = 0; p < PARTITIONS; p++) {
            queues.put(p, new ArrayList<>());
            offsets.put(p, 0);
        }
    }

    static int partitionOf(String key) {
        return Math.floorMod(key.hashCode(), PARTITIONS);
    }

    static void produce(String key, String msg) {
        int p = partitionOf(key);
        queues.get(p).add(msg);
        System.out.printf("  生产 key=%-8s -> 分区 %d：%s%n", key, p, msg);
    }

    /** 消费一个分区：遇到失败消息则阻塞（保序） */
    static void drain(int p) {
        List<String> q = queues.get(p);
        int off = offsets.get(p);
        while (off < q.size()) {
            String msg = q.get(off);
            if (failing.contains(msg)) {
                int n = attempts.merge(msg, 1, Integer::sum);
                System.out.printf("  分区 %d 队头 %s 失败（第 %d 次）-> 阻塞，后续消息等待%n",
                        p, msg, n);
                return;
            }
            System.out.printf("  分区 %d 消费 offset=%d：%s%n", p, off, msg);
            off++;
            offsets.put(p, off);
        }
        System.out.printf("  分区 %d 已清空%n", p);
    }

    public static void main(String[] args) {
        System.out.println("【生产：同一订单的事件进同一分区】");
        produce("order-1", "OrderCreated");
        produce("order-1", "OrderPaid");
        produce("order-1", "OrderShipped");
        produce("order-2", "OrderCreated");
        produce("order-2", "OrderPaid");
        produce("order-3", "OrderCreated");

        System.out.println();
        System.out.println("  分区分布：" + queues);

        System.out.println();
        System.out.println("【正常消费】");
        for (int p = 0; p < PARTITIONS; p++) {
            System.out.println("  -- 分区 " + p);
            drain(p);
        }

        System.out.println();
        System.out.println("【故障：order-1 的 OrderPaid 处理失败】");
        produce("order-1", "OrderRefunded");
        String bad = "OrderPaid";
        // 重置 offset 模拟重放
        int p1 = partitionOf("order-1");
        offsets.put(p1, 0);
        queues.get(p1).clear();
        queues.get(p1).addAll(List.of("OrderCreated", "OrderPaid", "OrderShipped", "OrderRefunded"));
        failing.add(bad);

        drain(p1);
        System.out.println("  -> 分区 " + p1 + " 卡在 OrderPaid，OrderShipped/Refunded 都不能处理");
        System.out.println("     （保序的代价：队头阻塞）");

        System.out.println();
        System.out.println("【其他分区不受影响】");
        produce("order-2", "OrderCompleted");
        drain(partitionOf("order-2"));

        System.out.println();
        System.out.println("【处理方案】失败消息转死信（78-08）或暂停分区人工介入，不能跳过");
```

### 78-05 事件溯源与 CQRS

**知识点**
- **事件溯源（Event Sourcing）**：**不存当前状态，只存状态变化的事件流**——**状态 = 事件回放**；**审计天然完整、可重建任意时点快照**（45-02 的 MVCC 思想在业务层的版本）。
- **事件存储的三个要求**：**只追加**（append-only）、**按聚合 ID 有序**（version 递增）、**乐观并发**（expectedVersion 冲突检测）——**不能更新/删除事件，只能追加补偿事件**。
- **CQRS（命令查询职责分离）**：**写侧走事件流**（命令 -> 事件），**读侧走投影**（事件 -> 读模型）——**读写模型可以不同**（写侧规范、读侧为查询优化）。
- **投影（Projection）**：**订阅事件更新读模型**，**可重放重建**（改了读模型逻辑就重放）；**投影要幂等**（78-03），**位点要持久化**（从哪继续）。
- 与 49 章的关系：49 章 DDD 的"聚合/领域事件"是事件溯源的基础，**本章把"领域事件"变成"唯一事实来源"**。
- 易错点：事件里塞"当前全量状态"（失去溯源意义）；允许修改历史事件；投影与事件不在同一事务（最终一致，可接受但要知道）；不存 version（并发写覆盖）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class EventSourcingCqrs {
    record Event(long orderId, int version, String type, double amount) {
    }

    static final Map<Long, List<Event>> eventStore = new LinkedHashMap<>();
    static final Map<Long, Double> readModel = new LinkedHashMap<>();   // 订单总额投影

    /** 追加事件：乐观并发（expectedVersion） */
    static boolean append(long orderId, int expectedVersion, String type, double amount) {
        List<Event> stream = eventStore.computeIfAbsent(orderId, k -> new ArrayList<>());
        int current = stream.size();
        if (current != expectedVersion) {
            System.out.printf("  并发冲突：order=%d 期望版本 %d，实际 %d%n",
                    orderId, expectedVersion, current);
            return false;
        }
        Event e = new Event(orderId, current + 1, type, amount);
        stream.add(e);
        System.out.printf("  追加事件 order=%d v%d %s %.2f%n",
                orderId, e.version(), e.type(), e.amount());
        project(e);
        return true;
    }

    /** 投影：事件 -> 读模型（幂等：按 version 去重） */
    static void project(Event e) {
        List<Event> stream = eventStore.get(e.orderId());
        // 简化：只处理最新版本，重复事件直接忽略
        if (e.version() != stream.size()) {
            return;
        }
        double total = readModel.getOrDefault(e.orderId(), 0.0);
        switch (e.type()) {
            case "OrderCreated" -> total = 0;
            case "ItemAdded" -> total += e.amount();
            case "ItemRemoved" -> total -= e.amount();
            case "OrderCancelled" -> total = 0;
            default -> { }
        }
        readModel.put(e.orderId(), total);
    }

    /** 回放聚合：从事件流重建状态 */
    static Map<String, Object> rebuild(long orderId) {
        List<Event> stream = eventStore.getOrDefault(orderId, List.of());
        double total = 0;
        String status = "NEW";
        int items = 0;
        for (Event e : stream) {
            switch (e.type()) {
                case "OrderCreated" -> status = "CREATED";
                case "ItemAdded" -> {
                    total += e.amount();
                    items++;
                }
                case "ItemRemoved" -> {
                    total -= e.amount();
                    items--;
                }
                case "OrderCancelled" -> status = "CANCELLED";
                default -> { }
            }
        }
        Map<String, Object> state = new LinkedHashMap<>();
        state.put("orderId", orderId);
        state.put("status", status);
        state.put("items", items);
        state.put("total", total);
        state.put("version", stream.size());
        return state;
    }

    public static void main(String[] args) {
        System.out.println("【命令 -> 事件】");
        append(1001, 0, "OrderCreated", 0);
        append(1001, 1, "ItemAdded", 69.0);
        append(1001, 2, "ItemAdded", 129.0);
        append(1001, 3, "ItemRemoved", 69.0);
        append(1002, 0, "OrderCreated", 0);
        append(1002, 1, "ItemAdded", 199.0);
        append(1002, 2, "OrderCancelled", 0);

        System.out.println();
        System.out.println("【乐观并发：两个客户端同时基于 v4 追加】");
        append(1001, 4, "ItemAdded", 10.0);
        append(1001, 4, "ItemAdded", 20.0);          // 第二个冲突

        System.out.println();
        System.out.println("【事件流（唯一事实来源）】");
        eventStore.forEach((id, list) -> {
            System.out.println("  order " + id + "：");
            list.forEach(e -> System.out.printf("    v%d %-14s %.2f%n",
                    e.version(), e.type(), e.amount()));
        });

        System.out.println();
        System.out.println("【读模型（投影）】");
        readModel.forEach((id, total) -> System.out.printf("  order %d 总额=%.2f%n", id, total));

        System.out.println();
        System.out.println("【回放重建聚合状态】");
        eventStore.keySet().forEach(id -> System.out.println("  " + rebuild(id)));

        System.out.println();
        System.out.println("【要点】只追加 + version 乐观锁 + 投影幂等 + 可重放；事件不可改，只能补偿");
    }
}
```

### 78-06 Saga 与补偿事务

**知识点**
- **Saga 解决"跨服务长事务"**：**把大事务拆成 N 个本地事务**，**每步成功发布事件/调用下一步**，**任一步失败就按反序执行补偿**——**没有全局锁，只有最终一致**。
- **两种编排方式**：**协同（Choreography）**（服务间互相订阅事件，无中心）与**编排（Orchestration）**（一个 Saga 协调器按状态机驱动）——**复杂流程用编排，简单流程用协同**。
- **补偿的三个坑**：**空补偿**（补偿一个没执行成功的步骤）、**悬挂**（补偿先到、原操作后到）、**重复补偿**（幂等）——**用"执行状态表 + 幂等键"解决**。
- **Saga 不保证隔离性**：**中间状态对外可见**（如"库存已扣、支付未完成"）——**对策：业务状态机 + 预留/确认两阶段**（TCC 思想）。
- 与 49/55 章的关系：49 章 DDD 的聚合边界决定"哪些步骤能拆"，**55 章 SaaS 的多租户一致性**也常靠 Saga——**分布式事务不是银弹，是业务妥协**。
- 易错点：补偿接口不幂等（重复补偿多退钱）；不记录"哪些步骤已执行"（空补偿/漏补偿）；把 Saga 当强一致（中间态可见）；补偿失败无兜底（人工介入）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;
import java.util.function.BooleanSupplier;

public class SagaOrchestration {
    static class SagaStep {
        final String name;
        final BooleanSupplier action;
        final Runnable compensation;
        boolean executed;

        SagaStep(String name, BooleanSupplier action, Runnable compensation) {
            this.name = name;
            this.action = action;
            this.compensation = compensation;
        }
    }

    static final List<String> log = new ArrayList<>();

    /** 编排器：顺序执行，失败反序补偿（只补偿已执行的步骤） */
    static boolean runSaga(List<SagaStep> steps) {
        List<SagaStep> executed = new ArrayList<>();
        for (SagaStep step : steps) {
            System.out.printf("  执行 %-12s ... ", step.name);
            boolean ok = step.action.getAsBoolean();
            if (ok) {
                step.executed = true;
                executed.add(step);
                System.out.println("成功");
            } else {
                System.out.println("失败 -> 开始补偿");
                for (int i = executed.size() - 1; i >= 0; i--) {
                    SagaStep s = executed.get(i);
                    System.out.printf("    补偿 %-12s ... ", s.name);
                    s.compensation.run();
                    System.out.println("完成");
                }
                return false;
            }
        }
        return true;
    }

    public static void main(String[] args) {
        System.out.println("【Saga：下单 -> 扣库存 -> 支付 -> 发货】");
        List<SagaStep> steps = new ArrayList<>();
        steps.add(new SagaStep("创建订单",
                () -> {
                    log.add("order-created");
                    return true;
                },
                () -> log.add("order-cancelled")));
        steps.add(new SagaStep("扣减库存",
                () -> {
                    log.add("stock-deducted");
                    return true;
                },
                () -> log.add("stock-restored")));
        steps.add(new SagaStep("支付扣款",
                () -> {
                    log.add("payment-failed");
                    return false;                    // 模拟支付失败
                },
                () -> log.add("payment-refunded")));
        steps.add(new SagaStep("创建发货单",
                () -> {
                    log.add("shipment-created");
                    return true;
                },
                () -> log.add("shipment-cancelled")));

        boolean ok = runSaga(steps);
        System.out.println("  Saga 结果：" + (ok ? "成功" : "失败（已补偿）"));
        System.out.println("  执行日志：" + log);

        System.out.println();
        System.out.println("【补偿的三个坑】");
        String[][] rows = {
                {"空补偿", "补偿了未执行的步骤", "记录 executed 列表，只补偿已执行"},
                {"悬挂", "补偿先到、原操作后到", "状态表 + 幂等键，拒绝已取消的操作"},
                {"重复补偿", "同一补偿执行多次", "补偿接口幂等（按业务键去重）"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-8s %-24s %s%n", r[0], r[1], r[2]);
        }

        System.out.println();
        System.out.println("【Saga vs TCC】");
        System.out.println("  Saga：本地事务 + 补偿，简单但中间态可见");
        System.out.println("  TCC：Try 预留 / Confirm 确认 / Cancel 取消，隔离性更好但侵入大");
        System.out.println("  选择：资金类用 TCC，长流程用 Saga");
    }
}
```

### 78-07 事件 Schema 演进与契约

**知识点**
- **事件是"跨团队的契约"**：**生产者改了字段，所有消费者都可能崩**——**事件 schema 要像 API 一样版本化**（64-07 的契约 diff 思想）。
- **兼容性三种**：**向后兼容**（新消费者读旧事件）、**向前兼容**（旧消费者读新事件）、**破坏性变更**（删除/改类型/改语义）——**只加可选字段是安全的，删字段/改类型是破坏性的**。
- **演进策略**：**加字段给默认值**（缺失时兜底）、**双写过渡**（新旧字段并存一段时间）、**版本化 topic/事件名**（`order.created.v1` -> `v2`）、**Schema Registry**（集中校验，生产前拦截）。
- **事件内容设计**：**放"事实 + 标识"**（orderId、amount、currency），**不放"可变快照"**（用户当前等级）——**消费者需要详情时回查**（避免事件变成"数据同步"）。
- 与 64 章的关系：64-07 讲"REST 契约 diff 兼容判定"，**事件契约的规则完全同构**——**加可选安全、删必填破坏**。
- 易错点：直接改字段类型（`int` -> `string`）；删除字段（旧消费者 NPE）；用事件传全量实体（耦合）；不建 schema 校验（上线才发现）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class EventSchemaEvolution {
    /** 事件统一用 Map 表示（贴近 JSON），版本号显式携带 */
    static Map<String, String> v1(long orderId, double amount) {
        Map<String, String> e = new LinkedHashMap<>();
        e.put("eventType", "OrderCreated");
        e.put("schemaVersion", "1");
        e.put("orderId", String.valueOf(orderId));
        e.put("amount", String.valueOf(amount));
        return e;
    }

    static Map<String, String> v2(long orderId, double amount, String currency) {
        Map<String, String> e = v1(orderId, amount);
        e.put("schemaVersion", "2");
        e.put("currency", currency);                 // 新增可选字段
        return e;
    }

    /** 旧消费者读 v2 事件：忽略未知字段，缺失字段用默认值 */
    static String oldConsumer(Map<String, String> e) {
        String orderId = e.getOrDefault("orderId", "?");
        double amount = Double.parseDouble(e.getOrDefault("amount", "0"));
        return "order=" + orderId + " amount=" + amount + "（旧消费者忽略 currency）";
    }

    /** 新消费者读 v1 事件：currency 缺失时兜底 */
    static String newConsumer(Map<String, String> e) {
        String currency = e.getOrDefault("currency", "CNY");
        return "order=" + e.get("orderId") + " amount=" + e.get("amount")
                + " currency=" + currency + "（新消费者兼容旧事件）";
    }

    record Change(String type, String detail, boolean compatible) {
    }

    static void compatibility() {
        List<Change> changes = List.of(
                new Change("新增可选字段", "v2 加 currency", true),
                new Change("新增必填字段", "消费者无法构造默认值", false),
                new Change("删除字段", "旧消费者读不到", false),
                new Change("字段改类型", "int -> string，解析失败", false),
                new Change("枚举加值", "旧消费者 switch 未覆盖", false),
                new Change("改字段语义", "amount 从元变分", false));
        System.out.println("【变更兼容性】");
        for (Change c : changes) {
            System.out.printf("  %-12s %-26s %s%n", c.type(), c.detail(),
                    c.compatible() ? "兼容" : "破坏性");
        }
        System.out.println();
    }

    public static void main(String[] args) {
        Map<String, String> e1 = v1(1001, 69.0);
        Map<String, String> e2 = v2(1002, 129.0, "USD");

        System.out.println("【事件样本】");
        System.out.println("  v1: " + e1);
        System.out.println("  v2: " + e2);

        System.out.println();
        System.out.println("【跨版本消费】");
        System.out.println("  " + oldConsumer(e2));
        System.out.println("  " + newConsumer(e1));
        System.out.println("  " + newConsumer(e2));

        System.out.println();
        compatibility();

        System.out.println("【演进策略】");
        System.out.println("  1) 只加可选字段，给默认值");
        System.out.println("  2) 破坏性变更 -> 新版本事件（order.created.v2），双写过渡");
        System.out.println("  3) Schema Registry 生产前校验，CI 做兼容性 diff");
        System.out.println("  4) 事件只放事实与标识，详情让消费者回查");
    }
}
```

### 78-08 死信队列与积压治理

**知识点**
- **重试要有边界**：**瞬时故障**（网络抖动/下游超时）重试有效；**永久故障**（数据非法/逻辑 bug）重试无意义——**必须区分，否则一条坏消息阻塞整个分区**（78-04）。
- **退避策略**：**固定间隔**（简单但可能打爆下游）、**指数退避**（100ms、200ms、400ms...）、**带抖动**（避免重试风暴同步）——**重试次数与总时长都要设上限**。
- **死信队列（DLQ）**：**超过重试上限的消息转入 DLQ**，**分区继续消费**（解除队头阻塞）——**DLQ 要有告警、可查询、可重放**（修复后重新投递）。
- **积压诊断三步**：**看 lag（生产-消费）**、**看消费速率与生产速率**、**看单条耗时**——**lag 持续增长 = 消费能力不足**（加消费者/优化单条/扩容分区）。
- 与 28/62 章的关系：28 章讲"MQ 的确认/重试/死信"机制，62 章讲"Kafka Lag"，**本章讲"积压发生时的处置流程"**。
- 易错点：无限重试（阻塞分区）；DLQ 不告警（坏消息静默堆积）；DLQ 不重放（数据永久丢失）；只看 lag 不看速率（误判）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class DlqBacklog {
    record Message(String id, String payload) {
    }

    static final int MAX_RETRY = 3;
    static final List<Message> dlq = new ArrayList<>();
    static final Map<String, Integer> attempts = new LinkedHashMap<>();
    static final List<String> consumed = new ArrayList<>();

    /** 消费一条：失败按指数退避重试，超过上限进 DLQ */
    static void consume(Message msg, boolean permanentFailure) {
        int attempt = attempts.getOrDefault(msg.id(), 0);
        while (attempt < MAX_RETRY) {
            attempt++;
            attempts.put(msg.id(), attempt);
            System.out.printf("  消费 %s 第 %d 次 ... ", msg.id(), attempt);
            if (!permanentFailure && attempt >= 2) {
                System.out.println("成功（瞬时故障已恢复）");
                consumed.add(msg.id());
                return;
            }
            long backoff = 100L * (1L << (attempt - 1));
            System.out.printf("失败，退避 %dms%n", backoff);
        }
        System.out.printf("  超过 %d 次 -> 转入死信队列%n", MAX_RETRY);
        dlq.add(msg);
    }

    /** 积压：生产 - 消费 */
    static void backlog(long produced, long consumedCount, long consumeRatePerSec,
                        long produceRatePerSec) {
        long lag = produced - consumedCount;
        System.out.printf("  produced=%,d consumed=%,d lag=%,d%n", produced, consumedCount, lag);
        System.out.printf("  生产速率=%,d/s 消费速率=%,d/s -> %s%n",
                produceRatePerSec, consumeRatePerSec,
                produceRatePerSec > consumeRatePerSec ? "积压将持续增长" : "可收敛");
        if (produceRatePerSec > consumeRatePerSec) {
            double hours = (double) lag / (produceRatePerSec - consumeRatePerSec) / 3600;
            System.out.printf("  按当前速率，%.1f 小时后 lag 翻倍（需扩容/优化）%n", hours);
        }
    }

    public static void main(String[] args) {
        System.out.println("【瞬时故障：重试后成功】");
        consume(new Message("msg-1", "order-1"), false);
        System.out.println();

        System.out.println("【永久故障：重试 3 次后进 DLQ，分区继续】");
        consume(new Message("msg-2", "bad-data"), true);
        consume(new Message("msg-3", "order-3"), false);

        System.out.println();
        System.out.println("【DLQ】");
        dlq.forEach(m -> System.out.println("  " + m));
```

### 78-09 事件驱动的可观测性

**知识点**
- **事件链路的 trace 要跨"生产 -> MQ -> 消费"**：**traceId 随消息头传递**，**生产者创建 span，消费者创建子 span**——**没有 traceId，一条事件经过三个服务后无法串联**（42-04 的分布式追踪）。
- **三个关键指标**：**生产速率/失败率**、**消费 lag**、**端到端延迟**（事件产生到消费完成）——**lag 大不代表慢，端到端延迟才代表用户体验**。
- **事件元数据**：**eventId（幂等 78-03）**、**occurredAt（业务时间）**、**traceId（链路）**、**schemaVersion（契约 78-07）**——**缺一个都会在排障时抓瞎**。
- **消费延迟的分解**：**排队延迟（lag/速率）+ 处理延迟（单条耗时）+ 重试延迟**——**分开度量才能定位是"消费不过来"还是"单条太慢"**。
- 与 42 章的关系：42 章的"日志/指标/追踪"三支柱，**在事件驱动里要额外加"事件维度"**——**按 eventType/topic 聚合**。
- 易错点：traceId 不传（断链）；只监控 lag（忽略端到端）；eventId 用随机数（无法去重）；不记录 occurredAt（无法算业务延迟）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class EventObservability {
    record Span(String traceId, String spanId, String parentId, String name,
                long startMs, long durationMs) {
        long endMs() {
            return startMs + durationMs;
        }
    }

    record EventMeta(String eventId, String traceId, long occurredAt, String schemaVersion) {
    }

    static final List<Span> spans = new ArrayList<>();

    static Span span(String traceId, String spanId, String parentId, String name,
                     long start, long duration) {
        Span s = new Span(traceId, spanId, parentId, name, start, duration);
        spans.add(s);
        return s;
    }

    static void printTree(String traceId) {
        System.out.println("  trace " + traceId + "：");
        for (Span s : spans) {
            if (!s.traceId().equals(traceId)) {
                continue;
            }
            int depth = 0;
            String parent = s.parentId();
            while (parent != null) {
                depth++;
                String target = parent;
                Span parentSpan = null;
                for (Span x : spans) {
                    if (x.spanId().equals(target)) {
                        parentSpan = x;
                        break;
                    }
                }
                parent = parentSpan == null ? null : parentSpan.parentId();
            }
            System.out.printf("    %s%-22s [%d, %d] %dms%n",
                    "  ".repeat(depth), s.name(), s.startMs(), s.endMs(), s.durationMs());
        }
    }

    public static void main(String[] args) {
        EventMeta meta = new EventMeta("evt-1001", "trace-abc", 1_000, "2");

        System.out.println("【事件元数据】");
        System.out.println("  eventId=" + meta.eventId() + " traceId=" + meta.traceId()
                + " occurredAt=" + meta.occurredAt() + " schemaVersion=" + meta.schemaVersion());

        System.out.println();
        System.out.println("【跨生产/消费的 span】");
        span("trace-abc", "s1", null, "OrderService.createOrder", 1_000, 30);
        span("trace-abc", "s2", "s1", "OutboxRelay.publish", 1_030, 5);
        span("trace-abc", "s3", "s2", "MQ.consume(order.created)", 1_200, 80);
        span("trace-abc", "s4", "s3", "PointsService.addPoints", 1_210, 60);
        span("trace-abc", "s5", "s3", "SmsService.send", 1_280, 40);
        printTree("trace-abc");

        System.out.println();
        System.out.println("【端到端延迟分解】");
        long produced = 1_000;
        long consumed = 1_280 + 40;
        long queueDelay = 1_200 - 1_030;             // 排队 170ms
        long processDelay = 80;                      // 消费处理 80ms
        System.out.printf("  事件产生=%d，消费完成=%d，端到端=%dms%n",
                produced, consumed, consumed - produced);
        System.out.printf("  排队延迟=%dms，处理延迟=%dms%n", queueDelay, processDelay);

        System.out.println();
        System.out.println("【消费 lag 与端到端不是一回事】");
        Map<String, Long> metrics = new LinkedHashMap<>();
        metrics.put("producedRate", 2_500L);
        metrics.put("consumedRate", 2_400L);
        metrics.put("lag", 12_000L);
        metrics.put("endToEndP99Ms", 850L);
        metrics.forEach((k, v) -> System.out.printf("  %-16s %s%n", k, v));
        System.out.println("  lag 大但端到端稳定 -> 可能只是流量高峰；端到端恶化才是真问题");

        System.out.println();
        System.out.println("【排障清单】traceId 透传 / eventId 唯一 / occurredAt 业务时间 / 按 eventType 聚合");
    }
}
```

### 78-10 事件治理与事件目录

**知识点**
- **事件目录（Event Catalog）是事件驱动架构的"资产清单"**：**每个事件有名称、owner、版本、schema、生命周期**——**没有目录，半年后没人知道谁在发、谁在消费**。
- **命名规范**：**`domain.entity.action.vN`**（如 `order.order.created.v1`）——**统一命名才能检索、才能治理**；**事件名用"过去式"**（已发生的事实），**命令用"祈使式"**（CreateOrder）。
- **生命周期**：**ACTIVE（在用）-> DEPRECATED（标记废弃）-> RETIRED（停止）**——**废弃要先通知消费者 + 双写过渡，不能直接删**（78-07）。
- **owner 与 SLA**：**每个事件必须有负责团队**（出了事找谁）、**schema 变更要走评审**、**消费方要登记**——**事件是"跨团队接口"，治理成本必须有人承担**。
- 与 64 章的关系：64 章的"API 治理"（版本/契约/配额）在事件侧同样适用——**API 与事件是"同步/异步"两种契约**。
- 易错点：事件命名随意（orderCreated/OrderCreated/order_created 混用）；无 owner（变更无人评审）；不登记消费者（删除事件才知道有人用）；生命周期不落地（废弃事件永远在发）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.regex.Pattern;

public class EventGovernance {
    enum Lifecycle { ACTIVE, DEPRECATED, RETIRED }

    record EventDef(String name, String owner, int version, Lifecycle lifecycle,
                    List<String> consumers) {
        boolean validName() {
            return Pattern.matches("^[a-z]+\\.[a-z]+\\.[a-z]+\\.v\\d+$", name);
        }

        String shortName() {
            int idx = name.lastIndexOf(".v");
            return idx < 0 ? name : name.substring(0, idx);
        }
    }

    static final List<EventDef> catalog = new ArrayList<>();

    static void register(EventDef def) {
        catalog.add(def);
        System.out.printf("  注册 %-28s owner=%-10s %s 消费者=%s%n",
                def.name(), def.owner(), def.lifecycle(), def.consumers());
    }

    static void validate() {
        System.out.println();
        System.out.println("【命名校验】");
        for (EventDef d : catalog) {
            System.out.printf("  %-30s %s%n", d.name(), d.validName() ? "合法" : "非法（应为 domain.entity.action.vN）");
        }
    }

    static void transitions() {
        System.out.println();
        System.out.println("【生命周期流转】");
        EventDef d = catalog.get(0);
        System.out.println("  " + d.name() + " ACTIVE -> DEPRECATED（通知消费者，双写）");
        System.out.println("  " + d.name() + " DEPRECATED -> RETIRED（消费者全部迁移后停止）");
        System.out.println("  禁止：ACTIVE 直接 RETIRED（消费者会断供）");
    }

    static void ownership() {
        System.out.println();
        System.out.println("【治理检查】");
        for (EventDef d : catalog) {
            List<String> issues = new ArrayList<>();
            if (d.owner() == null || d.owner().isBlank()) {
                issues.add("缺 owner");
            }
            if (d.consumers().isEmpty()) {
                issues.add("无消费者登记");
            }
            if (!d.validName()) {
                issues.add("命名不合规");
            }
            if (d.lifecycle() == Lifecycle.RETIRED && !d.consumers().isEmpty()) {
                issues.add("已退役但仍有消费者");
            }
            System.out.printf("  %-30s %s%n", d.name(),
                    issues.isEmpty() ? "通过" : "问题：" + issues);
        }
    }

    public static void main(String[] args) {
        System.out.println("【事件目录】");
        register(new EventDef("order.order.created.v1", "交易团队", 1,
                Lifecycle.ACTIVE, List.of("库存服务", "积分服务", "推荐服务")));
        register(new EventDef("order.order.paid.v1", "交易团队", 1,
                Lifecycle.ACTIVE, List.of("履约服务", "财务服务")));
        register(new EventDef("order.order.created.v2", "交易团队", 2,
                Lifecycle.ACTIVE, List.of("积分服务")));
        register(new EventDef("OrderCreated", "未知", 1,
                Lifecycle.ACTIVE, List.of()));
        register(new EventDef("stock.stock.deducted.v1", "库存团队", 1,
                Lifecycle.DEPRECATED, List.of("履约服务")));
        register(new EventDef("legacy.event.retired.v1", "老系统", 1,
                Lifecycle.RETIRED, List.of("报表服务")));

        validate();
        transitions();
        ownership();

        System.out.println();
        System.out.println("【事件 vs API 治理】");
        Map<String, String> rows = new LinkedHashMap<>();
        rows.put("契约形式", "同步 OpenAPI / 异步 Schema");
        rows.put("版本策略", "URL/Header / 事件名 vN");
        rows.put("兼容性", "加可选安全 / 同左");
        rows.put("Owner", "接口负责人 / 事件 owner");
        rows.put("下线", "灰度 + 通知 / DEPRECATED + 双写");
        rows.forEach((k, v) -> System.out.printf("  %-10s %s%n", k, v));

        System.out.println();
        System.out.println("【结论】事件目录 = 资产清单 + 责任人 + 生命周期；治理从登记开始");
    }
}
```

### 78-11 综合案例：订单履约事件流

**知识点**
- **把本章收口成一条完整事件流**：**下单（Outbox 78-02）-> 支付成功 -> 库存预留 -> 发货 -> 完成**，**任一步失败走 Saga 补偿**（78-06），**全程幂等**（78-03）、**按订单分区保序**（78-04）、**可追溯**（78-09）。
- **状态机是履约的核心**：**每个事件只允许合法状态迁移**（`CREATED -> PAID -> RESERVED -> SHIPPED -> COMPLETED`），**重复/乱序事件被状态机拒绝**——**这是业务层幂等的最后一道防线**。
- **补偿与正向流程对称**：**支付失败 -> 取消订单**；**库存不足 -> 退款 + 取消**；**发货失败 -> 释放库存 + 退款**——**每一步都要有对应的逆向操作**。
- **验收清单**：**不丢事件**（Outbox）、**不重复处理**（幂等）、**同一订单有序**（分区键）、**失败可补偿**（Saga）、**全链路可查**（traceId + eventId）。
- 与 49/78 章的关系：本章是 49 章 DDD 领域事件与 78 章事件驱动模式的**联合落地**——**从建模到运行**。
- 易错点：状态机允许任意跳转（脏数据）；补偿不对称（退了款没释放库存）；重复事件导致重复发货；traceId 断链（排障靠猜）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

public class OrderFulfillmentCase {
    enum State { CREATED, PAID, RESERVED, SHIPPED, COMPLETED, CANCELLED }

    static class OrderFulfillment {
        final long orderId;
        State state = State.CREATED;
        final Set<String> processedEvents = new LinkedHashSet<>();
        final List<String> timeline = new ArrayList<>();
        final List<String> compensations = new ArrayList<>();

        OrderFulfillment(long orderId) {
            this.orderId = orderId;
            timeline.add("CREATED");
        }

        /** 事件处理：幂等 + 状态机 */
        void onEvent(String eventId, String type) {
            if (processedEvents.contains(eventId)) {
                System.out.printf("  [幂等] 重复事件 %s 已忽略%n", eventId);
                return;
            }
            boolean ok = switch (type) {
                case "PAYMENT_SUCCEEDED" -> transition(State.PAID);
                case "INVENTORY_RESERVED" -> transition(State.RESERVED);
                case "SHIPPED" -> transition(State.SHIPPED);
                case "DELIVERED" -> transition(State.COMPLETED);
                case "PAYMENT_FAILED" -> cancel("支付失败");
                case "INVENTORY_SHORTAGE" -> cancel("库存不足");
                default -> false;
            };
            if (ok) {
                processedEvents.add(eventId);
            }
            System.out.printf("  %-8s %-20s -> %-10s %s%n", eventId, type, state,
                    ok ? "接受" : "拒绝（非法迁移/已取消）");
        }

        boolean transition(State next) {
            if (state == State.CANCELLED || state == State.COMPLETED) {
                return false;
            }
            int cur = state.ordinal();
            int nxt = next.ordinal();
            if (nxt != cur + 1) {
                return false;
            }
            state = next;
            timeline.add(next.name());
            return true;
        }

        boolean cancel(String reason) {
            if (state == State.SHIPPED || state == State.COMPLETED
                    || state == State.CANCELLED) {
                return false;
            }
            if (state.ordinal() >= State.PAID.ordinal()) {
                compensations.add("退款");
            }
            if (state.ordinal() >= State.RESERVED.ordinal()) {
                compensations.add("释放库存");
            }
            state = State.CANCELLED;
            timeline.add("CANCELLED(" + reason + ")");
            return true;
        }

        void report() {
            System.out.println("  order " + orderId + "：");
            System.out.println("    状态：" + state);
            System.out.println("    时间线：" + timeline);
            System.out.println("    补偿：" + (compensations.isEmpty() ? "无" : compensations));
        }
    }

    static final Map<Long, OrderFulfillment> orders = new LinkedHashMap<>();

    public static void main(String[] args) {
        OrderFulfillment o1 = new OrderFulfillment(1001);
        orders.put(1001L, o1);

        System.out.println("【正常履约：下单 -> 支付 -> 预留库存 -> 发货 -> 签收】");
        o1.onEvent("e1", "PAYMENT_SUCCEEDED");
        o1.onEvent("e2", "INVENTORY_RESERVED");
        o1.onEvent("e3", "SHIPPED");
        o1.onEvent("e4", "DELIVERED");
        System.out.println();
        o1.report();

        System.out.println();
        System.out.println("【重复投递：e2 再来一次】");
        o1.onEvent("e2", "INVENTORY_RESERVED");
        System.out.println();
        o1.report();

        System.out.println();
        System.out.println("【乱序：先收到 SHIPPED 再收到 INVENTORY_RESERVED】");
        OrderFulfillment o2 = new OrderFulfillment(1002);
        o2.onEvent("e1", "PAYMENT_SUCCEEDED");
        o2.onEvent("e3", "SHIPPED");
        o2.onEvent("e2", "INVENTORY_RESERVED");
        System.out.println();
        o2.report();
        System.out.println("  注：真实系统应短暂缓存乱序事件，待前置事件到达后重放，而不是直接丢弃");

        System.out.println();
        System.out.println("【失败补偿：支付成功、库存不足】");
        OrderFulfillment o3 = new OrderFulfillment(1003);
        o3.onEvent("e1", "PAYMENT_SUCCEEDED");
        o3.onEvent("e2", "INVENTORY_SHORTAGE");
        o3.onEvent("e3", "SHIPPED");
        System.out.println();
        o3.report();

        System.out.println();
        System.out.println("【验收清单】Outbox 不丢 / 幂等不重 / 分区保序 / Saga 可补偿 / trace 可查");
    }
}
```

**课后练习**
1. 扩展状态机：加入"取消中/退款中"中间态，验证重复事件与乱序事件都被正确处理。
2. 模拟"支付成功 -> 库存不足 -> 退款 -> 释放库存"的完整补偿链，检查补偿顺序与幂等。
3. 思考题：为什么"状态机是业务幂等的最后防线"？从"重复/乱序事件无法只靠 msgId 去重"分析。
