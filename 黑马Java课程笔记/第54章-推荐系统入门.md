# 第54章 推荐系统入门

第38章解决了"用户主动找"，本章解决"无明确意图下给用户看什么"。工业级推荐是四段漏斗：多路召回补盲区、粗排便宜砍规模、精排精细算分数、重排兜底体验规则——每级都是性能与效果的折衷。本章按「全景 → 多路召回融合 → ItemCF → 特征工程 → 粗排精排 → 重排打散 → 曝光过滤 → A/B 实验 → 实时特征 → 冷启动 → 商品推荐案例」的顺序讲。所有示例仍是纯 JDK：多路融合配额真实去重、ItemCF 共现与热门惩罚真实计算、双塔点积真实排序、曝光布隆与冷启动升降级真跑闭环，不需要任何推荐引擎。

### 54-01 推荐系统全景

**知识点**
- **推荐系统回答"海量商品里给这个用户看什么"**：与搜索（38 章，用户主动找）相对，推荐是**无明确意图下的个性化排序**。工业级流水线四段：**召回**（万级 -> 千级，多路并行）-> **粗排**（千 -> 百，轻量模型）-> **精排**（百 -> 几十，复杂模型精算）-> **重排**（业务规则/多样性/打散）。**漏斗每级都是"性能 vs 效果"的折衷**。
- **为什么是漏斗而不是一个大模型打全场**：10 万商品 × 复杂模型逐个打分 = 延迟爆炸；粗排便宜筛掉大概率无关项，精排把算力花在幸存者上——**与搜索引擎的召回/排序同构（38 章），与推理服务的两阶段同理（48 章）**。
- **推荐的三类数据**：用户行为（曝光/点击/购买/停留——正负样本来源）、物品侧（类目/价格/文案）、上下文（时间/场景/设备）。**数据回路是推荐的生命线**：线上行为回流 -> 特征更新 -> 模型迭代（46 章数据平台的消费方）。
- **评估双轨**：**离线**（AUC/召回率，44-10 评测思想）与**在线**（CTR/转化/GMV 提升，A/B 实验 54-08）——离线好在线差是常态（分布漂移/位置偏差），**在线 A/B 才是最终裁决**。
- **Java 工程师的位置**：推荐系统大部分是工程——召回服务、特征服务、打分服务编排、AB 平台、曝光过滤——**模型是算法团队产出的 artifact，工程决定这些模型能不能正确、快速、稳定地服务**（48-01 服务分层的推荐版）。
- 易错点：把推荐当搜索做（无用户维度）；漏斗各级独立优化不看全局（粗排优化砍掉精排想要的候选）；只看离线指标上线；忽略位置偏差（排第一的 CTR 天然高）。

### 54-02 召回：多路召回与融合

**知识点**
- **单路召回的死穴**：任何单一策略（热门/协同/向量）都有系统性盲区——热门路没个性化、协同有冷启动问题、向量召回同质化。**多路召回并行补盲区**：热门榜、协同过滤（看过又看）、向量近邻（40-07）、类目偏好、运营精选、新品池——**每路保底条数，融合去重**。
- **融合与配额**：各路返回后合并去重 -> 按路配额（如热门 ≤30%、协同 ≤40%、向量 ≤30%）——**配额防止强路垄断**（热门路永远跑赢，其他路没有曝光就无法积累数据——54-10 冷启动的联动）。
- **召回服务工程要点**：各路并行调用（50 章扇出）、单路超时降级（路级熔断 44-08）、合并去重（按 item id）、**路级可观测**（每路返回数/最终入选数/点击贡献——路的价值要可衡量，砍路加路有依据）。
- **与 ES 的关系**：向量召回可直接查 ES KNN（38 章集群）；关键词召回用 BM25——**ES 是召回路之一而不是全部**。
- 易错点：各路串行调用（延迟叠加，50 章扇出）；路无配额（热门垄断）；去重保留哪路的分数未定义；路级无监控（盲砍）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Map;
import java.util.Set;

public class RecallFusion {
    /** 多路召回融合：去重 + 路配额 */
    record Candidate(long itemId, String source, double score) {
    }

    static List<Long> fuse(List<Candidate> all, Map<String, Integer> quotas) {
        List<Long> result = new ArrayList<>();
        Set<Long> seen = new LinkedHashSet<>();          // 去重（保先到路）
        Map<String, Integer> perSource = new LinkedHashMap<>();
        for (Candidate c : all) {
            int quota = quotas.getOrDefault(c.source(), 0);
            int used = perSource.getOrDefault(c.source(), 0);
            if (used >= quota || !seen.add(c.itemId())) {
                continue;
            }
            perSource.merge(c.source(), 1, Integer::sum);
            result.add(c.itemId());
        }
        return result;
    }

    public static void main(String[] args) {
        List<Candidate> all = List.of(
                new Candidate(1, "hot", 9.9), new Candidate(2, "hot", 9.8),
                new Candidate(2, "cf", 9.7), new Candidate(3, "vector", 9.5),
                new Candidate(4, "cf", 9.0));
        Map<String, Integer> quotas = Map.of("hot", 1, "cf", 2, "vector", 1);
        System.out.println("  融合配额后：" + fuse(all, quotas) + "（去重 2 + 配额约束）");
    }
}
```

### 54-03 协同过滤与相似度

**知识点**
- **协同过滤（CF）的核心假设：相似的人喜欢相似的东西**。**ItemCF**（工业主流）："看过 A 的人也看了 B"——物品相似度矩阵；**UserCF**："与你相似的用户喜欢什么"——用户相似度。**ItemCF 更稳**（物品关系比用户兴趣变化慢、可离线预计算、可解释"因为你看过 X"）。
- **相似度计算**：余弦相似（40-07 同款）/ Jaccard / 改进版（惩罚热门物品：热门共同出现不能说明相似—— IDF 加权）。**共现矩阵 + 归一化**是 ItemCF 的实现骨架。
- **工程实现**：离线计算物品相似度矩阵（46 章批处理）-> 存储 Top K 相似（每物品只存最相似的 K 个）-> 在线：用户历史 -> 查相似表 -> 候选聚合打分。**矩阵分片与稀疏存储**是规模化的关键。
- **衰减与时效**：行为权重随时间衰减（近期行为更能代表兴趣）；热门惩罚防止"人人看过 iPhone"把 iPhone 推到所有相似表首位。
- 易错点：不惩罚热门物品（推荐全是大爆款）；相似度没有下限截断（弱相关也进候选）；离线频率过高（算力浪费）或过低（兴趣漂移跟不上）；未去重已购物品。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ItemCFDemo {
    /** ItemCF：共现 -> 余弦 -> 热门惩罚（示意） */
    static Map<String, Map<String, Double>> sim = new LinkedHashMap<>();

    static void build(List<List<String>> userHistories) {
        Map<String, Integer> itemPop = new LinkedHashMap<>();
        Map<String, Map<String, Integer>> co = new LinkedHashMap<>();
        for (List<String> history : userHistories) {
            for (String a : history) {
                itemPop.merge(a, 1, Integer::sum);
                for (String b : history) {
                    if (!a.equals(b)) {
                        co.computeIfAbsent(a, k -> new LinkedHashMap<>()).merge(b, 1, Integer::sum);
                    }
                }
            }
        }
        for (var e : co.entrySet()) {
            Map<String, Double> row = new LinkedHashMap<>();
            for (var inner : e.getValue().entrySet()) {
                // 余弦近似：共现 / sqrt(流行度积)，惩罚热门
                double denom = Math.sqrt(itemPop.get(e.getKey()) * (double) itemPop.get(inner.getKey()));
                row.put(inner.getKey(), inner.getValue() / denom);
            }
            sim.put(e.getKey(), row);
        }
    }

    public static void main(String[] args) {
        build(List.of(
                List.of("手机壳", "钢化膜", "充电器"),
                List.of("手机壳", "钢化膜"),
                List.of("充电器", "数据线"),
                List.of("iPhone", "手机壳")));
        System.out.println("  手机壳 的相似表：" + sim.get("手机壳"));
        System.out.println("  钢化膜 排前（强相关），iPhone 被热门惩罚压低");
    }
}
```

### 54-04 特征工程与 Embedding 特征

**知识点**
- **特征是模型的燃料，特征工程决定模型上限**：三类特征——**用户特征**（画像/历史行为统计：近 7 天点击类目分布）、**物品特征**（类目/价格/热度统计）、**交叉特征**（用户×物品：该用户对该类目的历史 CTR）。**训练与推理特征必须同源同口径**（46-10 特征平台铁律）。
- **Embedding 特征**：把 ID 类稀疏特征（用户 ID/类目 ID）映射为稠密向量——**向量既作为模型输入，也可直接用于向量召回**（40-07 闭环：双塔模型的用户/物品向量余弦召回）。Embedding 的离线训练与在线服务版本要一致（40-07 换模型重建的教训）。
- **特征的时效分层**：实时特征（秒级：本次会话点击）、小时级特征（近 1 小时统计）、天级特征（离线 T+1）——**时效越高工程越贵**，按特征价值分层（43 章流处理的消费方）。
- **特征服务化**：46-10 特征平台的推荐版——在线低延迟取数（Redis 预灌）、离线批量回填、训练-推理一致性校验。
- 易错点：训练用离线特征、推理用实时口径（分布不一致模型失效）；特征穿越（用未来数据训练，离线指标虚高）；Embedding 版本混用；高基数 ID 直接 one-hot（维度爆炸，Embedding 是解）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class FeatureDemo {
    /** 交叉特征：用户 × 类目 历史点击率（训练/推理同源） */
    static Map<String, Double> userCategoryCtr = new LinkedHashMap<>();

    static double ctr(String userId, String category) {
        return userCategoryCtr.getOrDefault(userId + ":" + category, 0.03);  // 全局默认
    }

    public static void main(String[] args) {
        userCategoryCtr.put("u1:phone-case", 0.25);
        userCategoryCtr.put("u1:laptop", 0.01);
        System.out.printf("  u1 在 phone-case 的历史 CTR = %.2f（强偏好特征）%n", ctr("u1", "phone-case"));
        System.out.printf("  u1 在 laptop 的历史 CTR = %.2f%n", ctr("u1", "laptop"));
        System.out.println();
        System.out.println("  铁律：这条 CTR 的计算口径（窗口/分子分母）训练与在线必须同一份定义（46-10）");
        System.out.println("  穿越警示：训练时若用\"当天之后的数据\"算 CTR -> 离线虚高、线上翻车");
    }
}
```

### 54-05 粗排与精排模型

**知识点**
- **粗排：轻量模型扛规模**——主流是**双塔**（用户塔 + 物品塔分别出向量，点积为分）：**物品塔可离线预计算**（物品向量入库），在线只算用户塔 + 点积——千级打分毫秒级。代价：无用户-物品交叉特征（双塔各自编码，交互靠点积）。
- **精排：复杂模型扛精度**——全量交叉特征（54-04）+ 复杂结构（深度网络/GBDT），输出 CTR/CVR 预估分；**精排分数是排序依据也是业务混排的货币**（eCPM = pCTR × 出价，广告与自然流混排）。
- **粗排与精排的模型一致性问题**：粗排与精排目标不一致会导致"粗排认为好的精排不认"——**对齐方式**：粗排用精排的蒸馏模型（知识蒸馏 44-06 的推荐应用）。
- **校准（calibration）**：pCTR 是概率估计，要与真实点击率对齐（否则业务用 pCTR 计算的 eCPM 系统性偏差）——**校准是精排上线前的必备步骤**（44-10 评测的延伸）。
- 易错点：粗排用全量交叉特征（算不动）；精排分数未校准直接当概率用；模型版本与特征版本错配；离线 AUC 与在线 CTR 脱节分析缺失。
- **工程要点**：粗排物品向量批量预灌 Redis/内存（离线更新）；精排特征在线拼接（特征服务 54-04）+ 模型服务（48 章推理容量同款）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class TwoTowerDemo {
    /** 双塔：用户向量 × 物品向量 点积（物品向量离线预计算） */
    static double dot(double[] a, double[] b) {
        double s = 0;
        for (int i = 0; i < a.length; i++) {
            s += a[i] * b[i];
        }
        return s;
    }

    public static void main(String[] args) {
        double[] user = {0.9, 0.1, 0.2};          // 在线：用户塔实时算（一次）
        List<double[]> itemVecs = List.of(         // 离线：物品向量已入库
                new double[]{0.8, 0.2, 0.1},       // 商品A
                new double[]{0.1, 0.9, 0.3});      // 商品B
        for (int i = 0; i < itemVecs.size(); i++) {
            System.out.printf("  商品%d 点积得分 %.3f%n", i + 1, dot(user, itemVecs.get(i)));
        }
        System.out.println("  千级打分 = 一次用户塔 + N 次点积 -> 毫秒级");
        System.out.println("  代价：无交叉特征（用户×物品联合模式学不到）-> 精排补");
    }
}
```

### 54-06 重排：多样性、打散与业务规则

**知识点**
- **精排分数最高 ≠ 最终展示顺序**：Top 结果全是同类目（10 个手机壳）体验崩坏——**重排解决"模型不知道的体验规则"**：类目打散（相邻不同类目）、同店打散、置顶插坑（运营/广告位）、负反馈过滤（已曝光未点击的降权）。
- **多样性算法**：**MMR**（最大边际相关：相关性与多样性加权轮选）——每一步选"与已选集合差异大且相关"的项；简单打散（滑动窗口内类目不重复）是工程常用版。
- **业务规则的优先级语义**：置顶 > 强插 > 打散 > 过滤——**规则要可配置可审计**（运营改规则不该改代码，44-08 配置化思想）；**每条规则的效果要可归因**（规则命中日志 + A/B）。
- **与精排分数的兼容**：打散会牺牲部分 pCTR——**打散强度是体验与收入的旋钮**（A/B 度量最优档位 54-08）。
- 易错点：规则硬编码（改规则=发版）；打散无上限（相关性崩）；置顶滥用（用户信任度下降，42 章点踩率上升）；曝光过滤内存无界（54-07）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class RerankDemo {
    record Item(long id, String category, double score) {
    }

    /** 滑动窗口打散：窗口 W 内同类目最多 1 个 */
    static List<Item> diversify(List<Item> ranked, int window) {
        List<Item> out = new ArrayList<>();
        List<Item> pool = new ArrayList<>(ranked);
        while (!pool.isEmpty()) {
            boolean placed = false;
            for (int i = 0; i < pool.size(); i++) {
                Item candidate = pool.get(i);
                boolean clash = out.stream()
                        .skip(Math.max(0, out.size() - window + 1))
                        .anyMatch(p -> p.category().equals(candidate.category()));
                if (!clash) {
                    out.add(candidate);
                    pool.remove(i);
                    placed = true;
                    break;
                }
            }
            if (!placed) {                  // 全部冲突 -> 放最优先的
                out.add(pool.remove(0));
            }
        }
        return out;
    }

    public static void main(String[] args) {
        List<Item> ranked = List.of(
                new Item(1, "case", 0.9), new Item(2, "case", 0.8),
                new Item(3, "charger", 0.7), new Item(4, "case", 0.6));
        List<Item> out = diversify(ranked, 2);
        for (Item i : out) {
            System.out.printf("  %d [%s] %.2f%n", i.id(), i.category(), i.score());
        }
    }
}
```

### 54-07 曝光过滤与去重

**知识点**
- **"看过不再推"是推荐的底线体验**——曝光记录（userId+itemId+时间）规模巨大（每天上亿），**存储与过滤是工程挑战**：布隆过滤器（40-10 同款：可能误判不存在必准——误判=少推，可接受）；分窗口保留（只过滤近 7 天曝光，更久的允许重推——重复曝光有时是必要的）。
- **存储选型**：Redis Set/Bitmap（按用户分 key，TTL 7 天）——**内存账要算**：人均曝光 200 × 1 亿用户 = 200 亿条，Bitmap 压缩是必需（46-03 成本思想）。
- **去重的时机**：召回后粗排前（尽早，省算力）；**曝光写入与过滤的竞态**：本次曝光写入后，同会话后续请求立即过滤（会话内去重）。
- **重复曝光的产品语义**：不是所有重复都该过滤——购物车商品、收藏商品、购买过的复购场景——**过滤清单可配置**（曝光/已购/不感兴趣 分维度）。
- 易错点：全量永久过滤（内存爆炸 + 复购场景错误）；布隆误判率没调（过高把新品全滤掉）；过滤在精排后（算力浪费）；负反馈（点踩/不感兴趣）没有独立于曝光的更强降权。

**示例代码**
```java
import java.util.BitSet;
import java.util.List;

public class BloomFilterDemo {
    static class SimpleBloom {
        final BitSet bits = new BitSet(1024);

        void add(String item) {
            bits.set(item.hashCode() & 1023);
            bits.set((item.hashCode() >>> 5) & 1023);
        }

        boolean mightContain(String item) {
            return bits.get(item.hashCode() & 1023) && bits.get((item.hashCode() >>> 5) & 1023);
        }
    }

    public static void main(String[] args) {
        SimpleBloom seen = new SimpleBloom();
        for (String id : List.of("item-1", "item-2")) {
            seen.add(id);
        }
        System.out.println("  已曝光 item-1 -> mightContain=" + seen.mightContain("item-1"));
        System.out.println("  未曝光 item-9 -> mightContain=" + seen.mightContain("item-9") + "（可能误判）");
    }
}
```

### 54-08 A/B 实验与效果评估

**知识点**
- **推荐的效果必须用 A/B 验证**：分流（按用户尾号/哈希到实验组与对照组——**同用户恒定同组**，41-07 粘性思想）-> 指标收集（CTR/转化/人均时长/留存）-> 显著性检验（样本量与置信度）-> 结论与放量。**没有 A/B 的推荐优化是玄学**（离线指标与在线表现经常背离）。
- **实验平台三要素**：分流服务（稳定分流 + 分层实验正交——多个实验同时跑互不污染，哈希不同盐）、指标管道（46 章数据平台的行为回流）、置信判定（统计显著性，避免"看起来涨了"）。
- **常见陷阱**：**新奇效应**（用户对新样式先点后腻，观察期要够长）；**辛普森悖论**（分组看都涨、合并看反跌——分流不均）；**多重检验**（同时跑太多实验，假阳性升高）；**观察期截断**（大促期实验结果不可外推）。
- **推荐特有的评估维度**：多样性/新鲜度/长尾覆盖（不只 CTR）——**只优化 CTR 会把推荐变成"标题党聚合器"**（52-06 的目标权衡思想）。
- 易错点：分流键不稳定（用户在组间跳变）；实验组与对照组流量不均（置信失效）；看完一周数据就下结论（未达统计显著）；只报显著正向不报负向（选择性汇报）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class AbSplitDemo {
    /** 稳定分流：哈希(user, experiment) % buckets，同用户恒定同组 */
    static String bucket(String userId, String experiment, int buckets) {
        int h = Math.abs((userId + ":" + experiment).hashCode());
        int slot = h % buckets;
        return slot < buckets / 2 ? "control" : "treatment";
    }

    public static void main(String[] args) {
        Map<String, String> observed = new LinkedHashMap<>();
        for (String u : new String[]{"u1", "u2", "u3", "u1", "u2"}) {
            observed.put(u, bucket(u, "new-ranking", 100));
        }
        System.out.println("  分流结果：" + observed);
        System.out.println("  u1/u2 两次请求分组一致 —— 粘性分流（41-07 同源）");
    }
}
```

2. 实现"显著性判定"简化版：给定两组 CTR 与样本量，计算是否达到 95% 置信（正态近似）。

### 54-09 实时特征与在线服务

**知识点**
- **实时特征让推荐"跟上用户"**：用户 5 分钟前看了手机壳 -> 本会话请求应立刻偏向手机配件——**实时特征的链路**：行为埋点 -> MQ（28 章）-> Flink 实时聚合（43 章）-> 特征存储（Redis，46-10）-> 推荐在线读取。**延迟目标：行为发生到影响推荐 < 1 分钟**。
- **在线特征读取的延迟纪律**：推荐接口总预算 200ms 中特征拼接占大头——**特征服务批量化**（一次取全特征，不全量逐个查）、本地缓存兜底、超时降级（特征缺失用默认值，44-08 阶梯）。
- **实时特征的新鲜度与正确性**：会话内去重联动（54-07）、特征抖动（短窗口统计噪声大，需平滑）、**特征回灌**（实时丢失后从离线兜底重建，46-10）。
- **与流处理的对接**：Flink 聚合窗口（43-03）输出实时统计 -> 写特征存储——**流处理的"状态 TTL"与特征窗口对齐**。
- 易错点：实时特征链路断了没人知道（新鲜度监控缺失 46-10）；特征拼接 N+1 查询（逐特征逐请求查 Redis）；实时特征覆盖离线特征口径（两套口径打架 54-04）。
- **延迟预算分配示例**：召回 60ms + 特征 40ms + 粗排 30ms + 精排 60ms + 重排 10ms = 200ms——**预算是设计出来的**（44-08）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class RealtimeFeatureDemo {
    /** 会话实时兴趣：最近 3 次点击的类目计数（Flink 输出 -> Redis） */
    static final Map<String, Map<String, Integer>> sessionInterest = new LinkedHashMap<>();

    static void onUserClick(String user, String category) {
        sessionInterest.computeIfAbsent(user, k -> new LinkedHashMap<>())
                .merge(category, 1, Integer::sum);
    }

    static Map<String, Integer> features(String user) {
        return sessionInterest.getOrDefault(user, Map.of());
    }

    public static void main(String[] args) {
        onUserClick("u1", "phone-case");
        onUserClick("u1", "phone-case");
        onUserClick("u1", "charger");
        System.out.println("  u1 实时兴趣：" + features("u1"));
        System.out.println("  推荐接口读取此特征 -> 本会话偏向手机配件（延迟 < 1min）");
        System.out.println();
        System.out.println("  工程要点：TTL 会话过期清理（43-05 状态治理）；断流兜底回退离线特征");
    }
}
```

### 54-10 冷启动问题

**知识点**
- **冷启动三类**：**新用户**（无历史——用人口属性/设备/地域 + 热门/运营精选兜底）、**新物品**（无交互——内容特征/相似物品扩散 + 流量扶持配额 54-02）、**新系统**（全无数据——运营策略先行，逐步引入个性化）。
- **新物品的流量扶持是"投资"**：新品无曝光就永远无数据——**扶持配额**（新品池固定占比 + 快速升降级：点击率达标升级流量池、不达标降级退出）——**探索与利用（explore/exploit）的平衡**是推荐系统的基础张力（54-02 配额的深化）。
- **新用户的快速收敛**：首次会话的行为价值极高（尽快收集兴趣信号）——**首屏策略**：热门 + 多样化类目试探（信息增益最大化：多样曝光比单类目曝光更快定位兴趣）。
- **Embedding 冷启动**：新物品无训练数据——**内容特征生成向量**（标题/图片文本 Embedding，40-08 RAG 同源技术）替代行为向量。
- 易错点：冷启动推荐全上热门（新用户看到的全是爆款，个性化无从谈起）；新品扶持无退出机制（垃圾新品长期占坑）；内容 Embedding 与行为 Embedding 混用同一空间（40-07 不同空间教训）。
- **与 54-02 配额的统一**：扶持配额、路配额、打散窗口——**本质都是"曝光资源的分配策略"**，全部需要 A/B 验证（54-08）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class ColdStartDemo {
    /** 新品扶持池：流量配额 + 快速升降级 */
    static class NewItemPool {
        final Map<String, Integer> impressions = new LinkedHashMap<>();
        final Map<String, Integer> clicks = new LinkedHashMap<>();

        boolean promote(String itemId) {
            int imp = impressions.getOrDefault(itemId, 0);
            int click = clicks.getOrDefault(itemId, 0);
            return imp >= 100 && (double) click / imp >= 0.05;
        }
    }

    public static void main(String[] args) {
        NewItemPool pool = new NewItemPool();
        pool.impressions.put("new-1", 150);
        pool.clicks.put("new-1", 12);
        System.out.printf("  新品 new-1（曝光150 点击12 CTR=%.0f%%）-> %s%n",
                100.0 * 12 / 150, pool.promote("new-1") ? "升级流量池" : "继续扶持观察");
    }
}
```

### 54-11 综合案例：商品推荐流水线

**知识点**
- **把本章收束成一条完整推荐流水线**：请求 -> 特征拼接（54-04）-> 多路召回（54-02：热门/ItemCF/向量）-> 曝光过滤（54-07）-> 粗排双塔（54-05）-> 精排 pCTR（54-05）-> 重排打散（54-06）-> 冷启动注入（54-10）-> 返回 + 曝光日志回写（数据回路）。**38 章搜索、40 章向量、43 章流、46 章数据平台在此合流**。
- **延迟预算**：特征 40ms + 召回 60ms + 过滤/粗排 30ms + 精排 60ms + 重排 10ms = 200ms——**每段可降级**（精排超时回退粗排分 44-08）。
- **正确性验收**：单测（各段逻辑）+ 回归（黄金请求集 44-10）+ 压测（目标 QPS 下 P99）+ A/B（54-08）——**推荐功能上线四门**。
- **可观测**：段级耗时/各路召回数/过滤量/最终 CTR 分实验组——**段级指标定位"效果劣化在哪一段"**（42 章分解思想）。
- 易错点：流水线各段无超时降级（一段卡全链）；曝光日志缺失（数据回路断，越跑越差）；无 A/B 直接过全量；精排分数与重排规则冲突无仲裁记录。
- **Java 工程师的验收清单**：召回并行化、特征批量读、过滤内存可控、降级链路完整、指标分实验组——**模型之外的工程能力决定推荐系统的下限**。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ProductRecCase {
    record RecItem(long id, double score, String source) {
    }

    static List<RecItem> pipeline(String userId, long deadlineMs) {
        long start = System.currentTimeMillis();
        Map<String, Long> budget = new LinkedHashMap<>();
        budget.put("feature", 40L);
        budget.put("recall", 60L);
        budget.put("rough+fine", 90L);
        budget.put("rerank", 10L);
        // 模拟各段（真实实现为服务调用）
        List<RecItem> result = new ArrayList<>(List.of(
                new RecItem(101, 0.92, "itemcf"),
                new RecItem(102, 0.88, "vector"),
                new RecItem(103, 0.81, "hot"),
                new RecItem(104, 0.75, "itemcf")));
```
