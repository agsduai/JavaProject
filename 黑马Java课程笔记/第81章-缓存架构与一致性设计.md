# 第81章 缓存架构与一致性设计

缓存是性价比最高的一招，也是最容易埋雷的一招：命中率上去 QPS 翻十倍，一致性没做好用户看到的价格就是错的。本章把缓存当成一套「有代价的架构决策」来讲：先算清收益与代价，再依次解决穿透/击穿/雪崩、一致性、热点、预热降级、多级缓存与监控。本章按「收益与代价 → 读写模式 → 三大故障 → 空值与布隆 → 一致性 → 延迟双删与 binlog → 热点与本地缓存 → 预热与降级 → 多级缓存 → 监控 → 商品详情改造案例」的顺序讲。所有示例仍是纯 JDK：命中率与延迟模型、三种读写模式对比、穿透/击穿/雪崩模拟、布隆过滤器位数组、双写不一致窗口、延迟双删、热点探测、预热与降级开关、多级缓存 TTL 抖动、命中率统计全部真实运行。

### 81-01 缓存的收益与代价

**知识点**
- **缓存的本质**：**用内存换时间**，把「每次都算 / 每次都查库」变成「一次算好、多次读取」——**收益 ≈ 命中率 × 单次回源耗时**，命中率 90% 时平均延迟掉到原来的 1/10 量级。
- **三种代价**：**一致性代价**（数据可能旧）、**内存代价**（缓存也是钱）、**复杂度代价**（失效、雪崩、热点都要额外处理）——**缓存不是免费加速，是把「慢」换成「可能不一致」**。
- **什么时候不该加缓存**：**数据量小且查询本来就快**、**强一致且不能容忍旧值**（如余额扣减）、**写多读少**——**读远多于写（10:1 以上）才是缓存的主场**。
- **命中率是第一指标**：**命中率 = 命中次数 / 总请求**，**低于 80% 基本白干**，还白担一致性风险（81-10 讲怎么量）。
- 与 25/38 章的关系：25 章讲 Redis 用法、38 章讲 ES 检索，**本章讲「怎么设计缓存层」**——**模式、故障、一致性、监控**四件套。
- 易错点：只算「快了」不算「旧了」；不看命中率；把缓存当数据库用（缓存丢了就全崩）；TTL 全设同一个值（雪崩）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class CacheCostBenefit {
    record Scenario(String name, double hitRate, double dbMs, double cacheMs,
                    double qps, double gb, double costPerGbMonth) {
    }

    static void compare(Scenario s) {
        double avgNoCache = s.dbMs();
        double avgWithCache = s.hitRate() * s.cacheMs() + (1 - s.hitRate()) * s.dbMs();
        double dbQpsNoCache = s.qps();
        double dbQpsWithCache = s.qps() * (1 - s.hitRate());
        System.out.printf("【%s】命中率 %.0f%%%n", s.name(), s.hitRate() * 100);
        System.out.printf("  平均延迟：%6.1fms -> %6.1fms（快 %.1f 倍）%n",
                avgNoCache, avgWithCache, avgNoCache / avgWithCache);
        System.out.printf("  回源 QPS：%8.0f -> %8.0f（降 %.0f%%）%n",
                dbQpsNoCache, dbQpsWithCache,
                (1 - dbQpsWithCache / dbQpsNoCache) * 100);
        System.out.printf("  内存成本：%.0f GB -> %.0f 元/月%n",
                s.gb(), s.gb() * s.costPerGbMonth());
        System.out.println();
    }

    public static void main(String[] args) {
        compare(new Scenario("商品详情（高命中）", 0.95, 25, 0.6, 20_000, 40, 60));
        compare(new Scenario("订单列表（低命中）", 0.55, 25, 0.6, 8_000, 60, 60));
        compare(new Scenario("余额查询（不该缓存）", 0.30, 8, 0.5, 3_000, 20, 60));

        System.out.println("【判断】");
        Map<String, String> rules = new LinkedHashMap<>();
        rules.put("命中率 < 80%", "先别加缓存：回源太多，收益覆盖不了复杂度");
        rules.put("强一致 + 金额", "不加缓存或只加极短 TTL，用数据库/行锁保证正确");
        rules.put("读:写 > 10:1", "缓存主场，值得投入");
        rules.put("缓存挂了会全崩", "先做降级与限流，再加缓存");
        rules.forEach((k, v) -> System.out.printf("  %-16s %s%n", k, v));

        System.out.println();
        System.out.println("【结论】缓存不是「有就快」，而是「算清楚才快」："
                + "命中率、延迟收益、内存成本、一致性风险，四项一起评估。");
    }
}
```

### 81-02 缓存读写模式：Cache-Aside 与 Write-Behind

**知识点**
- **Cache-Aside（旁路缓存）**：**读**时先查缓存、未命中查库并回填；**写**时**先写库、再删缓存**——**最常用**，缓存只是「加速层」，挂了也能退化到库。
- **Read-Through**：**缓存组件自己负责回源**（调用方只跟缓存打交道）——**代码简单**，但**缓存与业务耦合**，回源逻辑要写进缓存层。
- **Write-Through**：**写请求同时写缓存与库（同步）**——**缓存永远新**，但**写延迟翻倍**，且**缓存里可能有大量从没被读过的冷数据**。
- **Write-Behind（回写）**：**先写缓存、异步批量刷库**——**写极快**，但**宕机会丢数据**，只适合**可容忍丢失的计数/埋点**类场景。
- **选型口诀**：**读多写少 → Cache-Aside；强一致读 → Read-Through + 短 TTL；写多但要快 → Write-Behind（能丢）；写少但要准 → Write-Through**。
- 易错点：写时「先删缓存再写库」（并发下会把旧值写回缓存）；Cache-Aside 写成「更新缓存」而不是「删缓存」（并发更新顺序乱）；Write-Behind 用在订单金额上。

**示例代码**
```java
import java.util.HashMap;
import java.util.Map;

public class CachePatterns {
    enum Pattern { CACHE_ASIDE, READ_THROUGH, WRITE_THROUGH, WRITE_BEHIND }

    static class Store {
        final Map<String, String> db = new HashMap<>();
        final Map<String, String> cache = new HashMap<>();
        int dbReads;
        int dbWrites;
        int cacheWrites;
        int cacheHits;
        int cacheMisses;
        int lostOnCrash;
    }

    static String read(Store s, String k) {
        String v = s.cache.get(k);
        if (v != null) {
            s.cacheHits++;
            return v + "@cache";
        }
        s.cacheMisses++;
        s.dbReads++;
        v = s.db.get(k);
        if (v != null) {
            s.cache.put(k, v);
        }
        return v + "@db";
    }

    static void write(Store s, String k, String v, Pattern p) {
        switch (p) {
            case CACHE_ASIDE, READ_THROUGH -> {
                s.dbWrites++;
                s.db.put(k, v);
                s.cache.remove(k);              // 删缓存，不是更新缓存
                s.cacheWrites++;
            }
            case WRITE_THROUGH -> {
                s.dbWrites++;
                s.db.put(k, v);
                s.cache.put(k, v);              // 同步写两份，缓存不会旧
                s.cacheWrites++;
            }
            case WRITE_BEHIND -> {
                s.cache.put(k, v);              // 只落缓存，库还是旧值
                s.cacheWrites++;
                s.lostOnCrash++;                // 宕机就丢这一笔
            }
        }
    }

    static void flush(Store s) {                // Write-Behind 的异步刷盘
        for (Map.Entry<String, String> e : s.cache.entrySet()) {
            if (!e.getValue().equals(s.db.get(e.getKey()))) {
                s.dbWrites++;
                s.db.put(e.getKey(), e.getValue());
                s.lostOnCrash--;
            }
        }
    }

    public static void main(String[] args) {
        System.out.printf("%-14s %-8s %-8s %-8s %-10s %s%n",
                "模式", "读库", "写库", "写缓存", "写后读源", "宕机丢失");
        for (Pattern p : Pattern.values()) {
            Store s = new Store();
            for (int i = 1; i <= 10; i++) {
                s.db.put("item:" + i, "v0-" + i);
            }
            // 100 次读，10 个 key 各 10 次
            for (int round = 0; round < 10; round++) {
                for (int i = 1; i <= 10; i++) {
                    read(s, "item:" + i);
                }
            }
            // 5 次写
            for (int i = 1; i <= 5; i++) {
                write(s, "item:" + i, "v1-" + i, p);
            }
            String source = read(s, "item:1");      // 写后立刻读，看从哪拿到新值
            String where = source.endsWith("@cache") ? "缓存" : "库";
            int lost = s.lostOnCrash;
            if (p == Pattern.WRITE_BEHIND) {
                flush(s);                            // 不宕机则最终刷盘
            }
            System.out.printf("%-14s %-8d %-8d %-8d %-10s %d%n",
                    p, s.dbReads, s.dbWrites, s.cacheWrites, where, lost);
        }

        System.out.println();
        System.out.println("【读结论】前 100 次读四种模式都是 10 次读库（10 个 key 各回源一次），读性能一样");
        System.out.println("          表里的「读库」= 前 100 次的 10 次 + 写后那次读，所以 Cache-Aside 是 11");
        System.out.println("【写结论】Cache-Aside/Read-Through 写完删缓存 -> 写后第一次读要回源（读库 +1）");
        System.out.println("          Write-Through 写两份 -> 写延迟翻倍，但读永远命中且是新的");
        System.out.println("          Write-Behind 只写缓存 -> 写最快，但刷盘前宕机这 5 笔全丢");
    }
}
```

2. 给 Cache-Aside 的写路径改成「先删缓存再写库」，用两个线程并发演示旧值被写回缓存。

### 81-03 穿透、击穿、雪崩

**知识点**
- **穿透（Penetration）**：**查一个数据库里根本不存在的 key**，缓存永远不命中，**每次都打到库**——**攻击者用随机 id 就能把库打挂**。
- **击穿（Breakdown）**：**某个热点 key 恰好过期的那一瞬间**，**大量并发同时回源**——**一个 key 打穿一层缓存**（81-07 的热点 key 更常见）。
- **雪崩（Avalanche）**：**大量 key 在同一时刻集中过期**，或**缓存集群整体宕机**，**流量全部涌向数据库**——**击穿是单点，雪崩是面**。
- **三类对策**：穿透 → **空值缓存 + 布隆过滤器**（81-04）；击穿 → **互斥锁 / 逻辑过期 + 单飞（singleflight）**；雪崩 → **TTL 加随机抖动 + 多级缓存 + 熔断降级**。
- **逻辑过期 vs 互斥锁**：**互斥锁**让其他线程等待（延迟高但不返回旧值）；**逻辑过期**让一个线程刷新、其他线程先返回旧值（可用性优先）——**按业务容忍度选**。
- 易错点：用 `if (cache == null) rebuild()` 但没加锁（等于没防击穿）；空值缓存不设 TTL（脏数据永驻）；TTL 全设 30 分钟（整点雪崩）。

**示例代码**
```java
import java.util.HashMap;
import java.util.Map;
import java.util.Random;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;

public class CacheProblems {
    static final Map<String, String> DB = new HashMap<>();
    static final Map<String, String> CACHE = new HashMap<>();
    static final AtomicInteger DB_HITS = new AtomicInteger();
    static final Random RND = new Random(7);

    static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    static String queryDb(String key) {
        DB_HITS.incrementAndGet();
        sleep(20);                                  // 模拟 20ms 慢查询
        return DB.get(key);
    }

    static String get(String key, boolean nullCache) {
        String v = CACHE.get(key);
        if (v != null) {
            return v.equals("NULL") ? null : v;
        }
        v = queryDb(key);
        if (v == null && nullCache) {
            CACHE.put(key, "NULL");                 // 空值也缓存，短 TTL
        } else if (v != null) {
            CACHE.put(key, v);
        }
        return v;
    }

    static void penetration() {
        DB_HITS.set(0);
        CACHE.clear();
        for (int i = 0; i < 200; i++) {
            get("user:" + (1000 + i % 50), false);    // 全是不存在的 id，50 个轮流
        }
        int without = DB_HITS.get();
        DB_HITS.set(0);
        CACHE.clear();
        for (int i = 0; i < 200; i++) {
            get("user:" + (1000 + i % 50), true);
        }
        System.out.printf("【穿透】无空值缓存 打库 %3d 次；有空值缓存 打库 %3d 次%n",
                without, DB_HITS.get());
        System.out.println("  200 次请求 50 个不存在的 id 轮流打（每个 id 4 次）：有空值缓存时每个 id 只回源一次，"
                + "之后都命中「NULL」");
    }

    static void breakdown() throws Exception {
        DB_HITS.set(0);
        CACHE.clear();
        DB.put("hot:sku:1", "iPhone");
        int threads = 50;
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);
        for (int i = 0; i < threads; i++) {
            new Thread(() -> {
                try {
                    start.await();
                    get("hot:sku:1", false);        // 热点 key 刚过期，50 线程同时回源
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }
        start.countDown();
        done.await();
        System.out.printf("【击穿】50 并发打同一个过期热点 key，打库 %d 次（本应 1 次）%n",
                DB_HITS.get());
    }

    static void avalanche() {
        DB_HITS.set(0);
        CACHE.clear();
        for (int i = 0; i < 200; i++) {
            DB.put("cfg:" + i, "v" + i);
        }
        for (int i = 0; i < 200; i++) {            // 所有 key 同一时刻过期
            CACHE.remove("cfg:" + i);
            get("cfg:" + i, false);
        }
        System.out.printf("【雪崩】200 个 key 同时过期，一次性打库 %d 次%n", DB_HITS.get());
        System.out.println("  对策：TTL = 基准 + random(0, 300s)，把过期时间摊开");
    }

    public static void main(String[] args) throws Exception {
        penetration();
        breakdown();
        avalanche();
        System.out.println();
        System.out.println("【总结】穿透防「不存在」，击穿防「同时回源」，雪崩防「同时过期」。");
        System.out.println("  穿透 -> 空值缓存 + 布隆过滤器；击穿 -> 互斥锁 / 逻辑过期；"
                + "雪崩 -> TTL 抖动 + 降级");
    }
}
```

**课后练习**

### 81-04 空值缓存与布隆过滤器

**知识点**
- **空值缓存**：**查不到也写一条 `NULL` 进缓存（TTL 60 秒）**——**最简单**的防穿透手段，缺点是**大量随机 key 会把缓存撑爆**，所以 TTL 必须短。
- **布隆过滤器**：**一个位数组 + k 个哈希函数**，**写入时把 k 个位置置 1**，**查询时 k 个位置全为 1 才「可能存在」**——**省内存（1 亿 key 约 114MB @ 1% 误判）**。
- **布隆的两种错误**：**不会漏判**（存在的一定说存在），**可能误判**（不存在的也可能说存在）——**误判率由位数组长度 m、哈希个数 k、元素个数 n 决定**。
- **标准用法**：**请求先过布隆**，说「不存在」直接返回（挡住 99% 的穿透）；说「可能存在」再查缓存/库——**布隆挡在缓存前面，不是替代缓存**。
- **布隆的局限**：**不支持删除**（置 1 的位置无法安全清零，会误伤别的 key）——需要删除时用**计数布隆**或**定期重建**。
- 易错点：布隆和真实数据不同步（新增商品没进布隆，正常请求被挡）；位数组太小导致误判率飙升；把布隆当唯一数据源（它只能回答「可能在不在」）。

**示例代码**
```java
import java.util.BitSet;
import java.util.Random;

public class BloomFilter {
    static class Bloom {
        final BitSet bits;
        final int size;
        final int hashCount;
        int inserted;

        Bloom(int expected, double fpp) {
            // m = -n*ln(p) / (ln2)^2 ; k = m/n * ln2
            double ln2 = Math.log(2);
            this.size = (int) Math.ceil(-expected * Math.log(fpp) / (ln2 * ln2));
            this.hashCount = Math.max(1, (int) Math.round((double) size / expected * ln2));
            this.bits = new BitSet(size);
        }

        static int mix(int h) {
            h ^= h >>> 16;
            h *= 0x85EBCA6B;
            h ^= h >>> 13;
            h *= 0xC2B2AE35;
            h ^= h >>> 16;
            return h;
        }

        int[] positions(String key) {
            int h1 = mix(key.hashCode());
            int h2 = mix(key.hashCode() ^ 0x5BD1E995) | 1;   // 奇数步长，位置更均匀
            int[] pos = new int[hashCount];
            for (int i = 0; i < hashCount; i++) {
                pos[i] = Math.floorMod(h1 + i * h2, size);   // 双重哈希
            }
            return pos;
        }

        void add(String key) {
            for (int p : positions(key)) {
                bits.set(p);
            }
            inserted++;
        }

        boolean mightContain(String key) {
            for (int p : positions(key)) {
                if (!bits.get(p)) {
                    return false;                        // 一定不存在
                }
            }
            return true;                                 // 可能存在（可能误判）
        }

        double fpp() {
            double k = hashCount;
            double n = inserted;
            return Math.pow(1 - Math.exp(-k * n / size), k);   // 理论误判率
        }
    }

    public static void main(String[] args) {
        int expected = 10_000;
        Bloom bloom = new Bloom(expected, 0.01);
        System.out.printf("位数组 %d bit（%.1f KB），哈希 %d 个%n",
                bloom.size, bloom.size / 8.0 / 1024, bloom.hashCount);

        for (int i = 0; i < expected; i++) {
            bloom.add("sku:" + i);
        }

        int miss = 0;
        for (int i = 0; i < expected; i++) {
            if (!bloom.mightContain("sku:" + i)) {
                miss++;                                  // 漏判：绝不该发生
            }
        }
        System.out.printf("已存在 key 的漏判数：%d（必须为 0）%n", miss);

        Random rnd = new Random(42);
        int falsePositive = 0;
        int probes = 100_000;
        for (int i = 0; i < probes; i++) {
            if (bloom.mightContain("ghost:" + rnd.nextInt(1_000_000))) {
                falsePositive++;
            }
        }
        System.out.printf("不存在的 key 误判率：%.2f%%（理论 %.1f%%）%n",
                falsePositive * 100.0 / probes, bloom.fpp() * 100);

        System.out.println();
        System.out.println("【用法】请求 -> 布隆说「不存在」-> 直接返回空（挡住绝大多数穿透）");
        System.out.println("        请求 -> 布隆说「可能存在」-> 查缓存 -> 未命中查库 -> 回填");
        System.out.println("【注意】布隆不支持删除；商品上下架要同步布隆，否则会误挡正常请求");
    }
}
```

### 81-05 缓存一致性：双写与失效

**知识点**
- **一致性不是「强一致」而是「收敛」**：**允许短暂不一致，但最终必须收敛到库里的值**——**缓存是加速层，数据库是唯一真相源（Single Source of Truth）**。
- **四种更新策略对比**：**先写库再删缓存（推荐）**、**先删缓存再写库（有并发漏洞）**、**先写库再更新缓存（并发写顺序乱）**、**延迟双删（缓解但不彻底）**。
- **为什么「先写库再删缓存」最好**：**删是幂等的**，**并发下最坏结果是「多删一次」导致一次回源**，**不会把旧值永久留在缓存里**。
- **「先删缓存再写库」的漏洞**：线程 A 删缓存 → 线程 B 读未命中、读库拿到旧值 → A 写库 → B 把旧值回填 → **缓存永久是旧值**。
- **「更新缓存」的漏洞**：两个写请求 A、B 并发，A 先写库、B 后写库，但 B 先更新缓存、A 后更新缓存 → **缓存留下 A 的旧值**。
- 易错点：以为「先写库再删缓存」就绝对一致（删失败会留旧值，需要重试/订阅 binlog 兜底）；把 TTL 当一致性方案（TTL 只管最终收敛，不管窗口内错多久）。

**示例代码**
```java
import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicReference;

public class CacheConsistency {
    static final Map<String, String> DB = new HashMap<>();
    static final Map<String, String> CACHE = new HashMap<>();

    static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    static void reset() {
        DB.clear();
        CACHE.clear();
        DB.put("price:1001", "100");
        CACHE.put("price:1001", "100");
    }

    // 策略一：先写库，再删缓存（推荐）
    static void writeDbThenEvict(String k, String v) {
        DB.put(k, v);
        sleep(30);                 // 写库后、删缓存前的时间窗
        CACHE.remove(k);
    }

    // 策略二：先删缓存，再写库（有并发漏洞）
    static void evictThenWriteDb(String k, String v) {
        CACHE.remove(k);
        sleep(30);
        DB.put(k, v);
    }

    // 策略三：先写库，再更新缓存（并发写顺序乱）
    static void writeDbThenUpdate(String k, String v) {
        DB.put(k, v);
        sleep(30);
        CACHE.put(k, v);
    }

    static String read(String k) {
        String v = CACHE.get(k);
        if (v != null) {
            return v;
        }
        sleep(10);                 // 模拟读库
        v = DB.get(k);
        if (v != null) {
            CACHE.put(k, v);       // 回填
        }
        return v;
    }

    static void runRace(String name, Runnable writer) throws Exception {
        reset();
        AtomicReference<String> observed = new AtomicReference<>("-");
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(2);

        Thread w = new Thread(() -> {
            try {
                start.await();
                writer.run();
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                done.countDown();
            }
        });
        Thread r = new Thread(() -> {
            try {
                start.await();
                sleep(5);           // 读者在写线程刚动手时进入，正好落在时间窗内
                observed.set(read("price:1001"));
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            } finally {
                done.countDown();
            }
        });
        w.start();
        r.start();
        start.countDown();
        done.await();

        String cacheNow = CACHE.getOrDefault("price:1001", "(空)");
        String dbNow = DB.get("price:1001");
        String afterRead = read("price:1001");
        System.out.printf("%-16s 并发读到=%-4s 结束时缓存=%-5s 再读一次=%-4s 库=%-4s%n",
                name, observed.get(), cacheNow, afterRead, dbNow);
    }

    // 两个写并发：A 先写库但后更新缓存，B 后写库但先更新缓存 -> 缓存留下 A 的旧值
    static void twoWriters(boolean updateCache) throws Exception {
        reset();
        Thread a = new Thread(() -> {
            DB.put("price:1001", "200");        // A 先写库
            sleep(40);
            if (updateCache) {
                CACHE.put("price:1001", "200");
            } else {
                CACHE.remove("price:1001");
            }
        });
        Thread b = new Thread(() -> {
            sleep(20);
            DB.put("price:1001", "300");        // B 后写库
            if (updateCache) {
                CACHE.put("price:1001", "300"); // B 先更新缓存
            } else {
                CACHE.remove("price:1001");
            }
        });
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.printf("  两写并发(%s)：最终库=%s 缓存=%s -> %s%n",
                updateCache ? "更新缓存" : "删缓存",
                DB.get("price:1001"),
                CACHE.getOrDefault("price:1001", "(空)"),
                updateCache ? "缓存被旧值 200 覆盖 <<<" : "缓存为空，下次读回源拿 300 ✓");
    }

    public static void main(String[] args) throws Exception {
        runRace("写库->删缓存", () -> writeDbThenEvict("price:1001", "200"));
        runRace("删缓存->写库", () -> evictThenWriteDb("price:1001", "200"));
        runRace("写库->更新缓存", () -> writeDbThenUpdate("price:1001", "200"));

        System.out.println();
        System.out.println("【两个写并发】");
        twoWriters(true);
        twoWriters(false);

        System.out.println();
        System.out.println("【结论】");
        System.out.println("  写库->删缓存：并发读者可能读到旧值一次（窗口内），但缓存里没有残留，"
                + "下一次读必然回源拿到新值 -> 收敛");
        System.out.println("  删缓存->写库：读者在写库前读到旧值并回填，缓存里留下旧值，"
                + "再读还是旧值 -> 长期不一致（最坏情况）");
        System.out.println("  写库->更新缓存：两个写并发时后写库的可能先更新缓存，"
                + "缓存被旧值覆盖 -> 不一致");
        System.out.println("  所以：删缓存（不更新）+ TTL 兜底 + 必要时订阅 binlog 补偿删除");
    }
}
```

### 81-06 延迟双删与 binlog 订阅

**知识点**
- **延迟双删**：**写库前删一次缓存 → 写库 → 睡 500ms 再删一次**——**第二次删是为了清掉「写库期间被并发读回填的旧值」**，**延迟要大于一次读库 + 回填的耗时**。
- **延迟双删的局限**：**延迟时间靠猜**（读库慢就失效）、**第二次删失败就没兜底**——**所以它只是「降低概率」，不是「保证一致」**。
- **binlog 订阅（canal / Debezium 思路）**：**数据库变更写入 binlog → 订阅组件解析 → 投递到 MQ → 缓存服务消费并删 key**——**业务代码零侵入，且删除可重试、可顺序化**。
- **binlog 方案的优点**：**写路径不关心缓存**（少一次调用）、**删除失败可重试**、**可回放补数据**、**天然支持多级缓存一起失效**。
- **binlog 方案的代价**：**多一个组件要运维**、**有秒级延迟**（不是实时）、**要处理顺序与重复消费（删除幂等所以重复无害）**。
- 易错点：延迟双删的 sleep 写死 100ms（读库 200ms 时完全无效）；binlog 消费失败不重试（缓存永久脏）；以为 binlog 是「强一致」（它仍是最终一致，只是窗口更小更可控）。

**示例代码**
```java

import java.util.ArrayList;
import java.util.Collections;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.LinkedBlockingQueue;

public class DelayedDoubleDelete {
    static final Map<String, String> DB = new HashMap<>();
    static final Map<String, String> CACHE = new HashMap<>();
    static final List<String> LOG = Collections.synchronizedList(new ArrayList<>());

    static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    // 读：命中直接返回；未命中先取库快照，再「慢查询」80ms 后回填。
    // snapshotTaken 用来告诉外部线程：快照已经取到，现在可以改库了。
    static String read(String k, CountDownLatch snapshotTaken) {
        String v = CACHE.get(k);
        if (v != null) {
            LOG.add("读 " + k + " 命中缓存=" + v);
            return v;
        }
        v = DB.get(k);                              // 快照：这一刻库里的值
        if (snapshotTaken != null) {
            snapshotTaken.countDown();
        }
        sleep(80);                                  // 模拟 80ms 慢查询
        if (v != null) {
            CACHE.put(k, v);                        // 回填的是 80ms 前的旧值
            LOG.add("读 " + k + " 未命中，读库=" + v + "，80ms 后回填");
        }
        return v;
    }

    static String read(String k) {
        return read(k, null);
    }

    static void scenarioDelayed(long delayMs) throws InterruptedException {
        DB.clear();
        CACHE.clear();
        LOG.clear();
        DB.put("stock:1", "100");
        CACHE.put("stock:1", "100");

        // 固定时序：删缓存 -> 读者取到旧快照 -> 写库 -> 睡 delayMs -> 第二次删 -> 读者回填
        CACHE.remove("stock:1");
        LOG.add("第 1 次删缓存 stock:1");
        CountDownLatch snapshot = new CountDownLatch(1);
        Thread reader = new Thread(() -> read("stock:1", snapshot));
        reader.start();
        snapshot.await();                           // 读者已经拿到 100，正在 80ms 读库
        DB.put("stock:1", "90");
        LOG.add("写库 stock:1=90");
        sleep(delayMs);                             // 第二次删的延迟
        CACHE.remove("stock:1");
        LOG.add("第 2 次删缓存（延迟 " + delayMs + "ms）");
        reader.join();                              // 等读者把旧值回填完
        String after = read("stock:1");             // 再读一次，看缓存里留下了什么
        boolean converged = String.valueOf(after).equals(DB.get("stock:1"));
        System.out.printf("【延迟双删 delay=%dms】最终读到 %s，缓存=%s，库=%s -> %s%n",
                delayMs, after, CACHE.get("stock:1"), DB.get("stock:1"),
                converged ? "收敛" : "仍是旧值，不一致");
        for (String s : LOG) {
            System.out.println("    " + s);
        }
        System.out.println();
    }

    // ---------- binlog 订阅：业务只写库，缓存由订阅端删 ----------
    static class BinlogSubscriber {
        final LinkedBlockingQueue<String> queue = new LinkedBlockingQueue<>();
        int retries;

        void publish(String key) {
            queue.offer(key);                       // 模拟 binlog 事件
        }

        void consumeOnce(boolean failFirst) {
            String k = queue.poll();
            if (k == null) {
                return;
            }
            if (failFirst) {
                retries++;
                queue.offer(k);                     // 消费失败，重新入队（至少一次语义）
                LOG.add("订阅端删除失败，重新入队 " + k);
                return;
            }
            CACHE.remove(k);
            LOG.add("订阅端删除缓存 " + k + "（幂等，重复无害）");
        }
    }

    public static void main(String[] args) throws InterruptedException {
        scenarioDelayed(50);        // 延迟 50ms < 80ms 读库：第二次删早于回填，旧值留下
        scenarioDelayed(150);       // 延迟 150ms > 80ms 读库：第二次删晚于回填，收敛

        System.out.println("========== binlog 订阅 ==========");
        DB.clear();
        CACHE.clear();
        LOG.clear();
        DB.put("stock:2", "50");
        CACHE.put("stock:2", "50");
        BinlogSubscriber sub = new BinlogSubscriber();

        DB.put("stock:2", "40");                    // 业务只写库，完全不碰缓存
        sub.publish("stock:2");                     // 库变更进 binlog
        sub.consumeOnce(true);                      // 第一次消费失败
        sub.consumeOnce(false);                     // 重试成功
        System.out.println("  最终缓存=" + CACHE.getOrDefault("stock:2", "null")
                + "，库=" + DB.get("stock:2") + "，重试次数=" + sub.retries);
        for (String s : LOG) {
            System.out.println("    " + s);
        }

        System.out.println();
        System.out.println("【选型】延迟双删 = 零额外组件、只是降低概率；binlog = 多一个组件、可重试可回放");
        System.out.println("        对一致性要求高（价格/库存）用 binlog；普通信息类用「删缓存 + TTL」即可");
    }
}
```

### 81-07 热点 key 与本地缓存

**知识点**
- **热点 key**：**单个 key 的 QPS 占全站很大比例**（如秒杀商品、热搜）——**单分片扛不住**，**Redis 集群再大也只落在一个节点上**。
- **热点探测**：**滑动窗口统计 key 访问次数**，**超过阈值（如 1 万/秒）判定为热点**，然后**推送本地缓存 / 拆分 key / 限流**。
- **本地缓存（进程内）**：**命中不走网络（纳秒级）**，**容量小、各节点独立、更新要广播**——**适合「极热 + 变化不频繁」的数据**（81-09 讲多级）。
- **本地缓存的一致性问题**：**N 个节点 N 份副本**，**更新要发广播（MQ/配置中心）**，**广播丢失就有节点长期旧**——**所以本地缓存 TTL 要短（秒级）**。
- **热点 key 的三板斧**：**本地缓存挡在前面**、**key 拆分（hot:1:0~9 分散到多个节点）**、**读写分离 + 限流（保护后端）**。
- 易错点：本地缓存设 1 小时 TTL（更新要等一小时）；用 HashMap 当本地缓存（无上限、无淘汰、会 OOM）；热点 key 拆分后聚合结果算错。

**示例代码**
```java

import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.Map;

public class HotKeyLocalCache {
    // ---------- 极简 LRU 本地缓存 ----------
    static class LocalCache<K, V> extends LinkedHashMap<K, V> {
        final int capacity;
        long hits;
        long misses;

        LocalCache(int capacity) {
            super(16, 0.75f, true);       // accessOrder=true -> LRU
            this.capacity = capacity;
        }

        @Override
        protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
            return size() > capacity;
        }

        V getOrLoad(K k, java.util.function.Function<K, V> loader) {
            V v = get(k);
            if (v != null) {
                hits++;
                return v;
            }
            misses++;
            v = loader.apply(k);
            if (v != null) {
                put(k, v);
            }
            return v;
        }
    }

    // ---------- 滑动窗口热点探测 ----------
    static class HotKeyDetector {
        final Map<String, int[]> windows = new HashMap<>();
        final int buckets;
        final int threshold;

        HotKeyDetector(int buckets, int threshold) {
            this.buckets = buckets;
            this.threshold = threshold;
        }

        void record(String key, long nowSec) {
            int[] w = windows.computeIfAbsent(key, k -> new int[buckets]);
            w[(int) (nowSec % buckets)]++;
        }

        int count(String key) {
            int[] w = windows.get(key);
            if (w == null) {
                return 0;
            }
            int sum = 0;
            for (int v : w) {
                sum += v;
            }
            return sum;
        }

        boolean isHot(String key) {
            return count(key) >= threshold;
        }
    }

    public static void main(String[] args) {
        Map<String, String> redis = new HashMap<>();
        for (int i = 1; i <= 100; i++) {
            redis.put("sku:" + i, "商品" + i);
        }
        LocalCache<String, String> local = new LocalCache<>(16);
        HotKeyDetector detector = new HotKeyDetector(10, 50);

        // 模拟：sku:7 是热点（占 60% 流量），其余长尾
        int tailRedis = 0;                 // 长尾：直接走 Redis
        int hotRedis = 0;                  // 热点：本地未命中才走 Redis
        int hotLocal = 0;                  // 热点：本地命中
        long now = 1000;
        for (int i = 0; i < 1000; i++) {
            String key = (i % 10 < 6) ? "sku:7" : "sku:" + (1 + (i * 37) % 100);
            detector.record(key, now);
            if (detector.isHot(key)) {
                long missBefore = local.misses;
                String v = local.getOrLoad(key, redis::get);
                if (local.misses > missBefore) {
                    hotRedis++;
                } else {
                    hotLocal++;
                }
                if (v == null) {
                    throw new IllegalStateException("热点 key 不存在：" + key);
                }
            } else {
                redis.get(key);            // 还没被判为热点，走 Redis
                tailRedis++;
            }
            if (i % 100 == 99) {
                now++;                     // 每 100 次请求推进 1 秒（滑动窗口按秒记）
            }
        }

        int redisCalls = tailRedis + hotRedis;
        System.out.printf("热点探测：sku:7 窗口内计数=%d，阈值=50，判定=%s%n",
                detector.count("sku:7"), detector.isHot("sku:7"));
        System.out.printf("本地缓存：容量=%d 条，命中 %d 次，未命中 %d 次%n",
                local.capacity, local.hits, local.misses);
        System.out.printf("Redis 调用：%d 次 / 总请求 1000 次（%.1f%%）%n",
                redisCalls, redisCalls / 10.0);
        System.out.printf("  其中 长尾直连 %d 次 + 热点判热前/首次回源 %d 次%n", tailRedis, hotRedis);
        System.out.printf("  热点命中本地缓存 %d 次，这 %d 次完全没走网络%n", hotLocal, hotLocal);

        System.out.println();
        System.out.println("【热点三板斧】");
        System.out.println("  1. 本地缓存：热点 key 落在每个进程内，不打 Redis（纳秒级）");
        System.out.println("  2. key 拆分：hot:1 拆成 hot:1:0 ~ hot:1:9，分散到 10 个分片");
        System.out.println("  3. 限流兜底：热点超出后端能力时，宁可拒绝也不把 DB 打挂");
        System.out.println();
        System.out.println("【本地缓存注意】TTL 必须短（1~5 秒），更新靠广播；否则多节点数据长期不一致");
        System.out.println("【探测注意】判热需要一点时间（本示例前 50 次仍走 Redis），"
                + "所以大促热点要靠「预热 + 人工白名单」补上这段窗口");
    }
}
```

### 81-08 缓存预热与降级

**知识点**
- **缓存预热**：**上线/重启/大促前，把确定会被访问的数据主动写进缓存**——**避免「冷启动瞬间全部回源」**（发布后 1 分钟打挂库的经典事故）。
- **预热的三种做法**：**启动时批量加载**（适合小数据量）、**定时任务跑热点清单**（适合可预测热点）、**流量回放/影子流量预热**（适合大促前，80-08）。
- **降级（Degrade）**：**缓存不可用时，用「本地缓存 / 静态兜底值 / 直接限流」代替正常路径**——**降级的目标不是「功能完好」，而是「不雪崩」**。
- **降级的触发条件**：**缓存错误率 > 阈值**、**缓存 RT > 阈值**、**连接池耗尽**、**手动开关（大促值守）**——**要能自动触发，也要能手動一键**。
- **降级的分级**：**L1 只读降级**（写路径保留、读走兜底）、**L2 功能降级**（关掉非核心模块）、**L3 限流熔断**（保住核心链路）——**按影响面从小到大**。
- 易错点：预热把整个库全加载（内存爆、启动慢）；降级后没恢复机制（一直降级）；降级兜底值不设过期（永远返回旧值）。

**示例代码**
```java

import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class CacheWarmupDegrade {
    static final Map<String, String> DB = new HashMap<>();
    static final Map<String, String> REDIS = new HashMap<>();
    static final Map<String, String> LOCAL = new HashMap<>();

    static int dbCalls;
    static boolean redisDown;
    static final int DB_MS = 2;                     // 单次读库 2ms

    static void init() {
        for (int i = 1; i <= 20; i++) {
            DB.put("sku:" + i, "商品" + i);
        }
    }

    static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    static String loadFromDb(String k) {
        dbCalls++;
        sleep(DB_MS);
        return DB.get(k);
    }

    // ---------- 预热：按热点清单批量灌缓存 ----------
    static void warmupByHotList(List<String> hotKeys) {
        long t0 = System.nanoTime();
        int loaded = 0;
        for (String k : hotKeys) {
            String v = loadFromDb(k);
            if (v != null) {
                REDIS.put(k, v);
                loaded++;
            }
        }
        long ms = (System.nanoTime() - t0) / 1_000_000;
        System.out.printf("【预热】按热点清单加载 %d 个 key 到 Redis，耗时 %dms（单次读库 %dms），DB 调用 %d 次%n",
                loaded, ms, DB_MS, dbCalls);
    }

    // ---------- 正常读 + 降级读 ----------
    static String read(String k, boolean degrade) {
        if (!redisDown) {
            String v = REDIS.get(k);
            if (v != null) {
                return v + "(redis)";
            }
            v = loadFromDb(k);
            if (v != null) {
                REDIS.put(k, v);
            }
            return v == null ? null : v + "(db->redis)";
        }
        if (degrade) {
            String v = LOCAL.get(k);
            if (v != null) {
                return v + "(local-degraded)";
            }
            return "默认兜底文案(degraded)";        // 静态兜底，绝不打库
        }
        return loadFromDb(k) + "(db-no-degrade)";   // 未降级：全部打库
    }

    public static void main(String[] args) {
        init();
        List<String> hot = List.of("sku:1", "sku:2", "sku:3", "sku:4", "sku:5");

        dbCalls = 0;
        warmupByHotList(hot);

        System.out.println();
        System.out.println("【冷启动对比】");
        dbCalls = 0;
        for (String k : hot) {
            read(k, false);
        }
        System.out.printf("  预热后读 5 个热点：DB 调用 %d 次%n", dbCalls);

        REDIS.clear();
        dbCalls = 0;
        for (String k : hot) {
            read(k, false);
        }
        System.out.printf("  不预热读 5 个热点：DB 调用 %d 次（冷启动放大）%n", dbCalls);

        System.out.println();
        System.out.println("【放大估算】发布后第 1 秒，2 万 QPS 全部未命中 -> 2 万次读库");
        System.out.println("  连接池 100、单次读库 20ms -> 上限 = 100 / 0.02s = 5000 次/秒");
        System.out.println("  2 万 QPS 是上限的 4 倍 -> 排队、超时、连接池耗尽，第一秒就把库打挂");
        System.out.println("  -> 预热的意义：上线第一秒就有 90% 命中，回源只剩 2000，落在 5000 的上限内");

        System.out.println();
        System.out.println("【降级】缓存集群宕机，本地缓存兜底");
        LOCAL.putAll(REDIS);
        redisDown = true;
        dbCalls = 0;
        for (String k : hot) {
            System.out.println("  " + k + " -> " + read(k, true));
        }
        System.out.printf("  降级后 DB 调用 %d 次（应为 0）%n", dbCalls);

        dbCalls = 0;
        for (String k : hot) {
            read(k, false);
        }
        System.out.printf("  不降级时 DB 调用 %d 次（可能打挂库）%n", dbCalls);

        System.out.println();
        System.out.println("【降级分级】L1 只读降级 -> L2 关非核心 -> L3 限流熔断");
        System.out.println("【要点】预热要有热点清单；降级要能自动触发 + 手动开关 + 自动恢复");
    }
}
```

### 81-09 多级缓存与 TTL 抖动

**知识点**
- **多级缓存结构**：**本地缓存（L1，纳秒）→ 分布式缓存（L2，百微秒）→ 数据库（L3，毫秒）**——**每层挡住一部分流量，逐级收敛**。
- **每层的容量与 TTL 不同**：**L1 小容量短 TTL（秒级）**、**L2 大容量长 TTL（分钟~小时）**——**TTL 越短越新，越长越省**。
- **TTL 抖动（jitter）**：**TTL = 基准 + random(0, 抖动窗口)**——**把同一批写入的 key 的过期时间摊开**，避免整点雪崩（81-03）。
- **多级缓存的一致性**：**更新时 L2 删除 + 广播让所有节点删 L1**——**广播丢失靠 L1 短 TTL 兜底**，**所以 L1 的 TTL 就是「最大不一致时间」**。
- **穿透率与放大**：**L1 未命中 → L2 未命中 → DB**，**如果 L1 命中率 90%、L2 命中率 90%，DB 只承担 1%**——**这就是多级缓存的乘数效应**。
- 易错点：L1 设 30 分钟 TTL（等于放弃一致性）；只删 L2 不广播（各节点 L1 长期旧）；抖动窗口大于基准 TTL（等于随机过期）。

**示例代码**
```java

import java.util.ArrayList;
import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Random;

public class MultiLevelCache {
    static final Map<String, String> DB = new HashMap<>();
    static final Map<String, String> L2 = new HashMap<>();
    static final Random RND = new Random(11);
    static final int L1_CAPACITY = 20;

    // L1：容量只有 20 条的小 LRU（accessOrder=true，最久未用的先淘汰）
    static class LocalCache extends LinkedHashMap<String, String> {
        LocalCache() {
            super(16, 0.75f, true);
        }

        @Override
        protected boolean removeEldestEntry(Map.Entry<String, String> eldest) {
            return size() > L1_CAPACITY;
        }
    }

    static LocalCache L1 = new LocalCache();
    static int l1Hit;
    static int l2Hit;
    static int dbHit;

    static int jitterTtl(int baseSec, int windowSec) {
        return baseSec + RND.nextInt(windowSec + 1);
    }

    static String get(String k, boolean useL1) {
        if (useL1) {
            String v = L1.get(k);
            if (v != null) {
                l1Hit++;
                return v;
            }
        }
        String v = L2.get(k);
        if (v != null) {
            l2Hit++;
            if (useL1) {
                L1.put(k, v);                   // 回填 L1
            }
            return v;
        }
        dbHit++;
        v = DB.get(k);
        if (v != null) {
            L2.put(k, v);
            if (useL1) {
                L1.put(k, v);
            }
        }
        return v;
    }

    // 同一份请求序列跑两遍：一遍只有 L2，一遍 L1+L2
    static int[] run(List<String> seq, boolean useL1) {
        L1 = new LocalCache();
        L2.clear();
        l1Hit = 0;
        l2Hit = 0;
        dbHit = 0;
        for (String k : seq) {
            get(k, useL1);
        }
        return new int[]{l1Hit, l2Hit, dbHit};
    }

    static void invalidate(String k) {
        L2.remove(k);
        L1.remove(k);                           // 单机演示；真实环境要广播给所有节点
        System.out.println("  失效 " + k + " -> L1/L2 均已删除（其他节点靠广播 + L1 短 TTL）");
    }

    public static void main(String[] args) {
        for (int i = 1; i <= 1000; i++) {
            DB.put("sku:" + i, "商品" + i);
        }

        // 请求序列：80% 集中在 50 个热 key（超出 L1 的 20 条容量），20% 长尾
        List<String> seq = new ArrayList<>();
        Random r = new Random(11);
        for (int i = 0; i < 10_000; i++) {
            seq.add(i % 10 < 8
                    ? "sku:" + (1 + r.nextInt(50))
                    : "sku:" + (1 + r.nextInt(1000)));
        }

        int[] onlyL2 = run(seq, false);
        int[] both = run(seq, true);
        int total = seq.size();

        System.out.println("同一份 10000 次请求，跑两遍：");
        System.out.printf("  只有 L2      ：L2 命中 %5d，DB 回源 %5d (%.1f%%)%n",
                onlyL2[1], onlyL2[2], onlyL2[2] * 100.0 / total);
        System.out.printf("  L1(%d 条)+L2 ：L1 命中 %5d (%.1f%%)，L2 命中 %5d，DB 回源 %5d (%.1f%%)%n",
                L1_CAPACITY, both[0], both[0] * 100.0 / total, both[1], both[2],
                both[2] * 100.0 / total);
        System.out.printf("  乘数效应：L1 挡掉 %.1f%%，落到 L2 的请求从 %d 降到 %d（降 %.0f%%）%n",
                both[0] * 100.0 / total, onlyL2[1] + onlyL2[2], both[1] + both[2],
                (1 - (both[1] + both[2]) * 1.0 / (onlyL2[1] + onlyL2[2])) * 100);
        System.out.printf("  注意：DB 回源没变（热 key 本来在 L2 就命中），L1 省的是 Redis 的 QPS 与网络往返%n");

        System.out.println();
        System.out.println("【TTL 抖动】同一批写入的 10 个 key，过期时间分布：");
        StringBuilder sb = new StringBuilder("  ");
        for (int i = 0; i < 10; i++) {
            sb.append(jitterTtl(1800, 300)).append("s ");
        }
        System.out.println(sb.toString().trim());
        System.out.println("  基准 1800s + 0~300s 随机，避免 1800s 整点集中过期");

        System.out.println();
        System.out.println("【更新】价格变更");
        DB.put("sku:1", "商品1-新价");
        invalidate("sku:1");
        System.out.println("  下次读 sku:1 -> " + get("sku:1", true) + "（回源并回填两层）");

        System.out.println();
        System.out.println("【要点】L1 短 TTL 定「最大不一致时间」；L2 长 TTL 省内存；TTL 一律加抖动");
    }
}
```

### 81-10 缓存监控与命中率治理

**知识点**
- **四个必看指标**：**命中率**（hits/(hits+misses)）、**回源 QPS**、**缓存 RT（P99）**、**内存使用率与大 key 数量**——**命中率掉了就是事故前兆**。
- **命中率要分层看**：**整体命中率**会掩盖问题，**按 key 前缀/业务线分组**才能定位「哪类数据在打库」（如 `sku:*` 96%、`order:*` 38%）。
- **命中率低的四个原因**：**TTL 太短**（频繁过期）、**key 设计太细**（同一对象拆成多个 key，回填不完整）、**缓存容量不足**（LRU 把热 key 挤掉）、**写入路径误删**（写一次删一片）。
- **大 key 与热 key**：**大 key**（单个 value 几 MB）会拖慢整个实例、**热 key**（单 key QPS 过高）会打爆单分片——**都要靠采样统计提前发现**。
- **监控落地**：**应用侧埋点（命中/未命中/回源耗时）+ 缓存侧指标（内存/连接/慢查询）+ 告警（命中率跌破阈值、回源 QPS 突增）**。
- 易错点：只监控缓存 RT 不看命中率（RT 好但一直回源）；命中率按总量算不分业务（掩盖局部问题）；不做容量水位告警（OOM 才发现）。

**示例代码**
```java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.TreeMap;

public class CacheMetrics {
    static class Counter {
        long hits;
        long misses;
        long totalNanos;

        void hit(long nanos) {
            hits++;
            totalNanos += nanos;
        }

        void miss(long nanos) {
            misses++;
            totalNanos += nanos;
        }

        long total() {
            return hits + misses;
        }

        double hitRate() {
            return total() == 0 ? 0 : (double) hits / total();
        }

        double avgMs() {
            return total() == 0 ? 0 : totalNanos / 1_000_000.0 / total();
        }
    }

    static void report(String name, Counter c, double warnThreshold) {
        String verdict = c.hitRate() < warnThreshold ? "告警：命中率低于 " + (int) (warnThreshold * 100) + "%"
                : "正常";
        System.out.printf("  %-12s 请求=%6d 命中率=%5.1f%% 平均=%.2fms  %s%n",
                name, c.total(), c.hitRate() * 100, c.avgMs(), verdict);
    }

    public static void main(String[] args) {
        Map<String, Counter> byPrefix = new TreeMap<>();
        byPrefix.put("sku:", new Counter());
        byPrefix.put("order:", new Counter());
        byPrefix.put("user:", new Counter());
        byPrefix.put("cfg:", new Counter());

        // 模拟真实流量：sku 命中高、order 命中低（TTL 太短）、user 中等、cfg 极高
        double[] hitRates = {0.96, 0.38, 0.82, 0.995};
        String[] prefixes = {"sku:", "order:", "user:", "cfg:"};
        int[] volumes = {50_000, 20_000, 15_000, 5_000};

        for (int i = 0; i < prefixes.length; i++) {
            Counter c = byPrefix.get(prefixes[i]);
            for (int n = 0; n < volumes[i]; n++) {
                boolean hit = (n % 1000) < hitRates[i] * 1000;
                long cost = hit ? 300_000L : 8_000_000L;      // 命中 0.3ms，未命中 8ms
                if (hit) {
                    c.hit(cost);
                } else {
                    c.miss(cost);
                }
            }
        }

        System.out.println("【按 key 前缀分组】");
        Counter all = new Counter();
        for (Map.Entry<String, Counter> e : byPrefix.entrySet()) {
            report(e.getKey(), e.getValue(), 0.90);
            all.hits += e.getValue().hits;
            all.misses += e.getValue().misses;
            all.totalNanos += e.getValue().totalNanos;
        }
        System.out.println();
        System.out.println("【整体】");
        report("ALL", all, 0.90);
        System.out.println("  -> 整体 81% 只说明「有问题」，说不出是谁：分前缀才看到 order 38%、user 82%");

        System.out.println();
        System.out.println("【order 命中率低的排查清单】");
        Map<String, String> checks = new LinkedHashMap<>();
        checks.put("TTL", "order 列表 TTL=30s，太短 -> 调到 5 分钟 + 抖动");
        checks.put("key 粒度", "把 order:list:user:1 拆成 3 个 key，回填不完整");
        checks.put("容量", "实例内存 80%，LRU 把 order 挤掉 -> 扩内存或降 TTL");
        checks.put("写路径", "每次下单删 order:list:*，误删一片 -> 改为精确删除");
        checks.forEach((k, v) -> System.out.printf("  %-10s %s%n", k, v));

        System.out.println();
        System.out.println("【告警规则】命中率 < 90% 持续 5 分钟 / 回源 QPS 突增 3 倍 / 内存 > 85% / 大 key > 1MB");
    }
}
```

**课后练习**
1. 把 order 的 TTL 从 30 秒改成 300 秒，重新计算命中率，说明 TTL 与命中率的定量关系。
2. 给 report 加 P99 统计（用数组存每次耗时），观察命中率正常但 P99 很差的情况。
3. 思考题：为什么「整体命中率」会掩盖问题？举一个两个业务线命中率互相掩盖的例子。

### 81-11 综合案例：商品详情页缓存改造

**知识点**
- **场景约束**：**QPS 2 万、DB 上限 3000、P99 要求 50ms、改价 1 秒内可见、大促零点不能雪崩**——**五个约束决定方案，不是「加个 Redis」就完事**。
- **方案分层**：**L1 本地缓存（热点商品，1 秒 TTL）+ L2 Redis（全量商品，5 分钟 + 抖动）+ 布隆过滤器（挡穿透）+ 互斥锁（防击穿）**。
- **写路径**：**改价先写库 → 删 Redis → 发广播删各节点 L1**——**1 秒内可见靠 L1 的 1 秒 TTL 兜底**，**广播丢失也不会超过 1 秒**。
- **大促保护**：**预热 Top 1 万商品**、**TTL 抖动 0~5 分钟**、**限流（超过 2.5 万 QPS 拒绝）**、**降级开关（Redis 挂 → 只读 L1 + 兜底文案）**。
- **验证指标**：**命中率 ≥ 95%**、**回源 QPS < 1000**、**P99 < 50ms**、**改价可见延迟 < 1s**、**压测 2.5 万 QPS 无错误**。
- 易错点：只做 Redis 不做 L1（热点仍打爆单分片）；改价只删 Redis 不广播（L1 长期旧）；不做预热（零点冷启动打穿）。

**示例代码**
```java

import java.util.ArrayList;
import java.util.BitSet;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Random;
import java.util.concurrent.atomic.AtomicLong;

public class ProductDetailCache {
    // ---------- 三层数据 ----------
    static final Map<String, Integer> DB = new HashMap<>();
    static final Map<String, Integer> REDIS = new HashMap<>();
    static final List<Map<String, Entry>> NODES = List.of(new HashMap<>(), new HashMap<>());
    static final BitSet BLOOM = new BitSet(1 << 16);
    static final int L1_TTL_MS = 1000;              // L1 短 TTL = 最大不一致时间

    record Entry(int price, long expireAt) {
    }

    static final AtomicLong L1_HIT = new AtomicLong();
    static final AtomicLong L2_HIT = new AtomicLong();
    static final AtomicLong DB_HIT = new AtomicLong();
    static final AtomicLong BLOOM_BLOCK = new AtomicLong();
    static final Random RND = new Random(3);

    static void bloomAdd(String k) {
        BLOOM.set(Math.floorMod(k.hashCode(), BLOOM.size()));
    }

    static boolean bloomMaybe(String k) {
        return BLOOM.get(Math.floorMod(k.hashCode(), BLOOM.size()));
    }

    static int jitterTtlMs(int baseMs, int windowMs) {
        return baseMs + RND.nextInt(windowMs + 1);
    }

    // ---------- 读路径：布隆 -> L1 -> L2 -> 单飞回源 ----------
    static Integer getPrice(int node, String sku, long now) {
        if (!bloomMaybe(sku)) {
            BLOOM_BLOCK.incrementAndGet();          // 一定不存在，直接挡掉
            return null;
        }
        Map<String, Entry> l1 = NODES.get(node);
        Entry e = l1.get(sku);
        if (e != null && e.expireAt() > now) {
            L1_HIT.incrementAndGet();
            return e.price();
        }
        Integer p = REDIS.get(sku);
        if (p != null) {
            L2_HIT.incrementAndGet();
            l1.put(sku, new Entry(p, now + L1_TTL_MS));
            return p;
        }
        synchronized (ProductDetailCache.class) {   // 防击穿：单飞，同一 key 只有一个线程回源
            p = REDIS.get(sku);                     // 进锁后再查一次，避免重复回源
            if (p != null) {
                L2_HIT.incrementAndGet();
                l1.put(sku, new Entry(p, now + L1_TTL_MS));
                return p;
            }
            DB_HIT.incrementAndGet();
            p = DB.get(sku);
            if (p != null) {
                REDIS.put(sku, p);
                l1.put(sku, new Entry(p, now + L1_TTL_MS));
            }
            return p;
        }
    }

    // ---------- 写路径：先写库 -> 删 Redis -> 广播删各节点 L1 ----------
    static void updatePrice(String sku, int newPrice) {
        DB.put(sku, newPrice);
        REDIS.remove(sku);
        for (Map<String, Entry> node : NODES) {
            node.remove(sku);
        }
    }

    public static void main(String[] args) {
        int totalSku = 5000;
        for (int i = 1; i <= totalSku; i++) {
            String sku = "sku:" + i;
            DB.put(sku, 100 + i);
            bloomAdd(sku);
        }

        // ---------- 预热：只把 Top 500 进 Redis（全量 5000 装不下也不该装） ----------
        for (int i = 1; i <= 500; i++) {
            REDIS.put("sku:" + i, DB.get("sku:" + i));
        }
        long redisTtl = jitterTtlMs(300_000, 300_000);
        System.out.printf("【预热】Top 500 商品进 Redis（TTL %dms，含抖动），其余 4500 个按需回源%n",
                redisTtl);

        // ---------- 模拟 2 万请求打到 2 个节点 ----------
        long now = 0;
        int total = 20_000;
        for (int i = 0; i < total; i++) {
            if (i % 100 == 0) {
                now += 100;                          // 每 100 请求推进 100ms，共 20 秒
            }
            String sku = (i % 100 < 97)
                    ? "sku:" + (1 + RND.nextInt(100))              // 97% 打在 Top 100 上
                    : "sku:" + (501 + RND.nextInt(4500));          // 3% 长尾，Redis 里没有
            getPrice(i % 2, sku, now);
        }

        long l1 = L1_HIT.get();
        long l2 = L2_HIT.get();
        long db = DB_HIT.get();
        System.out.println();
        System.out.printf("【压测结果】正常请求 %d（2 个节点各一半，时间跨度 20 秒）%n", total);
        System.out.printf("  L1 命中 %6d (%5.1f%%)%n", l1, l1 * 100.0 / total);
        System.out.printf("  L2 命中 %6d (%5.1f%%)%n", l2, l2 * 100.0 / total);
        System.out.printf("  DB 回源 %6d (%5.2f%%)%n", db, db * 100.0 / total);
        System.out.printf("  命中率 %.2f%%（要求 >= 95%%）%n", (l1 + l2) * 100.0 / total);
        System.out.printf("  回源 QPS ≈ %.0f（要求 < 1000，DB 上限 3000）%n", db * 1.0 / 20);

        // ---------- 穿透请求单独看：布隆挡掉，一次库都不打 ----------
        long dbBefore = DB_HIT.get();
        for (int i = 0; i < 2000; i++) {
            getPrice(i % 2, "ghost:" + i, now);       // 2000 次不存在的 sku
        }
        System.out.printf("  另有 2000 次穿透请求：布隆拦截 %d 次，DB 回源增加 %d 次%n",
                BLOOM_BLOCK.get(), DB_HIT.get() - dbBefore);

        // ---------- 改价可见性：一个节点收到广播，一个节点丢广播 ----------
        System.out.println();
        System.out.println("【改价时间线】sku:1 当前价 101，两个节点都已缓存");
        long t = now + 10_000;
        getPrice(0, "sku:1", t);
        getPrice(1, "sku:1", t);
        System.out.println("  T+0ms   写库 price=999");
        updatePrice("sku:1", 999);
        System.out.println("  T+1ms   删 Redis + 广播删 2 个节点 L1");
        System.out.printf("  T+2ms   节点0 读到 %s（广播到了，立刻是新值）%n", getPrice(0, "sku:1", t + 2));
        NODES.get(1).put("sku:1", new Entry(101, t + L1_TTL_MS));   // 模拟节点1 漏收广播
        System.out.printf("  T+500ms 节点1 读到 %s（漏收广播，L1 里还是旧值）%n", getPrice(1, "sku:1", t + 500));
        System.out.printf("  T+1500ms 节点1 读到 %s（L1 的 1 秒 TTL 到期，回源拿新值）%n",
                getPrice(1, "sku:1", t + 1500));
        System.out.println("  -> 所以 L1 的 TTL 就是「最大不一致时间」，广播只是把窗口从 1s 缩到 1ms");

        System.out.println();
        System.out.println("【降级】Redis 不可用时：L1 命中继续服务，未命中返回兜底价 + 限流");
        System.out.println("【结论】布隆挡穿透、单飞防击穿、L1+L2 分摊回源、广播 + 短 TTL 保可见性、"
                + "抖动防雪崩，五个约束逐一被满足");
    }
}
```

## 本章综合练习

### 综合题：商品详情页的缓存改造

**场景**

商品详情页 QPS 2 万，DB 单机只能扛 3000，现在 70% 的请求在打库，P99 已经 800ms。要求：加一层缓存把 P99 压到 50ms 以内，同时保证「改价后 1 秒内可见」，还要防止大促零点整批 key 同时过期把库打穿。请给出完整的缓存方案与验证数据。

**任务**
1. 算收益：按当前 QPS 与命中率目标（90%/95%/98%）估算回源 QPS 与平均延迟，说明为什么 90% 不够。
2. 选模式：商品详情是读多写少、允许秒级旧值，选 Cache-Aside 并说明写路径为什么是「先写库再删缓存」。
3. 防三大故障：为空结果加 60 秒空值缓存、给热点 key 加互斥锁或逻辑过期、给 TTL 加 0~5 分钟随机抖动。
4. 做验证：模拟 2 万 QPS 跑一遍，输出命中率、回源 QPS、P50/P99，以及「改价后缓存何时失效」的时间线。
5. 补降级：缓存集群整体不可用时，用本地缓存 + 限流把流量挡在 DB 之外，给出降级开关的触发条件。

**验收清单**
- [ ] 命中率 ≥ 95%，回源 QPS 从 2 万降到 1000 以内，有计算过程不是拍脑袋。
- [ ] 写路径是「先写库、再删缓存」，并能说清并发下为什么不能「更新缓存」。
- [ ] 穿透/击穿/雪崩三种故障各有一条具体对策，且能在代码里找到对应实现。
- [ ] 改价后 1 秒内可见，有一致性时间线（写库 → 删缓存 → 下次读回填）佐证。
- [ ] 有降级开关与触发阈值，缓存全挂时 DB 不被打穿。
