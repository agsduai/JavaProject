# 第46章 湖仓一体与数据平台

第43章解决了实时计算，本章解决"数据最终住在哪里"。数据库存不下分析负载，数据湖灵活却容易变沼泽——湖仓一体用表格式（Iceberg）把"目录里的文件"升级成"有事务、有版本的表"：快照即事务、时间旅行即回滚、schema 演进不再重写数据。本章按「从数仓到数据湖 → 列式存储与 Parquet → 对象存储 → Hive 元数据 → Iceberg 表格式 → 批流一体存储 → MPP 即席查询 → 数据质量治理 → 数据集成 → 平台服务化 → 订单湖仓案例」的顺序讲。所有示例仍是纯 JDK：行列存取的 IO 对比真实计算，谓词下推与 Row Group 裁剪真跑，快照链与乐观并发提交真实推演，小文件 compaction、质量规则阻断、幂等重跑全部真实闭环，不需要 S3、Spark 或 Trino 集群。

### 46-01 从数仓到数据湖

**知识点**
- **数仓与数据湖的分野是 schema 何时确定**：数仓（schema-on-write）——数据写入前先定义表结构，质量高但灵活差；数据湖（schema-on-read）——原始数据原样存（JSON/日志/CSV），用到时再解释，灵活但容易变"数据沼泽"（无目录、无格式、无质量）。**湖仓一体（lakehouse）= 湖的灵活 + 仓的治理**。
- **数据平台的典型分层**（43-09 实时数仓分层的离线对应）：ODS 原始层（原样备份）、DWD 明细层（清洗/拆列/关联）、DWS 汇总层（预聚合）、ADS 应用层（报表/接口）。**层与层之间的 transform 用 SQL/DAG 调度（Airflow 类）编排**。
- **为什么"直接把数据丢 HDFS"会变沼泽**：无 schema 契约（上游改列下游炸）、无元数据（没人知道这张表是谁的）、无小文件治理（千万个小文件拖垮文件系统）。**治理先行：表注册、责任人、格式规范、生命周期**（46-08 细讲）。
- **湖仓一体的技术三角**：**表格式**（Iceberg/Hudi/Delta：给"一堆文件"加事务与版本）、**引擎**（Spark/Trino/Flink 统一读写）、**目录/元数据**（Hive Metastore 或 Glue 类）。**表格式是湖仓一体的核心创新**——它让"目录里的文件"拥有了数据库表的能力（46-05）。
- **批流一体的数据侧形态**：同一份湖表既被离线批任务读（T+1 报表）、也被流任务写（CDC 持续写入，43-09）——**存储统一后"Lambda 双跑"（43-01）在数据侧真正消失**。
- **Java 工程师的位置**：数据平台的服务化层（46-10）——特征 API、指标 API、数据导出服务，多为 Java 实现；Flink 作业本身也是 Java/SQL。**数据平台不是"数据团队专属"，业务 Java 团队是主要生产者与消费者**。
- 易错点：把数据湖当备份盘（丢进去不管，三个月后没人认识）；每张表都没有责任人（坏了没人修）；不分层全在 ADS 直接改（口径失控）；以为湖仓一体是买一个产品（核心是治理流程 + 表格式选型）。

### 46-02 列式存储与 Parquet

**知识点**
- **行存与列存 answering 的查询不同**：行存（MySQL）按行组织——OLTP 点查改一行快；列存（Parquet）按列组织——分析查询"只碰 3 列扫 10 亿行"时 IO 直降一个数量级。**OLTP 用行存，OLAP 用列存**是存储选型的第一判断。
- **列存的两个物理收益**：**裁剪**（查询只读需要的列文件段）+ **压缩**（同列类型一致、基数低，RLE/字典编码压缩率远高于行存）。真实分析负载压缩比常见 5~10 倍。
- **Parquet 的文件结构**：Row Group（行组，通常 128MB~1GB，行存段）内按 Column Chunk 分列，列内分 Page；**每个 Column Chunk 带统计信息（min/max/null 计数）**——查询谓词（WHERE date='11-17'）直接跳过不含目标的 Row Group，这就是**谓词下推**的物理基础。
- **分区与裁剪的双层结构**：目录分区（date=2026-11-17/ 按目录裁剪）+ 文件内统计（Row Group 裁剪）。**分区键的选择**（高频过滤列、基数适中）直接决定查询速度——分区选错了查询永远全扫。
- **写入端的设计**：小文件是列存的死敌（每个文件一个 footer，打开成本高）——**写入攒批**（每 128MB~1GB 落一个文件）、流式写入用 compaction 合并（46-06）。
- **与 MySQL 的分工**：MySQL 服务交易（行存 + 索引）；Parquet 湖表服务分析（列存 + 扫描）。**同一个业务两类存储并存**，由 CDC（43-09/46-09）连接。
- 易错点：把高频更新数据放列存（更新 = 重写整个文件，代价爆炸）；分区键选低基数列（每分区几行，小文件爆炸）；Row Group 太小（统计信息开销占比高）；忽略 null 与编码列的统计（裁剪失效）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ParquetColumnar {
    /** 模拟 Row Group 统计：min/max 用于谓词裁剪 */
    record RowGroup(int id, String dateMin, String dateMax, double amountMin,
                    double amountMax, long rows, int bytes) {
        boolean mayMatch(String dateFilter) {
            return dateFilter.compareTo(dateMin) >= 0 && dateFilter.compareTo(dateMax) <= 0;
        }
    }

    static void rowGroupPruning() {
        System.out.println("【谓词下推：统计信息跳过无关 Row Group】");
        List<RowGroup> groups = List.of(
                new RowGroup(1, "2026-11-15", "2026-11-15", 10, 500, 1_000_000, 130),
                new RowGroup(2, "2026-11-16", "2026-11-16", 12, 800, 1_000_000, 128),
                new RowGroup(3, "2026-11-17", "2026-11-17", 15, 999, 1_000_000, 132));
        String filter = "2026-11-17";
        long scanned = 0, skipped = 0;
        for (RowGroup g : groups) {
            if (g.mayMatch(filter)) {
                scanned += g.bytes();
                System.out.printf("  RG%d [%s~%s] -> 读取 %dMB%n", g.id(), g.dateMin(), g.dateMax(), g.bytes());
            } else {
                skipped += g.bytes();
                System.out.printf("  RG%d [%s~%s] -> 跳过（统计不含目标日期）%n", g.id(), g.dateMin(), g.dateMax());
            }
        }
        System.out.printf("  扫描 %dMB / 总 %dMB，省 %.0f%% IO%n", scanned, scanned + skipped,
                skipped * 100.0 / (scanned + skipped));
        System.out.println();
    }

    static void columnVsRow() {
        System.out.println("【同一查询：行存 vs 列存的 IO 对比】");
        long rows = 1_000_000_000L;
        int rowWidth = 200, neededCols = 3, colWidth = 8;
        long rowIo = rows * rowWidth;                      // 行存：每行全字段
        long colIo = rows * neededCols * colWidth;         // 列存：只碰 3 列
        System.out.printf("  行存读取 %d 行 × %dB = %.0f GB%n", rows, rowWidth, rowIo / 1024.0 / 1024 / 1024);
        System.out.printf("  列存读取 %d 行 × %d 列 × %dB = %.1f GB（%.0f 倍差距，压缩后更小）%n",
                rows, neededCols, colWidth, colIo / 1024.0 / 1024 / 1024,
                (double) rowIo / colIo);
        System.out.println("  结论：宽表 + 少列查询的分析负载，列存是数量级优势");
        System.out.println();
    }

    static void partitionChoice() {
        System.out.println("【分区键选择：裁剪效率与小文件平衡】");
        String[][] rows = {
                {"按天分区", "每天 500 万行 -> 单文件 300MB", "时间范围查询的主键，常规选择"},
                {"按 shop_id 分区", "50 万商家 -> 每分区 30 行", "小文件灾难，禁止"},
                {"不分区", "全表扫描依赖 Row Group 统计", "小表可行，大表慎用"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-12s %-32s %s%n", r[0], r[1], r[2]);
        }
        System.out.println("  经验：分区后单分区 ≥ 数百 MB；嵌套分区（天+小时）要验证分区数");
        System.out.println();
    }

    static void smallFileProblem() {
        System.out.println("【小文件：列存的慢性病】");
        Map<String, String> impact = new LinkedHashMap<>();
        impact.put("元数据开销", "100 万文件 × 每文件 footer/kv 元数据 = NameNode/目录压力");
        impact.put("调度开销", "每个文件一个 task，调度时间超过计算时间");
        impact.put("治理手段", "写入攒批 + 定时 compaction 合并到目标大小");
        for (Map.Entry<String, String> e : impact.entrySet()) {
            System.out.printf("  %-8s %s%n", e.getKey(), e.getValue());
        }
        System.out.println("  目标文件大小：128MB~1GB；流式写入后每天 compaction 是标配运维");
    }

    public static void main(String[] args) {
        rowGroupPruning();
        columnVsRow();
        partitionChoice();
        smallFileProblem();
    }
}
```

### 46-03 对象存储与数据分层

**知识点**
- **对象存储（S3/OSS/MinIO）已是数据湖的默认底座**：无限容量、按量付费、高持久性（11 个 9）；代价是**没有目录语义与原子 rename**（列出桶要分页、改名 = 复制+删除）。**HDFS 正在被对象存储替代**（存算分离）。
- **存算分离的架构意义**：计算集群（Spark/Trino）按需起停，数据常驻对象存储——**计算与数据各自弹性**（HDFS 时代计算与存储绑死在一批机器上）。代价：数据不在本地（网络读），靠缓存与列裁剪补。
- **对象存储的语义陷阱**：**rename 不原子**——"先把数据写到 tmp 再 rename 到正式目录"的提交模式在对象存储上不安全；**这就是表格式（46-05）存在的理由之一**：用元数据清单（meta.json 指向文件列表）实现原子提交，而不是依赖文件系统 rename。
- **数据分层布局**：ODS 原样桶（低频访问、生命周期 90 天转归档）、加工层桶（频繁读）、归档层（合规保留，最低成本）。**生命周期策略**让冷数据自动降级——数据平台的"冷热分离"（39-10 思想的数据版）。
- **一致性模型**：对象存储普遍提供强一致读（写后立即可见），但**列举与 rename 的语义与本地文件系统不同**——依赖"目录列表"的程序要按前缀分页设计。
- **成本结构**：存储费 + 请求费 + 出网流量费——**出网（跨云/下载）是隐形大头**，数据不出域（内网分析）同时省钱与合规。
- 易错点：把对象存储当文件系统用（大量小文件 + rename 依赖，性能与正确性双崩）；生命周期没配（十年日志躺在热存储烧钱）；跨云出网无预算（账单惊吓）；安全上桶策略过宽（匿名可读 = 数据泄露，36 章教训）。

### 46-04 Hive 与元数据管理

**知识点**
- **Hive 的历史贡献是把 SQL 带到大数据**：表 = 目录 + schema + 分区的映射（Metastore 记录），SQL 编译成分布式作业。今天 Hive 引擎本身渐渐淡出，**Hive Metastore（ HMS ）仍是元数据事实标准**——Spark/Trino/Flink 都从它读"表在哪、什么格式"。
- **Metastore 记录什么**：库/表/列 schema、分区列表、存储位置与格式、表属性。**它是"数据目录"的雏形**（46-08 治理的载体）：表注册即入 HMS，无注册不可查询。
- **分区管理的运维成本**：每天加分区（`ADD PARTITION`）在高表数场景成为管理负担——Iceberg 类表格式把分区做成表数据的一部分（隐藏分区），**分区演进不再破坏数据**。
- **schema on read 的双刃剑**：ODS 层原样存储靠读时解释，灵活但**列类型错误在读时才爆**——规范：ODS 保留原始 payload + 注册层给出推断 schema 与校验报告。
- **权限与审计**：HMS 层做库表权限（Ranger 类），配合桶策略（46-03）与行级权限——**数据权限的落点在元数据层而不是散在各引擎**。
- **小表大表的管理差异**：维表小表直接全量缓存（43-07）；事实大表分区 + 增量。**元数据里记录表的规模与更新频率**，供引擎做执行计划与调度决策。
- 易错点：元数据与实际文件漂移（手工删了文件，HMS 还指向它——查询报错）；分区手工 ADD 漏掉（数据在目录里但查不到）；权限只配在引擎层（换引擎权限失效）；表无注释无责任人（治理无从下手）。

### 46-05 Iceberg 表格式

**知识点**
- **表格式回答"怎么让一堆文件成为一张有事务的表"**：Iceberg 的答案是**元数据清单树**——snapshot（快照）指向 manifest list，manifest 记录数据文件清单与统计。**表状态 = 当前快照指针；提交 = 原子替换指针**——在无原子 rename 的对象存储上实现了事务（46-03 的解法落地）。
- **ACID 能力**：多个写入方并发提交时通过**乐观并发 + 冲突检测**——两个写都基于同一快照，各自产出新快照，先提交者赢，后提交者若与已提交变更的文件冲突则重试。**"写冲突重试"与 45-06 的 txn 语义同源**。
- **时间旅行（time travel）**：任意历史快照可查询——`SELECT ... VERSION AS OF snapshot-42`。**用途**：误操作回滚（指针回退即回滚，秒级）、审计重现（上周报表为什么是这个数）、实验复现。**快照保留策略**决定可回溯窗口与存储成本。
- **隐藏分区（hidden partitioning）**：分区信息在元数据里（`days(ts)`），用户写 SQL 不需要知道分区列——**分区从用户负担变成引擎知识**，分区演进（天 -> 小时）不破坏旧数据。
- **schema 演进**：加列/改列名/删列都不重写数据（旧文件 + 新 schema 元数据兼容映射）——**演进成本从"全表重写"降到"改元数据"**。
- **增量消费**：快照间 diff 即变更流——Flink/Spark 结构化流直接订阅 Iceberg 增量（43-09 CDC 链路的湖端形态）。
- 易错点：快照不过期（存储无限膨胀，保留 7 天 + 定期 expire）；并发写无冲突检测（两个引擎覆盖写同一文件）；把 Iceberg 当普通目录手工改文件（元数据与数据漂移，46-04 同款病）；小文件治理被忽略（写入频繁时 manifest 膨胀）。

import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class IcebergTableFormat {
    record DataFile(String path, long rows, String dateMin, String dateMax) {
    }

    record Snapshot(long id, String parentId, List<DataFile> files, String operation) {
    }

    /** 当前快照指针（原子替换的对象） */
    static long currentSnapshot = 0;
    static Map<Long, Snapshot> snapshots = new LinkedHashMap<>();

    static void commitFlow() {
        System.out.println("【一次提交：写文件 -> 原子替换快照指针】");
        Snapshot s0 = new Snapshot(0, null, List.of(), "init");
        snapshots.put(0L, s0);
        System.out.println("  当前快照 #0（空表）");
        List<DataFile> f1 = List.of(new DataFile("data/part-0001.parquet", 1_000_000,
                "2026-11-17", "2026-11-17"));
        Snapshot s1 = new Snapshot(1, "#0", f1, "append");
        snapshots.put(1L, s1);
        currentSnapshot = 1;
        System.out.println("  写 data/part-0001.parquet（幂等命名）-> 提交快照 #1 <- 原子替换指针");
        List<DataFile> f2 = new ArrayList<>(f1);
        f2.add(new DataFile("data/part-0002.parquet", 900_000, "2026-11-18", "2026-11-18"));
        snapshots.put(2L, new Snapshot(2, "#1", f2, "append"));
        currentSnapshot = 2;
        System.out.println("  第二次提交 -> 快照 #2（指针指向新清单，旧文件不重写）");
        System.out.println();
    }

    static void concurrentWrite() {
        System.out.println("【并发提交：乐观并发与冲突检测】");
        System.out.println("  写入方 A、B 都基于快照 #2：");
        System.out.println("  A 先提交 -> 快照 #3（当前指针 = 3）");
        System.out.println("  B 提交时发现自己基于的 #2 已不是当前快照：");
        boolean conflict = true;   // B 的文件与 A 的变更文件重叠
        System.out.println("    冲突检测：" + (conflict
                ? "文件重叠 -> B 重试：基于 #3 重算后提交 -> 快照 #4"
                : "文件不重叠 -> 直接提交（快照链线性化）"));
        System.out.println("  同一层语义：46-03 的“清单原子替换” + 乐观锁");
        System.out.println();
    }

    static void timeTravel() {
        System.out.println("【时间旅行：回滚与审计】");
        Snapshot s1 = snapshots.get(1L);
        System.out.printf("  VERSION AS OF #1 -> 只看 %d 个文件（11-17 的数据）%n", s1.files().size());
        System.out.println("  误操作回滚：把当前指针从 #4 回退到 #3（原子操作，秒级）");
        currentSnapshot = 3;
        System.out.println("  当前快照 = " + currentSnapshot + "（数据回到发布前状态）");
        System.out.println("  审计重现：“上周报表为什么是 860 万”-> 查当时快照即可复现");
        System.out.println("  保留策略：快照保留 7 天 + 每日一存（expire_snapshots 排期）");
        System.out.println();
    }

    static void evolution() {
        System.out.println("【隐藏分区与 schema 演进】");
        System.out.println("  分区：PARTITIONED BY days(ts) —— SQL 里 WHERE ts >= '...' 自动裁剪");
        System.out.println("  分区演进：天 -> 小时，旧数据保持天分区，新数据小时分区（元数据共存）");
        System.out.println("  schema：新增列 refund_status -> 只改元数据，旧文件缺列按 null 读取");
        System.out.println("  重命名：列改名通过映射完成，无需重写数据");
        System.out.println("  对比 Hive 分区：加列要重建表/重写数据 —— 演进成本数量级差异");
    }

    public static void main(String[] args) {
        commitFlow();
        concurrentWrite();
        timeTravel();
        evolution();
    }
}

### 46-06 批流一体存储

**知识点**
- **批流写同一张湖表是湖仓一体的试金石**：Flink CDC 持续写入（秒级一批小文件）+ Spark 每日批读——**写入频繁产生小文件**，读取要求文件足够大——矛盾由 **compaction（合并）机制**解决。
- **两种读模式**：**copy-on-write（COW）**——写时重写受影响文件，读永远干净（读快写贵）；**merge-on-read（MOR）**——写入追加 delta 文件，读时合并 base+delta（写快读贵）。**选型看读写比例**：读多写少选 COW，写多读少或延迟敏感选 MOR。
- **小文件的治理节奏**：流写入每分钟一个小文件 × 1440 分钟 = 每天 8.6 万文件/分区——**异步 compaction**（每 10 分钟合并一次 delta，每天把整分区重整为目标大小）是流式湖表的标配运维。
- **快照与 compaction 的关系**：compaction 本身也是一次提交（产生新快照），**读端不受影响**（快照一致性保证读到的始终是完整状态）；合并后旧文件进"待回收"（快照过期后物理删除）。
- **Flink 写湖的一致性**：checkpoint（43-05）成功后才提交 Iceberg 快照——**流作业的 exactly-once 与湖表事务对齐**：checkpoint 间隔 = 数据可见延迟。
- **下游感知**：46-05 的增量消费让下游订阅"compaction 后的新快照"，或者直接消费数据变更（append 流）。**消费模式选择**决定下游时效（分钟级 vs 天级）。
- 易错点：流写入不做 compaction（小文件雪崩，读取越来越慢）；compaction 与写入抢资源（错峰排期）；MOR 的读放大没预估（查询变慢 3~5 倍才发现）；checkpoint 间隔设太长（下游数据可见延迟跟随变长）。

### 46-07 MPP 与即席查询

**知识点**
- **MPP（大规模并行处理）引擎服务"即席分析"**：Trino/StarRocks/Doris 在内存中把查询拆到多节点并行执行——**分析师写一条 SQL 秒级出结果**，区别于 Spark 批作业（分钟级调度）。**交互式分析是数据平台体验的分水岭**。
- **CBO（基于代价的优化）依赖统计信息**：行数、NDV（列基数）、直方图——**统计过期的执行计划必然翻车**（本该裁剪的全表扫）。湖表的统计来自 46-02 的文件统计与 ANALYZE 收集。
- **物化视图（materialized view）是预聚合的工程化**：高频查询模式（日 GMV、类目销量）预计算存储——**查询从扫明细变成扫汇总**，秒级变毫秒级；代价是**刷新与一致性**（T+刷新、实时刷新、查询改写命中）。
- **资源隔离是共享集群的秩序**：即席查询大扫描会拖垮整集群——按业务方/查询类型分队列（prod 报表队列 / adhoc 队列），限制扫描上限与并发（42 章限流思想）。**"一条 SQL 打挂数据平台"是真实事故**。
- **查询治理**：慢查询排行榜（42 章 slow log 思想）、扫描量告警、强制 LIMIT、结果集大小限制。**分析师的教育与工具护栏并行**。
- **与湖表的关系**：MPP 引擎直接查 Iceberg（外部表）或把热数据本地化（StarRocks 内表 + 湖加速）——**热数据进引擎、冷数据留湖**是常见的两级架构。
- 易错点：不配资源队列（即席与生产报表互相干扰）；统计信息从不更新（执行计划劣化无人知）；物化视图刷新与源表脱节（数字对不上）；把 MPP 当 OLTP 用（高频点查应该走 MySQL/Redis）。

### 46-08 数据质量与治理

**知识点**
- **数据质量问题的成本随时间指数上涨**：上游悄悄改了枚举值，当天无人发现 -> 下游聚合全错 -> 报表决策错误 -> 一个月后发现 -> 回溯修复所有历史分区。**质量检查必须"在写入时"而不是"在使用时"**。
- **数据契约（data contract）是生产者与消费者的合同**：schema（列名/类型/可空）、语义（单位、口径、枚举值域）、SLA（更新频率、延迟上限）、变更流程（加列兼容、删列走两版本）。**契约以版本化文档 + 自动校验存在**，不是聊天记录。
- **质量规则的四个层级**：**完整性**（非空率、行数波动）、**有效性**（枚举值域、格式、范围）、**一致性**（跨表核对：订单表总额 = 支付表总额）、**及时性**（分区准时产出）。每条规则带**告警阈值与阻断策略**（软警告 vs 硬阻断下游）。
- **血缘（lineage）回答"这个数字从哪来"**：列级血缘把 ADS 报表指标一路追到 ODS 原始字段——**排障与影响面分析的基础设施**：上游表变更，血缘自动列出全部受影响下游（41-09 影响面思想的数据库版）。
- **数据目录（catalog）是治理的门面**：表注册、责任人、业务描述、质量评分、使用热度——**让"找数据"从问人变成搜目录**。没有目录的团队 50% 的时间花在"这张表是什么"上。
- **变更管理**：上游 schema 变更走契约评审（兼容性检查）-> 通知订阅方 -> 灰度切换——**与 41-09 数据库变更协同同构**，只是粒度是表。
- 易错点：质量规则只在报表出事后补（永远慢一步）；契约只有文档没有校验（形同虚设）；血缘只有表级没有列级（影响面太粗）；质量评分没人看（治理变成表格式主义）。

### 46-09 数据集成与同步

**知识点**
- **数据集成的管道形态**：**库 -> 湖**（业务库 CDC 全量+增量进 ODS，43-09 的离线延伸）、**文件 -> 湖**（日志/埋点批量导入）、**湖 -> 库**（ADS 结果回写业务库/Redis 供查询）、**湖 -> 湖**（跨域共享/备份）。每条管道都要回答：全量还是增量、频率、一致性校验。
- **全量与增量的组合模式**：首日全量快照 + 之后增量（CDC/文件时间戳）；**大表拆段**（按主键范围并行拉取）；**幂等写入**（按主键覆盖，重跑无损——39-11 迁移思想在数据平台的复用）。
- **一致性校验是集成的验收标准**：行数核对、checksum 抽查、抽样比对关键列——**"同步完成"必须由校验声明**（43-09 对账思想）；差异进差异表自动修复或告警人工。
- **延迟分层**：交易类近实时（CDC 分钟级）、分析类小时级、报表 T+1——**每张表声明自己的 SLA**，管道按 SLA 选技术（CDC vs 定时批）。
- **管道的运维**：断点续传（offset/checkpoint）、重跑幂等、速率限制（不拖垮源库，39 章归档同款）、告警与补数流程（某天分区失败 -> 重跑该分区）。
- **跨域共享的合规**：数据出域（给第三方）走审批 + 脱敏 + 水印——**集成层是合规检查点**（36 章敏感数据治理的落点）。
- 易错点：增量靠"update_time 轮询"但源表无索引（拖垮源库）；全量重跑无幂等（重复行翻倍）；校验缺失（静默丢数一个月）；补数流程缺失（失败分区永远缺数据）。

### 46-10 数据平台服务化

**知识点**
- **数据平台的价值在"被业务系统消费"**：报表是终点，**特征 API（推荐/风控实时取数）、指标 API（运营后台）、榜单缓存（大屏/首页）**是数据反哺业务的出口——46 章所有铺垫（分层、质量、MPP）最终为了这几个服务。
- **指标平台统一口径**：指标定义（名称/口径/维度/负责人）注册一次，报表/大屏/接口全部引用——**"GMV 是多少"只有一个权威答案**（46-01 打架问题的终解）。指标变更走评审，历史口径留档。
- **特征平台**：离线特征（湖表 T+1）与在线特征（Redis 实时）**同一套定义**——训练与推理特征一致性（"训练用昨天数据、线上用今天数据"的口径错位是模型效果劣化的隐形元凶）。
- **数据 API 的工程要求**：与业务 API 同标准（40-09 分层、限流、鉴权、监控）；**查询下推到正确的存储**（点查走 Redis/StarRocks，聚合走 MPP）；大结果集异步导出（对象存储 + 通知）。
- **数据的 SLA 与告警**：API 可用性、数据新鲜度（"数据最后更新于 5 分钟前"要暴露）、下游依赖的数据分区就绪通知（调度事件驱动而不是轮询）。
- **组织协作**：数据团队提供平台与规范，业务团队生产与消费——**自助化是目标**（自助建表模板、自助质量规则、自助指标注册），全部人工排队的服务不可扩展。
- 易错点：指标口径散落在各报表 SQL 里（没人说得清哪个准）；特征线上线下两套定义（训练-推理偏差）；数据 API 走了错误存储（点查打到 Trino 全表扫）；"数据就绪"靠人盯着（下游 9 点开工发现上游 10 点才产出）。

### 46-11 综合案例：订单主题湖仓

**知识点**
- **把本章串成一条完整数据链路**：MySQL 订单（binlog）-> Flink CDC 写 Iceberg ODS（46-05/06，checkpoint 对齐）-> 每日批清洗 DWD（Parquet 分区 + 质量校验 46-08）-> DWS 预聚合 -> ADS 物化视图（46-07）-> 指标 API/大屏/回灌 Redis（46-10）。**每一课的设计决策在链路上各就各位**。
- **关键设计参数**：ODS 按 CDC 写（MOR + 每 10 分钟 compaction）、DWD 按 COW 天分区（读优先）、快照保留 7 天 + 每日过期、ADS 回灌 Redis 分钟级。**参数背后都是读写比例与时效 SLA 的权衡**。
- **质量与治理贯通**：契约（46-08）约束上游事件、每层产出跑质量规则、血缘覆盖全链、目录登记责任人。**一次口径变更的影响面靠血缘在 10 分钟内评估完**。
- **故障与修复叙事**：上游误把退款金额写负数 -> 质量规则当日拦截（金额范围）-> 阻断 DWD 产出 -> 修复后重跑该分区（幂等）-> 时间旅行核对修复前后差异 -> 下游自动恢复。**全链路无人工救火**。
- **上线检查单**：管道 SLA 与告警、质量规则覆盖率、compaction 排期、快照过期排期、权限最小化、成本三层兜底、演练（分区失败重跑/时间旅行回滚/下游新鲜度降级）。
- 易错点：全链路只有 ODS 没有 DWD（下游直接扫原始 JSON）；质量规则上线后从不演练（规则失效无人知）；ADS 与 DWS 口径两套代码（指标打架复发）；时间旅行当成日常修复手段滥用（应修根因，回滚只是止血）。
