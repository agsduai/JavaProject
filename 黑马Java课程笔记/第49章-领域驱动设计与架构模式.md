# 第49章 领域驱动设计与架构模式

第31章的设计模式解决"类与对象怎么组织"，本章解决"业务复杂度怎么在代码中表达"。贫血模型把规则散在 Service 里，促销规则一变就横跨五个类；DDD 用限界上下文划清语义边界、用聚合收拢不变量、用领域事件连接协作——**业务复杂时这是投资，简单时是负担**。本章按「DDD 总览 → 聚合实体值对象 → 领域事件 → 六边形架构 → CQRS → 事件溯源 → 防腐层 → 微服务与单体 → 营销建模实战 → 遗留系统演进 → 订单域建模案例」的顺序讲。所有示例仍是纯 JDK：贫血与充血同规则对比真跑，聚合不变量（超退/超抵扣）真实拦截，outbox 投递与消费幂等真跑闭环，防腐层翻译矩阵真实测试，不需要 Spring 或 DDD 框架。

### 49-01 领域驱动设计总览

**知识点**
- **DDD 解决的问题是"复杂业务在代码中的表达"**：贫血模型（POJO + 一堆 Service）把业务规则散落在 Service 方法里，改一个促销规则要横跨五个类；DDD 把**业务规则收进领域模型**，让代码结构映射业务结构。**业务复杂时 DDD 是投资，业务简单时是负担**——CRUD 系统不必上 DDD。
- **两条腿：战略设计与战术设计**：战略设计回答"系统怎么拆"——限界上下文（Bounded Context）、通用语言（Ubiquitous Language）、上下文映射（Context Map）；战术设计回答"一个上下文内部怎么写"——聚合（Aggregate）、实体（Entity）、值对象（Value Object）、领域服务、领域事件。**战略先于战术**：上下文划错了，战术写得再漂亮也是错的模型。
- **通用语言是 DDD 的灵魂**：业务说"核销"、代码里就该有 `redeem`（而不是 `updateStatus2`）——**语言统一后，沟通成本与代码歧义同步消失**。看到代码里出现"管理器/工具/助手"类命名，多半是通用语言缺失。
- **限界上下文 ≠ 微服务**（29 章的拆分其实就是在划上下文）：一个上下文内语言统一（"商品"在库存上下文指 SKU，在营销上下文指可参加活动的商品池）——**同一个词在不同上下文含义不同，跨上下文必须转换**。上下文可以包含多个服务，也可以一个服务承载多个小上下文。
- **DDD 与分层的关系**：领域层（模型与规则）在最里、应用层（用例编排）在其上、基础设施（DB/MQ）在外——**依赖方向永远指向领域层**（49-04 六边形架构）。
- **落地路径**：事件风暴（Event Storming）工作坊梳理业务事件 -> 按事件聚类划上下文 -> 每个上下文内识别聚合 -> 写代码。**从"事件"出发比从"表"出发更接近业务**。
- 易错点：给 CRUD 系统硬套 DDD（聚合根/仓储全套上，代码量翻倍收益为零）；一个"大模型"贯穿全系统（没有上下文边界，语义混乱）；战术设计先行（聚合划错）；把 DDD 等同于"代码分层模板"（DDD 是思维方式不是目录结构）。

### 49-02 战术设计：聚合、实体与值对象

**知识点**
- **聚合（Aggregate）是事务与一致性的边界**：聚合根（Aggregate Root）是外部唯一入口，聚合内部对象只能被根引用——**跨聚合引用必须用 ID，不能持对象引用**。这条纪律让"哪些修改可以放在一个事务里"有了明确答案：**一个事务只改一个聚合**（39-09 跨库事务的根本答案）。
- **实体 vs 值对象的判据**：**实体**有身份（订单 9001 换了地址还是订单 9001），靠 ID 区分、有生命周期；**值对象**无身份靠属性区分（金额 69.00 元与另一个 69.00 元不可区分），不可变、可替换。**"它有 ID 吗"是第一个问的问题**。
- **聚合划小原则**：聚合越小事务越短、并发冲突越少——**跨聚合协作用领域事件最终一致**（订单聚合与库存聚合之间用 OrderPaid 事件，而不是一个巨大聚合包住两者）。大聚合是 DDD 最常见的失败原因。
- **不变量（invariant）归属聚合**："订单明细之和 ≥ 0"、"同一 SKU 明细唯一"这类规则必须**在一个事务内可验证**——它们定义聚合边界（规则涉及谁，聚合就包含谁）。
- **领域事件建模**：过去时命名（OrderPaid/OrderCancelled）、不可变、带业务字段与发生时间——**事件是跨聚合/跨上下文的粘合剂**（28 章 MQ、39 章本地消息表的领域层根基）。
- **仓储（Repository）只为聚合根定义**：`OrderRepository.findById/save`——聚合整体存取；聚合内部对象通过根访问，不单独建 Repository。
- 易错点：聚合划成"一张表一个聚合"（OrderItem 单独聚合 -> 一致性无处安放）；聚合间持对象引用（加载一个聚合拖出半个库）；值对象做成可变实体（金额还能 set）；领域事件带可变引用（事件应不可变）。

**示例代码**
```java
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public class DddTactical {
    /** 值对象：不可变、靠属性判等 */
    record Money(BigDecimal amount, String currency) {
        Money add(Money other) {
            if (!currency.equals(other.currency)) {
                throw new IllegalArgumentException("币种不同不可相加");
            }
            return new Money(amount.add(other.amount), currency);
        }

        boolean isPositive() {
            return amount.compareTo(BigDecimal.ZERO) > 0;
        }
    }

    /** 实体：订单明细（有身份，但只在聚合内可见） */
    static class OrderLine {
        final String sku;
        int quantity;
        Money unitPrice;

        OrderLine(String sku, int quantity, Money unitPrice) {
            this.sku = sku;
            this.quantity = quantity;
            this.unitPrice = unitPrice;
        }

        Money subtotal() {
            return new Money(unitPrice.amount().multiply(BigDecimal.valueOf(quantity)),
                    unitPrice.currency());
        }
    }

    /** 聚合根：唯一入口，不变量在聚合内闭环 */
    static class Order {
        final String orderId;
        final List<OrderLine> lines = new ArrayList<>();
        private Money coupon;
        private String status = "DRAFT";

        Order(String orderId, Money currency) {
            this.orderId = orderId;
            this.coupon = currency;
        }

        void addLine(String sku, int qty, Money unitPrice) {
            if (!"DRAFT".equals(status)) {
                throw new IllegalStateException("已下单订单不可改明细");
            }
            lines.add(new OrderLine(sku, qty, unitPrice));
        }

        Money subtotal() {
            return lines.stream().map(OrderLine::subtotal)
                    .reduce(new Money(BigDecimal.ZERO, coupon.currency()), Money::add);
        }

        /** 不变量校验：抵扣不可超订单额 —— 规则收在聚合内 */
        void applyCoupon(Money discount) {
            if (!discount.isPositive()) {
                throw new IllegalArgumentException("抵扣必须为正");
            }
            if (discount.amount().compareTo(subtotal().amount()) > 0) {
                throw new IllegalArgumentException("抵扣不可超过订单总额");
            }
            this.coupon = discount;
        }

        void submit() {
            if (lines.isEmpty()) {
                throw new IllegalStateException("空订单不可提交");
            }
            this.status = "PLACED";
            System.out.println("  事件发布: OrderPlaced(orderId=" + orderId + ")");
        }
    }

    static void tacticalDemo() {
        System.out.println("【聚合内交互：规则与不变量闭环】");
        Money cny = new Money(new BigDecimal("10.00"), "CNY");
        Order order = new Order("9001", cny);
        order.addLine("SKU-A", 2, cny);
        order.addLine("SKU-B", 1, new Money(new BigDecimal("25.00"), "CNY"));
        System.out.printf("  小计 = %s 元%n", order.subtotal().amount());
        order.applyCoupon(new Money(new BigDecimal("5.00"), "CNY"));
        System.out.println("  应用优惠券 5 元 -> 通过（不超小计 45 元）");
        try {
            order.applyCoupon(new Money(new BigDecimal("999.00"), "CNY"));
        } catch (IllegalArgumentException e) {
            System.out.println("  超额抵扣被聚合拒绝：" + e.getMessage());
        }
        order.submit();
        System.out.println();
    }

    static void boundaries() {
        System.out.println("【聚合边界三问】");
        List<String> questions = List.of(
                "① 这条不变量要在哪个事务内成立？（涉及谁，聚合就含谁）",
                "② 谁是外部访问的唯一入口？（聚合根，其余全内部）",
                "③ 跨聚合协作怎么传？（ID 引用 + 领域事件，一个事务只改一个聚合）");
        for (String q : questions) {
            System.out.println("  " + q);
        }
        System.out.println("  反例：OrderItem 单独成聚合 -> “明细之和>=0”跨了两个事务 -> 不变量失效");
    }

    public static void main(String[] args) {
        tacticalDemo();
        boundaries();
    }
}
```

### 49-03 聚合设计与领域事件实战

**知识点**
- **聚合间协作的三种模式**：① 同步调用（聚合 A 直接调 B —— 耦合最强，慎用）；② **领域事件最终一致**（A 发事件，B 订阅处理 —— 默认选择）；③ 过程管理器（Saga，编排跨聚合流程，39-09 TCC/本地消息表的领域版）。**默认选事件，强实时才同步**。
- **事件的设计原则**：过去时命名、携带"消费者所需最小字段"（ orderId + paidAmount + paidAt，不要整个聚合序列化）、不可变、带事件 ID（消费幂等键）。**事件瘦身**是消费者稳定的前提——事件字段即契约（46-08 数据契约的同源思想）。
- **事件的可靠发布**：进程内事件（Spring 事件总线，同事务）与跨服务事件（MQ）不同——**跨服务必须本地消息表/outbox**（39-09），"聚合保存 + 事件入库"同事务提交，后台投递。
- **同一上下文内的一致性策略**：强一致规则放聚合内（同事务）；跨聚合规则用事件 + 消费端校验（最终一致窗口内业务可接受吗？不能接受就合并进同一聚合或同步调用）。
- **用例编排归应用层**：应用服务（Application Service）负责"加载聚合 -> 调领域方法 -> 保存 -> 发事件"的编排，**不含业务规则**（规则在聚合）——贫血与充血的分界就在这层是否膨胀。
- **测试策略**：聚合单元测试（纯内存，无 Mock 依赖）跑不变量；应用层测试用例编排（Mock 仓储）；事件消费者测试幂等与失败重试（40-09 mock 思想）。
- 易错点：事件带聚合全量字段（契约爆炸，上游改字段下游全炸）；进程内事件当跨服务用（无持久化，宕机丢事件）；应用服务里写满业务规则（充血退化回贫血）；事件消费无幂等（重放翻倍）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class DomainEventFlow {
    /** 领域事件：过去时、不可变、最小字段 */
    record OrderPaid(String eventId, String orderId, String userId, long paidAtMs, int amountCents) {
    }

    /** 聚合内产生事件（聚合不负责投递） */
    static class Order {
        final List<Object> pendingEvents = new ArrayList<>();

        void markPaid(String orderId, String userId, int cents) {
            pendingEvents.add(new OrderPaid("EV-" + orderId, orderId, userId,
                    System.currentTimeMillis(), cents));
            System.out.println("  聚合产生事件 OrderPaid（等待应用层投递）");
        }
    }

    /** 应用层：编排 + outbox 同事务 */
    static class OrderApplicationService {
        final Map<String, List<Object>> outbox = new LinkedHashMap<>();   // 待投递事件

        void pay(String orderId, String userId, int cents) {
            Order order = new Order();                      // 真实场景先查仓储
            order.markPaid(orderId, userId, cents);
            // 同事务：保存聚合 + 事件入 outbox（39-09 本地消息表）
            outbox.put(orderId, order.pendingEvents);
            System.out.println("  应用层：聚合保存 + 事件入 outbox（同一事务）");
        }
    }

    static void flow() {
        System.out.println("【完整事件流：聚合 -> outbox -> MQ -> 消费者】");
        OrderApplicationService app = new OrderApplicationService();
        app.pay("9001", "1001", 6900);
        System.out.println("  后台投递线程：outbox -> MQ（失败重试，N 次进死信）");
        // 消费者（库存上下文）
        OrderPaid ev = new OrderPaid("EV-9001", "9001", "1001", 0, 6900);
        boolean first = true;
        for (int attempt = 1; attempt <= 2; attempt++) {
            String seenKey = ev.eventId();
            boolean processed = seenKey.equals("EV-9001") && first;
            System.out.printf("  消费尝试#%d：幂等键=%s -> %s%n", attempt, seenKey,
                    processed ? "首次处理：扣减库存" : "重复事件 -> 忽略（幂等生效）");
            if (processed) {
                first = false;
            }
        }
        System.out.println();
    }

    static void eventDesignRules() {
        System.out.println("【事件设计五条军规】");
        List<String> rules = List.of(
                "过去时命名：OrderPaid / OrderCancelled（不是 PayOrder）",
                "最小字段：消费者要什么给什么，不序列化整个聚合",
                "不可变：事件是历史事实，无 setter",
                "带事件 ID：消费幂等的天然键（39 章/43 章同一思想）",
                "带发生时间与版本：消费端排序与乱序防护（39-08）");
        for (String r : rules) {
            System.out.println("  - " + r);
        }
        System.out.println();
    }

    static void consistencyChoice() {
        System.out.println("【同一上下文：强一致还是事件？】");
        String[][] rows = {
                {"订单-明细", "同一聚合（强一致）", "不变量必须同事务"},
                {"订单-库存", "事件最终一致", "超卖由库存侧兜底（预留+校验）"},
                {"订单-优惠券核销", "事件 + 消费端校验", "核销失败进补偿队列"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-12s %-16s %s%n", r[0], r[1], r[2]);
        }
        System.out.println("  判断式：最终一致窗口内业务可接受吗？不可接受 -> 合并聚合或同步");
    }

    public static void main(String[] args) {
        flow();
        eventDesignRules();
        consistencyChoice();
    }
}
```

### 49-04 六边形架构与端口适配器

**知识点**
- **六边形架构（端口与适配器）的依赖规则**：**领域层在最内圈，不依赖任何外圈**；应用层编排用例；外圈的适配器（Web 控制器、DB 仓储、MQ 生产者）实现领域定义的"端口"（接口）。**依赖倒置（11 章 DIP 原则）的架构级应用**：不是领域依赖 DB，是 DB 适配器实现领域接口。
- **端口的两种方向**：**驱动侧端口**（左：用例接口，如 `PlaceOrderUseCase`，Web 控制器调用它）与**被驱动侧端口**（右：领域需要的出口，如 `OrderRepository`、`PaymentGateway`，由基础设施适配器实现）。**领域定义接口，外部实现接口**——业务可测试性（纯内存 Mock）与可替换性（换 DB 不改领域）由此而来。
- **与三层架构的对照**：传统三层 Controller->Service->Dao（领域逻辑渗进 Service，Service 依赖 Dao 具体实现）；六边形 Controller->Application(端口)->Domain<-Adapter(实现端口)。**箭头方向相反**——这是本质差异不是目录差异。
- **收益的验证方式**：领域模块 `mvn compile` 不依赖 Spring/JDBC 任何框架 jar（**无框架依赖测试**）；换存储时领域零改动；单元测试不启动容器。
- **何时值得**：核心域、规则复杂、生命周期长（三年以上维护）的系统；一次性活动页/CRUD 用标准三层更省。**架构也是成本决策**（49-01 的复杂度投资论）。
- 易错点：六边形只学目录不学依赖（领域层 import MyBatis，白搭）；端口粒度错（一个端口一个方法爆炸，按用例聚类）；为六边形而六边形（简单模块硬拆四层）；领域对象直接当 DTO 返回 Web（聚合边界泄漏到 API）。

### 49-05 CQRS 读写分离建模

**知识点**
- **CQRS（命令查询职责分离）把写模型与读模型分开建模**：写模型（聚合）保证不变量与事务，为业务正确性服务；读模型（查询视图）为查询体验服务——**两者可以不同结构、不同存储、不同一致性**。"一个模型既当事务守卫又当查询视图"是复杂系统的常见负担。
- **读写不对称的根源**：写要满足不变量（订单聚合完整），查要跨表聚合展示（订单列表要商品名/用户名/物流状态）——**写模型稠密归一，读模型稀疏反范式**。强行用一个模型两头迁就（大宽表 + 事务守卫）两头都难受。
- **CQRS 的实现光谱**：轻量级——同一个库，写走聚合、读走 SQL 视图（**90% 场景够用**）；重量级——写库 + 事件投影到读库（ES/宽表），最终一致（第 38 章 ES 同步的架构身份就是"读模型投影"）。
- **事件驱动投影**：领域事件 -> 投影器（Projection）更新读模型——**读模型可整体重建**（事件回放，46-05 时间旅行同源思想），坏了重建而不是修补。
- **一致性的明确契约**：写后读自己的写（45-02）在读模型上如何保证——版本号 + 等待投影 + 超时回主读；**契约写进设计文档**。
- **何时需要重量级 CQRS**：查询维度与事务维度严重分歧（多维度列表/全文搜索/报表）、读性能独立伸缩、读模型可容忍秒级延迟。**不需要时重量级 CQRS 是分布式事务税**。
- 易错点：轻量级需求上了双库（维护投影管道，成本翻倍）；读模型无版本契约（写后读旧值客诉）；投影不可重建（读模型坏了手工修数据）；把 CQRS 理解成"必须事件溯源"（CQRS 可独立使用）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class CqrsPattern {
    /** 写模型：聚合，保证不变量 */
    static class OrderWriteModel {
        final Map<String, Integer> orders = new LinkedHashMap<>();   // id -> amountCents
        final Map<String, String> statuses = new LinkedHashMap<>();

        void place(String orderId, int amountCents) {
            if (amountCents <= 0) {
                throw new IllegalArgumentException("金额必须为正");
            }
            orders.put(orderId, amountCents);
            statuses.put(orderId, "PAID");
            System.out.printf("  [写模型] 订单 %s 落库（不变量已校验）%n", orderId);
        }
    }

    /** 读模型：为列表查询而生的反范式视图 */
    record OrderListItem(String orderId, String status, String userName,
                         String productNames, int amountCents) {
    }

    static class OrderListView {
        final List<OrderListItem> rows = new ArrayList<>();

        /** 投影器：订阅事件更新视图（可整体重建） */
        void project(String orderId, String status, String userName,
                     String productNames, int amountCents) {
            rows.add(new OrderListItem(orderId, status, userName, productNames, amountCents));
            System.out.printf("  [投影] 视图行更新：%s（%s %s %s）%n", orderId, status, userName, productNames);
        }

        List<OrderListItem> listByUser(String userName) {
            List<OrderListItem> hits = rows.stream()
                    .filter(r -> r.userName().equals(userName)).toList();
            System.out.printf("  [读模型] 按 user=%s 查询 -> %d 行（一次反范式读，无 join）%n",
                    userName, hits.size());
            return hits;
        }
    }

    static void twoModels() {
        System.out.println("【同一业务：写模型与读模型各自成形】");
        OrderWriteModel write = new OrderWriteModel();
        write.place("9001", 6900);
        OrderListView view = new OrderListView();
        view.project("9001", "PAID", "小王", "iPhone 手机壳, 手机支架", 6900);
        view.listByUser("小王");
        System.out.println("  写模型关心不变量，读模型关心展示 —— 结构不同天经地义");
        System.out.println();
    }

    static void spectrum() {
        System.out.println("【CQRS 实现光谱：从轻到重】");
        String[][] rows = {
                {"L1 同库视图", "SQL 视图/接口聚合", "90% 场景，零管道成本"},
                {"L2 双模型同库", "写走聚合表、读走宽表（同库同步）", "查询形状差异大时"},
                {"L3 事件投影异构", "事件 -> ES/宽表，最终一致", "全文检索/多维列表（38 章正是 L3）"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-12s %-32s %s%n", r[0], r[1], r[2]);
        }
        System.out.println("  升级原则：从 L1 开始，查询需求推不动再升");
        System.out.println();
    }

    static void rebuild() {
        System.out.println("【投影可重建：读模型的修复姿势】");
        List<String> steps = List.of(
                "1) 读模型损坏/口径变更 -> 不修补，重建",
                "2) 清空视图 -> 从事件流重放（46-05 时间旅行同源）",
                "3) 双写期：新旧视图并存，对比一致后切流",
                "4) 投影器幂等：同一事件重放结果不变（39 章幂等原则）");
        for (String s : steps) {
            System.out.println("  " + s);
        }
        System.out.println("  前提：事件是完整真源（Event Sourcing 的价值由此显现，49-06）");
        System.out.println();
    }

    static void consistencyContract() {
        System.out.println("【写后读契约：读模型的最后一块拼图】");
        List<String> rules = List.of(
                "写侧返回版本号（事件 revision）",
                "读侧校验：投影版本 >= 写入版本才返回；否则回退写模型读",
                "超时兜底：等待投影 500ms 超时 -> 回写模型（正确性优先）",
                "契约写进接口文档（42 章新鲜度元数据同款思想）");
        for (String r : rules) {
            System.out.println("  - " + r);
        }
        System.out.println("  反例：支付成功页读到“未支付”-> 客诉 —— 45-02 read-your-writes 的落地");
    }

    public static void main(String[] args) {
        twoModels();
        spectrum();
        rebuild();
        consistencyContract();
    }
}
```

### 49-06 事件溯源与投影

**知识点**
- **事件溯源（Event Sourcing）把"状态"变成"事件的派生品"**：不存"订单当前状态"，存"订单的全部变更事件"；当前状态 = 事件按序回放的结果。**事件流是唯一真源（source of truth）**——审计天然完整、时间旅行免费（46-05 同源）、任何视图可重建。
- **快照（snapshot）解决回放成本**：事件千条后回放变慢——**每 N 条事件存一个状态快照**，恢复 = 快照 + 之后的事件重放（43-05 checkpoint 的同源思想：状态自持 + 日志重放）。
- **事件溯源 ≠ 事件消息**：溯源事件是"领域事实的完整记录"（真源），消息是"传递通知"（可丢可重）；**溯源事件流要求不可变存储与完整保留**——存储成本与治理成本更高。
- **版本化与升级**：事件 schema 演进（加字段/改语义）是事件溯源的最大运维负担——**upcaster（事件升级器）**把旧版本事件在读时转换为新版本；避免破坏性变更。
- **适用边界**：审计强需求（金融账务、合规）、需要重建任意历史视图（51-08 账务）、复杂协作需要回放调试——**普通 CRUD 用事件溯源是自找麻烦**（查询、修复、心智成本全上升）。
- **与 CQRS 的关系**：事件溯源天然伴生 CQRS（写侧是事件流，读侧是投影视图）——但两者可独立使用（49-05）。
- 易错点：把事件溯源当潮流上 CRUD 系统（复杂度爆炸）；事件 schema 无版本管理（历史事件读不出来）；快照策略缺失（回放越来越慢）；敏感数据进事件流（加密与脱敏难题，36 章合规约束）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class EventSourcing {
    /** 事件流：真源 */
    sealed interface OrderEvent permits Created, Paid, Cancelled {
    }

    record Created(String orderId, int amountCents) implements OrderEvent {
    }

    record Paid(String orderId, long paidAtMs) implements OrderEvent {
    }

    record Cancelled(String orderId, String reason) implements OrderEvent {
    }

    /** 状态 = 事件回放的派生品 */
    record OrderState(String orderId, int amountCents, String status) {
    }

    static OrderState replay(List<OrderEvent> events, OrderState snapshot) {
        OrderState s = snapshot;
        for (OrderEvent e : events) {
            if (e instanceof Created c) {
                s = new OrderState(c.orderId(), c.amountCents(), "CREATED");
            } else if (e instanceof Paid) {
                s = new OrderState(s.orderId(), s.amountCents(), "PAID");
            } else if (e instanceof Cancelled) {
                s = new OrderState(s.orderId(), s.amountCents(), "CANCELLED");
            }
        }
        return s;
    }

    static void replayDemo() {
        System.out.println("【事件回放：状态是派生品】");
        List<OrderEvent> stream = List.of(
                new Created("9001", 6900),
                new Paid("9001", System.currentTimeMillis()));
        OrderState s = replay(stream, null);
        System.out.printf("  回放 %d 个事件 -> 状态 %s%n", stream.size(), s);
        List<OrderEvent> withCancel = new ArrayList<>(stream);
        withCancel.add(new Cancelled("9001", "用户申请"));
        System.out.printf("  追加 Cancelled -> %s%n", replay(withCancel, null));
        System.out.println("  任意历史时点：截断事件流即可重建当时状态（时间旅行）");
        System.out.println();
    }

    static void snapshotFlow() {
        System.out.println("【快照：回放成本的控制】");
        int totalEvents = 5000, snapshotEvery = 1000;
        List<OrderEvent> tail = new ArrayList<>();
        System.out.printf("  每 %d 个事件存一个快照 -> 恢复 = 快照 + %d 条尾部事件重放%n",
                snapshotEvery, totalEvents % snapshotEvery);
        System.out.printf("  对比全量回放 %d 条：快照路径只重放 %d 条（成本降 %.0f%%）%n",
                totalEvents, totalEvents % snapshotEvery,
                (1 - totalEvents % snapshotEvery / (double) totalEvents) * 100);
        System.out.println("  快照本身也要版本化：状态 schema 变更时快照作废重建");
        System.out.println();
    }

    static void versionUpgrade() {
        System.out.println("【事件 schema 演进：upcaster】");
        record PaidV1(String orderId) {
        }
        System.out.println("  旧事件 PaidV1(orderId) 缺 paidAtMs 字段：");
        System.out.println("  upcaster：读时转换 PaidV1 -> Paid(orderId, paidAtMs=0 默认)");
        List<String> rules = List.of(
                "只加不改：新字段给默认值，禁止改语义",
                "upcaster 链：V1 -> V2 -> V3 逐级升级，历史事件永远可读",
                "破坏性变更 -> 新事件类型（PaidV2），不修改旧类型");
        for (String r : rules) {
            System.out.println("  - " + r);
        }
        System.out.println();
    }

    static void fitDecision() {
        System.out.println("【适用决策：值不值得事件溯源】");
        String[][] rows = {
                {"账务/资金流水", "值得", "审计是业务需求本身（51-08）"},
                {"订单生命周期", "酌情", "事件流对账与重现有价值，成本可控"},
                {"普通 CRUD", "不值得", "查询/修复/心智成本全上升"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-12s %-6s %s%n", r[0], r[1], r[2]);
        }
        System.out.println("  门槛三问：需要完整审计吗？需要重建历史视图吗？愿意承担 schema 演进成本吗？");
    }

    public static void main(String[] args) {
        replayDemo();
        snapshotFlow();
        versionUpgrade();
        fitDecision();
    }
}
```

### 49-07 上下文集成与防腐层

**知识点**
- **上下文之间的集成模式**：**共享内核**（共用部分模型，耦合强，慎用）、**客户-供应商**（下游适配上游）、**防腐层（ACL，Anti-Corruption Layer）**（在边界上做模型翻译，保护自己的领域不被外部模型污染）、**事件集成**（49-03 的默认选项）。**防腐层是跨上下文集成的标配防线**。
- **防腐层解决什么**：第三方/遗留系统的模型与你的领域模型不一致——**翻译发生在边界适配器**，领域内永远说自己的通用语言。"外部返回 status=A1/B2" vs 你的 OrderStatus 枚举——没有 ACL，外部枚举会渗透进领域代码。
- **遗留系统集成是 ACL 的主战场**：不改老系统（改不动），在边界写翻译层——**绞杀者模式（Strangler Fig）**：新系统逐功能接管，ACL 承接过渡期流量，旧功能逐个"绞杀"下线。
- **ACL 的实现位置**：适配器层（49-04 六边形的外圈）——`PaymentGatewayAdapter` 把渠道返回码翻译为领域事件；**领域层只认识自己的语言**。
- **集成测试的重心**：ACL 的翻译正确性是跨上下文 Bug 高发区——**翻译表（映射矩阵）驱动测试**：外部状态 × 内部状态全覆盖（40-03 few-shot 边界示例同源思想）。
- 易错点：外部模型直接进领域（DTO 直接当聚合用）；ACL 退化成透传（没有真正翻译）；绞杀者改造无流量开关（无法回退旧系统）；翻译表无测试（外部升级一改，静默错译）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class AntiCorruptionLayer {
    /** 外部遗留系统的模型（不能渗透进领域） */
    static class LegacyPaymentResponse {
        String retCode;      // "00"=成功, "A1"=处理中, "B2"=失败
        String retMsg;
        String amt;          // 单位：分（字符串！）
    }

    /** 领域自己的语言 */
    enum PaymentStatus {
        SUCCESS, PENDING, FAILED
    }

    /** 防腐层：翻译发生在边界 */
    static class PaymentGatewayAdapter {
        record Translation(LegacyPaymentResponse raw, PaymentStatus status, int amountCents) {
        }

        private static final Map<String, PaymentStatus> CODE_MAP = Map.of(
                "00", PaymentStatus.SUCCESS,
                "A1", PaymentStatus.PENDING,
                "B2", PaymentStatus.FAILED);

        Translation translate(LegacyPaymentResponse resp) {
            PaymentStatus status = CODE_MAP.getOrDefault(resp.retCode, PaymentStatus.FAILED);
            int cents;
            try {
                cents = Integer.parseInt(resp.amt);
            } catch (NumberFormatException e) {
                cents = -1;                      // 异常金额 -> FAILED，绝不透传垃圾
            }
            return new Translation(resp, cents >= 0 ? status : PaymentStatus.FAILED, cents);
        }
    }

    static void aclDemo() {
        System.out.println("【防腐层：外部模型在边界被翻译】");
        PaymentGatewayAdapter adapter = new PaymentGatewayAdapter();
        for (String[] raw : new String[][]{{"00", "OK", "6900"}, {"A1", "处理中", "6900"},
                {"B2", "银行拒绝", "6900"}, {"X9", "未知码", "abc"}}) {
            LegacyPaymentResponse resp = new LegacyPaymentResponse();
            resp.retCode = raw[0];
            resp.retMsg = raw[1];
            resp.amt = raw[2];
            var t = adapter.translate(resp);
            System.out.printf("  外部 retCode=%-3s amt=%-5s -> 领域状态=%s 金额=%d 分%n",
                    resp.retCode, resp.amt, t.status(), t.amountCents());
        }
        System.out.println("  领域代码只见 PaymentStatus.SUCCESS —— 未知码被安全兜底");
        System.out.println();
    }

    static void stranglerPlan() {
        System.out.println("【绞杀者模式：逐步替换遗留订单系统】");
        List<String> steps = List.of(
                "阶段0：新订单上下文上线，ACL 承接遗留系统的读取（数据仍由旧系统写）",
                "阶段1：新订单接管创建（写切新，读兼容旧）—— 按流量灰度",
                "阶段2：查询/报表切新 —— 旧系统只处理历史只读",
                "阶段3：历史数据迁湖（46-09）-> 旧系统下线，ACL 移除");
        for (String s : steps) {
            System.out.println("  " + s);
        }
        System.out.println("  每阶段有流量开关可回退（41-07 灰度纪律的基础设施版）");
        System.out.println();
    }

    static void translationTests() {
        System.out.println("【翻译矩阵测试：ACL 的单元测试核心】");
        List<String> cases = List.of(
                "retCode 全枚举 × amt 合法/非法/空 -> 状态与金额全覆盖",
                "新增外部码 X9（未映射）-> 默认 FAILED 而不是崩溃",
                "amt 字段类型漂移（分->元）-> 校验规则当场拦截（46-08 契约同源）");
        for (String c : cases) {
            System.out.println("  - " + c);
        }
        System.out.println("  ACL 是外部系统的“看门人”：翻译矩阵就是它的测试用例集");
    }

    public static void main(String[] args) {
        aclDemo();
        stranglerPlan();
        translationTests();
    }
}
```

### 49-08 DDD 与微服务、单体落地

**知识点**
- **DDD 与微服务的关系：上下文是服务的理论依据**——29 章按业务拆服务，本质就是按限界上下文切（49-01）。**一个上下文 = 一个（或一组）服务**；上下文间用事件与 API 集成（上下文映射图 = 服务调用图）。
- **不是每个上下文都要独立微服务**：上下文与服务的映射是弹性决策——小团队可以把 2~3 个小上下文放进一个模块化单体（modular monolith），**用包边界 + 架构测试（ArchUnit 类）守护边界**，等服务规模再拆。**先模块化单体、再按痛点拆微服务**是多数团队的正确路径。
- **模块化单体的纪律**：包间只通过公共接口调用（internal 包不可跨模块引用）、独立构建模块（Maven 多模块）、边界测试（依赖方向检查）——**单体里的边界 discipline 是未来拆分的全部基础**。
- **拆分的触发条件**：上下文要独立伸缩（吞吐曲线不同）、独立部署节奏（发布频率冲突）、独立技术栈、团队边界（康威定律）——**没有这些痛点就别拆**（29 章的拆分代价在 DDD 视角下更清晰）。
- **数据库的对应决策**：模块化单体可共享库但分 schema（禁止跨模块 join，49-05 的读模型解决跨上下文查询）；拆微服务时按上下文分库（39 章的分片在上下文内做）。
- 易错点：分布式单体（服务拆了但耦合还在：同步调用链、共享库、共享库表）；一步到位微服务（上下文边界都没摸清就拆，拆错再合并成本极高）；边界无守护（单体三个月后包互相乱引，形同虚设）。

### 49-09 领域建模实战：营销与优惠

**知识点**
- **营销域是检验建模能力的试金石**：优惠券有“满减/折扣/秒杀价”多种类型、有使用门槛、叠加规则、有效期、库存——**规则交织度高，贫血模型在这里最容易失控**（一个 if-else 大山）。
- **建模的第一步：识别值对象与多态**——“优惠”是策略族：`CouponPolicy` 接口 + `FullReduction`（满减）/ `PercentageDiscount`（折扣）/ `FixedAmount`（固定金额）实现——**策略模式（31 章）在领域内的正名**：不是“代码技巧”，是业务本身的多态。
- **叠加规则是一等公民**：哪些优惠可叠加（优惠券+会员折扣）、不可叠加（两张券互斥）、计算顺序（先商品折扣再满减）——**叠加策略独立成对象**（`StackingRule`），不要散落在计算流程的 if 里。
- **优惠计算的可测试性**：纯函数计算（输入订单上下文 + 优惠清单 -> 输出分摊结果）——**分摊（分摊到每个订单明细）要处理除不尽**（金额尾差按行分摊，最后一行吸收尾差——BigDecimal 必备功夫）。
- **营销上下文与交易上下文的边界**：交易只关心“最终应付金额”与“优惠明细快照”（用于审计与退款）；**算价过程是营销域的事**——交易侧保存计算结果快照而非实时重算（价格快照原则）。
- 易错点：优惠规则写死在订单 Service（营销改动波及交易）；金额用 double（精度灾难，14 章 BigDecimal 的领域级应用）；分摊尾差随机分配（对账差一分钱）；优惠库存与交易扣减跨上下文强一致（用事件+校验兜底，49-03）。

**示例代码**
```java
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public class MarketingModeling {
    record Money(BigDecimal amount) {
        static Money of(String v) {
            return new Money(new BigDecimal(v));
        }

        Money minus(Money o) {
            return new Money(amount.subtract(o.amount));
        }

        boolean greaterThan(Money o) {
            return amount.compareTo(o.amount) > 0;
        }

        int cents() {
            return amount.movePointRight(2).intValueExact();
        }
    }

    /** 策略族：优惠本身是多态的业务概念 */
    interface CouponPolicy {
        String name();

        Money discountFor(Money orderAmount);
    }

    record FullReduction(Money threshold, Money off) implements CouponPolicy {
        public String name() {
            return "满" + threshold.amount() + "减" + off.amount();
        }

        public Money discountFor(Money orderAmount) {
            return orderAmount.greaterThan(threshold) || orderAmount.amount().compareTo(threshold.amount()) == 0
                    ? off : Money.of("0");
        }
    }

    record PercentageDiscount(int percent, Money cap) implements CouponPolicy {
        public String name() {
            return percent + "%折扣（上限" + cap.amount() + "）";
        }

        public Money discountFor(Money orderAmount) {
            Money d = new Money(orderAmount.amount()
                    .multiply(BigDecimal.valueOf(percent))
                    .divide(BigDecimal.valueOf(100)));
            return d.greaterThan(cap) ? cap : d;
        }
    }

    /** 叠加规则：独立建模，不散落 if */
    record StackingRule(List<String> exclusiveGroups) {
        boolean canStack(String couponA, String couponB) {
            return true;   // 简化：本例全部可叠，互斥组留作练习
        }
    }

    static void calculate() {
        System.out.println("【订单 100 元，两张券叠加计算】");
        List<CouponPolicy> coupons = List.of(
                new FullReduction(Money.of("80"), Money.of("20")),
                new PercentageDiscount(10, Money.of("15")));
        Money orderAmount = Money.of("100.00");
        Money total = Money.of("0.00");
        for (CouponPolicy c : coupons) {
            Money d = c.discountFor(orderAmount);
            total = new Money(total.amount().add(d.amount()));
            System.out.printf("  %-16s -> 优惠 %s 元%n", c.name(), d.amount());
        }
        Money payable = orderAmount.minus(total);
        System.out.printf("  应付 = 100 - %s = %s 元（%d 分）%n", total.amount(), payable.amount(), payable.cents());
        System.out.println("  快照原则：交易侧保存“优惠明细+应付金额”快照，退款按快照走");
        System.out.println();
    }

    static void allocationTail() {
        System.out.println("【分摊尾差：最后一行吸收】");
        Money payable = Money.of("10.00");
        int[] lineWeights = {1, 1, 1};
        int totalCents = payable.cents();
        int per = totalCents / lineWeights.length;
        int[] alloc = new int[lineWeights.length];
        int assigned = 0;
        for (int i = 0; i < alloc.length; i++) {
            alloc[i] = per;
            assigned += per;
        }
        alloc[alloc.length - 1] += totalCents - assigned;   // 尾差给最后一行
        for (int i = 0; i < alloc.length; i++) {
            System.out.printf("  明细%d 分摊 %d 分%n", i + 1, alloc[i]);
        }
        System.out.printf("  合计 %d 分 = 应付 %d 分（对账恒等）%n", alloc[0] + alloc[1] + alloc[2], totalCents);
        System.out.println("  尾差规则写进契约：随机分配会导致退款与对账差一分钱");
    }

    public static void main(String[] args) {
        calculate();
        allocationTail();
    }
}
```

### 49-10 遗留系统改造与演进式架构

**知识点**
- **遗留系统不是技术问题，是演进策略问题**：三个月赶工的订单系统跑着 70% 的交易——推倒重写的风险（业务中断、隐性规则丢失）远大于演进改造。**演进式架构（evolutionary architecture）**：增量重构 + 持续可发布。
- **改造的第一步是“知道现状”**：特征检测（failure mode analysis）——耦合度分析、圈复杂度热点、变更频率分布（**改得最频繁的类就是业务核心**，49-01 事件风暴的代码侧佐证）。补测试是改造的安全网（33 章测试金字塔：先给核心路径铺集成测试）。
- **绞杀者路线（49-07）+ 接缝引入（seam）**：在旧代码里先挖出“接缝”（可替换点）——把“直接调库”改成“调接口”（49-04 端口），一步一小步，每步可发布可回退。
- **数据同步期**：新旧库并存的同步方案（43-09 CDC）——双向写期要版本仲裁（45-08 fencing 思想），切换期灰度读。
- **演进式架构的守护**：适应度函数（fitness function）——把架构约束写成自动化检查（依赖方向、分层违例、API 兼容性）进 CI，**让架构随演进不退化**（49-08 ArchUnit 的体系化）。
- **改造的节奏与止损**：每两周一个可发布增量；改造期间冻结大需求（或只允许与改造相关的）；**改造预算有上限**（超过 X 人月仍未见效 -> 重新评估方案）。
- 易错点：大爆炸重写（两年没上线，旧系统还在演进，永远追不上）；只重构不补测试（改一处崩三处）；接缝不清理（重构完留下抽象层垃圾）；没有业务方参与（技术自嗨改造，业务感知为零价值）。

**示例代码**

### 49-11 综合案例：订单域建模全流程

**知识点**
- **把本章收束成一次完整建模**：从业务描述出发——事件风暴（49-01）梳理订单域事件 -> 划定上下文与通用语言 -> 识别聚合与不变量（49-02）-> 设计领域事件与协作（49-03）-> 端口适配器落地（49-04）-> CQRS 读模型（49-05）-> 事件溯源决策（49-06）-> 部署形态（49-08）。**一条从业务语言到代码结构的完整映射链**。
- **建模产出物清单**：上下文映射图、事件清单（含消费方）、聚合卡片（不变量/边界/入口）、端口清单、读模型定义、一致性策略表——**每个产出物都是可评审文档**，评审通过才写代码。
- **订单聚合卡片示例**：聚合根 Order；成员 OrderLine/Money（值对象）；不变量：明细和≥0、提交后金额不可变、同 SKU 唯一；边界：不含库存/优惠（跨上下文）；事件：OrderPlaced/OrderPaid/OrderCancelled；仓储：OrderRepository（事件溯源可选 49-06）。
- **建模的迭代性**：第一版聚合卡片在实现中会暴露边界错误（比如发现“金额不可变”在改价场景不成立）——**建模是渐进的**，卡片与代码同步演进（49-10 适应度函数守护）。
- **评审检查单**：通用语言一致（代码命名=业务语言）？聚合够小？不变量闭环？跨聚合只走事件？端口无框架依赖？读模型契约明确？——**六问全过才进开发**。
- 易错点：产出物写完不评审（建模沦为个人行为，团队不认）；聚合卡片与代码漂移（改代码不改卡片）；通用语言只停在设计文档（代码里还是 OrderManager）；一版建模用三年（业务变了模型不跟）。
