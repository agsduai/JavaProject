# 第61章 分布式任务调度与工作流引擎

第28章讲了消息队列，第41章讲了发布流水线，但企业系统里还有一类"必须在这个时刻执行一次"的批量任务：对账、报表、超时关单、数据回刷。单机 cron 的三个缺口（无高可用、无分片、无观测）催生了调度平台。本章按「调度全景 → 调度中心与故障转移 → 任务分片 → DAG 依赖编排 → 幂等与重复执行防护 → 失败重试与补偿 → 工作流状态机 → 长流程持久化与恢复 → 调度可观测 → 与 MQ/批处理的边界 → 超时关单案例」的顺序讲。所有示例仍是纯 JDK：执行器心跳与忙碌转移、分片再平衡、DAG 环检测与拓扑分层、三层幂等、拉链式重试补偿、工作流版本推进、调度指标与积压诊断全部真实运行。

### 61-01 调度系统全景：从 cron 到调度平台

**知识点**
- **单机 cron 的三个致命问题**：**无高可用**（机器挂了任务就没了）、**无分片**（10 万台机器上的任务配置散落各处）、**无统一观测**（任务跑没跑、耗时多少、失败几次全靠人问）——**这三点就是调度平台存在的全部理由**。
- **调度平台的四个核心能力**：**任务注册与发现**（所有任务登记在一处）、**触发与分片**（按时间/事件触发，任务可分片并行）、**故障转移**（执行器挂了任务重派）、**可观测**（执行历史/耗时/成功率/告警）。
- **调度的两种触发模型**：**时间驱动**（cron/固定频率/延迟）与**事件驱动**（某个任务完成 -> 触发下游，即 DAG 依赖 61-04）；**两者常混合**（定时触发根节点，依赖串联下游）。
- **调度与消息队列的边界**（28/43 章的对照）：MQ 是"事件流式、毫秒级、无状态消费者"；调度是"**有明确执行时刻与执行记录**的批处理单元"——**"每天 2 点跑对账"是调度，"订单创建后通知积分"是 MQ**，判据是"是否需要保证某个时刻执行一次"。
- **调度平台的分层**：调度中心（触发/分片/路由）+ 执行器（真正跑任务的 worker）+ 存储（任务定义/执行日志/依赖关系）——**中心轻、执行器可水平扩**是标准架构。
- **开源方案参照**：XXL-JOB（中心-执行器模型，国内最常见）、ElasticJob（分片与弹性）、Quartz（单机/集群基础库）——**本章用纯 JDK 模拟这三者的核心机制**。
- 易错点：把调度当 MQ 用（毫秒级事件驱动不适合调度）；任务无分片（单机跑千万数据）；执行日志只留最新一次（历史无法复盘）；调度中心单点（全公司任务停摆）。

### 61-02 调度中心架构：注册、发现与故障转移

**知识点**
- **执行器注册与心跳**（29-01 的调度版，但语义不同）：执行器启动时注册到调度中心（地址/支持的 jobHandler/负载），**周期性心跳**维持在线；超过阈值未心跳则标记下线——**与注册中心不同：调度中心还要记录"哪些执行器能跑哪些任务"**（路由依据）。
- **路由策略**：**轮询/随机/一致性哈希**（29-04 的负载均衡）+ **分片广播**（61-03，所有执行器各跑一片）+ **故障转移**（失败重试其他执行器）+ **忙碌转移**（执行器排队过多时换一台）。
- **任务派发模型**：调度中心**主动调用执行器**（HTTP/RPC，触发 -> 执行 -> 回调结果），还是**执行器拉取任务**（pull 模型）？**主动派发**时效好但需要中心知道执行器地址；**拉取**解耦但有时延——XXL-JOB 用主动派发，ElasticJob 用注册中心 + 本地触发。
- **调度中心的高可用**：中心本身也要集群（45 章共识/主备），**触发时刻的重复触发防护**（同一任务同一时刻只允许一个中心触发——用分布式锁或数据库唯一约束，39/45 章思想）。
- **时钟与触发精度**：cron 触发依赖"时间片扫描"（每秒扫一次到期任务）或"时间轮"（28-02）——**扫描粒度决定触发精度**（秒级扫描 vs 时间轮毫秒级）；**夏令时/闰秒**不是玩笑（跨时区业务尤其）。
- 易错点：执行器心跳超时就判定死亡（网络抖动误杀，需容忍次数）；中心多实例同时触发（任务重复执行）；执行器地址硬编码（扩容要改配置）；触发时间用本地时区（跨时区业务错乱）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class SchedulerCenter {
    record Executor(String id, List<String> handlers, long lastHeartbeat,
                    int runningTasks, boolean online) {
    }

    static final long TIMEOUT_MS = 30_000;

    /** 心跳判定：连续超时才摘除（容忍一次抖动） */
    static List<Executor> alive(List<Executor> all, long now) {
        List<Executor> out = new ArrayList<>();
        for (Executor e : all) {
            boolean ok = e.online() && now - e.lastHeartbeat() <= TIMEOUT_MS;
            System.out.printf("  %-8s handlers=%-18s 心跳间隔=%-6dms -> %s%n",
                    e.id(), e.handlers(), now - e.lastHeartbeat(), ok ? "在线" : "摘除");
            if (ok) {
                out.add(e);
            }
        }
        return out;
    }

    /** 路由：按 handler 过滤 + 忙碌转移（取负载最低） */
    static Executor route(List<Executor> alive, String handler) {
        return alive.stream()
                .filter(e -> e.handlers().contains(handler))
                .min((a, b) -> Integer.compare(a.runningTasks(), b.runningTasks()))
                .orElse(null);
    }

    /** 触发去重：同一任务同一时间片只允许一个中心实例触发 */
    static boolean tryTrigger(Map<String, String> triggerLocks, String jobId,
                              String slot, String centerId) {
        String key = jobId + "@" + slot;
        String holder = triggerLocks.putIfAbsent(key, centerId);
        if (holder == null) {
            System.out.printf("  中心 %s 获得触发权：%s%n", centerId, key);
            return true;
        }
        System.out.printf("  中心 %s 重复触发被拒（%s 已由 %s 触发）%n", centerId, key, holder);
        return false;
    }

    public static void main(String[] args) {
        long now = 100_000;
        List<Executor> all = new ArrayList<>(List.of(
                new Executor("exec-1", List.of("closeOrderJob"), now - 5_000, 2, true),
                new Executor("exec-2", List.of("closeOrderJob", "reportJob"), now - 28_000, 0, true),
                new Executor("exec-3", List.of("closeOrderJob"), now - 45_000, 0, true),
                new Executor("exec-4", List.of("reportJob"), now - 3_000, 5, true)));
        System.out.println("【在线判定】");
        List<Executor> online = alive(all, now);
        System.out.println();
        System.out.println("【路由（忙碌转移）】");
        Executor target = route(online, "closeOrderJob");
        System.out.println("  closeOrderJob -> " + (target == null ? "无可用执行器"
                : target.id() + "（运行中 " + target.runningTasks() + "）"));
        System.out.println();
        System.out.println("【多中心触发去重】");
        Map<String, String> locks = new LinkedHashMap<>();
        tryTrigger(locks, "closeOrderJob", "2026-11-18T02:00", "center-A");
        tryTrigger(locks, "closeOrderJob", "2026-11-18T02:00", "center-B");
    }
}
```

### 61-03 任务分片与并行执行

**知识点**
- **分片是"把一个大数据量任务拆给多个执行器并行跑"**：总片数固定（如 8），执行器数量可变（如 3 台）——**每台执行器拿到的分片数 = 8 ÷ 3 上取整**，跑不完的由后续执行器补（或按"分片数 = 执行器数"动态调）。
- **分片参数的下发**：调度中心把 `(分片序号, 总片数)` 传给执行器，**执行器按"取模"或"范围"切分数据**——如 `WHERE id % totalShards = shardIndex`，或按 id 区间。**两种切法的性能差异巨大**（取模均匀但索引效果差，区间索引好但可能倾斜）。
- **分片后的结果汇总**：分片执行各自写结果（分表/分文件），**汇总阶段在调度中心或下游聚合**——汇总也要幂等（61-05），失败重跑只重跑失败的分片。
- **动态分片（弹性）**：执行器扩缩容时，**分片重新分配**（ElasticJob 的再平衡）——扩一台机器，分片自动从其他机器挪走一部分；**缩容时未完成的分片要重新派发**（不能丢）。
- **分片与数据倾斜**（59-08 的调度版）：按 id 取模均匀但**按业务键分片可能倾斜**（大客户数据集中）；**分片粒度太粗**（4 片跑 1 亿）-> 单分片慢；**太细**（1000 片）-> 调度与汇总开销大。
- 易错点：分片数与执行器数固定绑定（扩容无意义）；分片不幂等（重跑重复写）；分片失败不重派（数据缺一块）；汇总阶段重复计算（分片已成功又重跑）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ShardingJob {
    record ShardAssignment(String executor, List<Integer> shards) {
        int count() {
            return shards.size();
        }
    }

    /** 静态分片：总片数固定，按执行器数均分（余数给前面的） */
    static Map<String, List<Integer>> assign(List<String> executors, int totalShards) {
        Map<String, List<Integer>> map = new LinkedHashMap<>();
        int base = totalShards / executors.size();
        int remain = totalShards % executors.size();
        int shard = 0;
        for (int i = 0; i < executors.size(); i++) {
            List<Integer> mine = new ArrayList<>();
            int n = base + (i < remain ? 1 : 0);
            for (int j = 0; j < n; j++) {
                mine.add(shard++);
            }
            map.put(executors.get(i), mine);
        }
        return map;
    }

    /** 取模切分：分片号 = id % totalShards */
    static int shardByMod(long id, int totalShards) {
        return (int) (id % totalShards);
    }

    /** 范围切分：按 id 区间 */
    static int shardByRange(long id, long maxId, int totalShards) {
        long span = Math.max(1, maxId / totalShards);
        int idx = (int) (id / span);
        return Math.min(totalShards - 1, idx);
    }

    static void compareSplit(int totalShards, long maxId, int samples) {
        Map<Integer, Integer> modDist = new LinkedHashMap<>();
        Map<Integer, Integer> rangeDist = new LinkedHashMap<>();
        for (int i = 0; i < samples; i++) {
            long id = i + 1L;
            modDist.merge(shardByMod(id, totalShards), 1, Integer::sum);
            rangeDist.merge(shardByRange(id, maxId, totalShards), 1, Integer::sum);
        }
        System.out.printf("  取模分布：%s%n", modDist);
        System.out.printf("  范围分布：%s%n", rangeDist);
    }

    public static void main(String[] args) {
        System.out.println("【分片分配：8 片 / 3 执行器】");
        assign(List.of("exec-1", "exec-2", "exec-3"), 8)
                .forEach((k, v) -> System.out.printf("  %s -> %s (%d 片)%n", k, v, v.size()));
        System.out.println();
        System.out.println("【扩容到 4 执行器：再平衡】");
        assign(List.of("exec-1", "exec-2", "exec-3", "exec-4"), 8)
                .forEach((k, v) -> System.out.printf("  %s -> %s (%d 片)%n", k, v, v.size()));
        System.out.println();
        System.out.println("【两种切分方式的数据分布（200 条 / 4 片）】");
        compareSplit(4, 200, 200);
        System.out.println("  取模：均匀但索引利用率差；范围：索引好但大 id 段可能倾斜");
    }
}
```

### 61-04 任务依赖与 DAG 编排

**知识点**
- **DAG（有向无环图）是任务编排的核心表达**：节点=任务，边=依赖（`A -> B` 表示 B 依赖 A）。**无环是硬约束**（有环 = 死锁，编译期/注册期就要检测）。
- **依赖的两种粒度**：**任务级**（A 成功 -> 触发 B）与**分片级**（A 的所有分片成功才触发 B）——**跨天依赖**（今天的任务依赖昨天的同任务完成）是数仓最常见形态（46-01 分层调度）。
- **DAG 的执行语义**：**拓扑排序**决定执行顺序；同一层的节点可并行（受资源限制）；**上游失败的处理**：下游跳过（不跑）或标记"等待补数"（跑批场景通常跳过 + 告警，补数后手动触发）。
- **关键路径与 SLA 保证**：DAG 的总耗时 = 关键路径长度（59-03 的调度版）——**想让报表 9 点出，就要反推关键路径的最晚启动时间**（`SLA - 关键路径耗时 = 最晚开始`），并给路径上的任务设"超时会拖累 SLA"的告警。
- **依赖的配置与版本**：依赖关系存数据库（可查可改），**变更要走评审**（改错依赖 -> 全链路数据错位）；**依赖成环检测**在保存时做（DFS 检测）。
- 易错点：DAG 有环（保存时应拒绝）；跨天依赖没配（下游读到不完整数据，46-08 的质量规则拦不住）；上游失败下游照样跑（用旧数据算出错结果）；关键路径无 SLA 告警（日报迟到才发现）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class DagOrchestration {
    /** 邻接表表示 DAG */
    static final Map<String, List<String>> graph = new LinkedHashMap<>();

    static void addTask(String name, String... deps) {
        graph.putIfAbsent(name, new ArrayList<>());
        for (String d : deps) {
            graph.computeIfAbsent(d, k -> new ArrayList<>()).add(name);
        }
    }

    /** DFS 检测环 */
    static boolean hasCycle() {
        Map<String, Integer> color = new HashMap<>();     // 0 未访问 1 访问中 2 已完成
        for (String node : graph.keySet()) {
            if (color.getOrDefault(node, 0) == 0 && dfs(node, color)) {
                return true;
            }
        }
        return false;
    }

    static boolean dfs(String node, Map<String, Integer> color) {
        color.put(node, 1);
        for (String next : graph.getOrDefault(node, List.of())) {
            int c = color.getOrDefault(next, 0);
            if (c == 1) {
                return true;                               // 回到访问中的节点 = 环
            }
            if (c == 0 && dfs(next, color)) {
                return true;
            }
        }
        color.put(node, 2);
        return false;
    }

    /** 拓扑排序 + 分层（同层可并行） */
    static List<List<String>> layers() {
        Map<String, Integer> indegree = new LinkedHashMap<>();
        graph.keySet().forEach(k -> indegree.put(k, 0));
        graph.values().forEach(list -> list.forEach(n -> indegree.merge(n, 1, Integer::sum)));

        List<List<String>> result = new ArrayList<>();
        List<String> frontier = new ArrayList<>();
        for (Map.Entry<String, Integer> e : indegree.entrySet()) {
            if (e.getValue() == 0) {
                frontier.add(e.getKey());
            }
        }
        while (!frontier.isEmpty()) {
            result.add(new ArrayList<>(frontier));
            List<String> next = new ArrayList<>();
            for (String node : frontier) {
                for (String child : graph.getOrDefault(node, List.of())) {
                    int d = indegree.merge(child, -1, Integer::sum);
                    if (d == 0) {
                        next.add(child);
                    }
                }
            }
            frontier = next;
        }
        return result;
    }

    public static void main(String[] args) {
        addTask("ods_orders_sync");
        addTask("dwd_orders_clean", "ods_orders_sync");
        addTask("dwd_payments_clean", "ods_orders_sync");
        addTask("dws_city_gmv", "dwd_orders_clean");
        addTask("dws_channel_gmv", "dwd_payments_clean");
        addTask("ads_daily_report", "dws_city_gmv", "dws_channel_gmv");

        System.out.println("【DAG 结构】");

        System.out.println();
        System.out.println("【拓扑分层（同层可并行）】");
        List<List<String>> ls = layers();
        for (int i = 0; i < ls.size(); i++) {
            System.out.printf("  L%d：%s%n", i, ls.get(i));
        }
```

### 61-05 调度幂等与重复执行防护

**知识点**
- **调度系统的三大重复来源**：**中心多实例重复触发**（61-02 的锁缺失）、**故障转移重派**（执行器"看起来挂了"但实际跑完了）、**人工重跑**（忘了上次已成功）——**三种都会导致任务跑两次**。
- **幂等的三层保障**：① **触发层去重**（同一任务同一时间片只触发一次，分布式锁/唯一约束）；② **执行层幂等**（任务逻辑本身可重入：按分区覆盖写、按主键 upsert、先删后插）；③ **结果层校验**（重跑后校验结果未翻倍，46-08 质量规则）。
- **"至少一次"与"恰好一次"的取舍**：调度系统通常保证**至少一次触发**（宁可重跑不能漏跑），**幂等由任务实现方保证**——**这与 28 章 MQ 的语义完全一致**（43-06 的同款结论：幂等是端到端正确性的最后一公里）。
- **重跑的正确姿势**：**按分区/按天覆盖**（`INSERT OVERWRITE PARTITION`，59-10）、**先清理目标再写**（清 -> 写 -> 校验三步）、**重跑前确认上游数据完整**（46-08）——**"直接追加"是最常见的错误**。
- **补数（backfill）**：历史缺口批量重跑——**按天串行**（跨天依赖不能并行，61-04）、**限速**（不压垮源库，46-09）、**进度可观测**（跑完哪天/还剩几天）。
- 易错点：任务"先查后写"非原子（两个实例同时判断"未处理"）；重跑直接追加（数据翻倍）；补数并行跑跨天依赖（下游读到半成品）；无执行记录（不知道跑没跑过）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class IdempotentJob {
    /** 任务执行记录：jobId + bizDate + 分片 为唯一键 */
    record Execution(String jobId, String bizDate, int shard, String status, long finishedAt) {
    }

    static final Map<String, Execution> history = new LinkedHashMap<>();

    static String key(String jobId, String bizDate, int shard) {
        return jobId + "#" + bizDate + "#" + shard;
    }

    /** 触发层：已成功则跳过（可重跑需显式 force） */
    static boolean shouldRun(String jobId, String bizDate, int shard, boolean force) {
        Execution prev = history.get(key(jobId, bizDate, shard));
        if (!force && prev != null && prev.status().equals("SUCCESS")) {
            System.out.printf("  [%s] 已成功于 %d -> 跳过（防重复）%n", key(jobId, bizDate, shard),
                    prev.finishedAt());
            return false;
        }
        return true;
    }

    /** 执行层：幂等写入（按分片覆盖，模拟"先删后写"） */
    static void runIdempotent(String jobId, String bizDate, int shard, List<String> target) {
        target.removeIf(row -> row.startsWith(jobId + "#" + bizDate + "#" + shard + "#"));
        for (int i = 0; i < 3; i++) {
            target.add(jobId + "#" + bizDate + "#" + shard + "#row-" + i);
        }
        history.put(key(jobId, bizDate, shard),
                new Execution(jobId, bizDate, shard, "SUCCESS", System.currentTimeMillis() % 100000));
        System.out.printf("  执行 %s 分片%d -> 覆盖写入 3 行（幂等）%n", jobId, shard);
    }

    public static void main(String[] args) {
        List<String> target = new ArrayList<>();
        System.out.println("【首次执行】");
        if (shouldRun("closeOrder", "2026-11-18", 0, false)) {
            runIdempotent("closeOrder", "2026-11-18", 0, target);
        }
        System.out.println("  目标数据行数：" + target.size());

        System.out.println();
        System.out.println("【重复触发（故障转移重派）】");
        if (shouldRun("closeOrder", "2026-11-18", 0, false)) {
            runIdempotent("closeOrder", "2026-11-18", 0, target);
        }
        System.out.println("  目标数据行数：" + target.size() + "（未翻倍）");

        System.out.println();
        System.out.println("【强制重跑（人工补数）】");
        if (shouldRun("closeOrder", "2026-11-18", 0, true)) {
            runIdempotent("closeOrder", "2026-11-18", 0, target);
        }
        System.out.println("  目标数据行数：" + target.size() + "（覆盖而非追加）");
        System.out.println();
        System.out.println("  三层保障：触发去重 + 执行覆盖 + 结果校验");
    }
}
```

### 61-06 失败重试与补偿

**知识点**
- **失败分类决定重试策略**（40-02 的错误分类在调度上的应用）：**可重试**（网络抖动/下游临时不可用——指数退避重试）、**不可重试**（数据错误/参数错误——立即失败告警）、**部分失败**（分片中部分失败——只重跑失败分片）。**无脑重试是事故放大器**（重试风暴把下游打穿，44-08）。
- **重试的退避与上限**：指数退避（1s/2s/4s/8s）+ 最大次数（3~5 次）+ **抖动**（避免所有实例同时重试）——与 40-02 的重试策略完全同构。
- **补偿 vs 重试**：**重试**是"再试一次同一操作"；**补偿**是"用反向操作抵消已产生的影响"（51 章的退款、39-09 的 Cancel）——**调度任务的补偿**典型是"失败后回滚已写入的分区"或"标记数据不可用"（46-08 的阻断规则）。
- **失败的可观测**：失败任务的**错误摘要 + 重试次数 + 最终状态**（SUCCESS/FAILED/DEAD）；**死信任务**（超过重试上限）进人工处理队列，**不能静默丢弃**（28 章死信语义）。
- **上游失败的下游影响**：DAG 中上游失败 -> 下游跳过并**标记"依赖未就绪"**（而不是跑出错误结果 61-04）；补数完成后**自动触发下游**（或人工确认后触发）。
- 易错点：对"数据错误"重试（永远失败还占资源）；重试无上限（死循环）；失败只打日志不告警（数据缺口无人知）；补偿逻辑本身失败（需要补偿的补偿，必须人工兜底）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class RetryAndCompensation {
    enum FailureKind {
        TRANSIENT, PERMANENT, PARTIAL
    }

    record Attempt(int no, long backoffMs, String result) {
    }

    /** 按失败类型决定重试策略 */
    static List<Attempt> retryPlan(FailureKind kind, int maxRetry) {
        List<Attempt> plan = new ArrayList<>();
        if (kind == FailureKind.PERMANENT) {
            plan.add(new Attempt(3, 0, "不重试，直接进入死信 + 告警"));
            return plan;
        }
        long backoff = 1000;
        for (int i = 1; i <= maxRetry; i++) {
            long jitter = i * 137L % 500;                 // 抖动，避免同步重试
            plan.add(new Attempt(i, backoff + jitter,
                    kind == FailureKind.PARTIAL ? "只重跑失败分片" : "重跑整个任务"));
            backoff *= 2;
        }
        plan.add(new Attempt(maxRetry + 1, 0, "仍失败 -> 死信 + 人工"));
        return plan;
    }

    /** 补偿：失败后回滚已写入的分区 */
    static void compensate(List<String> writtenPartitions, List<String> livePartitions) {
        System.out.println("  补偿：回滚本次已写入的分区 " + writtenPartitions);
        livePartitions.removeAll(writtenPartitions);
        System.out.println("  回滚后线上分区：" + livePartitions + "（下游读到的是上一次的完整数据）");
    }

    public static void main(String[] args) {
        System.out.println("【重试计划：临时故障】");
        retryPlan(FailureKind.TRANSIENT, 3).forEach(a ->
                System.out.printf("  第%d次 退避=%5dms %s%n", a.no(), a.backoffMs(), a.result()));
        System.out.println();
        System.out.println("【重试计划：永久故障】");
        retryPlan(FailureKind.PERMANENT, 3).forEach(a ->
                System.out.printf("  第%d次 %s%n", a.no(), a.result()));
        System.out.println();
        System.out.println("【补偿：半写入失败】");
        List<String> live = new ArrayList<>(List.of("dt=2026-11-16", "dt=2026-11-17"));
        List<String> written = new ArrayList<>(List.of("dt=2026-11-18"));
        live.addAll(written);                              // 已写入但不完整
        compensate(written, live);
        System.out.println("  原则：宁可让下游用旧数据，也不让它读到半成品");
    }
}
```

### 61-07 工作流引擎：状态机与审批流

**知识点**
- **工作流引擎与调度的区别**：调度是"**时间驱动的批量任务**"（61-01），工作流是"**人机混合的长流程**"——审批流里有人工节点（等待审批）、有状态持久化（流程跑一周）、有分支与回退。**两者都用 DAG 表达，但工作流的节点要持久化状态**。
- **状态机是工作流的内核**：流程定义（节点 + 转移条件）-> 流程实例（某个业务单据的执行状态）-> 任务（待办）-> 变量（流程上下文）——**与 51-03 的支付状态机同源，只是节点更多、有等待态**。
- **审批流的四个要素**：**节点类型**（审批/抄送/条件分支/并行会签）、**审批人规则**（指定人/角色/上级/动态计算）、**流转规则**（同意/驳回/加签/转办）、**超时策略**（自动通过/自动驳回/催办）——**每个要素都是配置，不是代码**。
- **长流程的持久化与恢复**（本章重点）：流程实例跑一周，**每次状态变更都要落库**（当前节点/历史轨迹/变量），引擎重启后从库恢复——**这与 43-05 的 checkpoint 思想一致：状态自持 + 可恢复**。
- **幂等的流程推进**：同一个审批动作重复提交（用户双击/网络重试）——**用"任务 ID + 动作 + 版本号"做幂等**（51-03 同源）；并行会签要处理"部分同意"的汇总（所有节点完成才推进）。
- 易错点：流程状态只存内存（引擎重启流程全丢）；审批人规则硬编码（组织调整要改代码）；并行会签无汇总逻辑（有人同意就推进）；流程定义变更影响在途实例（需版本隔离）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class WorkflowEngine {
    enum NodeType {
        START, APPROVE, CONDITION, END
    }

    record Node(String id, NodeType type, String approver, String next) {
    }

    record Instance(String id, String currentNode, String status,
                    List<String> history, int version) {
    }

    static final Map<String, Node> definition = new LinkedHashMap<>();

    static void define() {
        definition.put("start", new Node("start", NodeType.START, null, "manager"));
        definition.put("manager", new Node("manager", NodeType.APPROVE, "直属主管", "finance"));
        definition.put("finance", new Node("finance", NodeType.APPROVE, "财务", "check"));
        definition.put("check", new Node("check", NodeType.CONDITION, null, "end"));
        definition.put("end", new Node("end", NodeType.END, null, null));
    }

    /** 推进一个节点：幂等（版本校验）+ 落库（历史追加） */
    static Instance approve(Instance inst, String action, int expectedVersion) {
        if (inst.version() != expectedVersion) {
            System.out.printf("  幂等拒绝：期望版本 %d，实际 %d（重复提交）%n",
                    expectedVersion, inst.version());
            return inst;
        }
        Node cur = definition.get(inst.currentNode());
        if (cur == null || cur.type() == NodeType.END) {
            System.out.println("  流程已结束");
            return inst;
        }
        List<String> history = new ArrayList<>(inst.history());
        if (!action.equals("APPROVE")) {
            history.add(cur.id() + ":REJECT -> 回退 start");
            return new Instance(inst.id(), "start", "RUNNING", history, inst.version() + 1);
        }
        history.add(cur.id() + ":APPROVE");
        String next = cur.next();
        Node nextNode = definition.get(next);
        String status = nextNode != null && nextNode.type() == NodeType.END ? "FINISHED" : "RUNNING";
        return new Instance(inst.id(), next, status, history, inst.version() + 1);
    }

    public static void main(String[] args) {
        define();
        System.out.println("【流程定义】");
        definition.values().forEach(n ->
                System.out.printf("  %-8s %-9s 审批人=%-8s -> %s%n",
                        n.id(), n.type(), n.approver() == null ? "-" : n.approver(), n.next()));

        System.out.println();
        System.out.println("【流程实例推进】");
        Instance inst = new Instance("AP-9001", "start", "RUNNING", new ArrayList<>(), 0);
        inst = approve(inst, "APPROVE", 0);
        System.out.printf("  当前节点=%s 版本=%d%n", inst.currentNode(), inst.version());
        inst = approve(inst, "APPROVE", 1);
        System.out.printf("  当前节点=%s 版本=%d%n", inst.currentNode(), inst.version());
        System.out.println("  重复提交（版本 1 已过期）：");
        approve(inst, "APPROVE", 1);
        inst = approve(inst, "APPROVE", 2);
        inst = approve(inst, "APPROVE", 3);
        System.out.printf("  最终状态=%s 历史=%s%n", inst.status(), inst.history());
    }
}
```

### 61-08 长流程的持久化与恢复

**知识点**
- **长流程的状态必须落库**：流程实例（当前节点/状态/版本）、历史轨迹（每个节点的动作与时间）、流程变量（表单数据/审批意见）——**三张表是工作流引擎的最小持久化模型**。
- **恢复语义**：引擎重启 -> 加载"运行中"的实例 -> 按当前节点继续等待或推进——**这要求"当前节点"是完整可达的状态**（不能只存"第几步"，要存"在哪个节点等谁"）。
- **状态与业务数据的一致性**：流程推进要同时改"流程实例状态"与"业务单据状态"（如审批通过 -> 单据变 APPROVED）——**两者必须同一事务**（39/49 章原则），否则出现"流程结束但单据未更新"。
- **定时扫表 vs 事件驱动**：等待中的流程（超时提醒/自动通过）靠**定时扫描**（61-06 的延迟队列思想）或**时间轮**推进——扫描频率决定超时精度。
- **历史轨迹的用途**：审计（谁在何时批了什么，51-10）、流程挖掘（哪一步最耗时）、申诉依据（44-09 证据链）——**轨迹不可修改**（append-only）。
- 易错点：流程状态与业务数据分两个事务（不一致）；历史轨迹可覆盖（审计失效）；恢复逻辑只认"当前节点"不认变量（表单数据丢失）；等待中的实例没有超时处理（流程永久挂起）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class WorkflowPersistence {
    record InstanceRow(String id, String node, String status, int version,
                       Map<String, String> variables) {
    }

    record HistoryRow(String instanceId, String node, String action, String operator,
                      long atMs) {
    }

    /** 模拟两张表 */
    static final Map<String, InstanceRow> instanceTable = new LinkedHashMap<>();
    static final List<HistoryRow> historyTable = new ArrayList<>();

    static void create(String id, Map<String, String> vars) {
        instanceTable.put(id, new InstanceRow(id, "manager", "RUNNING", 0, new LinkedHashMap<>(vars)));
        historyTable.add(new HistoryRow(id, "start", "SUBMIT", "alice", 1000));
        System.out.printf("  创建实例 %s，变量=%s%n", id, vars);
    }

    /** 推进 + 落库（模拟同一事务） */
    static void advance(String id, String action, String operator, long now) {
        InstanceRow row = instanceTable.get(id);
        if (row == null || !row.status().equals("RUNNING")) {
            System.out.println("  实例不存在或已结束：" + id);
            return;
        }
        historyTable.add(new HistoryRow(id, row.node(), action, operator, now));
        String next = action.equals("APPROVE") ? "finance" : "manager";
        String status = action.equals("APPROVE") && row.node().equals("finance")
                ? "FINISHED" : "RUNNING";
        instanceTable.put(id, new InstanceRow(id, next, status, row.version() + 1, row.variables()));
        System.out.printf("  %s：%s --%s--> %s（状态 %s，变量保留 %s）%n",
                id, row.node(), action, next, status, row.variables());
    }

    /** 重启恢复：从表里加载运行中实例 */
    static void recover() {
        System.out.println("【引擎重启恢复】");
        instanceTable.forEach((id, row) -> {
            if (row.status().equals("RUNNING")) {
                System.out.printf("  恢复实例 %s -> 当前节点 %s（变量 %s）%n",
                        id, row.node(), row.variables());
            }
        });
    }

    public static void main(String[] args) {
        Map<String, String> vars = new LinkedHashMap<>();
        vars.put("amount", "12000");
        vars.put("reason", "设备采购");
        create("AP-1", vars);
        advance("AP-1", "APPROVE", "manager-zhang", 2000);
        System.out.println();
        recover();
        System.out.println();
        advance("AP-1", "APPROVE", "finance-li", 3000);
        System.out.println();
```

### 61-09 调度可观测与积压治理

**知识点**
- **调度的四个核心观测指标**（42 章方法论在调度上的特化）：**成功率**（按任务维度，失败率超标告警）、**耗时分布**（P50/P99，慢任务识别）、**及时性**（实际开始时间 vs 计划时间，延迟告警）、**积压**（待执行任务数/失败任务数）。
- **告警的分级**：**失败告警**（任务失败，按任务重要性分 P1/P2）、**延迟告警**（超过 SLA 未完成，61-04）、**积压告警**（待执行/待重试队列长度，46-10 新鲜度）。
- **执行日志的结构化**（42-02 的应用）：每次执行记录 `jobId/bizDate/shard/状态/开始/结束/错误摘要/重试次数`——**日志平台按 jobId 检索整个执行历史**（46-03 时间线重建）。
- **积压治理**：积压原因分类（**产出不足**——执行器不够/分片太少；**消费过慢**——任务本身慢；**上游未就绪**——依赖等待）——**对症下药**：扩执行器、加并发分片、优化任务、查上游。
- **调度的成本视角**：任务数 × 频率 × 耗时 = 计算资源消耗——**高频小任务可以合并**（每小时跑 60 次不如每分钟一次）；**低价值任务下调度**（45 章容量与成本）。
- 易错点：只监控"任务是否跑"不监控"跑多久"（慢任务拖垮 SLA 无人知）；告警无分级（值班被次要任务淹没）；日志无 bizDate（无法按日期追溯）；积压只看总数不看原因（扩容解决不了上游问题）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class SchedulerObservability {
    record Run(String jobId, String bizDate, long startedAtMs, long costMs, boolean success) {
    }

    /** 指标汇总：成功率 / P50 / P99 / 及时性 */
    static void metrics(List<Run> runs, long scheduledAtMs, long slaMs) {
        long total = runs.size();
        long failed = runs.stream().filter(r -> !r.success()).count();
        List<Long> costs = new ArrayList<>(runs.stream().map(Run::costMs).sorted().toList());
        long p50 = costs.get(Math.min(costs.size() - 1, (int) (costs.size() * 0.5)));
        long p99 = costs.get(Math.min(costs.size() - 1, (int) (costs.size() * 0.99)));
        long lateStart = runs.stream()
                .filter(r -> r.startedAtMs() - scheduledAtMs > 60_000).count();
        long overSla = runs.stream().filter(r -> r.costMs() > slaMs).count();

        System.out.printf("  总执行=%d 失败=%d（成功率 %.1f%%）%n", total, failed,
                (total - failed) * 100.0 / total);
        System.out.printf("  耗时 P50=%dms P99=%dms%n", p50, p99);
        System.out.printf("  延迟启动（>60s）=%d 超 SLA（>%dms）=%d%n", lateStart, slaMs, overSla);
    }

    /** 积压原因分类 */
    static String diagnose(int pending, int failed, boolean upstreamReady,
                           int executorCount, long avgCostMs) {
        if (!upstreamReady) {
            return "上游未就绪 -> 查依赖任务（61-04），扩容无用";
        }
        if (failed > pending / 2) {
            return "失败重试堆积 -> 先查失败根因（61-06），不是容量问题";
        }
        if (pending > executorCount * 10) {
            return "执行器不足 -> 扩容执行器或增加分片（61-03）";
        }
        if (avgCostMs > 300_000) {
            return "任务本身过慢 -> 优化任务（59 章调优），扩容治标";
        }
        return "正常";
    }

    public static void main(String[] args) {
        System.out.println("【指标汇总：closeOrderJob 近 20 次执行】");
        List<Run> runs = new ArrayList<>();
        for (int i = 0; i < 20; i++) {
            runs.add(new Run("closeOrderJob", "2026-11-" + (10 + i),
                    10_000L * i + (i == 12 ? 120_000 : 5_000),
                    8_000 + i * 500L, i != 7));
        }
        metrics(runs, 0, 30_000);

        System.out.println();
        System.out.println("【积压诊断】");
        Map<String, String> cases = new LinkedHashMap<>();
        cases.put("上游未就绪", diagnose(50, 5, false, 4, 20_000));
        cases.put("失败堆积", diagnose(50, 40, true, 4, 20_000));
        cases.put("执行器不足", diagnose(200, 5, true, 4, 20_000));
        cases.put("任务过慢", diagnose(30, 2, true, 10, 400_000));
        cases.forEach((k, v) -> System.out.printf("  %-8s -> %s%n", k, v));
    }
}
```

### 61-10 调度与消息队列、批处理的边界

**知识点**
- **三种"异步执行"机制的定位**：**MQ**（事件流、毫秒级、无时刻语义）、**调度**（有执行时刻与执行记录、批处理单元）、**批处理框架**（Spark/Flink 作业，跑一次处理海量数据，59 章）——**调度是"触发器"，批处理是"执行器"，MQ 是"事件通道"**，三者常组合（调度触发 Spark 作业、作业结果发 MQ）。
- **常见误用与纠正**：**用 MQ 做定时任务**（消息延迟投递精度差、无重跑能力 28-02）；**用调度做实时事件**（最小粒度秒级，且每次触发都有调度开销）；**用调度跑短小高频任务**（每小时 60 次不如一次批量）。
- **"调度 + MQ"的标准组合**：调度触发 -> 生产任务消息 -> MQ 削峰 -> 多消费者并行处理（43 章）——**适合"一次性要处理百万条数据"**（调度负责"何时跑"，MQ 负责"怎么并行"）。
- **批处理的容错分工**：调度负责"触发与重试"（61-06），批处理框架负责"分片内计算的血统容错"（59-06），**两者都要幂等**（59-10 分区覆盖）。
- **数据链路上的选择**：CDC 实时同步（43-09）vs 调度批量拉取（46-09）——**时效要求决定选择**（分钟级要 CDC，T+1 用批量），**两者可并存**（实时主链路 + 每日全量对账）。
- 易错点：实时链路和批链路同一份数据双写无对账（43-01 Lambda 的债）；调度触发的高频小任务压垮执行器；用 MQ 延迟消息替代调度（精度与可观测都差）。

### 61-11 综合案例：订单超时关闭调度平台

**知识点**
- **把本章收口成一个真实场景**：订单超时关闭——**触发方式**（时间轮/延迟队列 28-02 vs 定时扫描）、**分片执行**（61-03：按订单 id 分片扫）、**幂等**（61-05：已关闭/已支付的订单跳过，51-03 状态机裁决）、**重试**（61-06：DB 超时可重试，数据异常不重试）、**可观测**（61-09：每次关闭多少单/失败多少/耗时）。
- **核心矛盾是"扫全表还是查索引"**：超时未支付订单的查询必须有索引（`(status, created_at)` 39-02），否则每次扫描全表（千万级订单扫不动）；**任务频率与单次扫描量要平衡**（每分钟扫 1 分钟窗口的订单）。
- **与支付回调的竞态**（51-03 的经典场景）：扫描关单与支付回调同时到达——**状态机只进不退**（已支付则关单失败，进差异单；已关闭则回调触发退款）。
- **分片与扩容**：订单量增长 -> 分片数增加（不是执行器数），**每片处理时间窗内的订单**——这样扩容后两片不会抢同一批订单（用 `id % totalShards` 严格划分）。
- **验收标准**：超时订单关闭时延 < 2 分钟、无重复关闭、无误关已支付订单、失败可重跑、指标可看。
- 易错点：全表扫描（无索引）；关单不校验支付状态（误关已支付订单）；分片按执行器数（扩容后重复处理）；无指标（不知道关了多少/失败多少）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class CloseOrderJob {
    record Order(long id, String status, long createdAtMs, long paidAtMs) {
        boolean timeout(long now, long timeoutMs) {
            return status.equals("WAITING_PAY") && now - createdAtMs > timeoutMs;
        }
    }

    /** 分片扫描 + 状态机裁决（只进不退） */
    static void runShard(List<Order> orders, int shard, int totalShards,
                         long now, long timeoutMs) {
        int scanned = 0, closed = 0, skipped = 0;
        for (Order o : orders) {
            if (o.id() % totalShards != shard) {
                continue;                                  // 严格按 id 分片，扩容不重叠
            }
            scanned++;
            if (!o.timeout(now, timeoutMs)) {
                continue;
            }
            if (o.paidAtMs() > 0) {
                skipped++;
                System.out.printf("    订单%d 已支付（%d）-> 跳过关单（状态机裁决）%n",
                        o.id(), o.paidAtMs());
                continue;
            }
            closed++;
        }
        System.out.printf("  分片%d：扫描=%d 关闭=%d 跳过=%d%n", shard, scanned, closed, skipped);
    }

    public static void main(String[] args) {
        long now = 1_000_000;
        long timeout = 15 * 60_000L;
        List<Order> orders = new ArrayList<>();
        for (int i = 0; i < 20; i++) {
            String status = i % 4 == 0 ? "PAID" : "WAITING_PAY";
            long createdAt = now - (i < 12 ? 20 * 60_000L : 5 * 60_000L);
            long paidAt = status.equals("PAID") ? now - 60_000 : 0;
            orders.add(new Order(i, status, createdAt, paidAt));
        }
        System.out.println("【订单超时关闭：4 分片执行】");
        for (int shard = 0; shard < 4; shard++) {
            runShard(orders, shard, 4, now, timeout);
        }
        System.out.println();
        System.out.println("【关键设计】");
        Map<String, String> design = new LinkedHashMap<>();
        design.put("索引", "(status, created_at) —— 否则千万订单全表扫（39-02）");
        design.put("分片", "id % 总片数 —— 扩片不重叠、扩执行器不重复");
        design.put("幂等", "已支付/已关闭跳过 —— 与支付回调竞态由状态机裁决（51-03）");
        design.put("频率", "每分钟扫 1 分钟窗口 —— 时延 < 2 分钟且单次量可控");
        design.put("观测", "每片扫描/关闭/跳过数 + 失败告警（61-09）");
        design.forEach((k, v) -> System.out.printf("  %-4s %s%n", k, v));
    }
}
```
