### 实操 46-01 快照链提交与时间旅行

**知识点注释**
- 【题目要求】实现迷你 Iceberg：快照对象（id/父指针/文件清单）、原子提交（CAS 替换当前指针，并发提交冲突时基于最新快照重试）、时间旅行（按快照 id 读历史清单）、回滚（指针回退）；场景：三次追加 + 一次并发冲突重试 + 一次回滚，输出每次提交后的快照链与各快照的文件清单。
- 【考核点】元数据清单即原子提交、乐观并发与冲突检测、时间旅行与回滚、快照指针语义。
- 【易错点】并发提交直接覆盖（丢失 A 或 B 的文件）；回滚删除快照（历史丢失，回滚只移指针）；快照无清理策略（存储膨胀）。
- 【提示】当前指针用 volatile long + CAS 语义（synchronized 简化亦可，说明真实实现是对象存储单对象原子替换）。

**示例代码**（技术示范：原子指针，另一套场景）
```java
public class CasPointerDemo {
    static long current = 0;

    static synchronized boolean cas(long expect, long update) {
        if (current != expect) {
            return false;
        }
        current = update;
        return true;
    }

    public static void main(String[] args) {
        long base = current;
        boolean a = cas(base, base + 1);      // A 先提交成功
        boolean b = cas(base, base + 1);      // B 基于旧快照 -> 失败重试
        System.out.printf("  A 提交=%b  B 提交=%b  当前=%d%n", a, b, current);
        System.out.println("  B 应基于最新快照重算后重新 CAS —— 乐观并发语义");
    }
}
```

**课后练习题**
1. 实现完整迷你 Iceberg（快照链 + 并发重试 + 时间旅行 + 回滚），输出快照链可视化与每个快照的文件清单。
2. 加入“快照过期”：保留最近 5 个快照，验证过期后时间旅行到更早版本的报错与提示。
3. 思考题：为什么回滚“只移指针”秒级完成而传统备份恢复要小时级？从元数据与数据分离的角度分析。

### 实操 46-02 Row Group 谓词裁剪

**知识点注释**
- 【题目要求】模拟 Parquet Row Group：每组带（date min/max、amount min/max、行数、字节数）；实现“按日期 + 金额范围”查询的裁剪引擎，输出每个 Row Group 的读取/跳过决策与 IO 节省率；再对比“无统计信息”时的全扫代价。
- 【考核点】统计信息与谓词下推、Row Group 裁剪、多条件裁剪（AND 交集）、IO 节省量化。
- 【易错点】多条件只按一个条件裁剪（应取交集）；把“可能包含”当“一定包含”（保守读是对的，激进跳过是错的）；忽略统计过期问题。
- 【提示】裁剪判定：区间 [min,max] 与查询区间相交才读——宁可多读不可漏读。

**示例代码**（技术示范：区间相交，另一套场景）
```java
public class RangePruneDemo {
    record Group(int id, int min, int max, int bytes) {
    }

    static boolean mayMatch(Group g, int qMin, int qMax) {
        return g.min <= qMax && g.max >= qMin;    // 区间相交判定
    }

    public static void main(String[] args) {
        Group[] groups = {new Group(1, 0, 100, 128), new Group(2, 200, 300, 128)};
        int qMin = 150, qMax = 250;
        for (Group g : groups) {
            System.out.printf("  RG%d [%d,%d] -> %s%n", g.id(), g.min(), g.max(),
                    mayMatch(g, qMin, qMax) ? "读取" : "跳过");
        }
    }
}
```

**课后练习题**
1. 实现完整裁剪引擎：8 个 Row Group + 日期/金额双条件，输出决策表与 IO 节省率。
2. 注入“统计信息过期”（实际数据超出 min/max），观察漏读风险，说明统计维护的必要性。
3. 思考题：为什么裁剪判定必须保守（相交即读）？从正确性优先与漏读后果的角度分析。

### 实操 47-01 金丝雀权重路由器

**知识点注释**
- 【题目要求】实现 Mesh 风格切流器：子集定义（v1/v2 由 label 划分）、两种匹配（header 定向 + 权重随机）、会话粘性（同一 userId 恒路由同版本）；输入 1000 个请求（含 100 个内部 header 请求），输出两版本的请求分布、每版本错误率模拟与粘性验证（同 userId 版本一致率 100%）。
- 【考核点】权重切流、header 定向、会话粘性实现（一致性哈希或映射表）、版本维度指标。
- 【易错点】权重随机导致同用户跳版本（无粘性）；粘性映射无清理（内存泄漏）；错误率混算（不分版本归因错误）。
- 【提示】粘性用 userId -> version 映射表 + TTL；header 请求优先级高于粘性与权重。

**示例代码**（技术示范：粘性映射，另一套场景）
```java
import java.util.HashMap;
import java.util.Map;

public class StickyDemo {
    static final Map<String, String> sticky = new HashMap<>();

    static String route(String userId, String defaultVersion) {
        return sticky.computeIfAbsent(userId, k -> defaultVersion);
    }

    public static void main(String[] args) {
        for (int i = 0; i < 3; i++) {
            System.out.println("  u1 第" + (i + 1) + " 次请求 -> " + route("u1", "v2"));
        }
        System.out.println("  同用户恒定同版本 —— 灰度体验一致性的最低要求");
    }
}
```

**课后练习题**
1. 实现完整切流器：header 定向 + 权重 + 粘性 + TTL，用 1000 请求验证分布与粘性率，输出版本维度错误率。
2. 实现“粘性副本过载降级”：粘性目标水位 >90% 时放弃亲和换副本（44/48 章思想的对照实现）。
3. 思考题：为什么灰度必须带会话粘性？构造“同用户在两版本间跳变”导致的数据不一致用例。

### 实操 47-02 故障注入实验设计器

**知识点注释**
- 【题目要求】实现混沌实验的四步法框架：稳态假设（指标基线与判定）、实验假设、注入动作（延迟/错误/资源，带比例与时长）、中止条件（一键停止 + 自动中止阈值）；运行器按分钟推进模拟指标流，验证假设成立或捕获缺陷，输出实验报告（时间线/观察值/结论/改进项）。
- 【考核点】稳态假设、假设先行、爆炸半径控制、中止条件、实验报告闭环。
- 【易错点】无稳态基线（出事不知道是否注入导致）；自动中止缺失（故障放大无人拦）；实验后无改进项（白炸）。
- 【提示】把“中止条件”做成硬编码守护：成功率跌破阈值立即回收注入——先保生产再谈实验。

**示例代码**（技术示范：自动中止，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;

public class AutoAbortDemo {
    public static void main(String[] args) {
        List<Double> successRates = List.of(0.995, 0.993, 0.985, 0.972, 0.951);
        double threshold = 0.97;
        for (int min = 0; min < successRates.size(); min++) {
            double r = successRates.get(min);
            System.out.printf("  min%d 成功率 %.1f%%%n", min, r * 100);
            if (r < threshold) {
                System.out.printf("  触发自动中止（阈值 %.0f%%），回收注入%n", threshold * 100);
                break;
            }
        }
    }
}
```

**课后练习题**
1. 实现完整实验框架：稳态定义 + 注入动作枚举 + 自动中止 + 报告生成，跑通“依赖延迟注入”实验全流程。
2. 构造“稳态假设错误”的实验（基线取自故障期数据），观察误判，总结基线选取纪律。
3. 思考题：为什么混沌实验“假设先行”而不是“先注入再看”？从实验可解释性与改进项闭环的角度分析。

### 实操 48-02 批调度空转统计器

**知识点注释**
- 【题目要求】对比 static 与 continuous batching：给定一批请求（输出长度 40~380 随机），static 按批（4 个/批）同步推进——批内最长决定整批结束；continuous 每步动态进出——完成的槽位立即补新请求；统计两种模式的“总完成步数、空转步数（GPU 白跑）、总耗时”，输出对比报告。
- 【考核点】批内最长决定整批（static 浪费）、动态进出（continuous 满负荷）、空转步数作为浪费度量。
- 【易错点】空转定义错误（static 中“已完成请求的等待步”才是空转）；continuous 实现成“整批滚动”（仍是静态）；忽略输出长度方差对结论的影响。
- 【提示】逐步模拟：每步所有在途请求各生成 1 token；static 批内全部完成才进下一批。

**示例代码**（技术示范：逐步模拟，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;

public class StepSimDemo {
    public static void main(String[] args) {
        List<Integer> batch = new ArrayList<>(List.of(40, 380, 120, 50));
        int step = 0;
        while (!batch.isEmpty()) {
            step++;
            batch.replaceAll(remaining -> remaining - 1);
            batch.removeIf(r -> r <= 0);
        }
        System.out.printf("  static：批内最长 %d token 决定总步数 %d%n", 380, step);
        System.out.println("  短请求的等待步 = 空转（continuous 会即时补位）");
    }
}
```

**课后练习题**
1. 实现两种调度器的完整模拟（200 个随机长度请求），输出空转步数与总耗时对比报告。
2. 修改输出长度分布（方差变小），观察 static 浪费的收窄，解释“方差决定 static 的浪费”。
3. 思考题：为什么 continuous batching 能让 GPU 接近满负荷？从“每步动态进出”与“decode 访存密集”两个特性推导。

### 实操 49-01 聚合不变量守护

**知识点注释**
- 【题目要求】实现订单聚合（Order + OrderLine + Money 值对象）与四条不变量：明细和 ≥0、提交后金额不可变、同 SKU 唯一、可退额 = 实付 - 已退；写并发测试：1000 个线程并发申请退款（部分超额），验证不变量永不破坏（超退全部被拒、成功退款总额 = 实付上限）。
- 【考核点】聚合边界与不变量闭环、值对象不可变、并发下的聚合一致性（乐观锁/同步）、充血模型测试。
- 【易错点】不变量写在服务层（绕过聚合直接改字段）；并发退款无同步（超退发生）；Money 可变（金额被意外修改）。
- 【提示】聚合内用 synchronized（或版本号 CAS）守护多字段一致性；测试断言“拒绝总数 + 成功总额”恒等。

**示例代码**（技术示范：并发守卫，另一套场景）
```java
public class InvariantGuardDemo {
    static long balance = 10_000;      // 分
    static final long MIN = 0;

    static synchronized boolean withdraw(long amount) {
        if (balance - amount < MIN) {
            return false;               // 不变量：余额永不低于 0
        }
        balance -= amount;
        return true;
    }

    public static void main(String[] args) throws Exception {
        Thread[] ts = new Thread[8];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> withdraw(2000));
            ts[i].start();
        }
        for (Thread t : ts) {
            t.join();
        }
        System.out.printf("  并发扣款后余额 = %d 分（不变量保持：>= 0）%n", balance);
    }
}
```

**课后练习题**
1. 实现订单聚合完整版（四不变量 + 并发退款测试），输出“拒绝次数/成功总额/剩余可退”的对账恒等式。

### 实操 49-02 Outbox 投递与幂等消费

**知识点注释**
- 【题目要求】实现 outbox 全闭环：业务事务内写 outbox（事件 ID/聚合 ID/类型/payload）-> 后台投递器（指数退避，失败重试）-> 消费者（按事件 ID 幂等：去重表 + 首次处理返回值缓存）-> 死信（N 次失败进死信并告警）。场景：3 个事件（1 正常/1 消费两次失败后成功/1 永远失败进死信），输出全轨迹与状态机（PENDING/SENT/DEAD）。
- 【考核点】outbox 与业务同事务语义、投递退避、消费幂等、死信与告警、事件状态机。
- 【易错点】投递失败删事件（丢失）；消费幂等用时间戳（重放窗口内仍重复）；死信无告警（静默丢事件）。
- 【提示】消费者“首次处理返回值缓存”很重要：重复事件应返回首次结果（接口语义幂等）。

**示例代码**（技术示范：状态机，另一套场景）
```java
public class OutboxStateDemo {
    enum State {
        PENDING, SENT, DEAD
    }

    static String advance(State s, boolean deliverOk, int retry) {
        if (s == State.PENDING) {
            return deliverOk ? State.SENT.name()
                    : (retry >= 5 ? State.DEAD.name() : State.PENDING.name());
        }
        return s.name();
    }

    public static void main(String[] args) {
        State s = State.PENDING;
        for (int retry = 1; retry <= 6; retry++) {
            s = State.valueOf(advance(s, false, retry));
            System.out.printf("  投递#%d 失败 -> 状态 %s%n", retry, s);
        }
        System.out.println("  进入 DEAD -> 告警 + 人工介入（事件不静默丢失）");
    }
}
```

**课后练习题**
1. 实现 outbox 完整闭环（同事务写入、退避投递、幂等消费、死信告警），用三个事件跑出全轨迹。
2. 实现“按聚合 ID 分区保序”（39-08 思想），构造同聚合乱序事件验证版本号幂等兜底。
3. 思考题：为什么 outbox 必须与业务表同事务？构造“业务提交但事件丢失”的反例并推演下游后果。
