### 实操 42-01 Histogram 分位数计算器

**知识点注释**
- 【题目要求】实现 Histogram：桶边界 {10,50,100,250,500,1000,2500}（毫秒）+ 累计计数；支持三件事——① 记录样本落桶；② 跨实例聚合（桶计数相加后再算分位数）；③ 输出 P50/P90/P99 与“两实例先聚合再算分位 vs 各自算分位再平均”的对比。
- 【考核点】分桶与累计计数、分位数插值逻辑、可合并性（Histogram 可聚合而 Summary 不可）、分桶粒度对精度的影响。
- 【易错点】桶计数用“区间数”而非“累计数”（分位数计算要用 cumulative）；桶边界开闭混乱；P99 直接取上界导致精度误差未声明。
- 【提示】分位数 = 找到累计数首次超过 target 的桶，桶宽内可线性插值（声明近似即可）。

**示例代码**（技术示范：累计计数，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;

public class CumulativeDemo {
    static double quantile(int[] cumulative, double[] upper, double q) {
        long total = cumulative[cumulative.length - 1];
        double target = q * total;
        for (int i = 0; i < cumulative.length; i++) {
            if (cumulative[i] >= target) {
                return upper[i];
            }
        }
        return upper[upper.length - 1];
    }

    public static void main(String[] args) {
        int[] cumulative = {50, 80, 95, 100};
        double[] upper = {50, 100, 200, 400};
        List<String> qs = List.of("P50", "P90", "P99");
        double[] q = {0.5, 0.9, 0.99};
        for (int i = 0; i < qs.size(); i++) {
            System.out.printf("  %s ≈ %.0fms%n", qs.get(i), quantile(cumulative, upper, q[i]));
        }
    }
}
```

**课后练习题**
1. 实现完整 Histogram：三实例样本合并算 P50/P90/P99，对比“先聚合再算”与“各自算再平均”的误差。
2. 调整桶边界（加粗 0~500 两桶），量化分桶粒度对 P99 精度的影响。
3. 思考题：为什么 Summary 无法跨实例聚合？从分位数计算需要原始分布的角度分析。

### 实操 42-02 告警聚合与抑制器

**知识点注释**
- 【题目要求】实现告警聚合器：输入带时间戳的告警流（服务/类型/严重度），按“根因服务 + 5 分钟窗口”聚合成事件；依赖抑制规则（DB 挂时抑制下游服务的连接错误告警）；输出事件列表（含被抑制的成员清单）与降噪统计（原始条数 vs 事件数）。
- 【考核点】窗口聚合、根因识别（依赖方向）、抑制链、降噪度量。
- 【易错点】抑制方向搞反（根因被下游告警抑制）；窗口边界归属（跨窗口事件拆分规则未定义）；聚合后丢失明细（排障需要成员清单）。
- 【提示】依赖方向表（db -> order/stock/pay）显式声明；被抑制的告警保留在事件成员里。

**示例代码**（技术示范：依赖抑制，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;
import java.util.Map;

public class SuppressDemo {
    record Alert(String service, String msg) {
    }

    static final Map<String, List<String>> DEPENDS = Map.of(
            "db", List.of("order", "stock", "pay"));

    public static void main(String[] args) {
        List<Alert> alerts = List.of(
                new Alert("db", "主库连接拒绝"),
                new Alert("order", "DB 连接超时"),
                new Alert("stock", "DB 连接超时"),
                new Alert("pay", "DB 连接超时"));
        List<Alert> rootCauses = new ArrayList<>();
        List<String> suppressed = new ArrayList<>();
        for (Alert a : alerts) {
            if (DEPENDS.containsKey(a.service())) {
                rootCauses.add(a);
            } else {
                boolean covered = rootCauses.stream()
                        .anyMatch(rc -> DEPENDS.getOrDefault(rc.service(), List.of())
                                .contains(a.service()));
                if (covered) {
                    suppressed.add(a.service());
                } else {
                    rootCauses.add(a);
                }
            }
        }
        System.out.println("  根因事件：" + rootCauses);
        System.out.println("  抑制成员：" + suppressed);
    }
}
```

**课后练习题**
1. 实现完整聚合器：5 分钟窗口 + 依赖方向表 + 成员清单保留，用 20 条模拟告警验证降噪比。
2. 构造“两个独立故障同时发生”的场景，验证聚合器不会错误合并（按服务依赖图分区）。
3. 思考题：为什么“抑制”必须基于显式的依赖方向表？用错误抑制方向的后果说明。

### 实操 43-01 三窗口聚合器

**知识点注释**
- 【题目要求】对同一事件流实现三种窗口：滚动（60s）、滑动（120s/60s）、会话（gap=20s）；输出各窗口的聚合结果与“事件归属矩阵”（每个事件落在哪些窗口）；滑动窗口结果标注“不可跨窗口累加”的消费契约。
- 【考核点】三种窗口语义、事件归属（滑动窗口多归属）、会话动态合并、窗口结果元数据。
- 【易错点】滑动窗口把结果累加求和（重复计入）；会话 gap 用“固定时长”理解；窗口边界闭开区间混乱。
- 【提示】事件归属矩阵是理解三种窗口差异的最好工具——先算矩阵再聚合。

**示例代码**（技术示范：归属矩阵，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;

public class BelongMatrixDemo {
    public static void main(String[] args) {
        int[] events = {5, 35, 65, 95, 125};
        int size = 60, slide = 60;
        System.out.println("  事件\\窗口  [0,60) [60,120) [120,180)");
        for (int e : events) {
            StringBuilder row = new StringBuilder();
            for (int w = 0; w + size <= 180; w += slide) {
                boolean belong = e >= w && e < w + size;
                row.append(belong ? "   ✓  " : "   ·  ");
            }
            System.out.printf("  事件%3d    %s%n", e, row);
        }
        System.out.println("  滚动窗口每事件只属一行；滑动窗口会多归属");
    }
}
```

**课后练习题**
1. 实现三种窗口完整聚合器（GMV/笔数），输出归属矩阵与各窗口结果，验证滑动窗口“重复计入”。
2. 调整会话 gap（10/20/40s），观察会话数变化，给出“gap 选择”的业务建议。
3. 思考题：为什么滑动窗口结果不能下游累加？结合归属矩阵的重复计数推导错误累加的后果。

### 实操 43-02 水位线与迟到旁路

**知识点注释**
- 【题目要求】实现水位线机制：事件流（事件时间 + 到达顺序，乱序 ≤15s）-> 全局 WM = max(事件时间) - 容忍度；窗口（60s）在 WM 越过终点+允许迟到（5s）时触发；迟到数据分两路——窗口未关则更新结果、已关则写入旁路计数；用不同容忍度（0/5/10s）跑同一数据流，输出“正确归属率 vs 结果延迟”交换表。
- 【考核点】水位线生成与推进、窗口触发时机、允许迟到两段式、旁路统计、容忍度交换曲线。
- 【易错点】WM 用当前墙钟（应来自事件时间）；容忍度 0 时大量迟到被丢且无旁路统计；空闲源拖住 WM 未处理。
- 【提示】旁路计数器本身是监控指标——突然升高说明上游时钟或网络异常。

**示例代码**（技术示范：容忍度交换，另一套场景）
```java
public class ToleranceSwapDemo {
    static void trade(int toleranceSec, int disorderMax) {
        int correct = Math.min(disorderMax, toleranceSec);
        int delay = toleranceSec;
        System.out.printf("  容忍%ds：正确归属 ≤%ds（覆盖 %.0f%% 乱序），结果延迟 +%ds%n",
                toleranceSec, correct, correct * 100.0 / disorderMax, delay);
    }

    public static void main(String[] args) {
        for (int t : new int[]{0, 5, 10, 15}) {
            trade(t, 15);
        }
        System.out.println("  交换曲线：容忍度↑ -> 归属率↑、延迟↑ —— 无免费午餐");
    }
}
```

**课后练习题**
1. 实现完整水位线机制（含旁路计数与空闲源标记），用 100 条乱序流跑三种容忍度输出交换表。
2. 注入“空闲分区”场景，观察 WM 卡住与窗口不触发，实现 idle 标记修复。
3. 思考题：为什么水位线是“赌乱序有界”？列出三种赌输的情形与各自的工程兜底。

### 实操 44-01 ReAct 循环执行器

**知识点注释**
- 【题目要求】实现 ReAct 循环执行器：工具注册表（查库存/计算/校验预算，模拟实现）、循环控制器（Thought->Action->Observation，最大 8 轮）、护栏（同一 Action+参数连续 2 次终止、工具错误返回结构化信息、偏离原计划重规划提示）；用“爆款补货”任务跑出完整轨迹。
- 【考核点】循环终止条件、重复检测、错误作为信息（结构化回传）、轨迹可审计。
- 【易错点】无最大轮数（死循环）；Observation 塞大 JSON（上下文爆炸）；Thought 不落轨迹（不可审计）。
- 【提示】轨迹是 Agent 的行车记录仪：每轮 (thought, action, args, result, tokens) 全量落表。

**示例代码**（技术示范：循环护栏，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;

public class LoopGuardDemo {
    static void run(List<String> actions) {
        String last = null;
        int repeat = 0;
        for (int i = 0; i < actions.size(); i++) {
            String a = actions.get(i);
            if (a.equals(last)) {
                repeat++;
            } else {
                repeat = 0;
            }
            last = a;
            if (repeat >= 2) {
                System.out.printf("  轮%d 动作 %s 连续重复 -> 强制终止%n", i + 1, a);
                return;
            }
            System.out.printf("  轮%d 执行 %s%n", i + 1, a);
        }
        System.out.println("  正常完成");
    }

    public static void main(String[] args) {
        run(List.of("query", "query", "query", "calc"));
    }
}
```

**课后练习题**
1. 实现完整 ReAct 执行器：注册 3 个模拟工具 + 四道护栏，用补货任务跑通正常轨迹与“工具反复失败”轨迹。
2. 给循环加检查点：第 N 轮崩溃后从检查点恢复，验证已完成步骤不重做。
3. 思考题：为什么 Observation 必须精炼而 Thought 可以全量保留？从上下文成本与审计价值两个维度分析。

### 实操 45-01 Raft 选举模拟器

**知识点注释**
- 【题目要求】实现三节点 Raft 选举模拟（单线程事件驱动即可）：随机选举超时（150~300ms 模拟刻度）、投票约束（一任期一票 + 日志不落后）、心跳抑制换届；输出 1000 轮模拟的选举耗时分布（min/avg/max）与选票分裂次数。
- 【考核点】任期单调性、投票安全约束、随机超时化解分裂、选举健康度统计。
- 【易错点】超时不随机（同步分裂死循环）；投完票仍接受旧 term 消息；节点日志 term 比较方向颠倒。
- 【提示】用整数“刻度”代替真实时间：每个刻度检查超时与消息队列——事件驱动模拟足够验证协议行为。

**示例代码**（技术示范：随机超时，另一套场景）
```java
import java.util.Random;

public class RandomTimeoutDemo {
    public static void main(String[] args) {
        Random r = new Random(42);
        int splits = 0;
        for (int round = 0; round < 1000; round++) {
            int a = 150 + r.nextInt(150);
            int b = 150 + r.nextInt(150);
            if (a == b) {
                splits++;
            }
        }
        System.out.printf("  1000 轮中同时发起（会分裂）：%d 次，其余随机错开自然化解%n", splits);
    }
}
```

**课后练习题**
1. 实现完整选举模拟器：1000 轮耗时分布 + 分裂统计 + 拒票原因分布，验证随机超时的化解能力。
2. 注入“固定超时”对照组，观察持续分裂，量化随机抖动的价值。
3. 思考题：为什么“日志不落后才可投”是安全的？构造违反约束导致已提交数据丢失的时序。

### 实操 45-02 Fencing Token 存储

**知识点注释**
- 【题目要求】实现租约锁 + fencing 存储：锁服务（TTL 租约、续约、过期自动失效、fencing 单调递增发号）+ 下游存储（只接受编号更大的写入）；场景脚本：A 拿锁 -> GC 停顿（时间推进）-> 锁转 B -> B 写入 -> A 醒来写入被拒；输出完整时间线与每笔写入的接受/拒绝日志。
- 【考核点】租约 TTL 与续约、fencing 单调编号、过期写入拦截、GC 停顿事故链。
- 【易错点】fencing 编号重置（服务重启后从 1 开始，旧请求反而被接受）；续约失败仍继续业务；拒绝时不留审计记录。
- 【提示】fencing 编号必须持久化（服务重启不回退）；拒绝的写入要记录（谁、编号、时间）供审计。

**示例代码**（技术示范：单调编号，另一套场景）
```java
public class MonotonicGateDemo {
    static long maxSeq = 0;

    static boolean accept(long seq, String who) {
        if (seq <= maxSeq) {
            System.out.printf("  拒绝 %s seq=%d（当前最大 %d）%n", who, seq, maxSeq);
            return false;
        }
        maxSeq = seq;
        System.out.printf("  接受 %s seq=%d%n", who, seq);
        return true;
    }

    public static void main(String[] args) {
        accept(3, "B");
        accept(2, "A（旧持锁者）");
        accept(5, "C");
    }
}
```

**课后练习题**
1. 实现完整租约锁 + fencing 存储（含持久化编号与拒绝审计），重演 GC 事故链并输出时间线。
2. 构造“锁服务重启编号回退”的反例，说明为什么编号必须持久化，并给出修复。
3. 思考题：为什么 Redis 锁比 ZK 锁更需要 fencing？从主从复制异步性与锁丢失场景分析。
