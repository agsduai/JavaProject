### 实操 30-01 内存泄漏定位实验

**知识点注释**
- 【题目要求】构造三版内存泄漏实验（-Xmx128m 运行）：① 静态 Map 无限累积（最常见）；② ThreadLocal 未 remove 的线程池泄漏；③ 监听器注册未注销；每版输出"堆占用曲线要点 + jmap 定位思路（Histogram 找最大类）+ 修复方案"，并验证修复后可长时间稳定运行。
- 【考核点】泄漏的三种经典形态、堆直方图定位（30 章 jmap）、修复方案（弱引用/移除/上限）、证据链方法。
- 【易错点】把内存涨当泄漏（无上限的增长 ≠ 泄漏，需区分"持续增长不回收"）；修复用 System.gc 掩盖；ThreadLocal 泄漏只怪线程池不怪代码。
- 【提示】泄漏判定标准：Full GC 后存活堆持续抬升（呈台阶状）——用 Runtime.totalMemory/freeMemory 采样模拟曲线。

**示例代码**（技术示范：增长采样，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;

public class LeakCurveDemo {
    public static void main(String[] args) {
        List<byte[]> hold = new ArrayList<>();
        for (int round = 1; round <= 5; round++) {
            hold.add(new byte[1024 * 1024]);        // 每轮 1MB，持有不释放
            long used = Runtime.getRuntime().totalMemory()
                    - Runtime.getRuntime().freeMemory();
            System.out.printf("  轮%d 存活堆 ≈ %dMB（台阶式抬升 = 泄漏特征）%n", round, used / 1024 / 1024);
        }
    }
}
```

### 实操 30-02 GC 日志解析器

**知识点注释**
- 【题目要求】实现 GC 日志解析器：输入典型 GC 日志行（自造格式：`[gc] type=MinorPause cause=AllocationFailure young_before=120M young_after=40M duration=15ms`），解析成结构化记录；统计：Minor/Major 频次、平均暂停、晋升速率（young_after 变化推算）；按"暂停时间预算"判定健康（P99 暂停 >50ms 告警）；输出健康报告。
- 【考核点】GC 日志字段语义、暂停时间与吞吐的权衡、晋升速率与老年代压力、日志解析的正则应用。
- 【易错点】只统计次数不看暂停分布；忽略 Full GC cause（System.gc vs 容量不足）；单位换算错误（M/K/B）。
- 【提示】解析器输出结构化列表后，用 42 章分位数方法统计暂停 P50/P99。

**示例代码**（技术示范：日志解析，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class LogParseDemo {
    public static void main(String[] args) {
        Pattern p = Pattern.compile("type=(\\w+).*?duration=(\\d+)ms");
        List<String> logs = List.of(
                "[gc] type=Minor cause=AllocationFailure duration=12ms",
                "[gc] type=Full cause=System.gc duration=180ms",
                "[gc] type=Minor cause=Promotion duration=18ms");
        long total = 0, full = 0;
        for (String line : logs) {
            Matcher m = p.matcher(line);
            if (m.find()) {
                long d = Long.parseLong(m.group(2));
                total += d;
                if (m.group(1).equals("Full")) {
                    full++;
                }
                System.out.printf("  %s 暂停 %dms%n", m.group(1), d);
            }
        }
        System.out.printf("  总暂停 %dms，Full 次数 %d（System.gc 应排查调用方）%n", total, full);
    }
}
```

**课后练习题**
1. 实现完整解析器（结构化 + 频次 + 暂停分位 + 晋升速率），对 50 行模拟日志输出健康报告。
2. 加入"cause 分类统计"（AllocationFailure/System.gc/Promotion），找出 Top 根因。
3. 思考题：为什么 Full GC cause=System.gc 要单独告警？从 RMI/堆外内存触发的隐式调用与容量不足的排查路径差异分析。

**示例代码**（技术示范：分支字典，另一套场景）
```java
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.function.Function;

public class BranchDictDemo {
    static final Map<String, java.util.function.UnaryOperator<Integer>> RULES = new LinkedHashMap<>();

    static {
        RULES.put("vip", x -> x * 90 / 100);
        RULES.put("svip", x -> x * 80 / 100);
        RULES.put("new", x -> x - 500);
    }

    static int apply(String type, int price) {
        return RULES.getOrDefault(type, java.util.function.UnaryOperator.identity()).apply(price);
    }

    public static void main(String[] args) {
        for (String t : new String[]{"vip", "svip", "new", "unknown"}) {
            System.out.printf("  %-8s %d -> %d%n", t, 10000, apply(t, 10000));
        }
        System.out.println("  新增优惠 = 加一行注册，不改主流程");
    }
}
```

### 实操 32-01 ConcurrentHashMap 并发聚合

**知识点注释**
- 【题目要求】实现多线程词频统计：8 线程各处理 1 段文本，用 ConcurrentHashMap.merge 聚合词频（线程安全无锁竞争争论点）；对比 HashMap+synchronized 全局锁与 LongAdder 计数；输出正确性验证（与单线程结果一致）与耗时对比。
- 【考核点】ConcurrentHashMap.merge 原子聚合、LongAdder 高频计数、正确性验证方法（并发 vs 串行等价）。
- 【易错点】get 后 put 的复合操作（丢失更新，用 merge/compute）；size() 精度误解（弱一致）；key null 值异常。
- 【提示】正确性验证的黄金方法：并发结果 == 单线程串行结果（词频全量比对）。

**示例代码**（技术示范：merge 原子聚合，另一套场景）
```java
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

public class MergeDemo {
    static final Map<String, Integer> count = new ConcurrentHashMap<>();

    static void hit(String key) {
        count.merge(key, 1, Integer::sum);      // 原子读改写
    }

    public static void main(String[] args) throws Exception {
        Thread[] ts = new Thread[8];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    hit("k");
                }
            });
            ts[i].start();
        }
        for (Thread t : ts) {
            t.join();
        }
        System.out.printf("  并发 merge 后 k=%d（期望 8000）%n", count.get("k"));
    }
}
```

**课后练习题**
1. 实现完整词频统计（8 线程 merge + 串行等价验证），输出正确性与耗时对比。
2. 把高频计数换 LongAdder（只加不改读），对比 sum 精度与吞吐（1000 万次自增实验）。
3. 思考题：为什么 ConcurrentHashMap 的 size() 是弱一致的？从分段计数与并发写的关系分析正确使用方式。

### 实操 32-02 死锁检测与预防

**知识点注释**
- 【题目要求】构造经典死锁（两线程交叉加锁 A->B 与 B->A），用 ThreadMXBean.findDeadlockedThreads 检测并输出死锁对（线程与持有的锁）；修复两版：① 统一加锁顺序（按锁 id 排序）；② tryLock 超时回退；输出修复前后对比（死锁发生 vs 正常完成）。
- 【考核点】死锁四条件、ThreadMXBean 检测、锁排序预防、tryLock 超时回退、死锁诊断输出。
- 【易错点】修复用"加 try-catch"（死锁不是异常）；锁排序 key 不稳定（对象 hashCode 不固定，用业务 id）；检测线程阻塞主流程。
- 【提示】ThreadMXBean.findDeadlockedThreads 返回死锁线程 id 数组，再取线程信息与锁信息打印证据。

**示例代码**（技术示范：锁排序，另一套场景）
```java
public class LockOrderDemo {
    static final Object L1 = new Object(), L2 = new Object();

    static void transfer(boolean direction) {
        Object first = direction ? L1 : L2;
        Object second = direction ? L2 : L1;
        synchronized (first) {
            synchronized (second) {
                System.out.println("  " + Thread.currentThread().getName() + " 完成转账");
            }
        }
    }

    public static void main(String[] args) {
        // 统一顺序：无论方向，先拿 L1 再拿 L2 —— 死锁四条件被破坏（占有且等待消失）
        Thread t1 = new Thread(() -> transfer(true), "t1");
        Thread t2 = new Thread(() -> transfer(false), "t2");
        t1.start();
        t2.start();
    }
}
```

**课后练习题**
1. 完整实现死锁复现（交叉加锁）+ ThreadMXBean 检测输出 + 两版修复验证。
2. 实现"tryLock 超时回退 + 事务语义回滚"版（拿不到第二把锁释放第一把），对比排序法的适用场景。
3. 思考题：为什么数据库死锁由 DB 自动检测回滚而应用层需要自己预防？从检测成本与回滚粒度的差异分析。

### 实操 34-01 LRU 缓存实现

**知识点注释**
- 【题目要求】实现 LRU 缓存三版：① 哈希表 + 双向链表手写（O(1) get/put）；② LinkedHashMap(accessOrder=true) 版；③ 带 TTL 过期的扩展版（过期惰性删除）；用随机访问序列验证三版行为一致；标注每版的容量淘汰次数统计与时间复杂度。
- 【考核点】双向链表 + 哈希表组合、LinkedHashMap accessOrder 语义、TTL 惰性删除、复杂度分析。
- 【易错点】手写链表的摘除漏 prev/next 指针；LinkedHashMap 重写 removeEldestEntry 的边界；TTL 惰性删除在读时才清理（size 不准需补偿）。
- 【提示】淘汰次数是缓存调优的关键指标（淘汰频繁=容量不足或访问模式不友好）。

**示例代码**（技术示范：LinkedHashMap LRU，另一套场景）
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class LruDemo {
    public static void main(String[] args) {
        Map<String, String> lru = new LinkedHashMap<>(16, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<String, String> eldest) {
                return size() > 3;
            }
        };
        lru.put("a", "1");
        lru.put("b", "2");
        lru.put("c", "3");
        lru.get("a");                       // a 变为最新
        lru.put("d", "4");                  // 淘汰最久未用的 b
        System.out.println("  LRU 现状：" + lru.keySet() + "（b 被淘汰）");
    }
}
```

### 实操 34-02 堆与 TopK

**知识点注释**
- 【题目要求】实现 TopK（10 亿流量的内存方案）：K 个元素的小顶堆（Java PriorityQueue）——流式添加，大于堆顶才入堆；对比三种方案内存：全排序（不可行）/ 全量小顶堆 / 分桶+堆合并；用 100 万随机数取 Top 100，验证堆版结果与全排序一致；标注时间复杂度 O(n log k) 与内存 O(k)。
- 【考核点】堆的性质与操作、TopK 的"小顶堆"选择逻辑（为什么不是大顶堆）、流式处理内存界、复杂度标明。
- 【易错点】用大顶堆做 TopK 大（堆顶是最小的逻辑颠倒）；全量数据入堆（内存 O(n) 违背方案初衷）；比较器方向写反。
- 【提示】TopK 大值用小顶堆：堆顶是"当前第 K 大"，新元素大于堆顶才替换——堆维持"最热的 K 个中最冷的"。

**示例代码**（技术示范：小顶堆 TopK，另一套场景）
```java
import java.util.PriorityQueue;
import java.util.Random;

public class TopKDemo {
    public static void main(String[] args) {
        PriorityQueue<Long> heap = new PriorityQueue<>();     // 小顶堆
        Random r = new Random(42);
        int k = 5;
        for (int i = 0; i < 1_000_000; i++) {
            long v = r.nextLong(1_000_000);
            if (heap.size() < k) {
                heap.add(v);
            } else if (v > heap.peek()) {
                heap.poll();
                heap.add(v);
            }
        }
        System.out.println("  Top5 = " + heap);
        System.out.println("  内存 O(k) 不随 n 增长 —— 流式 TopK 的核心");
    }
}
```

1. 实现完整 TopK（100 万数据 + 全排序对拍），输出一致性与内存占用对比。
2. 扩展为"分桶 TopK 合并"（模拟多机器各自 TopK 后合并），验证合并结果与全局一致。

```java
import java.util.Map;

public class StateMachineDemo {
    record Transition(String from, String event, String to) {
    }

    static final Map<String, String> TABLE = Map.of(
            "CLOSED+connect", "SYN_SENT",
            "SYN_SENT+synack", "ESTABLISHED",
            "ESTABLISHED+close", "FIN_WAIT_1",
            "FIN_WAIT_1+ackfin", "TIME_WAIT");

    public static void main(String[] args) {
        String state = "CLOSED";
        for (String event : new String[]{"connect", "synack", "close", "ackfin"}) {
            String next = TABLE.get(state + "+" + event);
            if (next == null) {
                System.out.printf("  %s + %s -> 非法迁移，拒绝%n", state, event);
                continue;
            }
            System.out.printf("  %s --%s--> %s%n", state, event, next);
            state = next;
        }
    }
}
```

```java
    static boolean evalPatched(String input) {
        // 拼接版：input 直接进"条件文本"
        String condition = "name = '" + input + "'";
        System.out.println("  拼接后条件文本：" + condition);

        // 绑定版：条件结构与值分离
        System.out.println("  绑定版：结构固定 name = ?，值=" + input + "（纯数据）");
        return "alice".equals(input);       // 值只参与比较
    }

    public static void main(String[] args) {

        System.out.printf("  绑定版判定 %b（值是纯数据）%n", evalBound(evil));
    }
}
```
