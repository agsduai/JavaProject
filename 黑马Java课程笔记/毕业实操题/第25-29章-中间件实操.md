## 第25章 Redis 与缓存

### 实操 25-01 缓存三大问题防护

**知识点注释**
- 【题目要求】实现缓存防护套件：① 穿透——空值缓存（TTL 30s）+ 布隆过滤思想（存在位图）；② 击穿——单飞（同一 key 只放一个线程回源，其余等待结果，类似 singleflight）；③ 雪崩——TTL 加随机抖动；用三个场景分别验证防护效果，输出命中/回源/拦截统计。
- 【考核点】三大问题的成因与对策、singleflight 回源合并、TTL 抖动、布隆过滤器思想（可能误判不存在误放）。
- 【易错点】空值缓存永不过期（脏数据）；单飞实现成"锁住所有 key"（应按 key 分组）；抖动写成固定值（失去打散效果）。
- 【提示】单飞用 ConcurrentHashMap<String, CompletableFuture>：第一个线程放 future，其余 get 同一 future。

**示例代码**（技术示范：单飞合并，另一套场景）
```java
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.ConcurrentHashMap;

public class SingleFlightDemo {
    static final ConcurrentHashMap<String, CompletableFuture<String>> inflight = new ConcurrentHashMap<>();
    static int sourceCalls = 0;

    static String load(String key) throws Exception {
        CompletableFuture<String> f = new CompletableFuture<>();
        CompletableFuture<String> existing = inflight.putIfAbsent(key, f);
        if (existing != null) {
            return existing.get();            // 等待首个回源结果
        }
        try {
            sourceCalls++;
            String value = "value-of-" + key;
            f.complete(value);
            return value;
        } finally {
            inflight.remove(key);
        }
    }

    public static void main(String[] args) throws Exception {
        for (int i = 0; i < 5; i++) {
            System.out.println("  并发请求同一 key：" + load("hot"));
        }
        System.out.printf("  回源次数 = %d（5 个请求只回源 1 次）%n", sourceCalls);
    }
}
```

**课后练习题**
1. 实现三大防护完整套件（空值缓存+单飞+TTL 抖动），三个场景各输出防护前后对比统计。
2. 实现简化布隆过滤器（位数组 + 双哈希），验证"存在必过、不存在大概率拦截"，并制造一次误判。
3. 思考题：为什么击穿防护用 singleflight 而不是分布式锁？对比两者的回源合并效果与复杂度。

### 实操 25-02 分布式锁与看门狗

**知识点注释**
- 【题目要求】实现迷你分布式锁（内存模拟 Redis SETNX+TTL）：acquire（SET NX EX 语义，key 不存在才设置）+ TTL 过期自动释放 + 续约看门狗（持有期间定时续 TTL）+ fencing 编号（45-08 复用）；场景：A 拿锁后"假死"超过 TTL -> B 获得锁 -> A 醒来续约失败（锁已易主）必须终止业务。
- 【考核点】SET NX EX 原子性、TTL 与看门狗续约、锁易主后的客户端自觉（续约失败即放弃）、fencing 防过期写入。
- 【易错点】SETNX 与 EXPIRE 分两步（非原子，挂了变死锁）；续约失败继续执行（资损/错乱）；无 fencing（过期者覆盖新持锁者）。
- 【提示】锁记录存（owner, expireAt, fencingToken）；续约校验 owner 一致才续。

**示例代码**（技术示范：原子 SETNX，另一套场景）
```java
import java.util.HashMap;
import java.util.Map;

public class SetnxDemo {
    static final Map<String, String> store = new HashMap<>();

    static synchronized boolean setnx(String key, String value, long ttlMs, long now) {
        String prev = store.get(key);
        if (prev != null && Long.parseLong(prev.split(":")[1]) > now) {
            return false;                      // 未过期 -> 获取失败
        }
        store.put(key, value + ":" + (now + ttlMs));
        return true;
    }

    public static void main(String[] args) {
        long now = 0;
        System.out.println("  A 获取：" + setnx("lock", "A", 1000, now));
        System.out.println("  B 获取（未过期）：" + setnx("lock", "B", 1000, now + 500));
        System.out.println("  B 获取（已过期）：" + setnx("lock", "B", 1000, now + 1500));
    }
}
```

**课后练习题**
1. 实现完整分布式锁（原子 SETNX + 看门狗续约 + fencing），重演"假死->易主->续约失败"时间线。
2. 实现可重入（同 owner 同 key 计数），验证重入次数与释放匹配。
3. 思考题：为什么看门狗续约失败后"必须终止业务"而不是继续？结合 fencing 被拒的下游证据分析。

## 第26章 Spring Boot 进阶

### 实操 26-01 AOP 代理链模拟

**知识点注释**
- 【题目要求】用 JDK 动态代理实现 AOP 链：切面（日志计时/权限校验/重试）按 Order 排序织成拦截链（责任链 31 章思想）；代理调用顺序 = 前置按 order 正序 -> 目标方法 -> 后置逆序；异常在链上传播（权限失败直接抛出，不进目标方法）；用计时+权限双切面演示完整链路输出。
- 【考核点】动态代理实现 AOP、拦截器链（pre/target/post 顺序）、切面排序、异常传播路径。
- 【易错点】后置逻辑顺序颠倒（应逆序）；权限切面放在计时之后（失败也计了时，日志误导）；链中吞异常（上层无感知）。
- 【提示】拦截器接口三方法（before/after/throwing）；链递归推进（每个拦截器调 next）。

**示例代码**（技术示范：拦截链，另一套场景）
```java
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.List;

public class InterceptorChainDemo {
    interface Handler {
        String handle(String req);
    }

    interface Interceptor {
        String name();

        String before(String req);

        void after(String resp);
    }

    public static void main(String[] args) {
        List<Interceptor> chain = new ArrayList<>(List.of(
                new Interceptor() {
                    public String name() {
                        return "audit";
                    }

                    public String before(String req) {
                        System.out.println("  audit.before: " + req);
                        return req;
                    }

                    public void after(String resp) {
                        System.out.println("  audit.after: " + resp);
                    }
                }));
        Handler target = req -> "resp:" + req;
        Handler proxied = (Handler) Proxy.newProxyInstance(Handler.class.getClassLoader(),
                new Class<?>[]{Handler.class},
                (proxy, method, args1) -> {
                    String req = (String) args1[0];
                    for (Interceptor i : chain) {
                        req = i.before(req);
                    }
                    String resp = target.handle(req);
                    for (int i = chain.size() - 1; i >= 0; i--) {
                        chain.get(i).after(resp);
                    }
                    return resp;
                });
        System.out.println("  最终：" + proxied.handle("hello"));
    }
}
```

**课后练习题**
1. 实现完整 AOP 链（三切面按 Order 织入 + 异常传播），验证前置正序/后置逆序/权限失败短路。
2. 实现重试切面（只对 IO 异常重试 2 次），演示异常类型敏感的重试。
3. 思考题：为什么 AOP 能把"日志/权限/重试"从业务代码剥离？从横切关注点与拦截链的结构分析收益与代价。

### 实操 26-02 JWT 签发与验签

**知识点注释**
- 【题目要求】用 javax.crypto.HmacSHA256 实现迷你 JWT：签发（header/payload Base64Url + HMAC 签名）、验签（重算签名比对，常量时间比较）、过期校验（exp 字段）、payload 篡改检测（改角色字段后验签失败）；输出签发->验签->篡改->过期四个场景的结果。
- 【考核点】JWT 三段结构、HMAC 签名与验签、Base64Url、exp 过期、篡改检测（36 章同款技术的闭环演练）。
- 【易错点】签名比对用 equals（时序攻击，应 MessageDigest.isEqual）；不校验 exp（过期 token 可用）；把敏感信息放 payload（Base64 可解码）。
- 【提示】Base64.getUrlEncoder().withoutPadding()；payload 是明文可读——只放非敏感声明。

**示例代码**（技术示范：HMAC 签名，另一套场景）
```java
import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.util.Base64;

public class HmacDemo {
    static String sign(String data, String secret) throws Exception {
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(secret.getBytes(), "HmacSHA256"));
        return Base64.getUrlEncoder().withoutPadding()
                .encodeToString(mac.doFinal(data.getBytes()));
    }

    static boolean verify(String data, String signature, String secret) throws Exception {
        byte[] expect = Base64.getUrlDecoder().decode(signature);
        byte[] actual = Base64.getUrlDecoder().decode(sign(data, secret));
        return java.security.MessageDigest.isEqual(expect, actual);   // 常量时间比较
    }

    public static void main(String[] args) throws Exception {
        String sig = sign("payload", "secret-key");
        System.out.println("  签名=" + sig);
        System.out.println("  正确验签：" + verify("payload", sig, "secret-key"));
        System.out.println("  篡改数据验签：" + verify("payload-tampered", sig, "secret-key"));
    }
}
```

**课后练习题**
1. 实现完整 JWT（签发/验签/exp/篡改检测），四场景输出结果，并解释 payload 为什么可被解码。
2. 实现常量时间比较的对照实验：普通 equals 与 MessageDigest.isEqual 的时序差异说明。
3. 思考题：为什么 JWT 无法"服务端注销"（除非黑名单）？从无状态验证机制推演登出语义的三种实现与代价。

### 实操 27-01 下单链路编排

**知识点注释**
- 【题目要求】实现下单编排器（应用服务层，49 章呼应）：校验参数 -> 幂等检查（orderId 去重）-> 调库存域（模拟，失败返回结构化错误）-> 调营销域（优惠券校验，失败降级不阻断）-> 落订单 -> 发事件；输出三种场景的编排轨迹：全成功/库存失败（整体失败）/营销失败（降级继续）。
- 【考核点】应用服务编排、幂等检查前置、关键 vs 非关键依赖的失败语义分级、事件发出。
- 【易错点】所有依赖失败都整体失败（营销失败不该拦下单）；幂等检查在业务后（重复下单已发生）；编排层写业务规则（49 章贫血回退）。
- 【提示】依赖分级声明：critical=false 的失败进降级清单，响应中标注。

**示例代码**（技术示范：依赖分级，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;

public class OrchestrateDemo {
    record StepResult(String step, boolean ok, boolean critical, String detail) {
    }

    static void orchestrate() {
        List<StepResult> results = List.of(
                new StepResult("param-check", true, true, "通过"),
                new StepResult("stock", true, true, "扣减成功"),
                new StepResult("coupon", false, false, "券池超时 -> 降级：不用券"),
                new StepResult("save-order", true, true, "落库成功"));
        boolean blocked = results.stream().anyMatch(r -> !r.ok() && r.critical());
        for (StepResult r : results) {
            System.out.printf("  %-12s %s %s%n", r.step(), r.ok() ? "OK" : "FAIL", r.detail());
        }
        System.out.println("  整体：" + (blocked ? "失败" : "成功（含降级）"));
    }

    public static void main(String[] args) {
        orchestrate();
    }
}
```

**课后练习题**
1. 实现完整下单编排器（幂等 + 分级依赖 + 事件发出），三种场景输出轨迹与最终状态。
2. 实现"编排层重试"：非关键失败自动重试一次，关键失败不重试直接终态，说明策略依据。
3. 思考题：为什么编排层要区分"关键/非关键"依赖？从用户视角（下单成功率）与系统视角（故障影响面）分析。

### 实操 27-02 并发扣减与幂等

**知识点注释**
- 【题目要求】实现商品扣减三版对比：① 无防护 DB 更新（超卖复现）；② 乐观锁 UPDATE WHERE stock >= qty（拒绝超卖）；③ Redis 预扣 + 异步落库（本地缓存先行）；200 线程并发抢 50 件库存，三版各跑一次，输出成功数/拒绝数/最终库存，验证"成功数恒等于初始库存"（②③版）。
- 【考核点】超卖根因（检查与扣减非原子）、乐观锁条件更新、预扣与异步落库的最终一致、并发正确性验证方法。
- 【易错点】先查再扣（两步间被插队）；预扣后落库失败无补偿（Redis 与 DB 分叉）；压测无恒等断言（正确性没有证据）。
- 【提示】③ 版的"异步落库失败"要补偿：落库失败把预扣回滚（Redis 加回）——写出补偿逻辑。

**示例代码**（技术示范：条件更新，另一套场景）
```java
public class ConditionalUpdateDemo {
    static int stock = 50;
    static int success = 0, rejected = 0;

    static synchronized boolean deduct(int qty) {
        if (stock >= qty) {                 // 原子化后的 check-then-act
            stock -= qty;
            success++;
            return true;
        }
        rejected++;
        return false;
    }

    public static void main(String[] args) throws Exception {
        Thread[] ts = new Thread[200];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> deduct(1));
            ts[i].start();
        }
        for (Thread t : ts) {
            t.join();
        }
        System.out.printf("  成功 %d / 拒绝 %d / 剩余库存 %d（恒等：%b）%n",
                success, rejected, stock, success == 50 && stock == 0);
    }
}
```

**课后练习题**
1. 实现三版完整对比（无防护/乐观锁/预扣+补偿），200 并发输出各自的成功/拒绝/最终库存。
2. 为预扣版实现"落库失败补偿"（Redis 加回），注入落库故障验证补偿生效。
3. 思考题：为什么乐观锁在热点商品上会大量拒绝？结合 44 章预扣方案说明"Redis 先行"如何把 DB 从热点路径摘除。

### 实操 28-01 重试与死信闭环

**知识点注释**
- 【题目要求】实现消费重试闭环：消息消费失败 -> 指数退避重试（1s/2s/4s）-> 3 次后进死信队列 -> 死信告警与人工重放接口（模拟重放成功）；输出一条"必然失败"消息的状态机轨迹（PENDING->RETRY1->RETRY2->RETRY3->DEAD->重放成功）与一条正常消息轨迹。
- 【考核点】指数退避、重试次数上限、死信队列语义、人工重放（修根因后重放而非重复投递）、状态机。
- 【易错点】无限重试（毒消息打爆系统）；重放不修根因（再进死信循环）；死信无告警（静默丢事件）。
- 【提示】重试次数与退避是消息属性；重放走"新消息 ID + 原业务键"（幂等依赖业务键而不是消息 ID）。

**示例代码**（技术示范：退避重试，另一套场景）
```java
public class RetryBackoffDemo {
    public static void main(String[] args) {
        long delay = 1000;
        for (int attempt = 1; attempt <= 3; attempt++) {
            System.out.printf("  第 %d 次重试（延迟 %dms）%n", attempt, delay);
            delay *= 2;
        }
        System.out.println("  3 次后进死信 -> 告警 + 人工重放");
    }
}
```

**课后练习题**
1. 实现完整重试闭环（退避/死信/告警/重放），两条消息轨迹输出，验证"重放前必须修根因"的流程。
2. 实现"重试风暴保护"：同一批次消息全部失败时合并重试（批量重投），避免风暴放大。
3. 思考题：为什么死信的"人工重放"要在修根因之后？从毒消息循环与下游幂等两个角度分析重放的正确姿势。

### 实操 28-02 延迟队列与本地消息表

**知识点注释**
- 【题目要求】实现延迟订单关闭：下单 15 分钟未支付自动关单——用时间轮/优先队列（按到期时间排序）模拟延迟投递；支付回调与关单竞态（先关单后回调 -> 触发退款差异单，51 章复用）；本地消息表保证"关单事件"可靠发出；模拟 3 单（按时支付/超时关单/竞态）输出全轨迹。
- 【考核点】延迟投递实现（优先队列/时间轮思想）、关单与支付竞态裁决、本地消息表可靠发出、超时关单的幂等。
- 【易错点】延迟队列重启丢消息（应持久化/用本地消息表驱动）；关单与支付无竞态裁决（双成功）；关单重复执行（未幂等）。
- 【提示】优先队列按 (到期时间, 单号) 排序，消费侧循环取到期项；竞态用状态机裁决（51-03 同款）。

**示例代码**（技术示范：优先队列，另一套场景）
```java
import java.util.PriorityQueue;
import java.util.Comparator;

public class DelayQueueDemo {
    record DelayedTask(long dueMs, String task) implements Comparable<DelayedTask> {
        public int compareTo(DelayedTask o) {
            return Long.compare(dueMs, o.dueMs);
        }
    }

    public static void main(String[] args) {
        PriorityQueue<DelayedTask> q = new PriorityQueue<>(Comparator.naturalOrder());
        q.add(new DelayedTask(3000, "close-order-9001"));
        q.add(new DelayedTask(1000, "send-reminder-9002"));
        long now = 0;
        while (!q.isEmpty() && now <= 3000) {
            if (q.peek().dueMs() <= now) {
                System.out.printf("  t=%dms 执行 %s%n", now, q.poll().task());
            }
            now += 1000;
        }
    }
}
```

**课后练习题**
1. 实现延迟关单完整版（优先队列/时间轮 + 本地消息表 + 竞态裁决），三单轨迹输出。
2. 实现"重启恢复"：延迟任务持久化，进程重启后重建队列，验证不丢不重。
3. 思考题：为什么关单用"延迟队列"而不用"定时扫表"？对比两者的时效精度、DB 压力与实现复杂度。

### 实操 29-01 注册中心心跳与剔除

**知识点注释**
- 【题目要求】实现迷你注册中心：服务实例注册（name/ip/port/心跳最后时间）、心跳续约线程、剔除线程（超过 15s 无心跳摘除）、订阅通知（实例变更回调）；场景：3 实例注册 -> 1 实例假死 -> 剔除 -> 订阅方收到变更 -> 假死实例复活重新注册；输出注册表变化时间线与订阅通知。
- 【考核点】注册/续约/剔除三机制、健康判定 TTL、订阅推拉结合、实例状态机（UP/DOWN）。
- 【易错点】心跳超时等于实例死亡（网络抖动误杀，需容忍次数）；剔除后无恢复路径；订阅用轮询（应事件回调）。
- 【提示】健康判定用"连续 N 次心跳缺失"更稳；剔除事件要推给订阅方（29 章的 Nacos 对比点）。

**示例代码**（技术示范：心跳判定，另一套场景）
```java
import java.util.LinkedHashMap;
import java.util.Map;

public class HeartbeatDemo {
    static final Map<String, Long> lastBeat = new LinkedHashMap<>();
    static final long TTL = 15000;

    static boolean alive(String instance, long now) {
        Long last = lastBeat.get(instance);
        return last != null && now - last <= TTL;
    }

    public static void main(String[] args) {
        lastBeat.put("i-1", 0L);
        lastBeat.put("i-2", 0L);
        System.out.println("  t=0    alive i-1=" + alive("i-1", 0) + " i-2=" + alive("i-2", 0));
        System.out.println("  t=16s  i-2 未续约 -> alive=" + alive("i-2", 16000) + "（剔除）");
        lastBeat.put("i-2", 16000L);
        System.out.println("  t=17s  i-2 复活续约 -> alive=" + alive("i-2", 17000));
    }
}
```

**课后练习题**
1. 实现完整注册中心（注册/心跳/剔除/订阅回调），完整场景时间线输出，验证订阅方收到 DOWN 与 UP 事件。
2. 实现"心跳容忍次数"（连续 3 次缺失才剔除），对比单次超时剔除的误杀率（模拟 10% 丢包）。
3. 思考题：为什么 29 章最终用"本地内存注册表 + 心跳"而不用 ZK？从心跳写吞吐与可用性依赖两个角度对比。

### 实操 29-02 熔断器三态

**知识点注释**
- 【题目要求】实现熔断器（CLOSED/OPEN/HALF_OPEN）：滑动窗口统计失败率（最近 20 次）、失败率超阈值 -> OPEN（拒绝请求，快速失败）、冷却时间到 -> HALF_OPEN（放行探测请求）、探测成功 -> CLOSED / 失败 -> OPEN；模拟下游"正常->故障->恢复"全周期，输出每请求的三态与决策日志。
- 【考核点】三态迁移条件、滑动窗口统计、快速失败保护上游、半开探测机制、与重试的区别（熔断不重试只拒绝）。
- 【易错点】半开放行全部流量（应限探测数）；窗口用总累计（历史失败拖住熔断器）；OPEN 期间仍打下游（保护失效）。
- 【提示】半开态维护探测计数：前 N 次真实放行，其余快速失败；成功 M 次才回 CLOSED。

**示例代码**（技术示范：三态迁移，另一套场景）
```java
public class CircuitDemo {
    enum State {
        CLOSED, OPEN, HALF_OPEN
    }

    static State state = State.CLOSED;
    static int fails = 0, probeOk = 0;

    static boolean call(boolean downstreamOk) {
        switch (state) {
            case OPEN -> {
                System.out.println("  熔断中 -> 快速失败");
                return false;
            }
            case HALF_OPEN -> {
                if (downstreamOk) {
                    probeOk++;
                    if (probeOk >= 2) {
                        state = State.CLOSED;
                        System.out.println("  探测成功 x2 -> 回 CLOSED");
                    }
                    return true;
                }
                state = State.OPEN;
                System.out.println("  探测失败 -> 回 OPEN");
                return false;
            }
            default -> {
                if (downstreamOk) {
                    fails = 0;
                    return true;
                }
                fails++;
                if (fails >= 3) {
                    state = State.OPEN;
                    System.out.println("  连续 3 失败 -> OPEN");
                }
                return false;
            }
        }
    }

    public static void main(String[] args) {
        for (int i = 0; i < 5; i++) {
            call(false);
        }
    }
}
```

**课后练习题**
1. 实现完整熔断器（滑动窗口 + 三态 + 半开探测），模拟"正常->故障->恢复"全周期输出决策日志。
2. 实现"按接口隔离熔断"（同一服务不同接口独立熔断器），对比全局熔断的误伤面。
3. 思考题：为什么熔断器"快速失败"比"等待超时"更保护系统？从线程占用与故障放大的角度分析 29 章熔断与超时的组合。

### 实操 29-03 配置中心客户端（可选题）

**知识点注释**
- 【题目要求】实现配置中心客户端迷你版（45-11 的 24 章呼应版）：长轮询模拟（定时检查版本）、版本单调校验、本地快照文件持久化、热更新回调；服务端三版本变更，客户端跟随并输出热更轨迹；服务端全挂时客户端用快照继续运行。
- 【考核点】推拉结合、版本单调、快照自持、热更新回调安全（配置校验后才应用）。
- 【易错点】热更新直接应用未校验（坏配置上线）；快照不落盘（重启丢配置）；版本回退被应用（旧配置覆盖新配置）。
- 【提示】回调里先过 schema 校验（46-08 契约思想）再触发应用层刷新。

**示例代码**（技术示范：版本单调，另一套场景）
```java
public class ConfigVersionDemo {
    static long local = 42;

    static void apply(long serverVersion, String value) {
        if (serverVersion <= local) {
            System.out.printf("  拒绝 v%d（本地 v%d）—— 防旧实例推送%n", serverVersion, local);
            return;
        }
        local = serverVersion;
        System.out.printf("  应用 v%d：%s%n", serverVersion, value);
    }

    public static void main(String[] args) {
        apply(43, "timeout=3000");
        apply(41, "timeout=1000");
        apply(44, "timeout=5000");
    }
}
```

**课后练习题**

2. 演练"服务端全挂"：客户端快照存活，恢复后对齐，输出完整时间线。

### 实操 29-04 负载均衡与重试预算（可选题）

**知识点注释**
- 【题目要求】实现负载均衡三策略对比（轮询/随机/最少连接）+ 重试预算（同一调用链最多重试 N 次、超预算直接失败）：3 个模拟实例（不同延迟），200 请求三种策略的延迟分布对比；重试预算演示"下游劣化时重试风暴被预算钳制"。
- 【考核点】三种 LB 策略语义、最少连接的公平性、重试预算（44-08）、压测对比方法。
- 【易错点】轮询打到慢实例（无水位感知）；重试无预算（风暴放大 32/29 章）；随机策略的短期不均未说明。
- 【提示】最少连接用 AtomicInteger 计数器选最小者；预算全局共享（调用链维度）而不是单请求。

**示例代码**（技术示范：最少连接，另一套场景）
```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.atomic.AtomicInteger;

public class LeastConnDemo {
    record Node(String name, AtomicInteger conn) {
    }

    public static void main(String[] args) {
        List<Node> nodes = List.of(new Node("n1", new AtomicInteger(5)),
                new Node("n2", new AtomicInteger(1)), new Node("n3", new AtomicInteger(3)));
        Node best = nodes.stream().min((a, b) -> Integer.compare(a.conn().get(), b.conn().get()))
                .orElseThrow();
        System.out.printf("  最少连接路由 -> %s（当前 %d 连接）%n", best.name(), best.conn().get());
    }
}
```

**课后练习题**
1. 实现三策略完整对比（200 请求 × 3 实例延迟），输出 P50/P99 表并解释差异来源。
2. 实现重试预算（调用链共享），注入下游劣化观察预算钳制重试风暴的效果。
3. 思考题：为什么"最少连接"比"轮询"更适合推理/长连接类不均匀负载？从请求时长差异的角度分析。
