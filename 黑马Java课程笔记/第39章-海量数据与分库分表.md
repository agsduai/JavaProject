# 第39章 海量数据与分库分表

第38章解决了"搜索快"，本章解决"数据多"。单表千万行还能撑，五千万之后 B+ 树变深、缓冲池命中率下降、DDL 时间失控——但**分库分表是最后手段而不是第一步**：先慢查询治理、再缓存挡读、再读写分离、再历史归档，都做完写瓶颈仍在才进入拆分。拆分后新问题随之而来：分片键怎么选、扩容怎么迁、ID 怎么全局唯一、跨分片查询与事务怎么办。本章按「数据量的代价 → 索引与执行计划 → 深分页 → 读写分离 → 拆分策略 → 路由与扩容 → 分布式 ID → 跨分片查询 → 跨库一致性 → 冷热归档 → 订单系统综合案例」的顺序讲。所有示例仍是纯 JDK：B+ 树深度真实估算，一致性哈希与槽位路由真实迁移，雪花算法带时钟回拨处理真实运行，跨分片归并、本地消息表、双写对账全部真跑逻辑，不需要装 MySQL 集群。

### 39-01 数据量大了会发生什么

**知识点**
- **单表性能拐点是经验值不是铁律**：千万级通常还能撑（看索引与查询模式），五千万到一亿级开始明显劣化。决定拐点的不是行数本身，而是 **B+ 树的深度**：主键索引树高从 3 层变 4 层，每次查找多一次磁盘/页读取，所有查询同时变慢。
- **量变引起质变的四个信号**：① 通过索引查单行仍快，但**无索引条件查询**从毫秒变秒；② 缓冲池（innodb_buffer_pool）命中率下降，数据页换进换出；③ 备份/DDL 时间从分钟变小时（`ALTER TABLE` 锁表风险飙升）；④ 主从延迟开始周期性飙高。
- **先优化索引与查询，再考虑拆**：绝大多数"数据量大了很慢"的真实原因是一个没走索引的 SQL。**分库分表是最后手段**，做之前必须先做：索引优化、SQL 治理、缓存挡读、历史归档。直接上分库分表是把架构复杂度当成特效药。
- **数据量的另一个代价是"写"**：B+ 树页分裂、redo/undo 膨胀、长事务持锁更久。读可以通过缓存与从库扛，**写瓶颈才是分库的真实动因**。
- **容量规划要按"三年后"算**：日增 50 万行，一年 1.8 亿行。规划分片数不是按今天的量，而是按三年后的量 ÷ 单分片合理上限（经验值 1000~2000 万行/表），一次规划到位，避免二次扩容。
- **判断该走哪条路**：读慢 → 缓存 + 读写分离 + 归档；写慢 → 批量化 + 削峰 + 分库；单表大但增长停止 → 归档即可；持续增长 → 分库分表。
- 易错点：用行数判断要不要拆（要看 QPS、索引命中、增长曲线）；把分库分表当成"性能优化第一步"；忽略归档——很多系统 80% 的数据是两年前的冷数据，归档完单表直接回到安全区。

```java
        int height = 1;

            height++;
        }
        return height;
```

### 39-02 索引优化与执行计划

**知识点**
- **EXPLAIN 是唯一可信的证据**：type 从好到坏：`system > const > eq_ref > ref > range > index > ALL`，出现 ALL（全表扫描）基本就是事故；rows 是预估扫描行数；key/Extra 说明用没用索引、有没有回表、有没有 filesort。
- **最左前缀原则**：联合索引 `(a, b, c)` 只能支持 a、a+b、a+b+c 的查询。条件里跳过 a 直接查 b，索引就用不上；a 有条件但 b 范围查询，c 就断了（范围之后失效）。**联合索引的列顺序 = 等值列在前、范围列在后、排序列跟随**。
- **回表与覆盖索引**：二级索引存的是（索引列+主键），SELECT 的列不在索引里就要回主键树再取一次。`SELECT id, status FROM t WHERE status=?` 用联合索引 `(status, id)` 可以**索引覆盖**不回表，Extra 显示 `Using index`。大查询覆盖索引常常是十倍差距。
- **索引选择性**：区分度 = 不重复值数/总行数。`status` 只有 3 个值，单独索引选择性差，但联合索引里作为前缀做等值过滤依然有效；`性别` 这种字段单独建索引是浪费。
- **隐式类型转换是隐形索引杀手**：`WHERE phone = 13800000000`（字符串列配数字）触发转换，索引失效；函数包住列（`DATE(create_time)=...`）同样失效，应改写为范围条件 `create_time >= '...' AND < '...'`。
- **深分页的 index 层优化**：`LIMIT 100000, 10` 要扫过前 10 万行。先用覆盖索引取出目标主键（延迟关联），再用主键回表，扫描成本从"全字段×10万"降到"索引×10万"。
- 易错点：为每个查询条件单独建一堆单列索引（MySQL 只会用一个，联合索引才是正解）；`ORDER BY` 列不在索引里导致 filesort； believing `FORCE INDEX` 能解决设计问题（治标）；线上加索引用 `ALGORITHM=INPLACE, LOCK=NONE` 忘了确认版本支持（8.0 大多支持但要看列类型）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class SlowQueryOptimize {
    /** 模拟联合索引前缀消耗：等值列可被优化器重排，范围列之后失效 */
    static int usablePrefix(List<String> eqCols, String rangeCol, String[] indexCols) {
        int used = 0;
        for (String idxCol : indexCols) {
            if (eqCols.contains(idxCol)) {
                used++;
            } else if (idxCol.equals(rangeCol)) {
                used++;               // 范围列本身可用，其后全部失效
                break;
            } else if (used < eqCols.size() && !eqCols.contains(idxCol)) {
                break;                // 前缀列缺席，断链
            }
        }
        return used;
    }

    static void leftmostRule() {
        System.out.println("【最左前缀：联合索引 (user_id, status, create_time)】");
        String[] indexCols = {"user_id", "status", "create_time"};
        String[][] queries = {
                {"user_id=,status=,create_time>", "等值x2+范围", "ref，时间列走范围"},
                {"user_id=,status=", "等值x2", "ref"},
                {"user_id=", "等值x1", "ref"},
                {"status=,user_id=", "等值x2（顺序故意颠倒）", "优化器重排等值列，仍可全用"},
                {"status=,create_time>", "跳过 user_id", "前缀断链，0 列可用"},
        };
        for (String[] q : queries) {
            List<String> eq = new ArrayList<>();
            String range = null;
            for (String part : q[0].split(",")) {
                if (part.endsWith("=")) {
                    eq.add(part.substring(0, part.length() - 1));
                } else {
                    range = part.substring(0, part.length() - 1);
                }
            }
            int used = usablePrefix(eq, range, indexCols);
            System.out.printf("  WHERE %-34s %-16s -> 用上 %d 列（%s）%n", q[0], q[1], used, q[2]);
        }
        System.out.println("  规则：等值列按索引顺序消耗；范围列可用但截断其后；缺前缀列=全废");
        System.out.println();
    }

    static void coveringIndex() {
        System.out.println("【覆盖索引：回表次数决定查询速度】");
        int matchRows = 10_000;
        System.out.printf("  SELECT * WHERE status=PAID 命中 %d 行：%n", matchRows);
        System.out.printf("    索引(status)        ：%d 次索引扫描 + %d 次回表取全字段%n", matchRows, matchRows);
        System.out.printf("    索引(status,id)     ：%d 次索引扫描 + 0 次回表（Using index）%n", matchRows);
        System.out.println("    延迟关联：先取 100 个主键再回表 -> 只回表 100 次");
        System.out.println("  设计口诀：高频查询的 SELECT 列尽量进联合索引，代价是索引变宽");
        System.out.println();
    }

    static void indexKillers() {
        System.out.println("【四个让索引失效的真实写法】");
        String[][] cases = {
                {"WHERE phone = 13800000000", "字符串列配数字 -> 隐式转换全表扫"},
                {"WHERE DATE(create_time)=CURDATE()", "函数包列 -> 改为时间范围条件"},
                {"WHERE name LIKE '%机'", "前置 % -> 只能放弃 B+ 树（或用倒排/前缀索引）"},
                {"WHERE status != 'PAID'", "不等于 -> 通常仍需扫描，靠选择性与数据分布判断"},
        };
        for (String[] c : cases) {
            System.out.printf("  %-38s %s%n", c[0], c[1]);
        }
        System.out.println();
    }

    static void explainChecklist() {
        System.out.println("【EXPLAIN 审核五步】");
        List<String> steps = List.of(
                "type 是不是 ALL/index -> 基本要 ref 以上",
                "rows 与实际命中数差几个数量级 -> 统计信息过期或索引选择错",
                "key 是否是预期索引 -> 不是就查最左前缀/类型转换",
                "Extra 有 Using filesort/Using temporary -> 排序与分组列进索引",
                "Extra 有 Using index -> 覆盖索引生效，记录为优化成果");
        for (String s : steps) {
            System.out.println("  " + s);
        }
    }

    public static void main(String[] args) {
        leftmostRule();
        coveringIndex();
        indexKillers();
        explainChecklist();
    }
}
```

### 39-03 深分页优化

**知识点**
- **`LIMIT 1000000, 20` 的真实成本**：不是"跳过一百万行很快"，而是**扫完前 1000020 行、扔掉前 100 万行**。每多翻一页成本线性增长，且页越深锁与 buffer pool 压力越大。页深上万时，一次查询就能把数据库拖挂。
- **游标分页（keyset pagination）是根本解**：记住上一页最后一条的排序键（如 `id=100023`），下一页查询 `WHERE id > 100023 ORDER BY id LIMIT 20`。成本恒定 O(页大小)，配合主键索引完美。代价：**只能顺序翻页，不能跳页**——这与第 38 章 ES 的 search_after 是同一个思想。
- **跳页需求用延迟关联**：`SELECT t.* FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 20) tmp ON t.id=tmp.id`。内层只扫覆盖索引（窄），回表只剩 20 次。再配合"业务上限制可跳页数"基本解决。
- **排序键设计决定游标可用性**：按 `create_time DESC, id DESC` 翻页时，条件是 `(create_time, id) < (last_time, last_id)` 的行序元组比较，MySQL 8.0 支持行构造器写法 `WHERE (create_time, id) < (?, ?)`；老版本用等价展开写法。**排序键必须带唯一列兜底**，否则同时刻数据翻页会漏。
- **总数（count(*)）是另一个坑**：深表 `SELECT COUNT(*)` 全索引扫描，页面每次请求都算一次总数是灾难。方案：近似总数（估算值 + "约"字）、缓存计数、或产品上去掉总数只留"下一页"。
- **与 ES 深分页的统一认知**：任何存储的深分页本质都一样——**offset 方案的成本随深度线性涨，游标方案成本恒定**。选型取决于产品需要跳页还是流式浏览。
- 易错点：前端强制要"总条数+跳页"就默默用 offset 硬扛（深页必炸）；游标分页的排序键不含唯一列导致漏数据；缓存 count 后写路径忘了失效（数字长期不准）；用 `LIMIT` 做数据导出循环（offset 越翻越慢，应按 id 游标批量拉）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class DeepPaginationFix {
    record Order(long id, String status, long createTime) {
    }

    /** 模拟一张有序表：id 递增 */
    static List<Order> table(int n) {
        List<Order> rows = new ArrayList<>();
        for (long i = 1; i <= n; i++) {
            rows.add(new Order(i, i % 3 == 0 ? "PAID" : "CREATED", 1700000000L + i));
        }
        return rows;
    }

    static void offsetCost() {
        System.out.println("【offset 分页的成本曲线】");
        List<Order> rows = table(2_000_000);
        int[] offsets = {20, 20_000, 200_000, 1_000_000};
        for (int off : offsets) {
            long scanned = Math.min(off + 20, rows.size());
            System.out.printf("  LIMIT %7d, 20 -> 必须扫过 %8d 行（命中率 %.4f%%）%n",
                    off, scanned, 20.0 / scanned * 100);
        }
        System.out.println("  扫描行数与 offset 同阶增长；offset=百万时一次查询等于半次全表扫描");
        System.out.println();
    }

    static void keysetPaging() {
        System.out.println("【游标分页：WHERE id > lastId LIMIT 20，成本恒定】");
        List<Order> rows = table(2_000_000);
        long cursor = 0;
        int page = 0;
        while (page < 3 && cursor < rows.size()) {
            int start = (int) cursor;
            List<Order> window = rows.subList(start, Math.min(start + 20, rows.size()));
            System.out.printf("  第 %d 页: id %d ~ %d（只扫 20 行）%n",
                    page + 1, window.get(0).id(), window.get(window.size() - 1).id());
            cursor = start + 20;
            page++;
        }
        System.out.println("  SQL：SELECT * FROM orders WHERE id > ? ORDER BY id LIMIT 20");
        System.out.println("  任何页深都只扫描 20 行，这就是游标的全部意义");
        System.out.println();
    }

    static void compositeKeyset() {
        System.out.println("【复合排序键的游标：按 create_time DESC 翻页】");
        List<Order> sorted = table(100).stream()
                .sorted(Comparator.comparingLong(Order::createTime).reversed()
                        .thenComparingLong(Order::id))
                .limit(6).toList();
        Order last = sorted.get(2);
        System.out.printf("  上一页最后一条：(create_time=%d, id=%d)%n", last.createTime(), last.id());
        List<Order> next = sorted.stream()
                .sorted(Comparator.comparingLong(Order::createTime).reversed()
                        .thenComparingLong(Order::id))
                .skip(3).limit(3).toList();
        System.out.println("  WHERE (create_time,id) < (?, ?) ORDER BY create_time DESC, id DESC LIMIT 3");
        System.out.println("  下一页: " + next.stream().map(o -> o.id()).toList());
        System.out.println("  唯一键兜底：同一毫秒的多条订单不会漏、不会重");
        System.out.println();
    }

    static void delayedJoin() {
        System.out.println("【必须跳页时：延迟关联只回表 20 次】");
        long total = 2_000_000, offset = 1_000_000, pageSize = 20;
        long narrowScan = offset + pageSize;
        System.out.printf("  原写法：扫描 %d 行 × 全字段宽行 -> 回表 %d 次%n", narrowScan, narrowScan);
        System.out.printf("  延迟关联：内层覆盖索引扫 %d 行（窄），回表 %d 次%n", narrowScan, pageSize);
        System.out.println("  SQL：SELECT o.* FROM orders o JOIN");
        System.out.println("       (SELECT id FROM orders ORDER BY id LIMIT 1000000, 20) t ON o.id=t.id");
        System.out.println("  配套产品约束：可跳页范围限制在最近 N 页（跳到 50 万条之外本就是伪需求）");
    }

    public static void main(String[] args) {
        offsetCost();
        keysetPaging();
        compositeKeyset();
        delayedJoin();
    }
}
```

### 39-04 读写分离与主从延迟

**知识点**
- **读写分离的本质是"按一致性要求路由"**：主库承担全部写入与强一致读，从库承担报表、列表等可容忍延迟的读。MySQL 一主多从是标配，复制基于 binlog（逻辑复制），从库重放主库的事务流。
- **主从延迟无法归零，只能管理**：单线程回放（老版本）、大事务、从库跑重查询、DDL 都会拉大 `Seconds_Behind_Master`。典型场景：写库成功 → 立即读从库 → **读不到刚写的数据**，用户看到"订单消失"，客服工单随即到达。
- **强一致读必须回主库**：写后立即读（下单成功页）、支付回调校验、唯一性检查，都走主库。实现手段：代码里用路由注解强制主库、或同一请求内写后读绑定主库（sticky routing，几秒内该用户请求全走主）。
- **半同步复制是折衷**：异步复制主库提交即返回（可能丢最近事务）；半同步要求至少一个从库收到 binlog 才算提交成功，牺牲一点写延迟换 RPO 收敛；组复制（MGR）更严格但成本高。
- **延迟的工程对策**：① 关键路径强制主库；② 版本号校验（读到的数据版本 < 本次写入版本就重试/回主库）；③ 从库只服务"不需要最新数据"的查询（历史订单、报表）；④ 监控 Seconds_Behind_Master 告警阈值（如 >10s）。
- **路由实现层次**：框架层（Spring 的 AbstractRoutingDataSource / ShardingSphere 的主从分离）、代理层（ProxySQL/MaxScale）、云上直接买数据库代理。应用侧要做的核心是把"读写意图"表达清楚。
- 易错点：写后读走了从库（下单页空白）；把报表大查询放主库（拖慢交易）；从库数量无脑加（每多一个从库主库 binlog 线程压力都增加，且延迟更难收敛）；故障切换后应用连接串没切（脑裂期双写）。

**示例代码**
```java
import java.util.HashMap;
import java.util.Map;

public class ReadWriteSplit {
    /** 简化数据源：主库实时，从库带固定延迟 */
    static class DataSource {
        final String name;
        final long lagMs;
        final Map<String, String> data = new HashMap<>();

        DataSource(String name, long lagMs) {
            this.name = name;
            this.lagMs = lagMs;
        }

        void write(String key, String value, long nowMs) {
            data.put(key, value + "@" + nowMs);
        }

        String read(String key, long nowMs) {
            String v = data.get(key);
            if (v == null) {
                return null;
            }
            long writtenAt = Long.parseLong(v.substring(v.indexOf('@') + 1));
            return (nowMs - writtenAt) >= lagMs ? v : null;   // 还没复制过来 -> 读不到
        }
    }

    static DataSource master = new DataSource("master", 0);
    static DataSource replica = new DataSource("replica-1", 2000);   // 延迟 2 秒

    static void lagProblem() {
        System.out.println("【主从延迟事故：下单成功页读不到订单】");
        long t = 0;
        master.write("order:1001", "PAID", t);
        String fromReplica = replica.read("order:1001", t);
        System.out.println("  t+0ms   主库写入 order:1001=PAID");
        System.out.println("  t+50ms  用户跳转订单页 -> 读从库 -> "
                + (fromReplica == null ? "null（读不到！页面空白）" : fromReplica));
        System.out.println("  t+2000ms 从库追平 -> 读到 PAID");
        System.out.println("  用户感知：钱扣了，订单没了 -> 客服工单 +1");
        System.out.println();
    }

    static void stickyRouting() {
        System.out.println("【对策一：写后读绑定主库（sticky routing）】");
        long writeAt = 1000;
        master.write("order:1002", "PAID", writeAt);
        long readAt = writeAt + 300;
        boolean sticky = readAt - writeAt < 5000;
        String read = sticky ? master.read("order:1002", readAt)
                : replica.read("order:1002", readAt);
        System.out.printf("  写于 %dms，读于 %dms，窗口 %dms 内 -> %s%n",
                writeAt, readAt, 5000, sticky ? "路由主库" : "路由从库");
        System.out.println("  读到：" + read);
        System.out.println("  实现：会话级标记，写操作后 N 秒内该用户读请求全走主库");
        System.out.println();
    }

    static void versionGuard() {
        System.out.println("【对策二：版本号校验，读旧了就重试主库】");
        long writeAt = 5000;
        master.write("order:1003", "PAID", writeAt);
        String fromReplica = replica.read("order:1003", writeAt + 100);   // 未复制完 -> null
        if (fromReplica == null) {
            System.out.println("  从库尚未复制到该版本 -> 回退主库读");
            System.out.println("  主库读到：" + master.read("order:1003", writeAt + 100));
        }
        System.out.println("  实现细节：写入时记录版本号，读到旧版本（写时间 < 我写的版本）就回主库");
        System.out.println("  适合点查（订单详情），不适合列表（无法对每行做版本比较）");
        System.out.println();
    }

    static void routingMatrix() {
        System.out.println("【路由决策表：把一致性要求说清楚】");
        String[][] rows = {
                {"写入", "主库", "唯一写入点"},
                {"写后立即读", "主库", "下单页、支付回调、唯一性校验"},
                {"列表搜索", "从库", "延迟 2~5s 可接受，产品话术兜底"},
                {"报表/导出", "从库或专用从库", "大查询隔离，别污染交易链路"},
                {"后台管理", "从库", "运营查看允许少量延迟"},
        };
        for (String[] r : rows) {
            System.out.printf("  %-10s -> %-14s %s%n", r[0], r[1], r[2]);
        }
    }

    public static void main(String[] args) {
        lagProblem();
        stickyRouting();
        versionGuard();
        routingMatrix();
    }
}
```

### 39-05 分库分表的拆分策略

**知识点**
- **垂直拆分按业务切，水平拆分按数据切**：垂直分库把订单、商品、用户拆成独立库（第 29 章的服务拆分在数据层的投影）；垂直分表把大字段、低频字段拆出去（订单表拆出 order_detail 的大文本）。水平分表把同一张表按分片键切成 N 张同构表。
- **水平拆分先解决"分片键选谁"**：分片键决定了数据分布，也决定了**所有查询的形状**。选 `user_id`：同一用户的订单在一起，"查某用户的订单"走单分片，但"平台按时间查全部订单"要扫全分片。选 `order_id`：单订单查询快，但用户侧列表要广播。**没有完美分片键，只有业务主路径的取舍**。
- **基因法让多维度都能命中单分片**：把 user_id 的低位"基因"嵌进 order_id（如 order_id = 时间戳 | user_id 低 8 位 | 序列），按 order_id 查和按 user_id 查都路由到同一分片。这是 C 端系统最常用的技巧，39-07 的分布式 ID 会实现它。
- **冗余一份"异构索引表"解决第二个维度**：下单时同时写 order 表（按 user_id 分片）与 order_by_shop 索引表（按 shop_id 分片），商家侧查索引表拿 order_id 列表再回主表。用"一次多写"换"多维度单分片查询"，代价是写放大与一致性维护。
- **不参与分片的查询怎么办**：后台报表、风控全量扫描这类查询不追求实时，走**异构副本**（同步到 ES/数仓/未分片的从库）而不是扫全分片。广播查询是分库分表的头号性能陷阱。
- **中间件两种形态**：SDK 模式（ShardingSphere-JDBC，嵌入应用，无中间层，性能好但升级随应用）与 Proxy 模式（独立代理，语言无关，多一跳延迟）。无论哪种，**跨分片 join、跨分片事务、聚合归并**都是它们的软肋，设计时绕开而不是硬用。
- 易错点：用自增主键当分片键还希望按用户查（必然广播）；分片键选了会变数据的字段（用户换城市？订单改状态？迁移地狱）；一张 800 列的大宽表直接水平拆（先把垂直拆完再水平）；分片后仍写 `JOIN` 多表 SQL（跨分片 join 语义与性能都不可控）。

**示例代码**

```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class ShardingStrategy {
    record Order(long orderId, long userId, double amount) {
    }

    /** 8 张表：t_order_0 ~ t_order_7，按 user_id 路由 */
    static final Map<Integer, List<Order>> SHARDS = new LinkedHashMap<>();
    static final int SHARD_COUNT = 8;

    static void verticalFirst() {
        System.out.println("【拆分顺序：先垂直，后水平】");
        String[][] steps = {
                {"垂直分库", "订单库 / 商品库 / 用户库 物理独立", "对应微服务边界"},
                {"垂直分表", "order 拆出 order_detail(大文本)、order_stat(低频统计)",
                        "热表变窄，缓存友好"},
                {"水平分表", "order -> t_order_0..7（按 user_id）", "解决单表行数与写入热点"},
                {"水平分库", "每 4 张表一个库实例", "解决单机连接数/磁盘/IO 上限"},
        };
        for (String[] s : steps) {
            System.out.printf("  %-8s %-44s %s%n", s[0], s[1], s[2]);
        }
        System.out.println();
    }

    static int routeByUser(long userId) {
        return (int) (userId % SHARD_COUNT);
    }

    static void shardKeyChoice() {
        System.out.println("【分片键选择：主路径决定一切】");
        List<Order> orders = List.of(
                new Order(90001, 101, 99.0),
                new Order(90002, 102, 199.0),
                new Order(90003, 101, 59.0));
        for (Order o : orders) {
            SHARDS.computeIfAbsent(routeByUser(o.userId()), k -> new ArrayList<>()).add(o);
        }
        for (Map.Entry<Integer, List<Order>> e : SHARDS.entrySet()) {
            System.out.printf("  t_order_%d: %s%n", e.getKey(), e.getValue());
        }
        System.out.println("  按 user_id 查：route(101)=" + routeByUser(101)
                + " -> 只查 1 个分片 ✓");
        System.out.println("  按时间查全部：8 个分片全部广播 -> 后台查询应走异构副本");
        System.out.println();
    }

    static void geneEmbedding() {
        System.out.println("【基因法：把 user_id 基因埋进 order_id】");
        long userId = 101;
        long gene = userId & 0xFF;                    // 取 user_id 低 8 位作基因
        long orderId = (1700000000L << 20) | (gene << 12) | 1234;   // 时间戳|基因|序列
        long extracted = (orderId >> 12) & 0xFF;
        System.out.printf("  userId=%d 基因=%d -> orderId=%d%n", userId, gene, orderId);
        System.out.printf("  从 orderId 反提取基因=%d -> 同一路由分片 t_order_%d%n",
                extracted, extracted % SHARD_COUNT);
        System.out.println("  按 orderId 查与按 userId 查命中同一分片，两个维度都免除广播");
        System.out.println();
    }

    static void indexTable() {
        System.out.println("【冗余索引表：第三个维度（商家侧）怎么办】");
        System.out.println("  主表：t_order（按 user_id 分片）");
        System.out.println("  索引表：t_order_by_shop（按 shop_id 分片，只存 shop_id/order_id/user_id）");
        System.out.println("  商家查订单：先查索引表拿 order_id 列表 -> 回主表取详情（仍在单分片）");
        System.out.println("  代价：双写（同事务或本地消息表）、索引表只增不改、一致性对账");
        System.out.println("  原则：宁可写放大，不可查询广播");
    }

    public static void main(String[] args) {
        verticalFirst();
        shardKeyChoice();
        geneEmbedding();
        indexTable();
    }
}
```

### 39-06 分片路由与扩容

**知识点**
- **路由算法两大流派**：**hash 取模**（`shard = hash(key) % N`）数据分布均匀，但扩容时几乎全部数据要迁移（模数变了）；**range 范围**（按时间/ID 区间）扩容只加新区间，但热点集中在最新区间，且需要维护区间表。
- **一致性哈希解决"扩容只迁一小部分"**：把分片与 key 都映射到环上，key 归顺时针遇到的第一个节点。节点数从 N 变 N+1 时，只有"环上新节点与前一个节点之间"的区间数据需要迁移（约 1/N+1），其余不动。虚拟节点（每物理节点 100~200 个虚拟槽位）让分布更均匀。
- **固定槽数（slot）方案是工程主流**：不直接对节点取模，而是对 1024/4096 个槽取模，槽再映射到节点。扩容时只调整"槽→节点"映射（迁移部分槽的数据），路由公式永远不变。Redis Cluster 的 16384 slot 就是这个思想。
- **扩容动作三步**：① 新节点加入，重新分配槽；② 按映射双写（新数据同时写新旧槽位）；③ 后台迁移存量数据，迁完切读、下线旧槽。**全程不停服**的关键是双写期与对账。
- **翻倍扩容最省心**：8 分片 -> 16 分片时，旧分片 i 的数据一半搬到 i+8（`hash % 16` 与 `hash % 8` 的关系保证只迁一半且目标可计算）。所以**分片数从一开始就选 2 的幂**，给翻倍留好路。
- **range 按时间分片的天然搭档**：订单按月分表，最新表承载写入热点，历史表归档——查询带时间条件直接路由单表。适合"时间维度主导"的业务（日志、交易流水），不适合"最新数据最热且查询不带时间"的场景。
- 易错点：直接 `% N` 后期扩容（全量迁移，等于重做一遍）；一致性哈希不配虚拟节点（分布倾斜）；迁移期间只双写不回滚旧写（故障时丢数据窗口）；按 range 分片但查询不带 range 条件（退化为广播）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

public class ShardRouting {
    /** hash 取模：8 分片 */
    static int modRoute(long key, int n) {
        return (int) (Math.abs(hash(key)) % n);
    }

    static long hash(long key) {
        return key * 31 + 7;
    }

    static void expansionCost() {
        System.out.println("【取模扩容的迁移成本】");
        int n = 1_000;
        int moved = 0;
        for (long i = 1; i <= n; i++) {
            if (modRoute(i, 8) != modRoute(i, 16)) {
                moved++;
            }
        }
        System.out.printf("  8 分片 -> 16 分片：%d%% 的数据换了分片%n", moved);
        moved = 0;
        for (long i = 1; i <= n; i++) {
            if (modRoute(i, 8) != modRoute(i, 9)) {
                moved++;
            }
        }
        System.out.printf("  8 分片 -> 9  分片：%d%% 的数据换了分片（几乎全部）%n", moved);
        System.out.println("  结论：扩容要翻倍（8->16），不翻倍等于重做数据分布");
        System.out.println();
    }

    /** 一致性哈希：虚拟节点 + TreeMap 环 */
    static class ConsistentHash {
        final TreeMap<Long, String> ring = new TreeMap<>();

        ConsistentHash(List<String> nodes, int vnodes) {
            for (String n : nodes) {
                for (int v = 0; v < vnodes; v++) {
                    ring.put(Math.abs(hash(n.hashCode() * 1000L + v)), n);
                }
            }
        }

        String route(long key) {
            Map.Entry<Long, String> e = ring.ceilingEntry(hash(key));
            return e != null ? e.getValue() : ring.firstEntry().getValue();
        }

        long hash(long key) {
            return key * 1103515245L + 12345;
        }
    }

    static void consistentHashDemo() {
        System.out.println("【一致性哈希：加一个节点只迁 1/(N+1)】");
        ConsistentHash c3 = new ConsistentHash(List.of("db1", "db2", "db3"), 100);
        ConsistentHash c4 = new ConsistentHash(List.of("db1", "db2", "db3", "db4"), 100);
        int moved = 0, total = 10_000;
        for (long i = 0; i < total; i++) {
            if (!c3.route(i).equals(c4.route(i))) {
                moved++;
            }
        }
        System.out.printf("  %d 个 key 从 3 节点扩到 4 节点：迁移 %d%%（理论 25%%）%n",
                total, moved / (total / 100));
        for (long probe : new long[]{7, 77, 777}) {
            System.out.printf("  key %d: 3节点=%s -> 4节点=%s%n",
                    probe, c3.route(probe), c4.route(probe));
        }
        System.out.println("  虚拟节点 100 个/台：让环上分布均匀，避免某台独占半环");
        System.out.println();
    }

    static void slotPlan() {
        System.out.println("【固定槽位：路由公式永不变，扩容只改映射】");
        int slots = 1024;
        Map<Integer, String> slotMap = new LinkedHashMap<>();
        for (int s = 0; s < slots; s++) {
            slotMap.put(s, s < 512 ? "db-a" : "db-b");
        }
        long key = 9527;
        int slot = (int) (Math.abs(hash(key)) % slots);
        System.out.printf("  key %d -> slot %d -> 节点 %s%n", key, slot, slotMap.get(slot));
        System.out.println("  扩容 db-c：把 slot 512~682 划给它，只迁移这 171 个槽的数据");
        System.out.println("  双写期：写旧槽+新槽，对账完成后切读，停旧槽");
        System.out.println("  Redis Cluster(16384 slot) 与部分分库中间件都是此方案");
    }

    static void rangeByTime() {
        System.out.println("【range 按月分表：热点集中但扩容无痛】");
        String[][] months = {{"2026-01", "orders_202601（300 万行，仍在写）"},
                {"2026-02", "orders_202602（280 万行，仍在写）"},
                {"2025-12", "orders_202512（320 万行，只读可归档）"}};
        for (String[] m : months) {
```

### 39-07 分布式 ID：雪花算法

**知识点**
- **分库分表后自增主键必然冲突**：两台机器各发 1、2、3，合并就是重复。业务需要**全局唯一且趋势递增**的 ID——递增保证 B+ 树顺序插入（随机主键会导致页分裂与缓存抖动），唯一保证路由与合并正确。
- **雪花算法（Snowflake）的三段结构（64 位）**：1 位符号恒 0 + 41 位毫秒时间戳（约可用 69 年）+ 10 位机器 ID（5 位数据中心 + 5 位机器，或全给机器=1024 台）+ 12 位序列号（同一毫秒内最多 4096 个）。**每毫秒每机器可发 4096 个 ID，每秒约 400 万**。
- **机器 ID 的分配是运维问题**：写死在配置里会人工重复；常用方案：ZooKeeper 顺序节点、数据库注册表、K8s StatefulSet 序号。**同一毫秒同一机器 ID 才可能撞**，机器 ID 冲突 = 灾难，必须中心化分配。
- **时钟回拨是雪花算法的头号故障**：NTP 校时把机器时间拨回去，时间戳变小，会发出与过去重复的 ID。对策：① 回拨 < 5ms 忙等追平；② 回拨大则报错拒发（拒绝服务优于数据重复）；③ 用"上次时间戳"维护单调性，`timestamp = max(now, lastTs)`。
- **序列号用尽**：单机单毫秒超过 4096 个请求，序列溢出——标准做法是**自旋等待下一毫秒**（把时钟推进到 lastTs+1）。高并发场景这是正常分支，不是异常。
- **趋势递增不等于严格递增**：多机器并发时，后发出的 ID 可能小于另一台刚发出的 ID（时间戳精度是毫秒）。排序场景要么容忍（按 create_time 排），要么牺牲并发换严格递增（号段模式）。
- **号段模式（Leaf）作为对照**：数据库里存当前最大值，应用一次取一段（如 1000 个）缓存在内存里用完再取。实现简单、ID 短，但取号段时重启会"跳号"，且强依赖数据库可用性。双 buffer 预取消除取号延迟。
- 易错点：机器 ID 重复（两台机器 ID 相同同时发号）；忽略时钟回拨（NTP 一定会来）；把雪花 ID 当严格排序键（跨机器不严格）；41 位时间戳的起始纪元乱设导致 69 年寿命缩水。

**示例代码**
```java
public class DistributedId {
    /** 雪花算法可运行实现：标准位分配 1+41+10+12 */
    static class Snowflake {
        private static final long EPOCH = 1735689600000L;  // 2025-01-01 起始纪元
        private static final long WORKER_BITS = 10, SEQ_BITS = 12;
        private static final long MAX_WORKER = (1L << WORKER_BITS) - 1;
        private static final long MAX_SEQ = (1L << SEQ_BITS) - 1;

        private final long workerId;
        private long lastTs = -1;
        private long seq = 0;

        Snowflake(long workerId) {
            if (workerId < 0 || workerId > MAX_WORKER) {
                throw new IllegalArgumentException("workerId 超范围: " + workerId);
            }
            this.workerId = workerId;
        }

        synchronized long nextId() {
            long now = System.currentTimeMillis();
            if (now < lastTs) {                       // 时钟回拨
                long rollback = lastTs - now;
                if (rollback <= 5) {                  // 小回拨：忙等追平
                    while (System.currentTimeMillis() <= lastTs) {
                        Thread.onSpinWait();
                    }
                    now = System.currentTimeMillis();
                } else {                              // 大回拨：拒发，宁停勿重
                    throw new IllegalStateException("时钟回拨 " + rollback + "ms，拒绝发号");
                }
            }
            if (now == lastTs) {
                seq = (seq + 1) & MAX_SEQ;            // 同毫秒序列递增
                if (seq == 0) {                       // 序列用尽：等到下一毫秒
                    while (System.currentTimeMillis() <= lastTs) {
                        Thread.onSpinWait();
                    }
                    now = System.currentTimeMillis();
                }
            } else {
                seq = 0;
            }
            lastTs = now;
            return ((now - EPOCH) << (WORKER_BITS + SEQ_BITS))
                    | (workerId << SEQ_BITS)
                    | seq;
        }

        static String dissect(long id) {
            long ts = (id >> (WORKER_BITS + SEQ_BITS)) + EPOCH;
            long worker = (id >> SEQ_BITS) & MAX_WORKER;
            long seq = id & MAX_SEQ;
            return String.format("时间戳=%d worker=%d seq=%d", ts, worker, seq);
        }
    }

    static void basicIssue() {
        Snowflake sf = new Snowflake(7);
        System.out.println("【同一毫秒连续发号：worker=7】");
        long first = sf.nextId();
        long second = sf.nextId();
        System.out.println("  id1=" + first);
        System.out.println("  id2=" + second);
        System.out.println("  id1 拆解：" + Snowflake.dissect(first));
        System.out.println("  趋势递增：id2 > id1 -> " + (second > first));
        System.out.println();
    }

    static void throughput() {
        System.out.println("【发号吞吐：单机每秒理论上限】");
        long perMs = 4096;
        System.out.printf("  12 位序列 -> 每毫秒 %d 个 -> 每秒约 %d 万个%n",
                perMs, perMs * 1000 / 10000);
        Snowflake sf = new Snowflake(1);
        long t0 = System.nanoTime();
        long[] ids = new long[100_000];
        for (int i = 0; i < ids.length; i++) {
            ids[i] = sf.nextId();
        }
        long ms = Math.max(1, (System.nanoTime() - t0) / 1_000_000);
        System.out.printf("  实测 %d 个耗时 %dms（含跨毫秒等待）%n", ids.length, ms);
        System.out.println();
    }

    static void twoWorkers() {
        System.out.println("【两台机器并发发号：唯一但全局不严格递增】");
        Snowflake w1 = new Snowflake(101), w2 = new Snowflake(202);
        long a = w1.nextId(), b = w2.nextId(), c = w1.nextId();
        System.out.printf("  w1:%d  w2:%d  w1:%d%n", a, b, c);
        System.out.println("  同毫秒时 w1 的第二个 ID 也可能小于 w2 的第一个（毫秒粒度内无全局序）");
        System.out.println("  排序需求：按 create_time + id 双键，或接受「近似有序」");
        System.out.println();
    }

    static void epochNote() {
        System.out.println("【纪元与寿命：41 位时间戳用 69 年】");
        long epoch = 1735689600000L;
        long maxTs = (1L << 41) - 1;
        System.out.printf("  纪元 %d + 2^41ms ≈ 纪元 + %.0f 年%n", epoch, maxTs / 3.15e10);
        System.out.println("  纪元取「项目上线日」而不是 1970，寿命从今天起算 69 年");
    }

    public static void main(String[] args) {
        basicIssue();
        throughput();
        twoWorkers();
        epochNote();
    }
}
```

### 39-08 跨分片查询与聚合

**知识点**
- **分片后的查询分三类**：① 带分片键 → 单分片，性能不变；② 带分片键以外的唯一索引（如按 order_id 查，路由靠基因）→ 单分片；③ 不带任何路由键（后台统计、全局搜索）→ **广播**，扇出到所有分片再归并。设计目标永远是让查询落在前两类。
- **归并排序是跨分片查询的核心动作**：每个分片返回本地 top N（LIMIT N 不是 LIMIT offset+N —— 分片内也要取够排序数据），协调层做**多路归并**取全局 top N。K 路归并成本 O(K×N)，K 是分片数。第 34 章的堆在这里直接复用：K 个流各出队首进小顶堆。
- **分页归并的陷阱**：全局 `LIMIT 1000, 20` 时每分片要取前 1020 条，页越深每分片成本越高——**跨分片分页继承第 39-03 课的全部问题**。游标分页（全局唯一排序键）在分片场景同样成本恒定，是首选。
- **聚合归并的语义**：COUNT/SUM/MAX 可直接分片值相加/比较（可分解）；AVG 不能直接平均（要 SUM 与 COUNT 分别汇总再算）；COUNT DISTINCT 与 MEDIAN **不可分解**，必须收集明细在协调层重算，数据量大时只能用近似或异构副本。
- **GROUP BY 归并**：每分片按组返回（group, aggValue），协调层按组合并（SUM 相加、AVG 用两元组）。组数多时协调层内存压力上升，组数爆炸的报表应走异构（同步到数仓/ES）而不是实时广播聚合。
- **order by 全局唯一性问题**：按 create_time 排序时各分片时钟独立、同毫秒冲突，归并顺序不稳定——与 search_after 相同，**全局排序键必须附加唯一列（id）兜底**。
- 易错点：以为 `LIMIT 10` 在每个分片取 10 条就够了（排序不均匀时会漏，必须每分片取够 N 且在协调层重排序）；AVG 各分片平均后平均（数学错误）；把管理后台的全量查询直接打在生产分库（应该打异构副本）；跨分片 JOIN 硬上（中间件大多退化为内存 join，先把数据冗余到一起再查）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.Comparator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.PriorityQueue;

public class CrossShardQuery {
    record Order(long orderId, long userId, double amount, long createTime) {
    }

    /** 4 个分片的本地数据（模拟同构表） */
    static List<List<Order>> shards() {
        List<List<Order>> s = new ArrayList<>();
        s.add(List.of(new Order(11, 1, 200, 1001), new Order(12, 2, 350, 1005)));
        s.add(List.of(new Order(21, 3, 500, 1003), new Order(22, 1, 90, 1007)));
        s.add(List.of(new Order(31, 2, 120, 1002), new Order(32, 4, 800, 1006)));
        s.add(List.of(new Order(41, 5, 30, 1004), new Order(42, 3, 660, 1008)));
        return s;
    }

    static void topNMerge() {
        System.out.println("【全局 top 3 金额：K 路归并】");
        List<List<Order>> shards = shards();
        record Entry(Order o, int shard) {
        }
        PriorityQueue<Entry> heap = new PriorityQueue<>(
                Comparator.comparingDouble((Entry e) -> e.o().amount()).reversed());
        // 每个分片本地排序取 top3（真实 SQL：ORDER BY amount DESC LIMIT 3）
        for (int i = 0; i < shards.size(); i++) {
            List<Order> localTop = shards.get(i).stream()
                    .sorted(Comparator.comparingDouble(Order::amount).reversed())
                    .limit(3).toList();
            System.out.printf("  分片%d 本地top: %s%n", i, localTop.stream().map(o -> o.orderId()).toList());
            if (!localTop.isEmpty()) {
                heap.add(new Entry(localTop.get(0), i));
            }
        }
        List<Order> globalTop = new ArrayList<>();
        List<List<Order>> cursors = new ArrayList<>();
        for (int i = 0; i < shards.size(); i++) {
            cursors.add(shards.get(i).stream()
                    .sorted(Comparator.comparingDouble(Order::amount).reversed()).toList());
        }
        while (globalTop.size() < 3 && !heap.isEmpty()) {
            Entry e = heap.poll();
            globalTop.add(e.o());
            int next = cursors.get(e.shard()).indexOf(e.o()) + 1;
            if (next < cursors.get(e.shard()).size()) {
                heap.add(new Entry(cursors.get(e.shard()).get(next), e.shard()));
            }
        }
        System.out.println("  全局 top3: " + globalTop.stream().map(Order::orderId).toList());
        System.out.println("  关键：每分片本地取 LIMIT N（不是 offset+N），协调层归并重排");
        System.out.println();
    }

    static void aggregations() {
        System.out.println("【聚合归并的可分解性】");
        long count = 0;
        double sum = 0, naiveAvgSum = 0;
        Map<Long, Double> sumByUser = new LinkedHashMap<>();
        Map<Long, Long> cntByUser = new LinkedHashMap<>();
        for (List<Order> s : shards()) {
            long c = s.size();
            double sm = s.stream().mapToDouble(Order::amount).sum();
            count += c;
            sum += sm;
            naiveAvgSum += sm / c;                    // 错误做法：平均的平均
            for (Order o : s) {
                sumByUser.merge(o.userId(), o.amount(), Double::sum);
                cntByUser.merge(o.userId(), 1L, Long::sum);
            }
        }
        System.out.printf("  COUNT：分片相加 = %d ✓%n", count);
        System.out.printf("  SUM  ：分片相加 = %.0f ✓%n", sum);
        System.out.printf("  AVG  ：先汇总 SUM/COUNT 再除 = %.1f；平均的平均 = %.1f ✗%n",
                sum / count, naiveAvgSum);
        System.out.println("  COUNT DISTINCT / MEDIAN：不可分解 -> 收集明细重算或近似");
        System.out.println("  GROUP BY 用户：");
        for (Long u : sumByUser.keySet()) {
            System.out.printf("    user %d: sum=%.0f count=%d%n", u, sumByUser.get(u), cntByUser.get(u));
        }
        System.out.println();
    }

    static void pagingRule() {
        System.out.println("【跨分片分页：每分片必须取 offset+N】");
        int offset = 1000, limit = 20;
        System.out.printf("  全局 LIMIT %d, %d -> 每分片取前 %d 条，4 分片共 %d 条%n",
                offset, limit, offset + limit, (offset + limit) * 4);
        System.out.println("  深页成本 = 分片数 × 页深，继承 39-03 的所有问题");
        System.out.println("  首选：全局游标（create_time+id 唯一键），每分片 WHERE 键 > 游标 LIMIT N");
        System.out.println("  兜底：后台深翻页走异构副本（ES/数仓），不占交易库");
    }

    public static void main(String[] args) {
        topNMerge();
        aggregations();
        pagingRule();
    }
}
```

### 39-09 跨库事务与一致性

**知识点**
- **分库后单库事务失效**：订单在 A 库、库存扣减在 B 库，本地事务罩不住两个库。可选方案从强到弱：**2PC/XA**（强一致，协调者单点、锁持有时间长，吞吐差）、**TCC**（Try-Confirm-Cancel，业务侵入大但性能好）、**本地消息表**（最终一致，实现简单，最常用）、**Saga**（长流程编排，正反补偿）。
- **本地消息表是 80% 场景的正确答案**：业务表更新与"待发送消息"记录在**同一个本地事务**里提交，后台任务扫描消息表投递到 MQ，下游消费成功回执。保证"本地事务成功则消息一定发出去"，最终一致由重试 + 幂等兜底。第 28 章已讲过 MQ 侧，本章补数据库侧的表结构。
- **TCC 的本质是把"预留"显式化**：Try 冻结库存（扣到 frozen 字段）、Confirm 真实扣减、Cancel 释放冻结。三个接口都要幂等、都要允许空回滚（Cancel 在 Try 未到达时也要成功）、都要防悬挂（Cancel 之后到达的 Try 拒绝）。**业务侵入极大**，只用于资金等强一致场景。
- **Saga 适合长流程**：下单 → 扣库存 → 扣优惠券 → 通知物流，每步有补偿动作，失败时按已执行步骤反向补偿。没有隔离性（中间态可见），需要业务接受"补偿期间数据不一致"。
- **能不分事务就不分**：很多"跨库事务"其实可以通过**调整边界**消除——把强关联的表放同一个库（按用户分片天然做到）、用状态机 + 异步核对替代实时强一致（订单状态 PENDING → 核对任务修复）、先落库后异步。
- **对账是所有最终一致方案的收尾**：定时比对两侧（订单 vs 支付流水、库存 vs 扣减记录），差异进差异表人工/自动修复。**架构承认最终一致，对账保证误差收敛**。
- 易错点：用 XA 硬扛高并发（锁等待拖垮连接池）；TCC 忘写空回滚与防悬挂（Cancel 比 Try 先到，资金状态错乱）；本地消息表只加不扫（消息堆积，下游永远收不到）；补偿动作不幂等（重试一次多扣一次）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class CrossDbConsistency {
    /** 本地消息表 */
    record Outbox(long id, String topic, String payload, String status, int retry) {
    }

    static Map<Long, String> orderDb = new LinkedHashMap<>();      // A 库：订单
    static Map<Long, Integer> stockDb = new LinkedHashMap<>();     // B 库：库存
    static List<Outbox> outbox = new ArrayList<>();
    static List<String> audit = new ArrayList<>();

    static void localMessageTable() {
        System.out.println("【本地消息表：一次扣库存的完整闭环】");
        long orderId = 9001, productId = 55;
        // 本地事务 1（A 库）：插入订单 + 写 outbox，原子提交
        orderDb.put(orderId, "CREATED");
        outbox.add(new Outbox(1, "OrderCreated", "order=9001,product=55,qty=1", "PENDING", 0));
        System.out.println("  A 库事务：订单 9001 = CREATED + outbox#1 PENDING（同一事务）");
        // 后台投递
        Outbox m = outbox.get(0);
        audit.add("投递 outbox#1 -> MQ -> 库存服务");
        // 本地事务 2（B 库）：扣库存 + 回执（幂等：按 orderId 判重）
        if (!audit.contains("扣减55 for 9001")) {
            stockDb.merge(productId, -1, Integer::sum);
            audit.add("扣减55 for 9001（幂等键=orderId）");
        }
        outbox.set(0, new Outbox(1, m.topic(), m.payload(), "SENT", m.retry() + 1));
        System.out.println("  B 库事务：库存 55 " + stockDb.get(productId) + "（消费幂等）");
        System.out.println("  outbox 状态：" + outbox.get(0).status() + "，retry=" + outbox.get(0).retry());
        System.out.println("  失败路径：投递失败 retry+1，退避重试；N 次后进死信告警");
        System.out.println();
    }

    static void tccDemo() {
        System.out.println("【TCC：预留 -> 确认/取消，以及空回滚】");
        int stock = 10, frozen = 0;
        boolean tryOk = stock >= 1;
        if (tryOk) {
            stock--;
            frozen++;
            System.out.println("  Try：库存 10 -> " + stock + "，冻结 " + frozen + "（预留但不提交）");
        }
        boolean confirm = true;
```

### 39-10 冷热分离与数据归档

**知识点**
- **80/20 法则在业务数据上同样成立**：绝大多数系统 80% 以上的行是"一年内没被读过"的冷数据，却占着主表的 B+ 树、缓存与备份窗口。**归档是性价比最高的"分库分表替代方案"**——很多声称需要分表的系统，归档完主表直接回到千万行以内。
- **冷热分离的判定标准**：访问频率（近 90 天命中率）、查询模式（是否必须与热数据同表查询，如"最近三个月订单"）、法规要求（交易数据保留 N 年）。冷数据特点：只读、查询低频且通常按时间批量。
- **三种归档形态**：**同库归档表**（orders -> orders_archive，最简单，但同一实例仍有压力）；**归档库/实例**（独立实例，主库直接瘦身，最常用）；**对象存储/数据仓库**（压缩转储 + 查询走数仓，适合超长保留期）。按"查询需求有多强"选择。
- **归档任务的正确姿势**：按时间批次（每天搬一天前已完结订单），`INSERT INTO archive SELECT ... LIMIT N` + `DELETE ... LIMIT N` 分批执行，**绝不一个事务搬千万行**（大事务锁表 + 主从延迟爆炸）。搬运要有进度表与断点续跑。
- **一致性窗口**：搬走的那一刻起，查询"历史订单"要去归档库——**应用层路由必须先上线**（按时间判断查主表还是归档库），否则用户查不到已归档订单。稳妥顺序：双查期（先查主表查不到再查归档）→ 验证 → 停双查。
- **归档不是删除**：法规要求的保留期要真保留；物理删除要有不可逆的备份（对象存储 + 校验和）。"归档完就从备份里也删掉"是重大合规事故。
- 易错点：归档任务无监控（半夜失败没人发现，主表继续膨胀）；归档后索引没同步建（归档库查询慢）；把"可能还要用的数据"归档到查询极慢的存储（用户投诉）；回捞流程没演练（真要恢复一条订单时手忙脚乱）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.List;

public class HotColdArchive {
    record Order(long id, String status, long createTime) {
    }

    static final long ARCHIVE_BEFORE = 1704000000000L;   // 2024-01-01

    static boolean isCold(Order o) {
        return o.createTime() < ARCHIVE_BEFORE;
    }

    static List<Order> hot = new ArrayList<>();
    static List<Order> archive = new ArrayList<>();

    static void initData() {
        hot.clear();
        archive.clear();
        // 前 499 条在归档线之前（冷），其余在归档线之后（热）
        for (long i = 1; i <= 1000; i++) {
            long t = ARCHIVE_BEFORE + (i - 500) * 900_000L;
            hot.add(new Order(i, i % 5 == 0 ? "DONE" : "PAID", t));
        }
        System.out.printf("  初始主表 %d 行（其中 499 行是归档线之前的冷数据）%n", hot.size());
    }

    static void batchArchive() {
        System.out.println("【分批归档：每批 N 行，绝不一个事务搬全量】");
        initData();
        int batchSize = 100, moved = 0, round = 0;
        while (round < 20) {
            List<Order> batch = new ArrayList<>();
            for (Order o : hot) {
                if (isCold(o) && batch.size() < batchSize) {
                    batch.add(o);
                }
            }
            if (batch.isEmpty()) {
                break;
            }
            hot.removeAll(batch);
            archive.addAll(batch);
            moved += batch.size();
            round++;
            System.out.printf("  批次 %2d：搬走 %d 行，主表剩 %d 行，归档 %d 行%n",
                    round, batch.size(), hot.size(), archive.size());
        }
        System.out.printf("  完成：主表 %d 行（瘦了 %.0f%%），归档库 %d 行%n",
                hot.size(), 100.0 * moved / (moved + hot.size()), archive.size());
        System.out.println("  SQL 模板：INSERT INTO orders_archive SELECT ... WHERE id BETWEEN a AND b;");
        System.out.println("          DELETE FROM orders WHERE id BETWEEN a AND b;（同一事务，每批 1000）");
        System.out.println();
    }

    static void queryRouting() {
        System.out.println("【查询路由：应用必须知道冷热边界】");
        Order recent = hot.get(hot.size() - 1);
        Order old = archive.get(0);
        Order probe = recent;
        String route = isCold(probe) ? "归档库" : "主库";
        System.out.printf("  查订单 %d（%s）-> 路由：%s -> %s%n",
                probe.id(), isCold(probe) ? "冷" : "热", route, "命中");
        probe = old;
        route = isCold(probe) ? "归档库" : "主库";
        System.out.printf("  查订单 %d（%s）-> 路由：%s -> %s%n",
                probe.id(), isCold(probe) ? "冷" : "热", route, "命中");
        System.out.println("  过渡期双查：主表查不到 -> 归档库兜底 -> 两边都有以主表为准");
        System.out.println("  上线顺序：路由改造先于归档任务，禁止先搬数据再改代码");
        System.out.println();
    }

    static void checklist() {
        System.out.println("【归档上线检查单】");
        List<String> items = List.of(
                "冷热判定规则经业务确认（法务：保留期）",
                "归档库索引按查询模式建（时间+订单号，不是照抄主表）",
                "应用路由/双查逻辑已上线并验证",
                "批次大小压测过（主从延迟在阈值内）",
                "进度表 + 失败重跑 + 归档告警",
                "回捞流程演练过一次（归档 -> 主库恢复单条）",
                "备份与合规：归档数据保留与销毁策略书面化");
        for (String i : items) {
            System.out.println("  [ ] " + i);
        }
    }

    public static void main(String[] args) {
        batchArchive();
        queryRouting();
        checklist();
    }
}
```

### 39-11 综合案例：订单系统从单表到分库分表

**知识点**
- **完整演进路线回顾**：慢查询治理（39-02）→ 深分页优化（39-03）→ 读写分离（39-04）→ 缓存挡读 → 历史归档（39-10）→ 仍然撑不住 → 水平分库分表（39-05/06）→ 分布式 ID（39-07）→ 跨分片查询治理（39-08）→ 跨库一致性（39-09）。**每一步都有前置条件与回退方案**，不是一步跳到分库分表。
- **最终架构**：4 库 × 8 表（32 分片），分片键 user_id（基因法嵌入 order_id），一套订单库承载 C 端主路径；商家维度走冗余索引表；后台统计走异构（binlog 同步到数仓）；历史订单按月归档到归档库。**每个查询维度都有明确归宿，没有广播查询**。
- **ID 设计落地**：雪花 64 位改造——41 位时间戳 + 4 位库号 + 6 位表号基因（取 user_id 哈希低 10 位）+ 13 位序列，既全局唯一又能反解路由。**ID 即路由信息**，任何分片只要拿到 ID 就知道数据在哪。
- **迁移方案（双写三阶段）**：① 存量迁移：按 id 范围分批搬历史数据到 32 分片，校验和比对；② 增量双写：新旧库同写（旧为准），对账任务持续比对差异；③ 切读：灰度按用户尾号切读流量到新库，观察一周全量切换，旧库降级为只读备份一个月后下线。**每阶段都有回退开关**。
- **验收指标**：单用户订单查询 P99 < 50ms（单分片）；下单链路 P99 < 300ms（含跨库扣库存）；无广播查询（后台报表全部走数仓）；对账差异为零；主从延迟稳定 < 2s。
- **回归测试清单**：所有高频 SQL 逐条确认路由（单分片/基因/索引表/异构）；深分页全部改游标；事务边界重新梳理（跨库的改本地消息表）；连接池重新评估（32 分片 × 应用实例数的乘积效应）。
- 易错点：迁移期旧库新库时间戳不一致导致对账误报（用业务版本号不用时间）；灰度切读时忘记切写（读新写旧，数据分裂）；连接数爆炸（每应用实例连 32 库，应用实例 20 台就是 640 连接，必须用连接池上限 + Proxy 收敛）；迁移完成立即下线旧库（至少保留一个月只读）。

```java
        }

        long gene() {
            return (value >> SEQ_BITS) & 1023;
        }

            return (int) (gene() % DB_COUNT);

        }
```
