### 56-07 风险治理：变更管理与风险清单

**知识点**
- **大部分故障是"变更引发"的**（行业数据 60~80%）——**变更管控是稳定性 ROI 最高的措施**：变更窗口（冻结期 41 章）、灰度强制（41-07）、变更审计（51-10）、快速回滚能力（41-11）。
- **风险清单（risk register）**：系统性的风险登记——每条风险（描述/概率/影响/缓解措施/owner/状态）；**风险分级驱动投入**（高概率高影响的缓解优先）；季度评审更新（新风险进、已消除出）。
- **变更风险分级**：高风险（数据库变更/核心链路发布/配置全量）需要完整门禁+双人；低风险（文案/只读接口）简化流程——**分级的目的让流程可执行而不是全流程重审批**（41-10 审批最小化）。
- **风险沟通**：高风险变更提前通报利益相关方（值班/客服/业务）；变更后观察期值守——**变更前"告诉别人"，变更后"盯着结果"**。
- 易错点：变更无窗口（周五下午发布）；风险清单一次性（不更新等于没有）；高风险变更单人选型与执行（无 second pair of eyes）；紧急变更无审计（41-10）。

import java.util.ArrayList;
import java.util.List;

public class RiskRegisterDemo {
    record Risk(String desc, int prob, int impact, String mitigation, String owner) {
        int score() {
            return prob * impact;
        }
    }

    public static void main(String[] args) {
        List<Risk> risks = new ArrayList<>(List.of(
                new Risk("订单库单点", 2, 5, "M4 分库分表（52-09）", "数据组"),
                new Risk("支付渠道单一", 3, 5, "双渠道熔断路由（51-10）", "支付组"),
                new Risk("无全链路压测", 4, 3, "季度压测（56-02）", "平台组")));
        risks.sort((a, b) -> b.score() - a.score());
        for (Risk r : risks) {
            System.out.printf("  风险=%2d %-14s 缓解=%-24s owner=%s%n",
                    r.score(), r.desc(), r.mitigation(), r.owner());
        }
        System.out.println("  分级驱动投入：高分优先；清单季度评审滚动更新");
    }
}

### 56-08 依赖治理与弱依赖降级清单

**知识点**
- **每个服务都有一张依赖清单，但很少人维护它**：依赖治理回答"我依赖谁、强依赖还是弱依赖、它挂了我怎么办"——**强弱依赖的判定标准**：不可用时核心业务是否可用（可用=弱依赖，必须降级方案；不可用=强依赖，必须容灾投入）。
- **弱依赖降级清单**：每个弱依赖的降级动作（返回缓存/默认值/隐藏功能）+ 降级开关（56-04）+ 演练验证——**清单是预案的索引**（42-11 闭环的依赖维度）。
- **依赖的治理动作**：减少依赖（能删就删）、降级依赖（强转弱）、隔离依赖（资源隔离 47-08）、监控依赖（健康度+慢查询 42 章）。
- **环状依赖是治理重点**：A 依赖 B、B 依赖 A——发布耦合与故障互锁，**必须解环**（事件化 49-03 或拆公共模块）。
- 易错点：强弱依赖未定义（故障时不知道谁该降级）；降级清单过期（依赖变了清单没变）；同步调用链过长（A->B->C->D，49-08 分布式单体）；对三方依赖无熔断（53-05）。

**示例代码**
```java
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class DependencyGovernance {
    record Dependency(String name, boolean strong, String fallback, boolean rehearsed) {
    }

    static void audit() {
        System.out.println("【订单服务的依赖清单审计】");
        List<Dependency> deps = List.of(
                new Dependency("库存服务", true, "无（强依赖：本地缓存短时兜底）", true),
                new Dependency("营销服务", false, "不用券下单（降级开关）", true),
                new Dependency("推荐服务", false, "返回默认位（占位数据）", false),
                new Dependency("短信服务", false, "队列缓冲延发", true));
        for (Dependency d : deps) {
            System.out.printf("  %-8s %s依赖  降级=%-24s 演练=%s%n",
                    d.name(), d.strong() ? "强" : "弱", d.fallback(),
                    d.rehearsed() ? "✓" : "未演练");
        }
        System.out.println();
        System.out.println("  审计结论：推荐服务降级未演练 -> 进季度演练计划（56-06）");
        System.out.println("  健康度：强依赖必须容灾投入；弱依赖必须有演练过的降级");
    }

    public static void main(String[] args) {
        audit();
    }
}
```

### 56-09 容量与成本的年度规划

**知识点**
- **容量规划从季度到年度的视角**：年度规划回答"明年资源盘子"——业务增长预测（52-01 三年外推）-> 资源换算（48-06 公式链）-> 预算分配（云资源/采购/人力）-> 季度滚动修正（56-03）。
- **成本结构分析**：固定成本（常驻集群）+ 弹性成本（弹性伸缩部分）+ 一次性（大促扩容）——**弹性化的收益**=把固定转弹性（47-08）；**单位成本对标**：每订单基础设施成本（趋势下降=架构效率提升）。
- **降本的四象限**：闲置回收（rightsizing 47-08）、架构降本（缓存/批处理替代实时）、采购策略（Spot/包年 47-08）、技术升级（新引擎/新硬件 48-05）。**每个降本动作要有质量门禁**（降本不能降 SLO）。
- **年度规划的产出**：资源预算 + 容量里程碑（52-09 对齐）+ 成本目标 + 风险预案——**规划与 52-09 里程碑联动**（架构演进与容量演进同步）。
- 易错点：规划只算服务器不算人力运维；降本动作无质量门禁（降出事故）；预测线性外推（业务季节性/拐点忽视）；弹性成本账单失控（无配额）。

### 56-10 稳定性度量与文化建设

**知识点**
- **稳定性度量四组指标**：**事故指标**（次数/MTTR/影响面）、**变更指标**（变更故障率 41 章 DORA）、**演练指标**（覆盖率/缺陷闭环 56-06）、**预算指标**（错误预算消耗 56-01）——**度量进月度例会**，趋势比单点重要。
- **文化建设是长效机制**：**无责复盘**（42-11，追责让问题藏起来）、**上报激励**（主动暴露问题受奖励）、**演练常态化**（故障是必修课不是意外）、**文档与传承**（事故手册/预案库是团队资产）。
- **稳定性的角色演进**：初级——救火队员；进阶——预案与演练的建设者；高级——把稳定性变成产品能力（自动化/平台化 56-04）——**52-07 长板策略的稳定性版**。
- **与业务的关系表达**：稳定性不是成本是收入保障——**用 GMV 损失换算故障代价**（51 章资金 + 27 章 GMV），让业务方参与优先级决策。
- 易错点：度量变成 KPI 表演（MTTR 造假）；复盘变追责（问题藏匿）；只建设不度量（不知道体系是否有效）；把稳定性做成运动（运动结束即松懈）。
- **体系的衰败信号**：演练台账停更、预案与架构脱节、复盘迟到、错误预算形同虚设——**定期审视体系本身**（56-01）。

### 56-11 综合案例：一次大促的稳定性闭环

**知识点**
- **用一次大促把第 56 章串成完整闭环**：容量规划（52-01+56-03）-> 全链路压测（56-02）-> 预案演练（56-04/06）-> 临战值守（56-05）-> 作战处置（42 章观测+预案执行）-> 复盘改进（42-11）-> 年度规划修正（56-09）。**41~48 章的全部能力在大促场景下协同运转**。
- **演练时间线（复盘式呈现）**：T-30 容量核算与扩容 -> T-21 全链路压测发现 MQ 瓶颈 -> T-14 瓶颈治理+预案更新 -> T-7 演练三项全过 -> T-1 冻结+值守就位 -> T0 峰值 66% 水位，一次预案触发（限流）自动处置 -> T+1 复盘：两个改进项。
- **复盘的产出清单**：容量公式参数修正、预案新增（演练发现的缺失项）、监控补盲（演练发现的盲区）、成本预算更新——**与 48-11 演练闭环同构**。
- **毕业视角**：这次大促闭环用到了全书近半数的章节能力——**稳定性工程是"把所有工程能力组织起来对抗不确定性"的最后一门课**。
- 易错点：大促闭环漏"预案更新"（演练发现缺失但不落预案）；复盘不修正容量参数；值守记录不完整（时间线无法复盘）；改进项无 owner。
- **课程收官**：从 2 章的第一个变量到 56 章的稳定性闭环——**判断力（遇到问题知道往哪走）是这门课的最终交付物**（52-11）。

    }
